# Caching and freshness

A cache stores reusable results near the code that needs them. It can reduce latency and repeated
work, but it introduces another copy of data. Decide what stale data would mean for the user before
choosing an expiration policy.

## Cache-aside

With cache-aside, the application first looks for a key in the cache. On a miss, it loads the value
from the underlying store and puts the result in the cache for future reads. A cache hit avoids
that load; a miss still needs a working source of truth.

<!-- section: 94eab322-7484-4c94-8a03-d3aab5cd87a3 -->

### Read flow

1. Look up the cache key.
2. On a hit, return the cached value.
3. On a miss, read the source of truth.
4. Cache the result with an appropriate expiration.

The cache is an optimization. An unavailable cache can often be bypassed, provided the underlying
service can handle the extra load. Do not accidentally interpret a cache failure as missing data.

<!-- section: e58957e9-6e76-4067-8e50-4f5e2c1fa3ac -->

## Expiration and invalidation

A time-to-live limits how long a cached entry is reusable. It is a freshness tradeoff rather than
a guarantee that a value always matches the source of truth. Writes may need to invalidate or
update cached entries sooner when the application requires fresher reads.

Use shorter lifetimes for rapidly changing values when stale results matter. Longer lifetimes can
be suitable for stable public content. Never use an old cached authorization decision without
considering the security consequences.

<!-- section: 9d835706-183e-42cb-ab71-5e3208a0e0eb -->

## Cache stampedes

When many requests miss the same key together, they can all repeat the expensive load. This can
happen when a popular entry expires. Combining concurrent loads for the same key can reduce the
burst. Jittered expiration spreads different keys out, but does not alone combine requests for one
missing key.

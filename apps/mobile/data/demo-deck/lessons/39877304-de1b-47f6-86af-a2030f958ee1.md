# Reliable requests

A client can know that a request failed to produce a response without knowing whether the server
performed its work. Reliability starts by treating that uncertainty explicitly.

## Timeouts

A timeout bounds how long a caller waits. It protects resources and lets the caller choose a
recovery path. A timeout is not evidence that the remote operation never happened: the server may
have completed the operation while its response was lost.

### Choosing a timeout

Consider expected latency, the caller's deadline, and the cost of waiting. A chain of services
should respect an overall deadline rather than granting every downstream call a fresh unlimited
budget. Observe latency and timeout rates to tune the decision.

## Retries

Retries can recover from temporary failures, but they also create additional load. Bound the
number of attempts and the total time spent. Backoff increases the delay between attempts; jitter
helps prevent many clients from retrying together at the same instant.

### Safe retries

Retry an operation only when repeating it is safe or the service can recognize the repetition.
A payment request that times out must not simply create another charge on every retry. Persistent
failures require a different response, not an endless retry loop.

## Idempotency

An idempotent operation has the same intended effect when repeated as when performed once. A
service can use an idempotency key to recognize repeated submissions of one logical request and
return the existing outcome. Different logical requests need different keys.

Recording the key and applying the side effect must be coordinated; checking a key and then
writing without protection can allow concurrent duplicates. Idempotency is a behavioral guarantee,
not just the presence of a request header.

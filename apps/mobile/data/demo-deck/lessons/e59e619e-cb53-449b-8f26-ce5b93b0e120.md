# Scaling systems

Scaling means changing a system so it can handle more work. Start by measuring the resource that
limits useful throughput: CPU, memory, disk, network, or a downstream service. Adding capacity to
the wrong resource can increase cost without making the application faster.

<!-- section: 98efbada-a1ad-42c5-a255-631514658ec8 -->

## Vertical scaling

Vertical scaling gives one machine more resources. A database server might move from 8 GB to
32 GB of memory, or an application server might gain more CPU cores. The application can often
keep the same deployment model, which makes this a practical first step for a small service.

More memory can let a database retain a larger working set instead of repeatedly reading disk.
More cores help work that can actually run in parallel. Neither change automatically fixes a slow
query or an application that waits on an external service.

<!-- section: 2c399930-4dbd-4dfc-8cd3-2d06bc05cba2 -->

### Benefits

- Fewer machines to deploy and observe.
- Local coordination can stay simple.
- Existing software may need little change.

<!-- section: fc249d38-bc33-46bb-89bb-ee5939ab3d15 -->

### Limitations

A machine has a finite hardware ceiling. Larger instances can also cost disproportionately more.
Replacing one machine with a larger one does not by itself remove that machine as a point of
failure. Availability requires its own plan, such as replication and tested recovery.

<!-- section: 018b3341-47ec-42ac-8d70-aa3feef72637 -->

#### Example

If a database repeatedly reads the same hot records from disk because they do not fit in memory,
more RAM may improve throughput. Measure cache hit rate and query latency before and after the
change. If the expensive part is an unindexed query, inspect the query plan as well.

<!-- section: 046f9304-51d2-46ca-b0a5-503f403866fc -->

## Horizontal scaling

Horizontal scaling adds machines or service instances and distributes work among them. A load
balancer can route requests to several application servers. Adding servers is useful when the
work can be divided; a bottleneck shared by every server can still limit the whole system.

<!-- section: 1f869c62-3000-4368-83e4-bb4b251c2867 -->

### State and coordination

Requests should not depend on private state stored only inside one application instance. Sessions
may live in a shared store, or requests may carry the information needed to handle them. Shared
storage and coordination introduce their own costs and failure modes.

<!-- section: d1a9d5ca-17f5-4bd3-b0f7-0b840b0d9555 -->

### Limitations

More machines mean network communication, partial failures, and operational work. Scaling the
application tier does not automatically scale its database. Keep measuring the end-to-end path.

# Queues and message delivery

Overload control decides what happens when demand arrives faster than a system can process it in the moment. A queue offers a different answer: don't process it in the moment at all. Put the work somewhere durable, let a consumer work through it at its own pace, and let the producer move on without waiting. That decoupling is powerful, and it comes with a new set of correctness questions this lesson works through.

## What a queue buys you

A **queue** decouples producers from consumers by storing work until consumers can process it, smoothing bursts and enabling asynchronous processing. A producer that would otherwise have to wait for a slow consumer — or fail outright if the consumer is briefly down — instead writes to the queue and continues; the consumer reads from the queue whenever it is ready. A burst of 10,000 arriving orders does not require 10,000 workers instantly; it requires enough workers to drain the queue at an acceptable rate over the following minutes.

This is a genuine trade-off, not a pure win. Asynchronous messaging improves decoupling and burst handling, but results are delayed (the producer no longer knows the outcome immediately), and the system must handle retries, duplicates, ordering, and operational visibility — each covered below — that a direct, synchronous call never had to deal with, precisely because a direct call fails or succeeds immediately and does not leave a message sitting in a queue that something must eventually resolve.

## Delivery guarantees

When a consumer might crash mid-processing, or a network call might succeed on the server but the acknowledgment gets lost on the way back, the system has to define what it promises about whether a message actually gets processed.

**At-most-once** delivery means a message is delivered zero or one times. It avoids duplicates — nothing is ever processed twice — but can lose work: if a failure happens before successful processing, the message is simply gone, with no way to tell it was lost.

**At-least-once** delivery means the system retries until delivery is believed successful, so messages are not intentionally lost, but consumers can receive duplicates: if the consumer crashes after processing a message but before telling the queue it succeeded, the queue will redeliver it, correctly assuming the first attempt might not have gone through.

**Exactly-once** delivery — each message processed once, with no loss and no duplicates — is what everyone would prefer, and it is genuinely difficult in distributed systems: failures can make it unclear whether work committed before an acknowledgment was lost, and there is no way to distinguish "the consumer processed it and the ack was lost" from "the consumer never processed it" without additional bookkeeping. Real systems approximate exactly-once _effects_ — not true exactly-once delivery — with idempotency, transactions, or deduplication, described next.

## Idempotency: living with at-least-once

An **idempotent operation** is one where repeating it with the same logical request produces the same intended final effect as performing it once. "Set balance to 500" is idempotent — running it twice leaves the balance at 500. "Add 100 to balance" is not — running it twice adds 200. If every operation a consumer performs is idempotent, at-least-once delivery's duplicates stop being a correctness problem: processing the same message twice does no additional harm.

Many real operations are not naturally idempotent ("charge the customer $100"), which is where an **idempotency key** comes in: the client sends a stable request identifier, and the server stores the outcome so retries can return the original result instead of performing the mutation again. A payment API receiving `POST /charges` with `Idempotency-Key: abc123` twice — because the client's first response was lost and it retried — looks up `abc123`, finds it already succeeded, and returns the stored result instead of charging the customer twice.

## Handling messages that keep failing

Some messages fail no matter how many times they are retried — a malformed payload, a bug triggered only by that message's specific content. Left in an at-least-once queue, such a message would retry forever, blocking every message behind it. A **dead-letter queue** stores messages that repeatedly fail processing so they stop blocking normal traffic and can be inspected, repaired, or replayed separately, once someone has figured out why they were failing.

## Ordering

**Message ordering** is a guarantee about the sequence in which consumers observe messages. Guaranteeing a strict global order across every message in a high-throughput system is expensive, because it usually means giving up parallelism (only one consumer can safely process messages at a time if any two could be out of order). Many systems instead guarantee order only within a partition or key — all updates for order `#4471` arrive in the order they were sent, but updates for order `#4471` and order `#9902` may be processed in either relative order, since nothing in the application depends on their relative sequence. This is usually sufficient, because most ordering requirements are really about "these related events must not be reordered," not about a total order across unrelated events.

## Common mistakes

- Assuming "asynchronous" means "eventually correct with no extra work." Every property a synchronous call gave you for free — knowing the outcome, no duplicates, ordering — becomes something the design has to earn back explicitly.
- Writing consumer logic that assumes exactly-once delivery from a system that only guarantees at-least-once, and discovering duplicate side effects (double charges, duplicate emails) under retry or redelivery.
- Requiring global message ordering when only per-key ordering was ever actually needed, and paying an unnecessary throughput cost for it.

## Key points

- A queue decouples producers from consumers, smoothing bursts and enabling asynchronous processing, at the cost of delayed results and new correctness concerns.
- At-most-once avoids duplicates but can lose messages; at-least-once avoids loss but can duplicate; exactly-once is difficult and usually only approximated.
- An idempotent operation produces the same effect whether performed once or repeated, which makes at-least-once delivery safe to build on.
- An idempotency key lets a server recognize a retried request and return the original outcome instead of repeating the mutation.
- A dead-letter queue isolates messages that repeatedly fail, so they stop blocking the rest of the queue and can be investigated separately.
- Global message ordering is expensive; most systems guarantee ordering only within a partition or key.

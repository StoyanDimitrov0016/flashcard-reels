# Caching

Many requests ask for the same data again and again, and producing that data can be slow: a database query, a call to another service, or an expensive computation. Recomputing it every single time wastes work and adds latency for no benefit, since the answer has not changed. Caching keeps a copy close at hand so repeated reads are cheap — one of the most effective performance tools in system design, and one of the easiest to get subtly wrong.

## What a cache is

A **cache** is temporary storage for expensive or frequently reused data, so later reads can avoid recomputing or refetching it. Caches appear at every level of a system: in-process memory, shared caches like Redis or Memcached, HTTP caches in browsers, and CDNs at the edge of the internet (below). The key word is _temporary_ — a cache is not the source of truth, and the system must still behave correctly, if more slowly, when a cached entry is missing or evicted.

## Measuring a cache

The main measure of a cache is its **hit rate**: the fraction of eligible reads served from the cache rather than the underlying source. A read found in the cache is a hit; one that must reach the source is a miss. A higher hit rate usually means more backend work is avoided, and the relationship is not linear: going from a 90% to a 99% hit rate cuts the traffic reaching the backend from one in ten reads to one in a hundred — a tenfold reduction, even though the hit-rate number only moved nine points.

## Read pattern: cache-aside

**Cache-aside** puts the application in charge of the cache directly. The application checks the cache first, reads the source on a miss, then writes the result into the cache:

```text
value = cache.get(key)
if value is missing:
    value = database.read(key)
    cache.set(key, value, ttl)
return value
```

Only data that is actually requested ever gets cached — an advantage when most of the data is rarely accessed. Because the application, not the cache, decides what is stored, writes to the source usually require invalidation or update of the cached entries, or later readers will see stale data.

## Write patterns: write-through and write-back

Cache-aside only describes reads. Two patterns describe how writes interact with the cache.

**Write-through** caching sends writes through the cache layer, which updates the backing store before acknowledging success. The cache and the source stay coordinated — the value is cached for the next read as a side effect of the write itself — at the cost of extra write-path work, since every write now touches both the cache and the store before it can be acknowledged.

**Write-back** (write-behind) caching acknowledges a write as soon as the cache is updated, and persists it to the backing store later, often in batches. This can reduce write latency substantially, since the caller does not wait for the slower store. It risks data loss: there is a window where the only copy of new data lives in the cache, and if the cache fails before flushing these dirty entries, they are gone — unless the cache itself protects them durably, for example by replicating or logging the pending writes.

## Cache invalidation

**Cache invalidation** removes or expires cached data when it may no longer match the source of truth. It has a reputation for being one of the two hardest problems in computer science for concrete reasons: multiple copies of the same data can live in different caches and all outlive an update; invalidation messages can be delayed, reordered, or lost, leaving a stale copy in place; and dependency relationships can be complex — one price change might affect a cached product page, cached search results, and a cached cart total, and missing any one of those leaves stale data somewhere. Because precise invalidation can silently fail, robust designs keep a fallback: a time-to-live (TTL) guarantees that stale data eventually expires even if an explicit invalidation message never arrives.

## Stampedes and jitter

A **cache stampede** happens when many requests miss the same hot key at once and all recompute or refetch it simultaneously, overwhelming the backend — commonly right after a popular entry expires. Request coalescing (only one request recomputes while others wait for its result), locks, serving slightly stale data while a refresh happens in the background, and jittered TTLs all reduce it.

**Jitter** deserves a closer look because the failure mode is easy to reproduce accidentally: if a million keys are loaded at once with the same one-hour TTL, they all expire at the same moment an hour later, creating a synchronized surge of backend traffic — the very stampede this is meant to prevent, self-inflicted by a uniform expiration policy. Adding jitter — setting each TTL to, say, 60 minutes plus a random 0–5 minutes — spreads expirations apart, so backend traffic stays smooth instead of arriving in synchronized waves.

## Content delivery networks

A **CDN** caches or serves content from geographically distributed edge locations, reducing origin load and network distance to users. A request from Tokyo is answered from an edge location in or near Tokyo rather than crossing an ocean to reach the origin server. CDNs shorten network distance (lower latency) and absorb most requests before they ever reach the origin (lower origin load). They are the standard choice for static assets — images, scripts, video — and can also cache API responses that many users share, effectively acting as a cache-aside layer operated by a third party in front of the whole system.

## Common mistakes

- Caching without a plan for invalidation: adding a cache always creates a second copy of the truth, and every write path must account for it, or reads will silently serve outdated data.
- Choosing write-back for its latency win without checking whether the data can tolerate loss in the (rare but real) window before it is flushed.
- Using a single, uniform TTL across many keys, which synchronizes their expirations and manufactures a stampede instead of preventing one.

## Key points

- A cache is temporary storage for expensive or reused data, avoiding recomputation or refetching on later reads.
- Hit rate is the fraction of reads served from the cache; small hit-rate gains near 100% can mean large drops in backend load.
- Cache-aside: the application reads the cache first, falls back to the source on a miss, and populates the cache with the result.
- Write-through keeps the cache and store coordinated at write time; write-back acknowledges faster but risks losing unflushed writes.
- Cache invalidation is hard because multiple copies, lost messages, and complex dependencies can all leave stale data behind; TTLs are the fallback.
- A cache stampede is many requests missing a hot key at once; jittered TTLs, coalescing, locks, or serving stale data prevent it.
- A CDN is a cache at geographically distributed edge locations, reducing both latency and origin load.

# Fault tolerance and redundancy

Hardware fails, networks partition, processes crash, and disks die — not as exotic edge cases, but as routine events at any real scale. A system with a thousand machines should expect to lose one on an ordinary day. The question system design answers is not "how do we prevent failure" (you cannot) but "how do we keep serving users when a piece of the system inevitably fails."

## The danger of one critical piece

A **single point of failure (SPOF)** is one component whose failure can make the whole service unavailable. A single database with no replica, a single load balancer with no standby, a single region hosting every instance — each is a SPOF: healthy everywhere else, and the whole system still goes down with it.

Finding SPOFs is mostly a matter of asking, for every component, "if this disappeared right now, what breaks?" Anything where the honest answer is "everything downstream of it" is a SPOF and a candidate for the techniques below.

## Removing it: redundancy

**Redundancy** keeps multiple components able to provide the same critical function, so that one failure does not necessarily stop the service. A redundant database has replicas; a redundant load balancer has a standby; a redundant service runs on multiple instances across multiple machines, and ideally multiple racks, availability zones, or regions, so that one shared failure (a power outage, a rack switch failure) cannot take out every redundant copy at once.

Redundancy is not free: extra copies cost money, and keeping them useful (in sync, healthy, ready to take over) is itself an engineering problem — replication lag and consistency, covered in a later lesson, exist precisely because redundant copies must be kept coherent.

## Switching to the healthy copy: failover

Redundancy only helps if the system actually switches to a healthy copy when one fails. **Failover** switches traffic or responsibility from a failed component to a healthy replacement, either automatically (a load balancer stops routing to an instance that fails health checks) or manually (an operator promotes a replica database to primary after the original primary crashes).

Automatic failover is faster but riskier: a system that fails over too eagerly on a false alarm (a health check that times out under normal load, not actual failure) can cause outages of its own, or — worse, in the case of a database primary — two components can each believe they are now in charge, which is exactly the split-brain problem covered in a later lesson on the CAP theorem.

## The resulting property: fault tolerance

**Fault tolerance** is the ability to continue providing acceptable service when some components fail. It is what redundancy and failover are for: not preventing failures, but arranging things so that failures do not become outages. A fault-tolerant system is defined by what it tolerates — how many simultaneous node failures, which kinds of failures (crash, slow response, corrupted data) — and no system tolerates unlimited failure. Design always assumes a fault model: "survives any one node failure" is a common and useful target; "survives every node failing at once" usually is not, because it would cost more than the business the system serves.

## When you cannot mask everything: graceful degradation

Sometimes a failure cannot be fully masked — a downstream recommendation service is down, or the system is under far more load than any redundancy plan sized for. **Graceful degradation** keeps core functionality available while disabling or reducing nonessential features under failure or overload: an online store that cannot compute personalized recommendations still lets you search, view, and buy products; it just shows a generic "popular items" list instead of a personalized one.

Graceful degradation requires deciding, in advance, what is essential and what is not, and building the fallback paths before the failure happens. It is one of the cheapest reliability investments available, since it usually only requires isolating the nonessential feature so its failure cannot cascade into the essential ones (a theme the bulkhead pattern, later, generalizes).

## Worked example

A checkout service depends on: the product catalog (essential — cannot sell without it), the payment processor (essential), and a "customers who bought this also bought" recommendation widget (nonessential). If the recommendation service starts timing out:

1. Health checks or timeouts detect the recommendation service is unhealthy.
2. The checkout page's rendering code catches the failure and omits the widget, rather than failing the whole page.
3. The customer completes checkout normally, having lost only a suggestion box they may never have noticed.

Contrast this with a design where the recommendation call is not isolated and a slow recommendation service ties up the same request thread handling payment, turning one nonessential failure into a checkout outage — exactly what graceful degradation, and later bulkheads, exist to prevent.

## Key points

- A single point of failure is one component whose failure can take down the whole service.
- Redundancy keeps multiple components able to serve the same function, so one failure need not stop the service — spread across failure domains, not just duplicated on one.
- Failover switches traffic to a healthy replacement, automatically or manually, when a component fails.
- Fault tolerance is the ability to keep providing acceptable service despite some component failures, always relative to an assumed fault model.
- Graceful degradation keeps essential functionality working by disabling nonessential features under failure or overload, and requires deciding in advance what is essential.

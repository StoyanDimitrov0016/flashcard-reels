# Event sourcing and CQRS

Event-driven architecture, from the previous lesson, treats events as messages between services. This lesson pushes the idea further: what if events were not just a notification mechanism, but the authoritative record of everything that ever happened to a piece of data — and what if the way you write data and the way you read it did not have to use the same model at all?

## Event logs

An **event log** is an ordered append-only sequence of records that consumers can read by position and often replay. Unlike a queue, which typically removes a message once consumed, an event log usually keeps every record around, so a new consumer can start from the beginning and replay the full history, or an existing consumer can rewind and reprocess a stretch it wants to see again. This makes the log a durable record of everything that happened, in the order it happened, not just a hand-off mechanism.

## Event sourcing

**Event sourcing** stores state changes as an authoritative sequence of domain events and derives current state by replaying or projecting those events. Instead of storing a bank account as one row with a `balance` column that gets overwritten on every transaction, an event-sourced system stores every event — `AccountOpened`, `Deposited(100)`, `Withdrew(30)` — and computes the current balance by replaying them in order. The stored events, not any derived balance, are the source of truth.

```text
events:  AccountOpened -> Deposited(100) -> Withdrew(30) -> Deposited(50)
current balance = fold(events) = 0 + 100 - 30 + 50 = 120
```

This gives a complete, auditable history for free — you can always answer "how did the balance get to 120," not just "what is the balance now" — and it lets new views of the same history be built later by writing a new projection over the existing events, without touching how they were originally recorded.

The trade-off is real: event sourcing provides history and replay but makes schema evolution, projections, debugging, and correction of bad events more demanding. A traditional system fixes a bad row with an `UPDATE`; an event-sourced system cannot rewrite history (the events already happened), so correcting a mistake means appending a new compensating event (`BalanceCorrected(+10)`) and living with both events in the log forever — which is more honest about what actually occurred, but is also more work than a quiet `UPDATE` and requires every consumer of the log to understand compensating events, not just original ones.

## CQRS

Deriving current state by replaying events, on every read, does not scale — nobody wants to replay a million events to answer "what is this account's balance right now." **Command Query Responsibility Segregation (CQRS)** separates write models from read models so each can use structures optimized for its workload: writes go through the event-sourced (or otherwise write-optimized) model, and reads are served from a separately maintained, read-optimized copy that is kept up to date as events arrive, rather than recomputed from scratch for every query.

CQRS is a natural pairing with event sourcing (the events are the write model, and a read-optimized copy is built from them), but the two ideas are separable: CQRS is useful any time reads and writes have very different shapes, even without full event sourcing behind it.

## Materialized views and denormalization

The read-optimized copy CQRS calls for is usually built from two closely related techniques.

A **materialized view** stores precomputed query results or projections, so reads avoid repeating expensive joins or aggregations, at the cost of refresh work and possible staleness. Replaying a customer's events to compute their current order history on every page load is exactly the kind of repeated, expensive work a materialized view — a table that already holds "this customer's current order history," kept updated as new events arrive — is meant to avoid.

**Denormalization** stores duplicated or prejoined data to make reads simpler or faster, trading extra storage and write-time consistency work for read efficiency. A materialized view is often denormalized on purpose: an order-history view might duplicate the customer's name and the product's title directly into each row, rather than joining out to separate customer and product tables on every read, because the read path values speed over the storage savings and single-source-of-truth purity a fully normalized structure would offer.

## Common mistakes

- Adopting event sourcing for a domain with no real need for a full audit history or replay, and paying its schema-evolution and correction costs for no corresponding benefit.
- Building the CQRS read side, then treating it as another source of truth to write to directly — the read model should always be derived from the write side's events, never edited independently, or the two will drift apart with no way to tell which is right.
- Forgetting that a materialized view can go stale between refreshes, and building logic that assumes it is always perfectly current.

## Key points

- An event log is an ordered, append-only, replayable sequence of records, distinct from a queue that removes messages once consumed.
- Event sourcing stores state changes as an authoritative sequence of domain events and derives current state by replaying or projecting them.
- Event sourcing gives full history and replay but makes schema evolution, projections, debugging, and correcting bad events harder, since past events cannot simply be rewritten.
- CQRS separates write models from read models so each can be optimized for its own workload, commonly pairing an event-sourced write side with a precomputed read side.
- A materialized view stores precomputed results to speed up reads, at the cost of refresh work and possible staleness; denormalization duplicates data for the same reason, trading storage and write-time consistency for read speed.

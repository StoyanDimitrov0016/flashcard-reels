# Capacity planning and autoscaling

Every technique so far in this deck helps a system use given resources well. This lesson is about deciding how much resource to have in the first place, and how to adjust that amount automatically as real demand rises and falls — rather than either overpaying for capacity that mostly sits idle, or running out of it at the worst possible moment.

## Capacity planning

**Capacity planning** estimates resource needs from expected load, growth, safety margins, and bottlenecks, so the system can meet targets before saturation. It is fundamentally a forecasting exercise: given current traffic, expected growth (a marketing push, a seasonal spike, organic user growth), and a safety margin for the unexpected, how many instances, how much storage, how much database capacity does the system need — not today's peak, but the peak it will face before the next planning cycle.

Getting this right requires knowing where the system actually bottlenecks first, since adding more of the wrong resource does nothing. A service that is memory-constrained gains nothing from more CPU cores; a service limited by downstream database connections gains nothing from more application instances if they all contend for the same fixed connection pool.

## Autoscaling

Static capacity planning sizes a system for its peak, which means real spare capacity sits idle most of the time — provisioning for a once-a-year peak, running it year-round, is expensive. **Autoscaling** changes the number or size of service instances in response to measured demand or schedules, adding capacity as load rises and removing it as load falls, so the system pays roughly for what it uses rather than for a fixed worst case held constantly in reserve.

## Why CPU-only autoscaling fails for some services

The obvious signal to autoscale on is CPU utilization — but **CPU-only autoscaling can fail for some services**, because a service may bottleneck on memory, queue depth, connections, I/O, or downstream limits before CPU becomes high. A service that spends most of its time waiting on a slow downstream database call, or blocked on network I/O, can be genuinely overloaded and failing requests while its CPU utilization looks unremarkably low — there is no CPU-bound work happening, just requests piling up waiting on something else. An autoscaler watching only CPU would see no reason to add instances, right as the service is actually falling over.

## Worked example

A checkout service is autoscaled purely on CPU utilization, targeting 60%. During a traffic spike, the downstream payment gateway slows down (its own p99 latency triples), so each checkout request now spends most of its time blocked waiting on that call rather than doing CPU work.

- CPU utilization on the checkout instances stays around 30%, since instances are mostly idle, waiting on the network, not computing.
- The autoscaler, watching only CPU, does not add instances.
- Meanwhile, each instance's limited pool of concurrent request slots fills up with requests stuck waiting on the slow payment gateway, and new incoming requests start queuing or timing out — real overload, invisible to the one signal being watched.

A corrected setup autoscales on a signal that actually reflects saturation for this service — in-flight request count, queue depth, or request latency itself — alongside or instead of CPU, so the autoscaler adds instances (which, notably, may not even help if the true bottleneck is the payment gateway itself and not the checkout service's own capacity) or at minimum surfaces the real condition instead of showing a falsely reassuring low number.

## Common mistakes

- Autoscaling on CPU alone for I/O-bound or downstream-dependent services, and being surprised when the service is visibly overloaded while its scaling metric looks fine.
- Sizing capacity planning only for average load rather than expected peak plus a safety margin, leaving no headroom for the traffic spike the plan should have anticipated.
- Adding instances in response to a bottleneck that is not actually in the layer being scaled — for example, autoscaling application instances when the real constraint is a shared database's fixed connection or throughput limit, which more application instances cannot relieve.

## Key points

- Capacity planning estimates resource needs from expected load, growth, safety margins, and bottlenecks, so the system meets targets before saturation.
- Autoscaling changes the number or size of instances in response to measured demand or schedules, avoiding both idle overprovisioning and running out of capacity.
- CPU-only autoscaling can fail because a service may bottleneck on memory, queue depth, connections, or I/O before CPU utilization rises.
- Effective autoscaling requires identifying the metric that actually reflects saturation for a given service, not defaulting to CPU regardless of workload shape.

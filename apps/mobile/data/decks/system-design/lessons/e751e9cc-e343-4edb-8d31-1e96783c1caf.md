# Events and data flow

How services talk to each other shapes almost everything else about a system: its latency, how failures spread, and how hard it is to change. This lesson compares direct calls with events, covers patterns for storing and reshaping data, and ends with evolving APIs safely.

## Synchronous calls and events

In **synchronous communication**, the caller sends a request and waits for the downstream response before it can finish its own operation. It is simple to reason about, but it creates direct dependencies. The caller's latency includes the callee's latency, and if the callee is down, the caller fails too.

In an **event-driven architecture**, components publish **events** that describe facts that have already happened, such as `OrderPlaced` or `PaymentCaptured`. Other components subscribe and react asynchronously. The publisher does not call each consumer, and it does not even need to know who they are. Adding a new consumer, such as a fraud check, requires no change to the publisher.

That looser coupling has costs. It becomes harder to follow **causality** (what caused this state?), to handle **retries** and **ordering** correctly, to evolve event **schemas** that many consumers depend on, and to **debug** a request end to end when it hops through several asynchronous steps.

## Event logs

An **event log** is an ordered, **append-only** sequence of records. New records are only ever added at the end; existing ones are not modified. Consumers read by **position** (an offset) and track how far they have got, so each consumer moves at its own pace. Because records are retained, a consumer can often **replay** the log from an earlier position, for example to rebuild a search index or to recover from a bug. Apache Kafka is the best-known example.

## Event sourcing

Most systems store current state and overwrite it on each change. **Event sourcing** stores the changes instead. The authoritative record is a sequence of domain events, such as `AccountOpened`, `Deposited 100`, and `Withdrew 30`, and the current state (a balance of 70) is derived by replaying or **projecting** those events.

This provides a complete **history** and an audit trail, and it lets you replay events to answer new questions or rebuild state. The trade-offs are real, though. Event schemas must evolve without breaking old events that are stored forever. Projections must be built and maintained. Debugging requires thinking in sequences of events. And a bad event cannot simply be edited away; it usually has to be corrected with a compensating event.

## Read models: CQRS, materialized views, and denormalization

**CQRS** (Command Query Responsibility Segregation) separates the **write model**, which validates commands and records changes, from one or more **read models**, which answer queries. Each side can use a structure optimized for its own workload. The write side might be a normalized relational schema, while a read side is a search index or a document store shaped exactly like a screen in the app. Read models are often updated from events, so they can lag slightly behind writes.

A **materialized view** stores precomputed query results or projections. Instead of running an expensive join or aggregation on every read, the system computes it ahead of time and reads the stored result. The costs are **refresh work** whenever the source data changes and possible **staleness** between refreshes.

**Denormalization** takes the same idea into the schema itself. It stores duplicated or pre-joined data, such as copying an author's name onto every post, so reads are simpler and faster. The price is extra storage and extra work at write time to keep every copy consistent when the author changes their name.

## Sagas

A database transaction can update several tables atomically. Across several services, each with its own database, there is no such transaction. A **saga** coordinates a multi-service workflow as a sequence of **local transactions**, one per service. If a later step fails, the saga runs **compensating actions** to logically undo the earlier ones.

Booking a trip might reserve a flight, then a hotel, then charge a card. If the charge fails, the saga cancels the hotel and releases the flight.

A saga is not equivalent to a database transaction. **Intermediate states are visible**: between steps, other users can see the reserved flight. And compensation is **application logic**, not an atomic rollback. A refund is a new action rather than the charge never having happened, and some effects, such as a sent email, cannot be undone at all.

## Publishing events reliably

A service often needs to update its database and publish an event about it. Doing these as two separate steps creates a gap: if the service crashes after committing but before publishing, the event is lost; if it publishes first and the commit fails, the event describes something that never happened.

The **transactional outbox** pattern closes the gap. The service writes the business data and an outgoing-event record to an `outbox` table in the **same local transaction**, so both are committed or neither is. A separate publisher reads the outbox and sends the events to the message broker, retrying until it succeeds. Delivery is at least once, so consumers should be idempotent.

**Change data capture (CDC)** solves a related problem from the database side. It reads the database's own change log and streams committed changes to downstream systems, such as search indexes or analytics stores, without application code having to publish a second copy of every write. CDC is also a common way to implement the outbox publisher.

## Evolving APIs and schemas

Services and their clients change on different schedules. **API versioning** lets an API evolve while preserving the behavior that existing clients expect, since they cannot all upgrade at once. Versions might appear in the path (`/v2/orders`), in a header, or in the message schema.

Versioning is a last resort for breaking changes; most changes should not need it. A change is **backward compatible** when existing clients can keep using the updated service without changing their behavior or payloads.

In a distributed system, older and newer components routinely run at the same time, during a rolling deploy or because a consumer has not been updated yet. That is why **additive changes** are preferred. Adding a new optional field is usually safe, because old readers ignore it and old writers simply omit it. Renaming a field, removing it, or changing what it means breaks any component that still expects the old shape. When a breaking change is truly needed, the safe path is to add the new form, migrate consumers, and remove the old form only once nothing uses it.

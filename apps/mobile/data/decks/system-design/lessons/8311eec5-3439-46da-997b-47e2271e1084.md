# Partitioning and replication

Stateless application servers are easy to multiply. Data is not. When one database can no longer hold all the records or serve all the traffic, you have two tools: split the data into pieces, and keep copies of it. This lesson covers both, and the problems each one introduces.

## Partitioning and sharding

**Partitioning** means splitting data or work into subsets that can be stored and processed independently. Because each subset can live on a different machine, partitioning is what makes horizontal scaling possible for data.

**Sharding** is partitioning applied to a database: the dataset is spread across multiple independent database nodes, called **shards**, so no single node has to store or serve every record. A users table might be split so that users with IDs in one range live on shard 1, the next range on shard 2, and so on. Each shard handles only its share of reads and writes.

## Choosing a shard key

The **shard key** is the attribute that decides which shard a record belongs to. It is one of the most consequential choices in a data design, because changing it later means moving large amounts of data.

A good shard key does two things at once:

- **Spreads load and data evenly**, so every shard gets a similar share of storage and traffic.
- **Keeps common access patterns efficient**, so frequent queries can be answered by one shard rather than by asking all of them.

For a chat application, sharding messages by conversation ID keeps each conversation on one shard, so loading a conversation touches a single node. Sharding by timestamp would be a poor choice: all new messages would land on the shard holding the current time range.

## Hot partitions

That timestamp example leads to a **hot partition**: a shard that receives far more traffic or data than the others. The hot shard becomes a bottleneck even when the cluster as a whole has plenty of spare capacity, because the extra capacity sits on nodes that are not receiving the load.

Hot partitions come from skewed keys, such as time-based keys, or from skewed popularity, such as one celebrity account with millions of followers. Remedies include choosing a key with more spread, adding a random suffix to hot keys so their data splits across shards, and caching the hottest items.

## Consistent hashing

A simple way to assign keys to nodes is modulo hashing: `node = hash(key) % N`. It spreads keys well, but it breaks down when `N` changes. Going from 4 to 5 nodes changes the result for most keys, so nearly all data has to move.

**Consistent hashing** avoids this. Both nodes and keys are hashed onto the same logical **ring**. Each key belongs to the first node found by moving clockwise from the key's position. When a node joins, it takes over only the keys between itself and its predecessor; when a node leaves, only its keys move to the next node. Adding or removing a node therefore moves only a fraction of the keys, roughly one Nth, instead of nearly all of them.

## Virtual nodes

With only a few nodes on the ring, their positions can be uneven, leaving one node responsible for a much larger arc than the others. **Virtual nodes** fix this by placing each physical node at many positions on the ring. With hundreds of positions per node, the arcs average out and load spreads evenly.

Virtual nodes also make capacity flexible. A machine with twice the resources can be given twice as many virtual nodes and so receive about twice the keys. And when a node fails, its many small arcs are spread across many surviving nodes, rather than all landing on one neighbor.

## Replication

**Replication** keeps copies of the same data on multiple nodes. It serves several goals:

- **Availability**: if one node fails, another copy can serve requests.
- **Read capacity**: reads can be spread across replicas.
- **Locality**: a replica in a nearby region answers users faster.
- **Disaster recovery**: a copy far away survives a regional disaster.

Partitioning and replication are usually combined: each shard is replicated, so the system scales through partitioning and survives failures through replication.

## Leader-follower replication

The most common scheme is **leader-follower replication** (also called primary-replica). One node, the **leader**, accepts all authoritative writes. The **followers** receive the leader's stream of changes and apply them in the same order. Reads can be distributed across followers to add read capacity, while writes all go through the leader, which keeps their order unambiguous.

## Replication lag

Followers are usually updated **asynchronously**, so they trail the leader. **Replication lag** is the delay between an update being committed on the source replica and another replica applying or exposing it. Normally it is milliseconds, but under heavy load or network trouble it can grow to seconds or more.

Lag produces visible anomalies. A user updates their profile, the write goes to the leader, the next page load reads from a follower that has not caught up, and the old profile appears as if the change was lost. The next lesson covers the consistency guarantees designed to describe and prevent exactly these surprises.

# Rate limiting and overload control

Caching reduces how often work has to be redone, but it does not stop a system from being handed more work than it can perform in the first place — a client bug that retries in a tight loop, a spike in real traffic, or a single abusive user. Overload control is the set of techniques that decide what to do when demand outpaces capacity, so the system degrades in a controlled way instead of falling over entirely.

## Rate limiting

**Rate limiting** rejects or delays requests that exceed a configured usage rate, protecting capacity and enforcing fairness or quotas. It answers "how much can any one client send," independent of what the system's total capacity happens to be at the moment — a per-client cap of 100 requests per second is the same rule whether the backend is idle or already at 90% utilization.

A common implementation is the **token bucket**: tokens accumulate up to a capacity at a fixed rate, and each request spends a token. If the bucket holds 100 tokens and refills at 10 per second, a client can burst up to 100 requests instantly (spending the full bucket), then sustain 10 requests per second indefinitely as it refills — allowing short bursts while enforcing a long-term average rate, which is usually closer to real traffic patterns than a rule that simply rejects anything above a flat per-second ceiling.

```text
bucket.tokens = min(capacity, bucket.tokens + elapsed_seconds * refill_rate)
if bucket.tokens >= 1:
    bucket.tokens -= 1
    allow request
else:
    reject or delay request
```

## Backpressure

Rate limiting caps what one client can send. **Backpressure** is the more general mechanism: it makes producers slow down, block, reject, or shed work when downstream consumers cannot keep up, preventing unbounded queues. Where rate limiting is a policy applied at the edge based on client identity, backpressure is a property of the whole pipeline — a slow database naturally applies backpressure to the application layer above it if that layer waits for writes to complete before accepting more work, and a bounded queue between two stages applies backpressure once it fills up, refusing new items until the consumer drains some.

The alternative to backpressure is an unbounded queue that keeps absorbing more work than it can process — which does not solve the overload, it just delays the moment the problem becomes visible, and by then far more work is queued up (and the latency of everything in that queue has grown far past any acceptable bound).

## Load shedding

**Load shedding** deliberately rejects lower-priority or excess work when capacity is exhausted, so the system can continue serving a manageable subset. This is a deliberate choice to fail some requests cleanly and immediately (with a fast, clear error) rather than accept all of them and let every single request degrade — including the ones that would otherwise have succeeded fine. A system that keeps accepting every request during an overload spike, without shedding anything, risks the far worse outcome of every request timing out, including requests that had nothing to do with the traffic causing the overload.

Effective load shedding needs a notion of priority: a checkout request probably matters more than a background analytics request, and shedding the latter first, under pressure, protects the requests that matter most.

## Admission control

**Admission control** decides whether new work is allowed into the system based on capacity, quotas, or resource limits, before expensive processing begins. This is the earliest possible point to reject work — rather than accepting a request and discovering partway through processing that there was no capacity for it, admission control checks up front (is there a free connection, a free worker, budget left in a quota) and rejects immediately if not.

The four mechanisms in this lesson form a spectrum from most specific to most general: rate limiting caps one client; backpressure propagates "slow down" signals through a whole pipeline; load shedding chooses what to sacrifice once capacity is already exhausted; admission control is the gate that decides, before any of that, whether work is let in at all.

## Worked example

An API is provisioned to handle 5,000 requests per second comfortably. A marketing campaign drives a spike to 12,000 requests per second.

1. Per-client rate limiting rejects a handful of misbehaving clients sending far above their normal rate — recovering some capacity immediately.
2. Admission control at the front door checks current in-flight request count against a configured limit and rejects new requests over that limit with a fast `503`, rather than accepting them and letting queues build.
3. Load shedding drops lower-priority background jobs (recommendation refresh, analytics ingestion) entirely during the spike, freeing capacity for user-facing checkout and search traffic.
4. Backpressure from the database's connection pool naturally throttles the application layer if it is still, after all of the above, sending more concurrent queries than the database can serve.

The result is that a fixed subset of requests are cleanly rejected fast, while the remaining traffic — the traffic the system decided to prioritize — gets a normal, fast response, instead of every request timing out slowly.

## Common mistakes

- Treating rate limiting as sufficient overload protection on its own. It protects against one misbehaving client; it does nothing when aggregate legitimate traffic exceeds total capacity.
- Building unbounded queues "to avoid dropping anything." An unbounded queue does not avoid the problem, it just converts an immediate, visible failure into a much larger, delayed one, with far worse latency for everything queued.
- Shedding load without a notion of priority, so low-value and high-value requests are equally likely to be dropped.

## Key points

- Rate limiting rejects or delays requests exceeding a configured usage rate, protecting capacity and enforcing fairness or quotas.
- A token bucket allows short bursts up to a capacity while enforcing a long-term average rate as tokens refill.
- Backpressure makes producers slow, block, reject, or shed work when consumers cannot keep up, preventing unbounded queues.
- Load shedding deliberately rejects lower-priority or excess work under exhausted capacity so a manageable subset keeps working.
- Admission control decides whether new work is allowed in at all, based on capacity or quotas, before expensive processing starts.

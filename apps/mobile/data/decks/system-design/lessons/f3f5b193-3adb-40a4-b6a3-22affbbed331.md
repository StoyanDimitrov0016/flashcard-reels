# Consistency and coordination

When data has several copies, a read can land on any of them, and they may not agree. Consistency models are precise statements about what a reader is allowed to see. This lesson walks from the weakest common guarantee to the strongest, explains what the CAP theorem really says, and introduces the mechanisms replicas use to coordinate.

## Eventual consistency

**Eventual consistency** is the weakest widely used guarantee. After an update, replicas may temporarily return different values. But if writes stop and the replicas can communicate, they **converge** toward the same state.

That is a promise about the future, not about any particular read. A read right after a write may return the new value, the old one, or, if you read from different replicas in turn, both in alternation. Eventual consistency is a good fit for data where brief staleness is harmless, such as like counts, product reviews, or a social feed.

## Strong consistency

At the other end, a **strongly consistent** read returns a value compatible with the system's single-copy ordering guarantees. In other words, the system behaves as if there were one copy of the data, and a read never returns arbitrarily stale data from a lagging replica. The strictest form, **linearizability**, requires that once a write completes, every later read, from any client, sees it or something newer.

Strong consistency is easier to program against but costs latency and availability, because replicas must coordinate before answering.

## Session guarantees

Between those extremes are guarantees scoped to one client's view. They are cheaper than strong consistency and fix the most confusing anomalies.

**Read-your-writes** consistency promises that after a client successfully writes a value, its own later reads will see that write or a newer value. This fixes the "I saved my profile and it reverted" problem from replication lag. Implementations include routing a user's reads to the leader for a short time after they write, or tracking the version the client last wrote and only reading from replicas that have reached it.

**Monotonic reads** promises that once a client has seen a version, later reads never return an older one. Without it, a user who refreshes a page and gets routed to a different, more lagged replica could watch a new comment appear and then vanish. Pinning each user to one replica is a simple way to provide it.

Note that these are per-client promises. Other clients may still see older data.

## The CAP theorem

The **CAP theorem** is often misquoted as "pick two of consistency, availability, and partition tolerance." The accurate version is narrower: when a **network partition** prevents nodes from communicating, a distributed data system cannot guarantee both **linearizable consistency** and **availability** for every request.

Partitions are not optional in real networks; links fail and packets are dropped. So the real question is what a system does _during_ a partition.

**Choosing consistency** means some requests are rejected or delayed rather than answered with a result that might violate the consistency guarantee. A node that cannot confirm it has the latest data returns an error or waits.

**Choosing availability** means nodes keep answering despite incomplete coordination. Clients may see stale or conflicting state, and the system must **reconcile** the differences once the partition heals, for example with last-write-wins rules, version vectors, or merge logic.

When there is no partition, a system can offer both. Many databases also let you choose per operation.

## Quorums

**Quorum replication** gives a tunable middle ground. With `N` replicas, each write must be acknowledged by `W` of them and each read must contact `R` of them. If `R + W > N`, every read quorum overlaps every write quorum in at least one replica, so under the model's assumptions a read will encounter the most recent successful write. With `N = 3`, choosing `W = 2` and `R = 2` gives that overlap while tolerating one slow or failed replica.

The guarantee holds only under assumptions, such as correct conflict handling and no concurrent failures that break the overlap, so quorums raise the probability of fresh reads rather than making every system linearizable.

## Split brain

A **split-brain** condition happens when a partition separates nodes and more than one side believes it is authoritative. Two leaders accept conflicting writes, and the data diverges in ways that may be impossible to merge cleanly.

Systems prevent or contain it with:

- **Quorum rules**: a node may act as leader only if it can reach a majority, and only one side of a partition can hold a majority.
- **Fencing**: each new leader receives a higher **fencing token** or term number, and storage rejects requests carrying an older one, so a deposed leader that has not noticed its demotion cannot do damage.

## Consensus

A **consensus algorithm** lets multiple nodes agree on a chosen value, or an ordered sequence of values, even when some nodes fail. Raft and Paxos are the best known. As long as a majority of nodes are working and can talk to each other, they keep making progress, and they never decide two different values for the same slot.

Consensus is the foundation for **leader election**, where the cluster agrees on exactly one leader per term, and for **replicated state machines**, where every node applies the same log of commands in the same order and so ends in the same state. Coordination services such as etcd and ZooKeeper provide consensus as a building block so that most applications never implement it themselves.

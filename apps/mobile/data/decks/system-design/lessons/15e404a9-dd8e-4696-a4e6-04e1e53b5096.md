# Sagas and reliable event publishing

A single-database transaction, from database design, guarantees that a group of writes commits atomically or not at all. Once a workflow spans several independently-owned services, each with its own database, that guarantee stops being available: there is no single database transaction spanning "reserve inventory" (owned by the inventory service) and "charge the customer" (owned by the billing service). This lesson covers how multi-service workflows are coordinated without it, and how a single service reliably tells the rest of the system what it just did.

## Sagas

A **saga** coordinates a multi-service workflow as a sequence of local transactions with compensating actions for steps that must be logically undone after failure. Instead of one atomic transaction across every service, a saga runs a sequence of ordinary local transactions, each in one service's own database: reserve inventory (local transaction in the inventory service), charge payment (local transaction in the billing service), schedule shipping (local transaction in the shipping service). If a later step fails — payment is declined after inventory was already reserved — the saga runs a **compensating action** for each already-completed step: release the inventory reservation, rather than relying on a rollback the database itself cannot provide across service boundaries.

```text
step 1: reserve inventory       (local transaction, succeeds)
step 2: charge payment          (local transaction, FAILS - card declined)
compensate step 1: release inventory reservation
```

## Why a saga is not a transaction

**A saga is not equivalent to a database transaction**, and the difference matters for what callers and other services can observe: intermediate steps can become externally visible, and compensation is application logic rather than an atomic rollback of all participants. Between step 1 succeeding and step 2 failing, the inventory really was reserved — another service querying inventory during that window sees it as reserved, not as if step 1 had never happened, the way a real transaction's isolation would hide an in-progress, not-yet-committed change. And "undoing" step 1 means running a hand-written compensating action, which the saga's author had to think through and implement correctly for every possible partial-failure point — the database provides no automatic equivalent of `ROLLBACK` across independently-owned services.

## The transactional outbox pattern

A recurring problem in event-driven systems: a service commits a change to its own database and then needs to publish an event about that change. Doing these as two separate steps — commit the database write, then separately publish the event — creates a gap: what if the process crashes after the commit but before the publish? The event is silently lost, even though the underlying change genuinely happened and other services now have no way to find out.

The **transactional outbox pattern** solves this: a service writes business data and an outgoing-event record in the same local database transaction, then a separate publisher sends the event, avoiding a gap between commit and publish. Concretely, the order service inserts the new `orders` row and an `outbox` row describing the `OrderCreated` event in one atomic local transaction — since both are ordinary rows in the same database, this is a transaction the database can genuinely guarantee. A separate process then reads unpublished rows from the outbox table and publishes them to the event log, retrying until it succeeds and marking them published once it does. Because the business write and the outbox write are atomic together, there is no window where the order exists but no record of the need to publish an event about it does.

## Change data capture

The outbox pattern requires deliberately writing an extra row for every event-worthy change. **Change data capture (CDC)** offers an alternative that requires no application code changes at all: CDC streams committed database changes to downstream systems without requiring application code to publish a second copy of every write. A CDC tool reads the database's own replication or transaction log — the same mechanism the database uses internally for leader-follower replication — and turns each committed row change into an event, published to a queue or event log for other systems to consume. Since it operates below the application layer, on the database's already-durable commit log, it gets the atomicity-with-the-write guarantee the outbox pattern works to construct, without asking application code to write anything extra.

## Common mistakes

- Assuming a saga rolls back like a transaction, and not writing (or testing) the compensating action for every step that could need one.
- Publishing an event right after a database commit, as two separate operations, and only discovering the lost-event gap after a crash between them in production.
- Choosing CDC or the outbox pattern based on which is more fashionable rather than on whether the team wants events tied to raw row changes (CDC) or to meaningful, application-defined events (outbox) — the two produce different granularities of event.

## Key points

- A saga coordinates a multi-service workflow as a sequence of local transactions, using compensating actions to logically undo already-completed steps after a later failure.
- A saga is not a transaction: intermediate steps are visible to other observers, and compensation is hand-written application logic, not an atomic rollback.
- The transactional outbox pattern writes business data and an outgoing-event record in the same local transaction, then publishes from that outbox, avoiding a gap between commit and publish.
- Change data capture streams committed database changes to downstream systems by reading the database's own transaction log, without requiring application code to publish a second copy of every write.

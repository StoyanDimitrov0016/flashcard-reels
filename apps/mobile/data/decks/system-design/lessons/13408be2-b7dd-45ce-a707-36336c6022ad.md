# Observability

Every pattern in this deck so far — circuit breakers, sagas, sharding, replication — assumes you can tell, in production, whether it is actually working. A system that fails silently, or whose operators only find out about a problem from angry users, has no real reliability no matter how well it was designed. Observability is what closes that gap.

## What observability means

**Observability** is the ability to infer a system's internal behavior from outputs such as metrics, logs, traces, and profiles. The word matters precisely: it is about being able to answer questions you did not necessarily anticipate in advance — "why did this specific request fail," "why did latency spike at 3:14am" — from the data the system already emits, rather than needing to add new instrumentation and reproduce the problem after the fact. Three data types do most of the work.

## Metrics

A **metric** is a numeric time-series measurement, such as request rate, error count, queue depth, or latency distribution. Metrics are cheap to collect and aggregate at scale (a counter incrementing on every request costs almost nothing) and are what dashboards and alerts are usually built on. They answer "how much" and "how many" questions well — request rate over the last hour, p99 latency by endpoint — but a metric alone rarely explains _why_ a number moved; it tells you where to look next.

## Structured logging

**Structured logging** records events as machine-readable fields instead of only free-form text, making filtering and correlation more reliable. A plain-text log line like `"user login failed for ada@example.com"` is readable by a person scrolling through a file, but hard to query at scale — searching for every failed login across a fleet of instances means grepping for a substring and hoping the message format never changed. A structured equivalent, `{"event": "login_failed", "user": "ada@example.com", "reason": "bad_password"}`, can be filtered, aggregated, and joined with other structured data reliably, because the fields are consistently named and typed rather than embedded in prose that varies slightly between call sites.

## Distributed tracing

**Distributed tracing** records the path and timing of one logical request across service boundaries using correlated spans. Where a metric tells you the aggregate p99 latency for an endpoint, a trace shows you one specific request's actual journey: it hit the API gateway, called the orders service, which called inventory and payments in parallel, and payments took 400ms of the request's total 480ms — pinpointing exactly where the time went for that request, not just that the endpoint is slow on average. Each unit of work in a trace (one service's handling of the request) is a **span**, and spans are correlated to the same trace to reconstruct the whole path.

Tracing depends on propagating identity across every hop, which is exactly what a **correlation ID** provides: an identifier propagated across related operations so logs or events from one request or workflow can be connected. A single incoming request is tagged with a correlation ID at the edge, and every service it touches includes that same ID in its own logs and any events it emits — so an operator investigating one failed request can find every log line and event connected to it across every service involved, instead of guessing which log lines from which services correspond to that one request.

## Monitoring versus alerting

**Monitoring** records and visualizes system behavior — dashboards showing request rate, error rate, latency, resource usage. **Alerting** notifies people or automation when selected conditions require action. Monitoring is passive: someone has to be looking at the dashboard for it to help. Alerting is what makes observability operationally useful without a human staring at a screen at 3am — it converts "the dashboard shows an anomaly" into "someone gets paged."

## What makes an alert actionable

Alerting well is harder than it looks, because the failure mode of "alert on everything unusual" is an operator who receives so many low-value alerts that real ones get ignored — a well-documented problem called alert fatigue. **An alert is actionable** when it identifies a condition that has user or operational impact and points toward an owner or response, rather than firing on every low-level anomaly. "CPU on instance 47 is at 85%" is not, by itself, actionable — it may be entirely normal, and there is no clear next step. "Error rate on the checkout endpoint exceeded 5% for 5 minutes, page the payments on-call" is actionable: it names a user-visible impact, a threshold, and who should respond.

## Worked example

A checkout endpoint's p99 latency spikes from 200ms to 3 seconds.

1. A **metric** dashboard shows the p99 latency spike starting at 14:02, and an alert (configured against that same metric, with a threshold and duration) pages the on-call engineer, because a sustained checkout latency spike is user-impacting and actionable.
2. The on-call engineer pulls a **trace** for one of the slow requests during that window and sees that a downstream inventory call, usually 15ms, took 2.8 seconds for this request.
3. **Structured logs** from the inventory service, filtered by the **correlation ID** from that trace, show the inventory service was retrying a failed database connection repeatedly during that exact window — the actual root cause.

Without structured, correlated data across all three types, the engineer would have a slow dashboard and no way to find the one failing dependency behind it.

## Common mistakes

- Building dashboards (monitoring) without any alerting on the metrics that actually matter, relying on someone noticing a problem by chance.
- Alerting on every metric that can move, rather than on conditions with real user or operational impact — the direct cause of alert fatigue, where real pages get ignored along with the noise.
- Logging freely formatted text without a correlation ID, making it effectively impossible to reconstruct one request's path across services after the fact.

## Key points

- Observability is the ability to infer a system's internal behavior from metrics, logs, traces, and profiles.
- A metric is a numeric time-series measurement; structured logging records events as machine-readable fields for reliable filtering and correlation.
- Distributed tracing records one request's path and timing across services using correlated spans, pinpointing where time was spent for a specific request.
- A correlation ID is propagated across related operations so logs and events from one request or workflow can be connected.
- Monitoring records and visualizes behavior; alerting notifies people or automation when a condition requires action.
- An actionable alert identifies user or operational impact and points to an owner or response, rather than firing on every low-level anomaly.

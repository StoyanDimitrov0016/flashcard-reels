# Fan-out and tail latency

A single request rarely maps to a single downstream call in a real service architecture. A product page might need inventory, pricing, reviews, and recommendations, all fetched in parallel to keep total latency down. That parallelism is powerful, but it changes how tail latency — the p99 and p999 from the very first lesson — behaves, in a way that catches many designs by surprise.

## Fan-out

**Fan-out** occurs when one request triggers parallel calls to many downstream partitions or services. It can reduce individual work per node — searching across a sharded index by fanning out to every shard in parallel is far faster than searching them one at a time — but it increases tail-latency exposure and dependency count: the request is now only as reliable, and only as fast, as its weakest and slowest participant.

## Why fan-out amplifies tail latency

The parent request often cannot finish until the slowest required subrequest finishes, so more parallel dependencies increase the chance that at least one is slow. Recall from the first lesson that a p99 latency means 1% of calls are slow. For a single call, that is a 1% chance of a slow response. For a fan-out to 20 dependencies, each individually still at that same p99, the chance that _at least one_ of the 20 hits its slow case is far higher than 1% — roughly `1 - 0.99^20 ≈ 18%`. A tail case that was rare for any one dependency becomes almost one-in-five for the composed request, purely from fanning out to enough of them, even though nothing about any individual dependency changed.

```text
p99 per call = 1% chance of a slow response
fan out to 20 independent calls:
  P(all 20 fast) = 0.99^20 ≈ 0.818
  P(at least 1 slow) = 1 - 0.818 ≈ 18.2%
```

This is why a page assembled from many small, individually-fast services can feel slower in practice than a monolith making one call — not because any one piece got slower, but because the parent now waits on the maximum of many, not the latency of one.

## Managing the timeout across the fan-out

Because the parent waits on the slowest branch, coordinating deadlines across the branches matters as much as coordinating them across a chain of nested calls. A **timeout budget** allocates an end-to-end request deadline across downstream calls, so nested or parallel calls do not each wait longer than the caller can tolerate. Applied to fan-out: every parallel branch should share the same overall deadline the parent was given — if the parent has 500ms left before its own caller's deadline, each of the 20 fanned-out branches gets a 500ms deadline, not its own independent, uncoordinated full timeout — otherwise the slowest _allowed_ branch, not the slowest _typical_ one, determines the parent's actual latency, and that number can end up far larger than what the original caller was ever willing to tolerate.

## Hedged requests: trading load for tail latency

**Hedged requesting** is a direct countermeasure: a client sends a duplicate request to another replica after a delay and uses the first successful result, trading extra load for lower tail latency. If a request to replica A has not returned after, say, the p95 latency for that call, the client fires an identical request to replica B and takes whichever response arrives first. Most requests never trigger the hedge at all (they return well before the delay threshold), so the extra load is proportional only to the fraction of requests that were actually running slow — a targeted fix for exactly the tail cases fan-out makes more common, rather than a blanket doubling of all traffic.

## Worked example

A search service fans out a query to 10 shards, each with a p99 latency of 200ms and a median of 20ms. Without hedging, the overall p99 for the fanned-out query is dominated by whichever shard is unlucky: roughly a `1 - 0.99^10 ≈ 9.6%` chance that at least one of the 10 shards is in its own slow tail for this particular query, meaning almost one in ten searches waits for the full 200ms tail case instead of the typical 20ms. Adding hedged requests — firing a duplicate to a replica of any shard that has not answered within, say, 40ms — lets the query use whichever shard replica responds first, cutting the effective p99 close to the per-shard median while adding only a small, targeted amount of duplicate traffic (roughly the fraction of calls that were actually slow, not all of them).

## Common mistakes

- Fanning out to many dependencies without noticing that each added dependency, even at an unchanged individual reliability, drives the composed request's tail latency and failure rate up.
- Letting each branch of a fan-out run its own full-length timeout instead of sharing the parent's deadline, so the slowest allowed branch — not the actual typical latency — determines what users experience.
- Using hedged requests against a dependency that is not read-only or idempotent, which can cause the duplicate request to perform an unwanted side effect a second time.

## Key points

- Fan-out is one request triggering parallel calls to many downstream services or partitions, reducing per-node work but increasing dependency count and tail-latency exposure.
- Because the parent waits for the slowest branch, more parallel dependencies increase the chance at least one hits its slow tail, even if each dependency's own reliability is unchanged.
- A shared timeout budget across fan-out branches keeps the parent's total latency bounded by the intended deadline, not by the slowest allowed branch.
- Hedged requesting sends a duplicate request to another replica after a delay and takes the first result, trading a small amount of extra load for lower tail latency.

# Load balancing and the edge

Once a service runs on several instances, something has to decide which instance handles each request. This lesson covers load balancers and their routing strategies, why stateless services are easy to spread across machines, and the edge components, reverse proxies and API gateways, that sit between clients and your backends.

## Load balancers

A **load balancer** distributes incoming requests across multiple backend instances. Clients talk to one address, and the load balancer forwards each request to one of the servers behind it. This lets you add capacity by adding instances, and it hides individual machines from clients.

A load balancer is only helpful if it avoids broken servers. **Health checks** solve that problem. The load balancer regularly probes each instance, for example by calling an endpoint such as `/healthz`, and removes instances that fail from rotation until they pass again. Health checks catch crashed processes, but also instances that are still starting up, overloaded, or unable to reach a required dependency. Many systems distinguish a **liveness** check (is the process running?) from a **readiness** check (can it safely serve traffic right now?).

## Choosing a backend

Load balancers use different algorithms to pick a backend.

**Round robin** sends each new request to the next backend in turn: first A, then B, then C, then A again. It is simple and fair when requests are similar. Its weakness is that it ignores how expensive each request is and how busy each backend currently is. If one request takes ten seconds and the next takes ten milliseconds, round robin still treats them as equal.

**Least connections** sends each new request to the backend with the fewest active connections. Because a backend that is stuck on slow work accumulates open connections, it naturally receives fewer new ones. This makes least connections a better fit for **long-lived** or **unevenly timed** requests, such as file uploads, streaming, or WebSockets.

Other strategies exist, such as weighted variants that send more traffic to larger machines, and hashing on a client attribute so the same client tends to reach the same backend.

## Sticky sessions

**Sticky-session routing**, also called session affinity, sends a given client to the same backend on every request. The load balancer usually does this with a cookie that names the backend or with a hash of the client's address.

Stickiness is convenient when a server keeps a user's session in local memory, because the user keeps landing on the server that has their data. It has costs, though:

- **Balancing weakens**: a few heavy users pinned to one server can overload it while others sit idle.
- **Failover suffers**: if the pinned server dies, the session state in its memory is gone, and the user may be logged out or lose work.
- **Scaling in is awkward**: removing an instance disrupts every client pinned to it.

## Stateless services scale best

The alternative to stickiness is to make application instances **stateless**. A stateless instance keeps no user-specific data in memory between requests. Session data, carts, and other durable state live in a shared store such as a database or a distributed cache.

Because any instance can handle any request, you can add instances when load rises, remove them when it falls, and replace failed ones without migrating anything. The load balancer is free to use whatever algorithm spreads load best. This is why "keep application servers stateless" is one of the most common pieces of scaling advice: it pushes the hard state problem into a few components designed for it.

## Reverse proxies

A **reverse proxy** accepts requests from clients on behalf of one or more backend services. From the client's point of view, the proxy is the server. (A forward proxy is the opposite: it acts on behalf of clients reaching out to the internet.)

Reverse proxies are useful because they give you one place to handle common concerns:

- routing requests to different backends by path or host name
- **TLS termination**, so backends do not each manage certificates
- authentication checks
- caching responses
- request shaping, such as compression, header rewriting, or size limits

Many load balancers are reverse proxies with a balancing algorithm.

## API gateways

An **API gateway** is a specialized edge service for APIs. It routes API calls to the right backend services and centralizes **cross-cutting concerns** such as authentication, rate limits, observability, and protocol translation (for example, accepting HTTP and JSON from clients while calling internal services over gRPC).

The gateway simplifies clients, which see one consistent entry point, and lets teams enforce policy in one place instead of in every service.

The trade-off is concentration of risk. Every request passes through the gateway, so it becomes a **high-impact dependency**: if it fails or is overloaded, everything behind it is unreachable. It can also become a **bottleneck**, especially when teams start adding business logic to it. A healthy gateway stays thin, is deployed redundantly, and leaves domain logic to the services behind it.

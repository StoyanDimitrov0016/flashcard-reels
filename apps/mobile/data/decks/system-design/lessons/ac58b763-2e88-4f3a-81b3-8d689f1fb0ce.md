# Overload and queues

Every system has a limit. When more work arrives than it can handle, it needs a plan other than slowly falling over. This lesson covers the tools for controlling how much work enters a system, then moves on to queues and messaging, which absorb bursts but bring their own delivery problems.

## Rate limiting

**Rate limiting** rejects or delays requests that exceed a configured usage rate. It protects capacity from runaway clients and bugs, enforces **fairness** so one customer cannot starve the others, and implements **quotas** such as "1,000 API calls per hour on the free plan." A rejected HTTP request typically gets status `429 Too Many Requests`, often with a `Retry-After` header.

The most common algorithm is the **token bucket**:

- A bucket holds tokens, up to a fixed **capacity**.
- Tokens are added at a steady **refill rate**, for example 10 per second.
- Each request spends a token. If the bucket is empty, the request is rejected or delayed.

A client that has been quiet builds up a full bucket and can make a **burst** of requests at once. Over any long period, though, it cannot exceed the refill rate. The token bucket therefore allows short bursts while enforcing a long-term average, which matches how real clients behave.

## Backpressure, shedding, and admission

Rate limits apply to individual clients. The next three ideas protect the system as a whole.

**Backpressure** is a signal flowing upstream: when downstream consumers cannot keep up, producers are made to slow down, block, reject work, or shed it. Without backpressure, work piles up in ever-growing buffers and queues until memory runs out or latency becomes absurd. An **unbounded queue** does not fix overload; it only delays the moment you notice it.

**Load shedding** deliberately rejects lower-priority or excess work when capacity is exhausted. The goal is to keep serving a manageable subset well rather than serving everyone badly. A payment service under stress might keep processing checkouts while rejecting analytics events.

**Admission control** decides whether new work is allowed in at all, based on capacity, quotas, or resource limits, before any expensive processing begins. Rejecting a request at the door costs almost nothing; rejecting it after it has already consumed a database connection and half a second of CPU wastes the very resources you are short of.

## Queues

A **queue** sits between **producers**, which create work, and **consumers**, which process it. The queue stores work until a consumer is ready. This decouples the two sides: they no longer have to run at the same speed or even be available at the same time. A burst of orders fills the queue, and workers drain it steadily. Sending emails, resizing images, and updating search indexes are classic examples of work that can be done **asynchronously** this way.

Asynchronous messaging has a clear trade-off. It improves decoupling and burst handling, but results arrive later instead of immediately, and the system must deal with **retries, duplicates, ordering, and operational visibility**. With a direct call you know right away whether it worked; with a queue, a message might sit unprocessed, fail repeatedly, or be processed twice.

## Delivery guarantees

Messaging systems describe how many times a message may be delivered.

**At-most-once** delivery sends a message zero or one time. There are never duplicates, but if a failure happens before the message is successfully processed, that work is simply lost. It suits data where occasional loss is acceptable, such as some metrics.

**At-least-once** delivery keeps retrying until delivery is believed to have succeeded. Messages are not intentionally lost, but consumers can receive **duplicates**, for example when a consumer processes a message and crashes before acknowledging it, so the broker sends it again.

**Exactly-once** delivery is what everyone wants and what distributed systems struggle to provide. The core difficulty is uncertainty: when an acknowledgment goes missing, the sender cannot tell whether the work was done and the acknowledgment was lost, or the work never happened. Systems therefore approximate **exactly-once effects** by combining at-least-once delivery with idempotency, transactions, or deduplication.

## Idempotency

An operation is **idempotent** if repeating it with the same logical request produces the same intended final effect as doing it once. "Set the order status to shipped" is idempotent. "Add 10 to the balance" is not; running it twice adds 20.

For operations that are not naturally idempotent, APIs use an **idempotency key**. The client generates a stable, unique identifier for the request and sends it with every retry. The server records the outcome under that key. When a retry arrives with a key it has already seen, the server returns the stored result instead of performing the mutation again.

```http
POST /transfers
Idempotency-Key: 7c1e9b52-4a0f-4d2e-9f63-2b8d0c5a1e47
```

This is how a client can safely retry a payment after a timeout without charging the customer twice.

## Messages that keep failing

Some messages fail no matter how often they are retried: malformed payloads, references to deleted records, or bugs in the consumer. If they stay at the front of the queue, they block everything behind them. A **dead-letter queue** collects messages that have failed a set number of times. Normal traffic keeps flowing, and engineers can inspect, repair, and **replay** the failed messages separately.

## Ordering

**Message ordering** is a guarantee about the sequence in which consumers observe messages. Global ordering, where every consumer sees every message in one agreed order, is expensive because it limits parallelism. Many systems instead guarantee order only **within a partition or key**. Apache Kafka, for instance, orders messages within a partition, so sending all events for one account with the same key keeps that account's events in order while different accounts are processed in parallel.

# Resilient service calls

In a system made of many services, most requests involve calls across the network, and every one of those calls can be slow or fail. This lesson covers the habits that keep one struggling dependency from dragging everything down, the special latency problems of calling many services at once, and how services find each other in the first place.

## Timeouts

A network call with no timeout can wait forever. If a dependency has crashed or a partition has cut it off, the caller simply hangs, holding a thread, a connection, and memory the whole time. Enough hanging calls and the caller itself runs out of resources and fails, even though its own code is fine.

A **timeout** bounds how long the caller waits. It limits how long resources stay occupied and gives recovery logic a chance to run: retry elsewhere, return a fallback, or report an error. Choosing the value is a balance. Too long and resources pile up; too short and slow but healthy calls are abandoned.

## Retries and retry storms

Retrying a failed call is a sensible response to brief glitches such as a dropped packet or a restarting instance. But retries have a dark side. When a dependency is struggling because it is overloaded, every client retrying multiplies its load exactly when its capacity is lowest. If each of three layers retries three times, one user request can become 27 calls at the bottom. This feedback loop is a **retry storm**, and it can turn a brief slowdown into a prolonged outage.

Retries should be limited in number, applied only to errors that might succeed on a second attempt, and used only for operations that are safe to repeat.

## Backoff with jitter

**Exponential backoff** spaces retries out, with the delay growing after each failure: for example 100 ms, then 200 ms, then 400 ms, up to a maximum. This eases the pressure on a dependency that needs time to recover.

Backoff alone still has a problem. If a thousand clients failed at the same moment, they all wait exactly 100 ms and retry together, then 200 ms and retry together again, hitting the dependency in synchronized waves. **Jitter** adds randomness to each delay, so the retries spread out over time:

```text
delay = random(0, min(maxDelay, base * 2^attempt))
```

This mirrors the jittered cache expirations from the caching lesson: randomness breaks up synchronized spikes.

## Circuit breakers

A **circuit breaker** wraps calls to a dependency and tracks failures. It has three states:

1. **Closed**: calls flow normally while the breaker counts failures.
2. **Open**: after too many failures, the breaker stops sending normal requests for a period and **fails fast**, returning an error or fallback immediately.
3. **Half-open**: after the period, a few **probe** requests are allowed through. If they succeed, the breaker closes; if not, it opens again.

Failing fast protects the caller, which stops wasting threads on doomed calls, and gives the dependency room to recover instead of being hammered.

## Bulkheads

A ship's hull is divided into watertight compartments, called bulkheads, so one leak does not sink the whole ship. The **bulkhead pattern** applies the same idea to resources. Instead of one shared pool of threads, connections, or workers, a service keeps separate pools per dependency or per workload.

If the recommendations service becomes slow, only the pool reserved for it fills up. Calls to the payments service still have their own pool and keep working. Without bulkheads, one slow dependency can consume every worker and take down unrelated features.

## Timeout budgets

Timeouts must fit together across layers. Suppose a user-facing request has two seconds, and it calls service A, which calls service B. If A and B each use a five-second timeout, they will keep working long after the user has given up.

A **timeout budget**, or deadline, fixes this by allocating the end-to-end deadline across downstream calls. The caller passes along how much time remains, and each service uses only what is left, minus its own work. Nested services then never wait longer than the original caller can tolerate. Frameworks such as gRPC propagate deadlines this way automatically.

## Fan-out and tail latency

**Fan-out** happens when one request triggers parallel calls to many downstream partitions or services. A search query sent to 50 index shards is a typical example. Fan-out reduces the work each node does, but it increases the number of dependencies and the exposure to **tail latency**.

The reason is simple probability. The parent usually cannot respond until the slowest required subrequest finishes. If each shard has a 1% chance of being slow, a request that touches one shard is slow 1% of the time. A request that touches 100 shards has about a 63% chance that at least one of them is slow. The more parallel dependencies, the more the rare slow response becomes the common case.

## Hedged requests

**Hedged requests** attack the tail directly. The client sends a request to one replica and, if no response has arrived after a short delay, often around the p95 latency, sends a duplicate to another replica. Whichever successful result comes first wins, and the other can be cancelled. Because the hedge fires only for the slowest few percent of requests, the extra load is small, and in exchange the long tail shrinks dramatically. Hedging suits reads and other idempotent operations.

## Service discovery

Instances come and go constantly as services scale, deploy, and fail, so hard-coded host lists go stale fast. **Service discovery** maps a logical service name, such as `payments`, to the instances currently reachable. Either the client looks up the instances and picks one, or a proxy or load balancer does the lookup on its behalf.

Discovery relies on a **service registry**: a store of instance locations along with health metadata. Instances register when they start, renew their registration through heartbeats or health checks, and are removed when they stop or fail. Consul, etcd, and the Kubernetes API with its DNS are common registries.

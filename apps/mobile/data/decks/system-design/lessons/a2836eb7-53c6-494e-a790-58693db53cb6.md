# Replication and consistency models

Partitioning spreads data across nodes so no single machine has to hold everything. Replication takes a different, complementary approach: keep copies of the _same_ data on multiple nodes. The two are often combined — a sharded system typically replicates each shard too — but replication introduces its own question that partitioning does not: when there are several copies of the same data, what can a reader expect to see, and how far can the copies drift apart?

## Why replicate

**Replication** keeps copies of data on multiple nodes to improve availability, read capacity, locality, or disaster recovery. Availability, because a copy survives even if one node holding it fails (this is exactly the redundancy from an earlier lesson, applied to data). Read capacity, because reads can be spread across copies instead of all hitting one node. Locality, because a copy placed near users in a given region can be read with lower latency than crossing the globe for every request. Disaster recovery, because a copy in a separate location survives a disaster that destroys another.

## Leader-follower replication

The most common replication scheme is **leader-follower replication**: one leader accepts authoritative writes and followers copy its changes. Reads may be distributed across the leader and followers, spreading read load, but followers can lag behind the leader, since replicating a change takes some nonzero time.

That lag has a name: **replication lag** is the delay between a committed update on a source replica and when another replica applies or exposes that update. Replication lag is not a bug to be eliminated; it is close to unavoidable when replicas are geographically distant or under load, and every consistency model below exists to define precisely what a reader is allowed to observe in its presence.

## Eventual and strong consistency

**Eventual consistency** allows replicas to temporarily return different values after updates, but if writes stop and communication succeeds, they converge toward the same state. It is a genuinely weak guarantee — it says nothing about _how long_ "eventually" takes, only that divergence does not persist forever once things settle. Its appeal is that it does not require readers to wait for every replica to agree before answering, which is what makes it compatible with high availability and low read latency even while replication lag exists.

**Strong consistency** for a read means the read returns a value compatible with the system's chosen single-copy ordering guarantees, rather than arbitrarily stale replica data — in practice, usually **linearizability**: the system behaves, to any observer, as though there were exactly one up-to-date copy of the data, even though there are really several. Achieving this generally requires reads (or writes) to coordinate across replicas rather than being answered independently by whichever replica happens to receive the request, which costs latency and can cost availability during a network partition — the trade-off the next lesson's CAP theorem makes precise.

## Two useful guarantees in between

Between "no guarantee at all" and full linearizability sit guarantees that are cheaper to provide and cover the cases users actually notice.

**Read-your-writes** consistency: after a client successfully writes a value, its later reads are guaranteed to observe that write or a newer value. Without it, a user who just updated their profile picture could refresh the page and see the old one, because the read happened to land on a follower that had not yet caught up — a confusing, very visible failure for something this cheap to prevent (routing that user's subsequent reads to the leader, or to a replica known to have caught up, is enough).

**Monotonic reads** consistency: once a client has observed a version, later reads will not return an older version. Without it, a user could refresh a page and see a comment disappear, because an earlier read happened to land on a more up-to-date replica than a later one — data moving _backwards in time_ from the user's point of view, which is a more disorienting failure than simple staleness.

## Worked example

A user posts a comment. The write lands on the leader; three followers each apply it after their own replication lag (50ms, 200ms, and 900ms respectively).

- Under plain eventual consistency with no further guarantee, a load balancer could route the user's own next read to the 900ms-lagging follower, and the user would not see their own comment yet.
- With read-your-writes, the system recognizes this is the same client that just wrote, and routes that read to the leader (or a replica confirmed caught up), so the user does see their comment.
- With monotonic reads added, once that user's session has observed the comment on one replica, a later read is never allowed to land on a replica that has not yet caught up to at least that point, even if load balancing would otherwise send it there — no jarring "the comment vanished."

## Common mistakes

- Assuming "replicated" implies "consistent." Replication is what makes divergence _possible_; consistency models are what constrain how much divergence a reader is allowed to see.
- Choosing strong consistency everywhere by default, without weighing the latency and availability cost, when the actual user-facing requirement was closer to read-your-writes.
- Ignoring replication lag when routing reads, and discovering read-your-writes or monotonic-reads violations only from confused user reports ("my comment disappeared").

## Key points

- Replication keeps copies of data on multiple nodes for availability, read capacity, locality, or disaster recovery.
- Leader-follower replication has one leader accept writes and followers copy them; followers can lag behind, which is replication lag.
- Eventual consistency allows temporary divergence between replicas that converges once writes and communication stop; strong consistency (typically linearizability) makes replicas behave as a single up-to-date copy.
- Read-your-writes guarantees a client sees its own successful write on later reads.
- Monotonic reads guarantees a client never sees an older version after having seen a newer one.

# Caching

Many requests ask for the same data again and again, and producing that data can be slow: a database query, a call to another service, or an expensive computation. Caching keeps a copy close at hand so repeated reads are cheap. It is one of the most effective performance tools in system design, and also one of the easiest to get subtly wrong.

## What a cache is

A **cache** is temporary storage for data that is expensive to produce or frequently reused, so that later reads can skip recomputing or refetching it. Caches appear at every level: CPU caches, in-process memory maps, shared caches such as Redis or Memcached, HTTP caches in browsers, and content delivery networks at the edge of the internet.

The key word is temporary. A cache is not the **source of truth**. Its contents can be evicted, expire, or be lost entirely, and the system must still work, if more slowly, when that happens.

## Measuring a cache

The main measure of a cache is its **hit rate**: the fraction of eligible reads served from the cache rather than from the underlying source. A read found in the cache is a **hit**; one that must go to the source is a **miss**.

A higher hit rate usually means more backend work is avoided. Going from a 90% to a 99% hit rate sounds small, but it cuts the traffic reaching the backend from 10% of reads to 1%, a tenfold reduction.

## Ways to use a cache

How reads and writes interact with the cache is a design choice. Three patterns come up constantly.

**Cache-aside** (also called lazy loading) puts the application in charge:

1. Look up the key in the cache.
2. On a hit, return the cached value.
3. On a miss, read from the source, store the result in the cache, and return it.

```text
value = cache.get(key)
if value is missing:
    value = database.read(key)
    cache.set(key, value, ttl)
return value
```

Only data that is actually requested gets cached. When the application writes to the source, it usually must **invalidate** or update the cached entry, or readers will see old data.

**Write-through** caching sends writes through the cache layer, which updates the backing store before acknowledging success. The cache and the source stay coordinated, and recently written data is already cached for the next read. The cost is extra work on the write path, since every write touches both.

**Write-back** (or write-behind) caching acknowledges a write as soon as the cache is updated and persists it to the backing store later, often in batches. Writes become fast, but there is a window in which the only copy of the new data lives in the cache. If the cache fails before flushing these **dirty** entries, the data is lost, unless the cache itself protects them durably, for example by replicating or logging them.

## Invalidation

**Cache invalidation** means removing or expiring cached data when it may no longer match the source of truth. The simplest form is a **time to live (TTL)**: each entry expires after a fixed period. More precise approaches delete or update entries when the underlying data changes.

Invalidation has a reputation for being hard, and the reasons are concrete:

- **Many copies** of the same data may exist in different caches, and all of them can outlive an update.
- **Invalidation messages** can be delayed, reordered, or lost, leaving a stale copy in place.
- **Dependencies** are complex: one change to a product price may affect cached product pages, search results, and cart totals.

Because precise invalidation can fail, robust designs keep a fallback. A TTL guarantees that stale data eventually expires, and **versioned keys** (for example, including a version number in the key) make old entries unreachable after an update.

## Stampedes and jitter

A **cache stampede**, sometimes called a thundering herd, happens when many requests miss the same hot key at the same moment. Each one goes to the backend to recompute the value, and the sudden surge can overwhelm it, often right after a popular entry expires.

Common defenses include:

- **Request coalescing**: only one request fetches the value while the others wait for its result.
- **Locks**: a request must acquire a lock on the key before recomputing it.
- **Serving stale data**: keep returning the old value briefly while one request refreshes it in the background.
- **Jittered TTLs**: add randomness to expiration times.

**Jitter** deserves a closer look. If you load a million keys at once with the same one-hour TTL, they will all expire at the same moment an hour later, creating a synchronized wave of misses. Setting each TTL to, say, 60 minutes plus a random 0 to 5 minutes spreads expirations out, so backend traffic stays smooth.

## Content delivery networks

A **content delivery network (CDN)** is a cache spread around the world. It serves content from **edge locations** close to users, so a request from Tokyo is answered in Tokyo rather than crossing an ocean to your **origin** servers. CDNs reduce latency by shortening network distance and reduce load on the origin, since most requests never reach it. They are ideal for static assets such as images, scripts, and videos, and can also cache API responses that many users share.

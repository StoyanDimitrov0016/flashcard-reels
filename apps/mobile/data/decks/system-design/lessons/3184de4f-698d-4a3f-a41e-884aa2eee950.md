# API versioning and compatibility

Every API in a real system eventually has to change — a field renamed, a new requirement added, a bug in the original design fixed. The difficulty is that clients calling that API do not all upgrade the moment the server changes; old mobile app versions, other teams' services, and third-party integrations keep calling the old shape for a long time, sometimes indefinitely. This lesson covers how APIs change without breaking them.

## Why versioning exists

**API versioning** lets an API evolve while preserving behavior expected by existing clients that cannot all upgrade at once. A `v1` and `v2` of an endpoint (via a URL path, a header, or a schema version field) let the server support the old contract for clients still on it while offering a new contract to clients that have upgraded, rather than forcing every caller to switch the moment the server does. Versioning is not free — supporting multiple versions means genuinely running more code paths, not just one — but the alternative, breaking every client that has not upgraded yet the instant the server changes, is usually far worse.

## Backward compatibility

The goal, wherever possible, is to avoid needing a new version at all. A change is **backward compatible** when existing clients can continue using the updated service without changing their behavior or payloads. A backward-compatible change might add an optional new field to a response, add a new endpoint, or relax a validation rule; existing clients, unaware the change happened, keep working exactly as before, and only clients that choose to use the new capability need to change anything.

## Why additive changes are the safe default

**Additive schema changes are preferred in distributed systems** for a specific structural reason: older and newer components often run simultaneously, so adding optional fields is usually safer than renaming or changing meanings that old consumers still expect. In a single-process application, you can often deploy client and server together, so a coordinated rename is momentarily fine. In a distributed system — a mobile app that updates on its own schedule, a partner integration you do not control, a service owned by a different team on a different deploy cadence — the old and new versions of a message's producer and consumer genuinely coexist in production for a real stretch of time, sometimes indefinitely for clients that never update. Renaming a field, changing what a field means, or removing a field breaks every consumer still expecting the old shape, for as long as any of them exist. Adding a new, optional field breaks nothing: old consumers simply ignore a field they do not recognize, and new consumers can start reading it whenever they are ready.

```json
// backward compatible: old consumers ignore the new optional field
{
  "orderId": "abc123",
  "total": 42.5,
  "currency": "USD" // added in a later version; optional, ignored by old clients
}
```

```json
// NOT backward compatible: renaming breaks every consumer expecting "total"
{
  "orderId": "abc123",
  "totalAmount": 42.5
}
```

## Worked example

A payments API originally returns `{"amount": 42.50}`, understood by every existing client as US dollars. The team needs to support multiple currencies.

- **Breaking approach**: rename `amount` to `amountInCents` and change its meaning to an integer. Every existing client, still expecting a decimal dollar amount under `amount`, now either crashes or silently misinterprets the new field — for as long as any client has not upgraded.
- **Additive approach**: keep `amount` exactly as it was (decimal dollars, implicitly USD), and add a new optional `currency` field alongside it, plus perhaps a new `amountMinorUnits` field for clients that want exact integer arithmetic. Old clients keep working unmodified, reading `amount` exactly as before; new clients can adopt `currency` and `amountMinorUnits` whenever they are ready, at their own pace.

The additive version does mean the API carries some redundancy (two representations of the same amount) for a while — a real, accepted cost in exchange for never breaking a client that has not upgraded yet.

## Common mistakes

- Renaming or repurposing a field "because it is a small change," without accounting for how many still-running old clients depend on the old name or meaning.
- Treating versioning as a substitute for backward compatibility, and bumping the API version for every change, rather than reserving new versions for the genuinely breaking ones and keeping the rest additive.
- Removing an old field as soon as a new one is added, before confirming every client has actually migrated off it.

## Key points

- API versioning lets an API evolve while preserving the behavior existing, not-yet-upgraded clients expect.
- A backward-compatible change lets existing clients keep working unmodified, with no change to their behavior or payloads.
- Additive schema changes (new optional fields) are safer than renaming or changing meaning, because old and new components typically run simultaneously in a distributed system.
- Reserve new API versions for genuinely breaking changes, and prefer additive, backward-compatible changes whenever the goal can be met without one.

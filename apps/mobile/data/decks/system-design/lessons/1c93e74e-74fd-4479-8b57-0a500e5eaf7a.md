# Partitioning and sharding

A single machine can only hold so much data and serve so many requests, no matter how well it is tuned. Once a workload outgrows one machine, the data itself — not just the compute in front of it — has to be split across many. This lesson covers how that split is done, and the traps that show up once it is.

## Partitioning

**Partitioning** splits data or work into subsets that can be stored and processed independently, enabling horizontal scale. It is the general concept: any time a big thing is split so pieces can be handled by separate machines, that's partitioning. Applied specifically to a dataset spread across database nodes, it usually goes by a more specific name.

**Sharding** partitions a dataset across multiple independent database nodes so no single node must store or serve all records. Each shard holds a subset of the rows (or documents, or keys), and a router or client-side logic sends each query to the shard that holds the relevant data — so total capacity, both storage and query throughput, grows as shards are added, in a way a single ever-larger machine cannot match indefinitely.

## Choosing what to split on

Sharding requires deciding, for every record, which shard it lives on — a decision driven by the **shard key**. A good shard key spreads load and data reasonably evenly while keeping common access patterns efficient and avoiding hot partitions. Concretely, this means picking a value that (a) has enough distinct values that records don't pile onto a handful of shards, and (b) matches how the data is actually queried, so that a typical request needs to touch one shard rather than scatter across all of them.

`user_id` is a common, reasonable shard key for a system where most queries are "show me this user's data" — each such query hits exactly one shard. A shard key like `signup_country` would be a poor choice for a global consumer app with users concentrated in a few countries: the shards for those countries would carry far more data and traffic than the rest.

## Hot partitions

A **hot partition** receives much more traffic or data than others, causing one shard to bottleneck even when the overall cluster has spare capacity. This is the direct, painful consequence of a shard key that does not spread load evenly — a celebrity's account on a social platform sharded by `user_id` is fine (that one user's shard is busy, but it is still just one shard's worth of load); the same platform sharded by, say, `signup_date` would concentrate an entire viral day's worth of new-user traffic onto a single shard, no matter how many shards exist in total.

## Consistent hashing

Deciding which shard owns a key is often done by hashing the key and taking the result modulo the number of shards (`hash(key) % N`). This works, but it has a serious weakness: changing `N` — adding or removing a single shard — changes the modulo result for nearly every key, meaning nearly all data has to move, just to add one machine.

**Consistent hashing** solves this by mapping keys and nodes onto a logical ring (a circular hash space) instead of using a plain modulo. Each node owns the range of the ring between itself and the next node going clockwise; a key belongs to the first node found going clockwise from the key's own hash position. Adding or removing a node only moves the fraction of keys owned by the ring segment directly affected, compared with simple modulo hashing, where nearly every key relocates.

```text
ring positions (clockwise):  A(10) -> key(25) -> B(40) -> key(55) -> C(70) -> ... -> A(10)
key at position 25 belongs to B (next node clockwise)
key at position 55 belongs to C (next node clockwise)
```

Adding a new node `D` at position 50 only takes over the range between the previous owner and 50 — a small slice of keys, not a wholesale reshuffle.

## Virtual nodes

Plain consistent hashing, with each physical node at a single ring position, can still distribute load unevenly if node positions happen to land unevenly around the ring (one node ends up owning a much larger arc than another purely by chance, or a more powerful node deserves more than an equal share). **Virtual nodes** address this by giving each physical node multiple positions on the ring instead of one. This improves load distribution — the unevenness of any single position matters less when it is averaged over many — and it makes it easier to assign more or less capacity to different nodes, since a more powerful physical machine can simply be given more virtual node positions than a weaker one.

## Common mistakes

- Choosing a shard key based on what is convenient to generate (an auto-incrementing ID) rather than what matches real access patterns and spreads load — a frequent cause of hot partitions discovered only after launch.
- Assuming more shards automatically fixes a hot partition. If the shard key itself concentrates load on one value, adding shards elsewhere does nothing for the one shard actually under pressure.
- Using plain modulo hashing for a cluster expected to grow, and being surprised by a massive, unnecessary data migration the first time a node is added or removed.

## Key points

- Partitioning splits data or work into independent subsets, enabling horizontal scale; sharding is partitioning applied to a database across independent nodes.
- A good shard key spreads load and data evenly and matches common query patterns, so most queries touch one shard.
- A hot partition receives disproportionate traffic or data, bottlenecking one shard even when the cluster overall has spare capacity.
- Consistent hashing maps keys and nodes onto a ring so adding or removing a node moves only a fraction of keys, unlike plain modulo hashing.
- Virtual nodes give each physical node multiple ring positions, improving load distribution and making uneven capacity allocation easier.

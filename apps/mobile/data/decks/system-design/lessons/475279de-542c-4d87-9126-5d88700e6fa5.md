# Reverse proxies and API gateways

A load balancer answers "which instance handles this request." A separate question is what happens to a request before it ever reaches a backend instance — where TLS is terminated, where authentication is checked, where the request is logged. Concentrating that work at the edge, rather than duplicating it inside every service, is the job of reverse proxies and API gateways.

## Reverse proxies

A **reverse proxy** accepts client requests on behalf of backend services and can perform routing, TLS termination, authentication, caching, or request shaping. "Reverse" distinguishes it from a forward proxy, which acts on behalf of clients (fetching pages for a browser behind a corporate firewall, for example); a reverse proxy instead sits in front of servers, hiding their existence and topology from the outside world. Clients only ever talk to the reverse proxy; it decides which backend actually handles the request, and it can rewrite, compress, or cache the response on the way back.

Terminating TLS at the reverse proxy is a common pattern: encrypted traffic from the internet is decrypted once at the edge, and internal traffic between the proxy and backends can run over a trusted internal network, often unencrypted or with simpler, uniformly-configured internal TLS — sparing every backend service from managing its own certificates. A load balancer is, in effect, a reverse proxy specialized for one job: choosing among interchangeable backend instances. Nothing stops a single piece of software from doing both jobs at once, which most production reverse proxies do.

## API gateways

An **API gateway** is an edge service that routes API calls and often centralizes cross-cutting concerns such as authentication, rate limits, observability, and protocol translation. Where a plain reverse proxy is mostly concerned with connection-level plumbing, an API gateway is aware of the API shape behind it: it can route `/orders/*` to the orders service and `/users/*` to the users service, translate an external REST call into an internal call to a different protocol, enforce per-client rate limits (covered in a later lesson), and emit consistent logs and metrics for every call that passes through it, regardless of which backend served it.

```text
client
  -> API gateway (auth, rate limit, routing, logging)
      -> orders service
      -> users service
      -> inventory service
```

Because every one of those cross-cutting concerns is implemented once at the gateway, individual backend services do not each need their own authentication logic, their own rate limiter, and their own tracing setup — a real simplification for every team building a service behind the gateway.

## The trade-off

Centralizing at the gateway simplifies clients (one entry point, one auth mechanism to integrate with) and centralizes policy (a rate-limit rule or an auth check written once applies everywhere). But it can become a high-impact dependency — every request to every backend service passes through it, so an outage or a bug in the gateway is not a single service's bad day, it is every service's bad day — and it can become a bottleneck if overloaded or overburdened with business logic that should have stayed in the services it fronts.

That last risk is worth naming directly: a gateway is meant to hold cross-cutting, request-shape-agnostic concerns (auth, rate limiting, routing, logging). It is tempting, over time, to also add business rules there ("special-case pricing logic for this one client") because it is a convenient central place to put things. Doing so turns the gateway into an undocumented, hard-to-test extension of business logic that every team now depends on and few teams can safely change — the opposite of what made it valuable.

## Common mistakes

- Treating the API gateway as a place for business logic because it is convenient, rather than keeping it limited to cross-cutting, backend-agnostic concerns.
- Under-provisioning or under-monitoring the gateway itself, on the assumption that "it just routes traffic" — it now sits on the critical path of every request to every service behind it.
- Confusing a reverse proxy's job (connection-level routing, TLS, caching) with an API gateway's job (API-aware routing, auth, rate limiting) when choosing or evaluating tooling; many products combine both, but the two concerns are still distinct.

## Key points

- A reverse proxy accepts requests on clients' behalf and can perform routing, TLS termination, authentication, caching, or request shaping, hiding backend topology from clients.
- An API gateway is an edge service that routes API calls and centralizes cross-cutting concerns like authentication, rate limits, observability, and protocol translation.
- Centralizing these concerns at the edge simplifies clients and centralizes policy, but makes the gateway a high-impact dependency and a potential bottleneck.
- A gateway should hold cross-cutting, backend-agnostic concerns; business logic belongs in the services it fronts, not in the gateway itself.

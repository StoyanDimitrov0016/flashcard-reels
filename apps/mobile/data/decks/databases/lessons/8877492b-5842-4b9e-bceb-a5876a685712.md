# Recovering from failures

A database promises that a committed transaction survives a crash. But it cannot afford to write every changed page to disk before answering every commit, and disks, data centers, and people fail in ways no single server can survive. Recovery works in layers: a write-ahead log that makes crashes survivable, checkpoints that keep recovery fast, and backups that protect against losing the server or the data itself, down to restoring the moment before a mistake.

## The problem with writing pages directly

Tables and indexes are stored in fixed-size **pages** (8 KB in PostgreSQL), cached in memory and written to disk later. A single transaction may change a row on one page, three index pages elsewhere, and a page of another table. If the database had to write all of those scattered pages to disk before acknowledging a commit, commits would be slow. And if it crashed after writing only some of them, the files on disk would contain half a transaction.

## The write-ahead log

A **write-ahead log** (WAL, also called a redo log or journal) solves both problems. Every change is first recorded as a record in an append-only log, and the rule is:

**The log record describing a change must be durable before the modified data page is written to disk**, and a commit is acknowledged only once its log records are flushed.

```text
1. T1 changes pages in memory         (data pages not yet on disk)
2. T1's WAL records are appended      (log in memory)
3. COMMIT: WAL flushed to disk        (fsync)  -> commit acknowledged
4. later: changed data pages written  (background)
```

After a crash, the data files may be missing recent changes or contain partial ones. Recovery reads the WAL and **replays** the logged changes, bringing every page up to date, while changes from transactions that never committed are treated as rolled back. Every acknowledged commit is restored.

The same log turns out to be useful beyond crash recovery. Because it is a complete, ordered record of every change, it can be streamed to other servers to keep copies in sync, which is how PostgreSQL's physical replication works, and archived to rebuild history, as the end of this lesson shows.

## Why WAL makes writes faster

Writing more data (the log and, later, the pages) sounds slower, but it is usually faster. Appending **sequential** log records to the end of one file is cheap: the disk writes one contiguous region, and one flush can cover the commits of many concurrent transactions (group commit). Writing many **scattered** data pages synchronously would mean many random writes on every commit.

With WAL, the commit path does only the cheap sequential write. The expensive random page writes happen later in the background, where many changes to the same hot page can be combined into one write.

## Checkpoints

If data pages are written "later", the log keeps growing, and after a crash the database would have to replay it all the way from the beginning. A **checkpoint** prevents that. It advances a known recovery point by flushing all data pages modified up to that point, then recording in the log that everything before it is safely in the data files.

Crash recovery then starts from the latest checkpoint instead of replaying the entire historical log, and log segments before it are no longer needed for crash recovery and can be recycled (unless archived for backups).

Checkpoint frequency is a trade-off. Frequent checkpoints mean fast recovery but more page-writing work during normal operation; infrequent ones mean less write overhead but longer replay after a crash. PostgreSQL controls this with `checkpoint_timeout` and `max_wal_size`, and spreads each checkpoint's writes out over time to avoid I/O spikes.

## Backups

WAL protects against crashes of a working server. It does nothing if the disk dies, the data center burns down, an attacker encrypts the files, or someone runs `DELETE FROM customers` without a `WHERE` clause and commits. The committed delete is durable too.

A **backup** is a separately recoverable copy or representation of the data, used to restore after **deletion, corruption, or infrastructure loss**. Backups come in two main forms:

- **Logical backups** export the data as SQL statements or a portable format, such as PostgreSQL's `pg_dump`. They are flexible, can restore single tables, and move between versions, but are slow for large databases.
- **Physical backups** copy the database's data files, such as `pg_basebackup`. They are fast to take and restore for large databases, and they serve as the base for point-in-time recovery.

A backup is only as good as its storage and its last successful restore: keep copies in a separate location or account from the live database, and regularly test that you can actually restore them.

## Point-in-time recovery

Nightly backups alone would lose up to a day of data. And if the bad `DELETE` ran at 14:03, restoring last night's backup loses everything from the morning too.

**Point-in-time recovery** (PITR) combines a **base backup** with the continuously **archived WAL** since that backup. To recover, you restore the base backup and replay the log **only up to a selected time**, just before the damaging change:

```text
base backup (Sunday 02:00) + archived WAL up to Tuesday 14:02:59
  -> the database exactly as it was one second before the DELETE
```

In PostgreSQL you set `recovery_target_time` and the server stops replaying at that moment. Everything before the mistake is recovered; the mistake and anything after it are not, and later legitimate changes may need to be reapplied by hand.

## Key points

- A write-ahead log records changes durably before modified data pages are considered safely persisted, enabling crash recovery and often replication.
- WAL improves write efficiency because appending sequential log records is cheaper than synchronously writing many scattered data pages on every commit.
- A checkpoint advances a known recovery point by flushing enough state that crash recovery need not replay the entire historical log.
- A backup is a separately recoverable copy of data used to restore after deletion, corruption, or infrastructure loss.
- Point-in-time recovery restores a base backup and replays logs only up to a selected time, recovering to just before a damaging change.

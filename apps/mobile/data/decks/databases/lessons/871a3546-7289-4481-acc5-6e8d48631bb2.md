# Beyond relational

Relational databases are a strong default, but they are not the only model. Other kinds of databases shape data around particular access patterns. And as systems grow, data rarely stays in one place: it is copied into caches, search indexes, and other services. This lesson covers the main non-relational models and the patterns for moving data between systems.

## Document databases

A **document database** stores self-contained records, typically JSON-like documents. A document can hold nested objects and arrays, and different documents in the same collection can have different fields.

```json
{
  "_id": "order-1842",
  "customer": { "id": 42, "name": "Ana" },
  "items": [
    { "sku": "BK-101", "qty": 2 },
    { "sku": "PN-007", "qty": 1 }
  ],
  "status": "paid"
}
```

The **document model is useful** when data is usually read and written as one **aggregate**, like an order with its line items, when fields vary between records, and when there are few relationships or constraints that span documents. One read fetches everything, with no joins. It fits less well when data is heavily interconnected and needs to be queried from many angles.

## Key-value databases

A **key-value database** does one thing: given a unique key, it returns a value. The value is usually opaque to the database, or only lightly structured. With so little to do, key-value stores favor **simple, very low-latency access**, which suits caches, sessions, feature flags, and counters. Queries by anything other than the key are generally not what they are built for.

## Wide-column databases

A **wide-column database** partitions rows by key across many nodes, and each row can have a sparse, flexible set of columns. These systems are designed for **very large distributed datasets** and high write volumes. The price is that you design tables around **predictable access paths** decided in advance, typically one table per query shape, rather than running arbitrary ad hoc queries.

## Graph databases

A **graph database** stores **vertices** (things) and **edges** (relationships between them) as first-class data. Edges can carry properties, such as when two people became friends. Its strength is **multi-hop traversal**: "friends of friends who like this band" or "every service that depends on this library, directly or indirectly". In a relational database, each hop is another join; in a graph database, following edges is the primary access pattern.

## Eventual consistency

Many distributed databases, and many derived copies of data, offer **eventual consistency**. After a write, replicas or derived views may temporarily disagree, one showing the new value and another the old. The guarantee is that they **converge**: if updates stop and the nodes can communicate, they eventually agree.

Eventual consistency buys availability and low latency, especially across regions, at the cost of stale reads. Applications must tolerate seeing slightly outdated data.

## Materialized views

A regular view is a saved query that runs every time you read it. A **materialized view** stores the query's output, so repeated reads avoid recomputing the full query. That is valuable for expensive aggregations such as dashboards and reports.

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS day, SUM(total) AS revenue
FROM orders
GROUP BY 1;

REFRESH MATERIALIZED VIEW daily_revenue;
```

The trade-off is freshness. The stored result goes stale as the underlying data changes, and **refresh logic**, on a schedule or triggered, must keep it acceptably current.

## Change data capture

Other systems often need to know when data changes: a search index, a cache, an analytics warehouse. Having the application send an event after every write is error-prone, since it is easy to forget one, and a crash between the write and the send loses the event.

**Change data capture (CDC)** reads the database's own record of committed changes, usually its replication log, and emits a stream of row-level changes. Downstream systems react to that stream, and the application does not have to write a separate event for every mutation.

## The outbox pattern

Sometimes the application does need to publish a meaningful domain event, like "order placed", to a message broker. Doing it naively has a **dual-write problem**: if the database commit succeeds and the publish fails, or the reverse, the two disagree.

The **outbox pattern** solves this with a transaction the application already trusts:

1. In **one database transaction**, write the domain change and insert a message record into an `outbox` table.
2. A separate **publisher** reads the outbox, sends each message to the broker, and then marks the record as sent or deletes it.

```sql
BEGIN;
INSERT INTO orders (id, customer_id, total) VALUES (1842, 42, 59.90);
INSERT INTO outbox (id, topic, payload)
VALUES (gen_random_uuid(), 'order-placed', '{"orderId": 1842}');
COMMIT;
```

Either both rows commit or neither does. If the publisher crashes after sending but before marking, it sends again, so delivery is at least once and consumers should handle duplicates. The publisher can poll the table or use CDC on it.

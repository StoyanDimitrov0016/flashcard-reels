# How the optimizer chooses a plan

You have created an index, the query filters on the indexed column, and the database still reads the whole table. Is it broken? Usually not. SQL is declarative: you describe the result, and the database decides how to compute it. That decision is made by the query optimizer, and it is based on estimates of how much work each strategy would take. Understanding those estimates explains most of the database's "strange" choices, and tells you what to do when they really are wrong.

## Execution plans

A **query execution plan** is the database's chosen strategy for running a statement. It is a tree of operators, each consuming rows from the operators below it:

- **access paths**: how each table is read, for example a sequential scan or an index scan;
- **join algorithms**: how rows from two inputs are matched;
- **sort** and **aggregate** steps;
- the **row counts** each operator is expected to produce, and, when the query was actually run, the counts it did produce.

In PostgreSQL, `EXPLAIN` shows the plan with estimates, and `EXPLAIN ANALYZE` runs the query and adds actual row counts and timings:

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
```

```text
Index Scan using orders_customer_id_idx on orders
    (cost=0.43..24.61 rows=18 width=64)
    (actual time=0.031..0.058 rows=21 loops=1)
  Index Cond: (customer_id = 42)
Planning Time: 0.110 ms
Execution Time: 0.081 ms
```

`rows=18` is the estimate; `rows=21` is what actually happened. `cost` is in abstract units the optimizer uses to compare plans, not milliseconds. Many different plans produce the same result; the optimizer's job is to pick the one with the lowest estimated cost.

## Statistics

To estimate cost, the optimizer needs to know how many rows each step will process. It cannot count them by running the query first, so it relies on **statistics**: summaries of data distributions and table sizes, collected ahead of time. In PostgreSQL they include:

- the number of rows and pages in each table;
- the fraction of nulls and the number of distinct values in each column;
- the **most common values** and their frequencies;
- a **histogram** of the remaining values, dividing them into buckets of equal population.

PostgreSQL gathers statistics with `ANALYZE`, which autovacuum runs automatically as data changes. Statistics are built from a sample and go stale between runs, so estimates are always approximations. After a large bulk load, running `ANALYZE` yourself avoids planning against an empty table's numbers.

## Selectivity

**Selectivity** describes how narrowly a predicate reduces rows: the fraction of the table it matches. The optimizer derives it from statistics.

On a 10-million-row `orders` table:

- `WHERE id = 123456` matches one row. It is **highly selective**.
- `WHERE customer_id = 42` might match 20 rows. Still highly selective.
- `WHERE status = 'paid'` might match 9 million rows, 90% of the table. It is barely selective at all.

Highly selective conditions benefit most from an index: the index narrows 10 million rows to a handful. A condition matching most of the table gains almost nothing from narrowing, and, as the next sections show, can even be slower through an index.

## Full table scans

A **full table scan** (in PostgreSQL, a **sequential scan**) reads the table, or all of its relevant storage pages, broadly from start to end, checking every row, instead of navigating through an index to a narrow subset.

Full scans have a bad reputation because they are the classic symptom of a missing index on a large table. If `SELECT * FROM orders WHERE customer_id = 42` scans 10 million rows to return 20, something is wrong.

## When a full scan is the right plan

Now consider `WHERE status = 'paid'`, matching 90% of the rows. Using an index means, for each of 9 million matching entries, following a pointer to a table row. Those rows are spread all over the table, so this is a stream of **random page reads**, and the same page may be visited many times.

A full scan reads each page exactly once, **sequentially**, which storage and the operating system handle very efficiently through read-ahead. When most rows are needed, reading everything in order is cheaper than millions of random lookups. The same holds for **small tables**: if the whole table fits in a few pages, reading it is faster than descending an index and then reading the table anyway.

The break-even point depends on the hardware and how the rows are laid out, but it is often a surprisingly small fraction of the table.

## Why the optimizer ignores an index

Put these pieces together and you have the answer to the opening question. The optimizer may ignore an available index because it **estimates that a table scan is cheaper**, especially for small tables or for predicates that match a large fraction of rows. That is the optimizer working correctly.

Other reasons are worth checking when the choice looks wrong:

- **Stale or misleading statistics** make the estimate wrong. Run `ANALYZE` and compare estimated and actual row counts.
- **The query cannot use the index.** Wrapping the column in a function (`WHERE lower(email) = ...` against an index on `email`), comparing against a mismatched type, or using a leading wildcard all prevent a normal B-tree from matching.
- **The index does not match the condition's columns**, as covered in the lesson on designing indexes.

## Common mistakes

- **Treating every sequential scan as a bug.** For small tables or broad predicates, it is the fastest plan.
- **Reading `EXPLAIN` without `ANALYZE`.** Estimates alone cannot show where the optimizer guessed wrong. (Remember that `EXPLAIN ANALYZE` really executes the statement; wrap data-modifying statements in a transaction you roll back.)
- **Forcing an index with hints before understanding the estimate.** Fix the statistics or the query first.

## Key points

- A query execution plan is the database's chosen strategy for a statement, including access paths, join algorithms, sort steps, and estimated or actual row counts.
- Statistics summarize data distributions and table sizes so the optimizer can estimate how many rows operators will process.
- Selectivity describes how narrowly a predicate reduces rows; highly selective conditions benefit more from an index.
- A full table scan reads the table or its relevant pages broadly instead of navigating an index to a narrow subset.
- When most rows are needed, sequentially reading the table can be cheaper than many random index lookups.
- The optimizer may ignore an available index when it estimates a table scan is cheaper, especially for small tables or broad predicates.

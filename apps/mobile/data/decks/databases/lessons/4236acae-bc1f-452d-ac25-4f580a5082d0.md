# Databases in application code

Many database problems start in the application, not the database. How code opens connections, issues queries, pages through results, and generates identifiers decides a lot about performance and correctness. This lesson covers the patterns that come up most often.

## Connection pools

Opening a database connection is expensive: a network handshake, authentication, and memory for a new server session. Doing that on every request wastes time.

A **connection pool** keeps a set of open connections that requests borrow and return. Requests skip the setup cost, and the pool size also puts a **cap on concurrent database sessions**, protecting the database from a flood of connections.

It is tempting to think a bigger pool means more throughput. It does not. A database has a limited number of CPU cores and disks. With too many concurrent sessions, it spends resources on memory per session, **context switching**, and **lock contention**, while work queues up inside the database instead of in the application. An **oversized pool** can reduce throughput. A modest pool, with extra requests waiting briefly for a free connection, usually performs better.

## The N+1 query problem

Object-relational mappers make it easy to write code like this:

```text
orders = query("SELECT * FROM orders WHERE customer_id = 42")   -- 1 query
for order in orders:
    order.items = query("SELECT * FROM order_items WHERE order_id = ?", order.id)  -- N queries
```

That is the **N+1 query problem**: one query for a collection, then one additional query per item. With 200 orders, that is 201 round trips, each paying network latency. The fix is to fetch related data together, with a join or one batched query:

```sql
SELECT * FROM order_items WHERE order_id IN (101, 102, 103);
```

## Pagination

Showing results one page at a time is common, and there are two main approaches.

**Offset pagination** skips a number of rows:

```sql
SELECT * FROM posts ORDER BY id LIMIT 20 OFFSET 10000;
```

It is simple, and it allows jumping to page 500. But the database must still produce and discard the 10,000 skipped rows, so **large offsets get slower**. It is also unstable: if rows are inserted or deleted while a user pages, items shift between pages and are shown twice or skipped.

**Keyset pagination**, also called cursor or seek pagination, remembers the last sort key seen and asks for rows after it:

```sql
SELECT * FROM posts
WHERE id > 10020        -- last id from the previous page
ORDER BY id
LIMIT 20;
```

With an index on `id`, the database jumps straight to the right place, so every page costs about the same, and concurrent changes do not shift the page boundaries. The trade-off is that you cannot jump directly to an arbitrary page number. When sorting by a non-unique column, include a unique tie-breaker such as `id` in the key.

## Upserts

An **upsert** inserts a row if no conflicting key exists, or updates the existing row when a defined conflict occurs, as one atomic statement. It avoids the race in "check if it exists, then insert or update", where two requests can both see "missing" and both insert.

```sql
INSERT INTO page_views (page_id, views)
VALUES (7, 1)
ON CONFLICT (page_id)
DO UPDATE SET views = page_views.views + 1;
```

Syntax varies: PostgreSQL and SQLite use `ON CONFLICT`, MySQL uses `ON DUPLICATE KEY UPDATE`, and others use `MERGE`.

## Sequences

A **sequence** is a database object that generates ordered numeric values, independently of any table's rows. It is commonly used to produce surrogate identifiers, often behind an auto-increment or identity column. Sequence values are handed out without waiting for transactions to finish, so a rolled-back insert leaves a gap. Expect gaps; do not rely on sequences being gapless.

## Surrogate and natural keys

Every table needs a primary key, and there are two kinds of choice.

A **surrogate key** is an artificial identifier with no meaning in the domain, such as an auto-increment integer or a UUID. It never needs to change, because nothing in the real world depends on it.

A **natural key** uses domain data that is already unique, such as a stable external code like an ISO country code. It avoids an extra column, but real-world identifiers that seem stable, such as email addresses or product codes, often turn out to change or to repeat. Many designs use a surrogate primary key and enforce the natural key with a unique constraint.

## UUID primary keys

UUIDs are popular surrogate keys because any service or client can **generate one without asking the database**, which helps in distributed systems and offline apps.

They have costs. A UUID is 16 bytes, twice a `BIGINT` and four times a 32-bit integer, and every index that references the key grows accordingly. Fully random UUIDs, such as version 4, also land at random positions in a B-tree index, so inserts touch pages all over it and **index locality** suffers. Time-ordered variants such as UUID version 7 put new keys near each other, recovering most of that locality.

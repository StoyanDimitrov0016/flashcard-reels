# Primary keys

If two rows in `customers` look identical, which one does an order belong to? Which one should an update change? A table needs a reliable way to point at exactly one row, and other tables need a stable value they can store to refer to it. That is the job of a primary key, and choosing what goes into it is one of the first real design decisions in any schema.

## What a primary key is

A **primary key** is a column, or a set of columns, whose value uniquely identifies each row in a table. The database enforces two things about it: no two rows may share the same key value, and no part of the key may be null. A table has at most one primary key.

```sql
CREATE TABLE countries (
  code CHAR(2) PRIMARY KEY,   -- 'GB', 'US', 'DE'
  name TEXT NOT NULL
);

CREATE TABLE order_items (
  order_id   BIGINT NOT NULL,
  product_id BIGINT NOT NULL,
  quantity   INT    NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

In `order_items`, neither column is unique alone: one order has many products, and one product appears in many orders. The pair is unique, so the pair is the key. A key made of several columns is called a **composite key**.

Because the primary key is how other rows refer to this one, a good key is **unique**, **never null**, and **stable**: if a key value changes, every reference to it must change too.

## Natural keys

A **natural key** uses domain data that is already unique to identify a row, such as a stable external code. ISO country codes, currency codes like `EUR`, or airport codes like `LHR` are good natural keys: they are short, they are genuinely unique, and they rarely change.

Natural keys have an appeal: the key means something, and you do not need to join to another table to read it. The danger is that data which looks unique and stable often is not. Email addresses change. People share names. National ID numbers get reissued or are simply not available for everyone. Product codes get reorganized by a marketing team. When a natural key turns out to change, you must update it everywhere it is referenced.

## Surrogate keys

A **surrogate key** is an artificial identifier with no domain meaning, such as an auto-increment integer or a UUID. It exists only to identify the row:

```sql
CREATE TABLE customers (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name  TEXT NOT NULL
);
```

Because the value means nothing, nothing in the business can force it to change. A customer can change their email without touching any order that references them. The trade-off is that the real-world uniqueness rule, "no two customers share an email", no longer comes for free from the key. You still declare it, here with `UNIQUE` on `email`.

A common design is a surrogate primary key plus unique constraints on whatever natural identifiers the domain has.

## Sequences

Auto-incrementing integers come from a **sequence**: a database object that generates ordered numeric values independently of table rows. Each call hands out the next number:

```sql
CREATE SEQUENCE invoice_number_seq;
SELECT nextval('invoice_number_seq');  -- 1
SELECT nextval('invoice_number_seq');  -- 2
```

In PostgreSQL, `GENERATED ... AS IDENTITY` and the older `SERIAL` both create a sequence behind the scenes. Because the sequence is separate from the table, it works across concurrent transactions without them waiting on each other.

Two properties surprise people. First, sequences are not transactional: a value handed out to a transaction that later rolls back is not returned, so **gaps are normal**. Second, values are increasing in the order they were handed out, not necessarily in the order transactions commit. Never use a sequence where you need gap-free numbering, and do not treat ID order as exact commit order.

## UUID primary keys

A **UUID** is a 128-bit identifier, such as `3f1c9d2e-7b4a-4c8e-9a61-2d5e8f0b7c43`, designed so that independently generated values practically never collide. That gives UUID primary keys their main advantage: **decentralized ID generation**. An application server, a mobile client working offline, or a separate service can create an ID without asking the database for the next number, and records created in different places can later be merged without conflicts.

The costs:

- **Width.** A UUID takes 16 bytes, twice a `BIGINT` and four times an `INT`. Every index containing the key, and every foreign key that references it, grows accordingly.
- **Index locality.** Random UUIDs (version 4) spread new keys uniformly across the whole index. Instead of appending at the right edge of a B-tree, each insert lands on an arbitrary page, which means more pages must stay in memory and more page splits occur.

The locality problem has a well-known fix: a **time-ordered** variant such as UUID version 7, whose leading bits are a timestamp. New keys then arrive in roughly increasing order and insert near each other, like a sequence would, while keeping decentralized generation. The other fix is a storage strategy: keep a compact sequential key for the table's primary key and joins, and store the UUID in a separate uniquely indexed column used only as the public identifier.

## Key points

- A primary key is a column or column set whose value uniquely identifies each row in a table; it cannot be null.
- A natural key uses domain data that is already unique, such as a stable external code; it is risky when that data can change.
- A surrogate key is an artificial identifier with no domain meaning, such as an auto-increment integer or a UUID.
- A sequence generates ordered numeric values independently of table rows, commonly for surrogate identifiers; gaps are normal.
- UUID primary keys allow decentralized ID generation but are wider than small integers.
- Random UUIDs reduce index locality unless a time-ordered variant such as UUIDv7 or a locality-friendly storage strategy is used.

# Partitioning data

Replication copies all of the data to every node, which helps with reads and failures but not with size. When one table holds billions of rows, its indexes no longer fit in memory, maintenance takes hours, and deleting old data means deleting row by row. When the write volume exceeds what one server can handle, adding replicas does not help at all, because every replica must apply every write. The answer to both problems is to split the data itself into pieces, first within one server, then across many.

## Partitioning

**Partitioning** divides one logical table or dataset into separate physical subsets, called **partitions**, based on a rule. Queries still address the logical table; the database routes rows to the right partition. The three common rules:

- **Range**: each partition holds a range of values, such as one month of `created_at`. Natural for time-series data.
- **List**: each partition holds an explicit set of values, such as `region IN ('EU')`, `('US')`, `('APAC')`.
- **Hash**: a hash of the key decides the partition, spreading rows evenly when there is no natural range.

In PostgreSQL, declarative partitioning looks like this:

```sql
CREATE TABLE events (
  id         BIGINT      NOT NULL,
  account_id BIGINT      NOT NULL,
  created_at TIMESTAMPTZ NOT NULL,
  payload    JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE events_2026_09 PARTITION OF events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Each partition is a smaller table with smaller indexes. A big operational win is data lifecycle: removing a month of old events becomes `DROP TABLE events_2025_09` (or detaching the partition), which is instant, instead of a huge `DELETE` that generates masses of WAL and dead row versions.

## Partition pruning

Partitioning also speeds up queries, through **partition pruning**: if a query's predicate identifies which partitions can hold matching rows, the database **skips scanning the unrelated partitions** entirely.

```sql
EXPLAIN SELECT count(*) FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```text
Aggregate
  -> Seq Scan on events_2026_09 events
        Filter: ((created_at >= '2026-09-10') AND (created_at < '2026-09-11'))
```

Only the September partition appears in the plan; every other month was pruned. Pruning works only when the query filters on the **partition key**. A query on `events` filtered only by `account_id` must look in every partition, which can be slower than one unpartitioned table. Choose the partition key from how the data is actually queried.

## Horizontal sharding

Partitioning within one server still leaves all the data, and all the load, on that server. **Horizontal sharding** distributes rows across **separate database servers**, called **shards**, so that total storage and traffic can exceed the capacity of any single node. Each shard holds a subset of the rows of the same tables, and together they hold all of them.

```text
shard A: accounts    1 – 1,000,000    (+ their orders, events)
shard B: accounts    1,000,001 – 2,000,000
shard C: accounts    2,000,001 – 3,000,000
```

Sharding is powerful and expensive. Each shard is an independent database, so everything that used to be a single-server feature becomes a distributed problem: joins across shards, unique constraints across shards, transactions across shards, schema migrations on every shard, and rebalancing data when one shard grows too large. Systems such as Citus, Vitess, and many distributed SQL databases automate much of this, but the underlying costs remain. Sharding is usually the last scaling step, after indexing, caching, read replicas, and partitioning have run out.

(The term "horizontal" contrasts with **vertical partitioning**, which splits a table's columns, or whole tables, onto different stores.)

## Shard keys

A **shard key** is the column or columns that determine which shard stores a row. It also decides which requests can be answered by **one shard**: if the application knows the shard key of what it needs, it can go straight to the right node. If not, it must ask **every shard** and combine the results, a scatter-gather query that is only as fast as the slowest shard.

A good shard key:

- **Matches the dominant access pattern.** In a multi-tenant SaaS product, sharding by `tenant_id` keeps each tenant's users, orders, and events on one shard, so nearly every request touches a single node and joins stay local.
- **Spreads load evenly.** Many distinct values, with no single value receiving a large share of the traffic.
- **Avoids hotspots.** Sharding by creation date with range sharding sends every new write to the newest shard. Hashing the key spreads writes but gives up efficient range queries over that key.

Because moving data between shards is costly, the shard key is one of the hardest decisions to change later.

## Key points

- Partitioning divides a logical table or dataset into separate physical subsets based on a rule such as range, hash, or list.
- Partition pruning lets the database skip unrelated partitions when a query predicate identifies the relevant ones.
- Pruning works only when queries filter on the partition key.
- Horizontal sharding distributes rows across separate database servers so storage and traffic can exceed one node's capacity.
- A shard key determines which shard stores a row and often which node can answer a request without contacting every shard.

# Join algorithms

A join in SQL says what to match: orders with their customers, line items with their products. It says nothing about how. Behind every join in an execution plan sits one of three algorithms, each fast in some situations and painfully slow in others. The optimizer picks among them using its row estimates, which is why a bad estimate so often shows up as a bad join, and why comparing estimated with actual row counts is the first thing to do with a slow plan.

The examples join `orders` to `customers` on `orders.customer_id = customers.id`.

## Nested-loop join

A **nested-loop join** takes each row from one input, the **outer** side, and searches the other input, the **inner** side, for matches:

```text
for each row o in orders (outer):
    look up customers where id = o.customer_id (inner)
    emit each match
```

Its cost is roughly "outer rows × cost of one inner lookup". That makes it effective when the **outer side is small** and the **inner lookup is cheap**, typically an index lookup. Fetching 20 orders and their customers through the primary key index on `customers.id` is 20 quick index probes: nothing beats that.

The same algorithm is a disaster at scale without an index. If the inner lookup has to scan the whole inner table, 100,000 outer rows mean 100,000 scans. Nested loops are also the only algorithm that works for any join condition, including inequalities like `a.x < b.y`, which is why they appear even when they are slow.

## Hash join

A **hash join** works in two phases:

1. **Build**: read one input, usually the smaller, and put its rows into an in-memory **hash table** keyed on the join column.
2. **Probe**: read the other input row by row, hash its join value, and look up matches in the hash table.

```text
build:  hash table of customers keyed by id
probe:  for each row o in orders:
            find customers[o.customer_id] in the hash table
```

Each input is read only once, and each probe is a constant-time lookup, so a hash join handles **large equality joins** efficiently, with no index needed. Its limits: it only works for **equality** conditions, and the hash table needs memory. If the build side does not fit in the memory available (`work_mem` in PostgreSQL), the database splits the inputs into batches on disk, which is much slower.

## Merge join

A **merge join** walks two inputs that are **ordered by the join keys** and matches them as it advances, like merging two sorted lists:

```text
orders sorted by customer_id:   1, 1, 2, 5, 5, 7
customers sorted by id:         1, 2, 3, 5, 7
advance whichever side has the smaller key; emit rows when keys are equal
```

Each input is read once, in order, with no hash table. The catch is the sorted input: if both sides already come ordered, for example from B-tree index scans or from an earlier sort step, a merge join is very efficient and works well for huge inputs that would not fit in a hash table. If the database must sort both inputs first, that sort often costs more than a hash join would.

Merge joins are for equality joins and, in some databases, range-compatible conditions that can also be matched by advancing through sorted input. PostgreSQL's merge join supports equality conditions only.

## How the optimizer chooses

The choice depends mostly on how many rows each input will produce:

- **Few outer rows, indexed inner side**: nested loop.
- **Large inputs, equality condition, no useful order**: hash join.
- **Large inputs already sorted on the join key**: merge join.

Those row counts are estimates built from statistics. When the estimate is right, the choice is usually good. When it is wrong, the choice can be wrong by orders of magnitude.

## Estimated versus actual rows

This is why you inspect **actual row counts** in an execution plan. Large differences between estimated and actual rows explain poor choices: the wrong join algorithm, memory sized for far fewer rows, or an inefficient access path. Here is a typical case in PostgreSQL:

```text
Nested Loop  (rows=12) (actual rows=480210 loops=1)
  -> Seq Scan on orders  (rows=12) (actual rows=480210 loops=1)
        Filter: (status = 'pending' AND region = 'EU')
  -> Index Scan using customers_pkey on customers
        (rows=1) (actual rows=1 loops=480210)
        Index Cond: (id = orders.customer_id)
```

The optimizer expected 12 matching orders, so a nested loop with 12 index probes looked ideal. In reality 480,210 rows matched, and the inner index scan ran 480,210 times (`loops=480210`). With a correct estimate, the optimizer would likely have chosen a hash join over the two tables.

Why was the estimate so far off? By default PostgreSQL assumes conditions on different columns are independent, and multiplies their selectivities. If most pending orders happen to be in the EU, that assumption badly underestimates the matches. Fixes include refreshing statistics with `ANALYZE`, increasing the statistics target for a skewed column, or creating extended statistics on correlated columns (`CREATE STATISTICS ... ON status, region FROM orders`).

When reading a slow plan, go node by node and look for the first place where estimated and actual rows diverge by a large factor. Everything above that node was planned on bad information.

## Key points

- A nested-loop join searches the inner input for each row of the outer input; it is effective when the outer side is small and the inner lookup is cheap.
- A hash join builds a hash table from one input and probes it with rows from the other, making large equality joins efficient.
- A merge join walks two inputs ordered by the join keys and matches them as it advances, efficient when sorted input is available.
- The optimizer chooses a join algorithm from estimated row counts.
- Large differences between estimated and actual rows can explain wrong join algorithms, undersized memory, or inefficient access paths.

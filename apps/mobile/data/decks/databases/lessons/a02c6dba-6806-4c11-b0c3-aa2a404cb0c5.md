# Non-relational databases

The relational model is a superb default: flexible queries, strong constraints, and transactions. But it is not the best fit for every workload. Some data is naturally one nested object that is always read whole. Some workloads need nothing but blazing-fast lookups by key. Some datasets are so large they must be spread over hundreds of machines, and some questions are all about following relationships many steps deep. Non-relational databases, often grouped under "NoSQL", each optimize for one of these shapes by giving up some of what relational databases offer.

## Document databases

A **document database** stores **self-contained records**, usually JSON-like documents, and typically allows **flexible nested structures** and **document-level access patterns**. MongoDB, Couchbase, and Firestore are examples.

```json
{
  "_id": "order-981",
  "customerId": "cust-42",
  "status": "paid",
  "shippingAddress": { "city": "Berlin", "postcode": "10115" },
  "items": [
    { "sku": "LAMP-01", "name": "Desk lamp", "qty": 2, "price": 35.0 },
    { "sku": "BULB-60", "name": "LED bulb", "qty": 4, "price": 4.5 }
  ]
}
```

In a relational schema this order would span `orders`, `addresses`, and `order_items` tables, joined on every read. Here it is one record: one read fetches it, one write saves it, and in most document databases, a write to a single document is atomic. Documents in the same collection need not share the same fields, so adding a field requires no migration.

The trade-offs are the mirror image. Data shared between many documents, such as a product name, is either duplicated in each document (with all the update problems of denormalization) or referenced by ID and joined in application code or with limited join features. Constraints across documents are usually weak or absent. And "schemaless" really means the schema lives in the application code that reads the documents.

## When a document model fits

A document model is useful when data is **commonly read and written as one aggregate**, has **variable nested fields**, and needs **few cross-document relational constraints**. Good fits:

- a product catalog where each category has different attributes;
- user profiles and settings;
- content such as articles with nested sections and metadata;
- event payloads whose shape varies by type.

Poor fits are data with many-to-many relationships queried from several directions, such as students, courses, and enrollments, or data where integrity across records is essential, such as accounting. Note that relational databases also support documents: PostgreSQL's `JSONB` type with GIN indexes lets you store nested, flexible data in a column while keeping relational tables and constraints for the rest.

## Key-value databases

A **key-value database** retrieves a value by a **unique key**, and not much else. The value is opaque, or at most semi-structured; the database does not query inside it. Redis, Memcached, and DynamoDB (in its simplest use) are examples.

```text
SET session:9f2c  '{"userId": 42, "expires": "2026-09-26T12:00:00Z"}'
GET session:9f2c
```

That narrow interface favors **simple, low-latency access patterns**: sessions, caches, feature flags, rate-limit counters, shopping carts. Lookups by key are easy to make extremely fast and to distribute across many nodes by hashing the key. The limitation is equally clear: any question not phrased as "give me the value for this key" requires you to maintain your own secondary keys.

## Wide-column databases

A **wide-column database** partitions rows by a key across many nodes and supports **sparse or flexible columns**: each row can have different columns, and missing ones take no space. Apache Cassandra, ScyllaDB, HBase, and Google Bigtable are examples, designed for **large distributed datasets** and **predictable access paths**.

In Cassandra, the primary key has two parts: a **partition key**, which decides which nodes store the row, and **clustering columns**, which sort rows within the partition:

```sql
-- Cassandra Query Language (CQL)
CREATE TABLE sensor_readings (
  sensor_id  text,
  reading_at timestamp,
  value      double,
  PRIMARY KEY ((sensor_id), reading_at)
) WITH CLUSTERING ORDER BY (reading_at DESC);

SELECT * FROM sensor_readings WHERE sensor_id = 'sensor-17' LIMIT 100;
```

All readings of one sensor live together, sorted by time, so "latest 100 readings for this sensor" is a single fast read from one partition. Writes scale almost linearly by adding nodes. The design discipline is that you model tables **around your queries**: there are no joins, and queries that do not specify the partition key are discouraged or rejected. A new access pattern often means a new table holding the same data arranged differently.

## Graph databases

A **graph database** stores **vertices** (nodes, such as people or products) and **edges** (relationships, such as `FOLLOWS` or `PURCHASED`) as **first-class** stored objects, each able to carry properties. Neo4j and Amazon Neptune are examples.

Relational databases can store relationships too, in join tables, but every step through a relationship is another join, and queries that follow a variable number of steps are awkward. In a graph database, **multi-hop traversal** is the primary access pattern: from a vertex, the database follows its edges directly to neighbors.

```text
// Cypher (Neo4j): people followed by the people Ada follows
MATCH (a:Person {name: 'Ada'})-[:FOLLOWS]->()-[:FOLLOWS]->(fof)
WHERE fof <> a
RETURN DISTINCT fof.name;
```

Good fits include social networks, recommendation engines ("customers who bought this also bought"), fraud detection through chains of shared accounts and devices, and dependency or permission graphs.

## Choosing a model

Each of these models trades general-purpose querying for strength in one shape of workload, and many trade strong consistency for availability and scale, often offering eventual consistency by default. A sensible approach is to start relational, and to add a specialized store when a specific workload, measured, needs what it offers.

## Key points

- A document database stores self-contained JSON-like records with flexible nested structures and document-level access patterns.
- A document model fits data read and written as one aggregate, with variable nested fields and few cross-document relational constraints.
- A key-value store retrieves an opaque or semi-structured value by a unique key, favoring simple low-latency access patterns.
- A wide-column store partitions rows by key and supports sparse or flexible columns, designed for large distributed datasets and predictable access paths.
- A graph database stores vertices and edges as first-class relationships, making multi-hop traversal a primary access pattern.

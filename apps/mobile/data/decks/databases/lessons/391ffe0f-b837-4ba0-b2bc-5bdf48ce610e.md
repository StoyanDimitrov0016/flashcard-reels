# Query planning

Because SQL is declarative, every statement must be turned into concrete steps before it runs. The database's **optimizer** considers many possible strategies and picks the one it estimates is cheapest. Learning to read that choice is how you find out why a query is slow.

## Execution plans

A **query execution plan** is the database's chosen strategy for one statement. It is a tree of operators and shows:

- **access paths**: how each table is read, by a full scan or through an index
- **join algorithms**: how pairs of inputs are combined
- **sort and aggregate steps**
- **row counts**: estimated, and, when the query is actually run, the real numbers

Most databases expose this through an `EXPLAIN` command. Variants such as `EXPLAIN ANALYZE` execute the query and report actual timings and row counts next to the estimates.

```sql
EXPLAIN ANALYZE
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= '2026-09-01';
```

## Estimated versus actual rows

The optimizer chooses a plan based on how many rows it expects each step to produce. When those estimates are far from reality, its choices can be badly wrong. Expecting 10 rows but getting 2 million can lead to the wrong join algorithm, too little memory reserved for a sort or hash table so it spills to disk, or an index lookup repeated millions of times.

That is why **comparing estimated and actual row counts** is one of the most useful things to look for in a plan. The operator where the numbers diverge sharply is often where the problem starts.

## Statistics

The optimizer's estimates come from **statistics**: stored summaries of table sizes and data distributions, such as row counts, the number of distinct values in a column, the most common values, and histograms of value ranges. With them, the optimizer can guess how many rows `WHERE status = 'pending'` will match without running the query.

Statistics are gathered periodically, automatically or by a command such as `ANALYZE`. After a large data load or a big shift in the data, they can be stale, and refreshing them is often the first fix for a surprising plan.

## Full table scans

A **full table scan** reads the table, or all of its relevant storage pages, broadly, instead of navigating through an index to a narrow subset of rows.

A full scan is not automatically bad. When a query needs most of the rows, **reading the table sequentially can be cheaper** than performing many random index lookups. Sequential reads are fast, and each index lookup may cost a separate page read. The optimizer picks the scan when it estimates that crossover has been passed. A scan is a problem when the query needs only a few rows and no suitable index exists.

## Join algorithms

Databases have several ways to join two inputs, and each fits different situations.

**Nested-loop join.** For each row from the outer input, search the inner input for matches. This is effective when the outer side is small and each inner lookup is cheap, usually because the inner table has an index on the join key. With a large outer side and no index, it degrades into comparing every row with every row.

**Hash join.** Build a hash table from one input, usually the smaller, keyed on the join columns. Then read the other input and probe the hash table for each row. This makes large **equality joins** efficient and needs no index, but it only works for equality conditions and needs memory for the hash table.

**Merge join.** Walk two inputs that are both **sorted by the join keys**, advancing through them side by side and matching rows as they line up, much like merging two sorted lists. It is efficient for equality and range-compatible joins when sorted input is already available, for example from B-tree indexes. If the inputs must be sorted first, that sort adds cost.

A quick way to remember them:

1. Nested loop: small outer input plus a cheap indexed lookup.
2. Hash join: large, unsorted inputs joined on equality.
3. Merge join: inputs that are already sorted on the join key.

When a plan shows a nested-loop join over millions of outer rows, check the row estimates. The optimizer probably expected far fewer.

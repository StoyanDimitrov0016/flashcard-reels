# How indexes work

Without help, the only way to find the orders for customer 42 is to read every row in `orders` and check each one. On a thousand rows that is instant; on a hundred million it takes seconds or minutes, on every request. Indexes are the database's answer: extra structures, maintained alongside the table, that let it jump to the rows it needs. Different index structures answer different kinds of questions, and every one of them has a cost.

## What an index is

An **index** is an additional data structure that lets the database find matching rows without scanning every row. Think of the index at the back of a book: instead of reading every page for "replication", you look it up alphabetically and go straight to pages 212 and 318.

```sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);

SELECT * FROM orders WHERE customer_id = 42;   -- can now use the index
```

The index stores the indexed values, sorted or hashed, each with a pointer to where the matching row lives in the table. A lookup navigates the index to the matching entries, then fetches only those rows.

Indexes are not free. They take **storage**, sometimes as much as the table itself, and they add **write maintenance**.

## Why indexes slow writes

The table and its indexes must always agree. So every change to the table also changes the affected index structures:

- An **insert** adds an entry to every index on the table.
- A **delete** removes entries from every index (or marks them for later cleanup).
- An **update** of an indexed column removes the old entry and adds a new one. Updates that touch only unindexed columns can often avoid index work; PostgreSQL calls these heap-only tuple (HOT) updates.

Each of these is extra I/O and CPU. A table with eight indexes does roughly eight extra structure updates per inserted row. That is why you add indexes for real query needs rather than on every column.

## B-tree indexes

The default index in almost every relational database is the **B-tree**. It keeps keys **in sorted order** in a balanced tree of pages. Finding a key means descending from the root through a few levels of internal pages to a leaf; even with billions of keys, that is only a handful of page reads. The leaves are linked in order, so after finding a starting point the database can walk forward through neighboring keys.

Sorted order is what makes the B-tree so versatile. It supports:

- **Equality lookups**: `WHERE email = 'ada@example.com'`.
- **Range queries**: `WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'`, by finding the start and walking the leaves.
- **Ordered scans**: `ORDER BY created_at` can read the index in order instead of sorting.
- **Prefix matching**: on a multi-column index, conditions on the leading columns; on text, a pattern with a fixed prefix such as `LIKE 'lamp%'`.

## Hash indexes

A **hash index** applies a hash function to each key and stores entries in **buckets** by hash value. Looking up `WHERE session_token = 'abc123'` hashes the value and goes straight to its bucket, which makes equality lookups fast.

But hashing deliberately scatters neighboring values: `'abc123'` and `'abc124'` land in unrelated buckets. So a hash index generally cannot support ordered range scans, `ORDER BY`, or prefix matching. In PostgreSQL, hash indexes support only `=`, and since B-trees handle equality nearly as well, B-trees remain the usual choice. Hash structures are more prominent in in-memory stores and in hash joins.

## Where a B-tree cannot help: leading wildcards

Compare two text searches on a B-tree index over `products.name`:

```sql
SELECT * FROM products WHERE name LIKE 'lamp%';    -- starts with 'lamp'
SELECT * FROM products WHERE name LIKE '%lamp%';   -- contains 'lamp'
```

In sorted order, every name starting with `lamp` sits together: one **contiguous key range**, from `lamp` up to just before `lamq`. The B-tree can navigate to its start and walk to its end.

A **leading wildcard** removes that fixed prefix. Names containing `lamp`, such as `desk lamp` and `floor lamp stand`, are scattered all over the sorted order. There is no single range to navigate to, so the engine usually has to scan every entry. (In PostgreSQL, even the prefix form needs a suitable collation, such as `C`, or an index with the `text_pattern_ops` operator class to use a B-tree.) Searching inside text needs a different structure: trigram indexes (PostgreSQL's `pg_trgm`) for substring matching, or full-text search for words.

## Full-text search

Searching prose is not substring matching. A user searching for "running shoes" expects to find "shoes for runners", does not care about case, and wants the best matches first.

**Full-text search indexing** builds structures optimized for matching **words, phrases, and relevance** rather than ordinary scalar equality. Text is broken into **tokens** (words), normalized by lowercasing, removing very common words, and reducing words to a stem so that "running" and "runs" both become "run". Queries go through the same processing, and results can be ranked by how well they match.

In PostgreSQL:

```sql
CREATE INDEX articles_search_idx
  ON articles USING GIN (to_tsvector('english', body));

SELECT id, title
FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'running & shoes');
```

## Inverted indexes

The structure behind full-text search is the **inverted index**. A normal table maps each document to its words. An inverted index turns that around and maps each **term to the documents that contain it**:

```text
"databas"  -> 3, 8, 21
"index"    -> 3, 14
"replica"  -> 8, 21
```

(The terms are stems, which is why "database" appears as "databas".) A search starts from the query terms instead of from the documents. Searching for "index" and "database" looks up two short lists and intersects them, finding document 3, without reading any document that contains neither word. PostgreSQL's GIN index and search engines such as Elasticsearch and Lucene are built on this idea.

## Key points

- An index is an additional data structure that finds matching rows without scanning every row, at the cost of storage and write maintenance.
- Inserts, deletes, and indexed-column updates must also modify affected index structures, adding I/O and CPU work.
- A B-tree keeps keys ordered, supporting equality lookups, ranges, ordered scans, and prefix matching on composite keys.
- A hash index maps keys to buckets for fast equality lookup but generally cannot support ordered range scans.
- `LIKE '%term%'` is hard to index with a B-tree because a leading wildcard removes the fixed prefix that defines one contiguous key range.
- Full-text search indexing uses token or inverted indexes optimized for matching words, phrases, and relevance.
- An inverted index maps terms to the documents containing them, so search starts from terms instead of scanning documents.

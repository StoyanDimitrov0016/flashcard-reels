# Replication

A single database server is a single point of failure. When it goes down, the application goes down; when it is overloaded with reads, everything slows; and users on another continent pay for every round trip. Replication addresses all of these by keeping copies of the data on several servers. But copies take time to update, and the choices about how long to wait for them shape what the application can safely assume about the data it reads.

## What replication is

**Replication** keeps copies of database data on multiple nodes. It serves several goals:

- **Availability**: if one node fails, another with the same data can take over.
- **Read scaling**: read queries can be spread across several copies.
- **Locality**: a copy near the users serves their reads with lower latency.
- **Recovery**: a standby copy can be promoted much faster than a backup can be restored.

The most common arrangement is **leader-based** (primary-replica) replication. One node, the **primary** or leader, accepts all writes. It streams its changes, typically its write-ahead log or a logical description of changed rows, to one or more **replicas**, which apply them in the same order. In PostgreSQL, **streaming replication** ships the WAL itself.

The key design question is when the primary tells a client that a write has committed.

## Synchronous replication

With **synchronous replication**, a write waits until one or more replicas **confirm** the required level of persistence before the commit is acknowledged to the client.

```text
client -> primary: COMMIT
primary: flush WAL locally
primary -> replica: WAL records
replica: flush, reply "persisted"
primary -> client: committed
```

The benefit is **failover durability**: every acknowledged commit exists on at least two machines, so losing the primary loses no acknowledged data. The costs are **latency**, since every commit includes a round trip to the replica, and **availability**: if the synchronous replica is down or unreachable, commits stall until it returns or the configuration changes. Setups often wait for any one of several replicas to reduce that risk. In PostgreSQL this is configured with `synchronous_standby_names` and `synchronous_commit`.

## Asynchronous replication

With **asynchronous replication**, the primary acknowledges a write **before replicas have applied it**, and changes flow to replicas in the background.

Commits are as fast as on a single server, and a slow or failed replica never blocks writes. The cost: replicas lag behind, and if the primary fails before a recently acknowledged write has reached any replica, promoting a replica **loses that write**, even though the client was told it committed. Many production setups accept this small window in exchange for performance, or combine one synchronous replica with several asynchronous ones.

## Replication lag

**Replication lag** is the delay between a write becoming authoritative on one node, usually the primary, and another replica applying or exposing that write. Under normal load it is often milliseconds. It grows when the network is slow, when a replica is underpowered, or when the primary produces changes faster than a replica can apply them, such as during a large batch update, and it can reach seconds or minutes.

Lag should be monitored like any other health metric. In PostgreSQL, `pg_stat_replication` on the primary shows how far each replica has received and replayed the log.

## Read replicas

A **read replica** is a replicated node used to **serve read traffic**, reducing load on the write leader. Dashboards, reports, search pages, and other read-heavy work can go to replicas, leaving the primary's capacity for writes.

The price is consistency: a replica shows the data as of a moment ago, and different replicas may be at different moments. That is acceptable for many reads, such as a product catalog or an analytics dashboard, and dangerous for others.

## Read-your-writes

One consequence surprises users more than any other. A user updates their profile, the request goes to the primary, and the page reloads. The reload's read goes to a replica that has not yet received the update, and the user sees their old profile, as if the save failed. This violates **read-your-writes** consistency: the guarantee that a client always sees its own previous writes.

It happens because the client **wrote to the primary and immediately read from a lagging replica**. Common fixes:

- Read from the primary for data the user has just modified, for example for a few seconds after any write by that user.
- Track the log position of the user's last write and read only from replicas that have replayed at least that far.
- Route all of one user's reads for a session to the primary when correctness matters more than load.

## Eventual consistency

Asynchronous replicas illustrate a broader model. **Eventual consistency** means replicas or derived views may **temporarily disagree** after a write, but **converge** to the same value if updates stop and communication succeeds. It makes no promise about how long convergence takes, and in the meantime different readers may see different answers.

Eventual consistency is the model of async read replicas, of caches and search indexes fed from a database, and of many distributed databases designed for availability. It is a reasonable model for many features, as long as the application is designed for it, for example by handling read-your-writes explicitly as described above.

## Replication is not a backup

Replication makes a copy of your data on another machine, so it is tempting to count replicas as backups. They are not. Replication copies **every legitimate write** quickly, and it copies **accidental deletes and corruption** just as quickly. When someone runs `DROP TABLE orders` on the primary, every replica drops it within moments.

A backup preserves **recoverable historical state independent of the live replicas**: a copy from before the mistake, which the mistake cannot reach. Replication protects against losing a machine; backups and point-in-time recovery protect against losing the data. A serious setup has both.

## Key points

- Replication keeps copies of database data on multiple nodes for availability, read scaling, locality, or recovery.
- Synchronous replication waits for replicas to confirm persistence before acknowledging a commit, improving failover durability at the cost of latency and availability.
- Asynchronous replication acknowledges writes before replicas apply them, reducing latency but allowing lag and possible loss of recently acknowledged data during failover.
- Replication lag is the delay between a write becoming authoritative on one node and a replica applying or exposing it.
- A read replica serves read traffic to reduce load on the leader, accepting consistency and lag trade-offs.
- Reading from a lagging replica right after writing to the primary can violate read-your-writes behavior.
- Eventual consistency means replicas may temporarily disagree but converge if updates stop and communication succeeds.
- Replication copies accidental deletes and corruption too; a backup preserves historical state independent of the live replicas.

# Designing indexes

Knowing what an index is does not tell you which index to create. A single-column index on every filtered column is a common first instinct, and it often misses: the query filters on two columns and sorts by a third, or the index finds the rows but the database still visits the table for every one of them. Good indexes are designed for specific queries, and they are added because a measurement showed they were needed.

The examples use this table:

```sql
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT        NOT NULL,
  status      TEXT          NOT NULL,
  total       NUMERIC(12,2) NOT NULL,
  created_at  TIMESTAMPTZ   NOT NULL
);
```

## Composite indexes

A **composite index** (or multi-column index) stores several columns together, in a defined order:

```sql
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at);
```

Queries that use compatible **leading columns** can search or order efficiently with it. This one index serves a whole family of queries:

```sql
-- equality on the first column
SELECT * FROM orders WHERE customer_id = 42;

-- equality on the first, range on the second
SELECT * FROM orders
WHERE customer_id = 42 AND created_at >= '2026-01-01';

-- equality on the first, ordered by the second: no sort step needed
SELECT * FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;
```

The last query is where composite indexes shine. The database jumps to customer 42's entries, which are already ordered by `created_at`, reads the last ten, and stops.

## Why column order matters

A composite B-tree is sorted **first by the leading column, then by the next column** within each value of the first, and so on, like a phone book sorted by last name and then first name. The entries for `(customer_id, created_at)` look like this:

```text
(41, 2026-03-02)
(42, 2026-01-05)
(42, 2026-02-11)
(42, 2026-03-20)
(43, 2026-01-09)
```

For `WHERE customer_id = 42 AND created_at >= '2026-02-01'`, the matching entries are one contiguous run: navigate to `(42, 2026-02-01)` and read forward until the customer changes.

Now try `WHERE created_at >= '2026-02-01'` alone. Matching entries appear inside every customer's section, scattered through the whole index. With the leading column unconstrained, there is no single range to navigate to, so the database cannot use the index for direct range navigation. At best it scans the entire index; often it ignores it. (Some databases, including PostgreSQL 18, can "skip scan" by probing each distinct leading value, which helps only when the leading column has few distinct values.)

Practical rules for ordering columns:

1. Columns compared with **equality** usually go first.
2. A column used for a **range** or for **ordering** goes after the equality columns. Columns after the first range column cannot narrow the navigation further.
3. An index on `(a, b)` also serves queries on `a` alone, so it usually makes a separate index on `a` redundant. It does not serve queries on `b` alone.

## Covering indexes

Even after the index finds the matching entries, the database usually has to fetch each matching row from the table, because the query needs columns the index does not have. For many rows, those table visits are the bulk of the work.

A **covering index** contains **all the columns a query needs**, so the database may answer from the index alone without fetching the base table rows. In PostgreSQL, this appears in the plan as an **Index Only Scan**. You can add extra non-key columns with `INCLUDE`:

```sql
CREATE INDEX orders_customer_created_total_idx
  ON orders (customer_id, created_at) INCLUDE (total);

SELECT created_at, total
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC;
```

Every column the query reads, `customer_id`, `created_at`, and `total`, is in the index. `INCLUDE` columns are stored in the leaf entries but are not part of the sort order, so they make the index cover more queries without changing how it is searched.

Note the word "may". In PostgreSQL, an index-only scan still checks the table's visibility map to confirm each row is visible to the current transaction; on a table with many recent changes, it falls back to visiting the table for those pages. Regular vacuuming keeps index-only scans effective. And a covering index is wider, so it costs more storage and write work than a narrow one.

## Measure before you add an index

Every index speeds up some reads and slows down every write to the table. So an index should match a **real access pattern**, not be added speculatively "in case". Before adding one, measure:

- **The slow query itself**: its exact text, and how long it takes.
- **Its execution plan**: run `EXPLAIN ANALYZE`, and look at the access paths and where time is spent.
- **Row counts**: how many rows each step processes, and where estimated and actual counts diverge. A bad estimate may need `ANALYZE`, not a new index.
- **Frequency**: a query run a million times a day deserves more help than a nightly report.
- **Write cost**: how write-heavy the table is, and how many indexes it already has.

Then create the index, re-run `EXPLAIN ANALYZE`, and confirm the plan changed as expected. In PostgreSQL, `CREATE INDEX CONCURRENTLY` builds the index without blocking writes on a busy table. Periodically check for unused indexes (PostgreSQL's `pg_stat_user_indexes` shows how often each index is scanned) and drop the ones that cost writes without serving reads.

## Common mistakes

- **One single-column index per column.** Two separate indexes on `customer_id` and `created_at` rarely serve a query as well as one composite index on both.
- **Putting the range column first.** An index on `(created_at, customer_id)` cannot navigate directly to one customer's recent orders.
- **Duplicating a prefix.** An index on `(customer_id)` next to one on `(customer_id, created_at)` is usually redundant.
- **Indexing speculatively.** Unused indexes only slow writes and consume storage.

## Key points

- A composite index stores multiple columns in a defined order so queries using compatible leading columns can search or order efficiently.
- A composite B-tree is ordered first by the leading column, then later columns; queries that skip unconstrained leading columns usually cannot navigate it directly.
- Equality columns usually go first, followed by a range or ordering column.
- A covering index contains all columns a query needs, so the database may answer from the index without fetching base table rows.
- Before adding an index, measure the slow query, its plan, row counts, frequency, and write cost.
- An index should match a real access pattern rather than be added speculatively.

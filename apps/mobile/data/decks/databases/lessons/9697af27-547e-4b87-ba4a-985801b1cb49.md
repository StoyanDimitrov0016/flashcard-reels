# Databases in application code

Many database performance problems are not caused by the database at all. They come from how the application talks to it: opening a new connection for every request, sending hundreds of tiny queries where one would do, or paging through results in a way that gets slower on every page. These patterns are easy to write, especially through an ORM, and invisible in development with ten rows of test data. This lesson covers three of the most common ones and their fixes.

## Connection pools

Opening a database connection is expensive. It means a network handshake, often TLS negotiation, authentication, and on the server, setting up a session. In PostgreSQL, every connection is a separate server process with its own memory. Doing all of that for every web request can take longer than the query itself.

A **connection pool** keeps a set of open, reusable connections. A request borrows a connection, runs its queries, and returns it to the pool instead of closing it. The next request reuses it immediately.

A pool does a second, equally important job: it **caps the number of concurrent database sessions**. If the pool has 20 connections and 200 requests arrive at once, 20 run queries and the other 180 wait briefly in the application for a free connection. The database sees a steady 20 sessions, not a sudden 200.

Pools live in the application (for example HikariCP in Java, or the pool built into most drivers and ORMs) or in a separate proxy such as PgBouncer, which lets many application instances share a small number of real database connections.

## Why a bigger pool can be slower

It is tempting to think that more connections mean more throughput. Past a point, the opposite happens. The database has a fixed number of CPU cores and a fixed disk bandwidth. With far more active sessions than cores:

- each session uses **memory**, leaving less for caching data;
- the operating system spends more time **context switching** between processes;
- more transactions hold locks at once, so **lock contention** grows and transactions wait on each other;
- work piles up in **queues** inside the database instead of in the application.

The result is that throughput falls and latency rises, and every query gets slower together. A pool sized near a small multiple of the database's CPU cores often outperforms one ten times larger. Remember also that the limit is per database, not per application instance: 30 instances with a pool of 50 each can open 1,500 connections.

## The N+1 query problem

Consider showing a list of 50 orders with each customer's name:

```text
orders = query("SELECT * FROM orders ORDER BY created_at DESC LIMIT 50")
for order in orders:
    customer = query("SELECT * FROM customers WHERE id = ?", order.customer_id)
    render(order, customer.name)
```

That is **one** query for the list plus **one more per item**: 51 queries. This is the **N+1 query problem**. Each query may take only a millisecond on the server, but each is a network round trip, and 51 round trips add up. With 1,000 items, the page makes 1,001 queries. ORMs make this easy to write by accident: accessing `order.customer` looks like reading a field but silently runs a query (lazy loading).

The fix is to fetch the related data in one go, either **joined**:

```sql
SELECT o.id, o.total, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
ORDER BY o.created_at DESC
LIMIT 50;
```

or **batched**, with a second query for all needed customers at once:

```sql
SELECT id, name FROM customers WHERE id = ANY(?);   -- the 50 customer IDs
```

ORMs call this eager loading (`include`, `joinedload`, `select_related`, depending on the library). Query logs in development make N+1 patterns obvious: look for the same query repeated with different parameters.

## Offset pagination

The simplest way to page through results is `LIMIT` and `OFFSET`:

```sql
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 10000;     -- page 501
```

It is easy to implement and supports jumping to any page number. It has two trade-offs:

- **Growing cost.** The database cannot jump to row 10,000. It must produce the first 10,020 rows in order and **discard** 10,000 of them. Deep pages get slower and slower.
- **Instability.** If a new post is inserted while a user moves from page 1 to page 2, every row shifts down by one, and the last item of page 1 appears again at the top of page 2. A deletion shifts rows the other way, so an item is skipped entirely.

## Keyset pagination

**Keyset pagination** (also called cursor or seek pagination) fetches the next page using the **last seen sort key** instead of a count of rows to skip. The client remembers the last row it received and asks for rows after it:

```sql
-- first page
SELECT id, title FROM posts ORDER BY id LIMIT 20;

-- next page: last id seen was 8715
SELECT id, title FROM posts WHERE id > 8715 ORDER BY id LIMIT 20;
```

With an index on the sort key, the database navigates straight to the starting point and reads 20 entries, so page 500 costs the same as page 1. Inserts and deletes elsewhere do not shift the boundary, because it is anchored to a value, not a position.

When the sort key is not unique, add a tie-breaker and compare both columns together. PostgreSQL supports row-value comparison, which a composite index on `(created_at, id)` can serve:

```sql
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ('2026-09-20 10:15:00+00', 8715)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

The trade-off is that you can only move to the next or previous page, not jump to page 501, which suits infinite scrolling and API cursors well.

## Key points

- A connection pool keeps reusable connections so requests avoid repeatedly opening expensive connections, and it caps concurrent database sessions.
- An oversized pool can increase memory use, context switching, lock contention, and queued work, reducing throughput.
- The N+1 query problem runs one query for a collection and one more per item; batching or joining removes the extra round trips.
- Offset pagination must scan and discard skipped rows, and concurrent inserts or deletes can shift items between pages.
- Keyset pagination fetches the next page using the last seen sort key, such as `WHERE id > ?`, avoiding growing scan cost and instability.

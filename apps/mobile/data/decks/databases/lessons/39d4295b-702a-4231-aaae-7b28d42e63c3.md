# Replication and sharding

A single database server eventually runs into limits: it can fail, it can only serve so many reads, and it can only hold so much data. Two techniques push past those limits. **Replication** copies the same data to several nodes. **Partitioning** and **sharding** split data into pieces so no single node has to hold or serve all of it.

## Replication

**Replication** keeps copies of database data on multiple nodes. Teams use it for **availability** (a replica can take over if the primary fails), **read scaling** (replicas can serve queries), **locality** (a copy near users in another region), and **recovery**.

In the common setup, one node, the primary or leader, accepts writes and streams changes, often its write-ahead log, to replicas. The key question is when the primary tells the client that a write succeeded.

## Synchronous and asynchronous replication

With **synchronous replication**, a write waits until one or more replicas confirm they have persisted it before the commit is acknowledged. If the primary then dies, a confirmed replica already has every acknowledged write, so failover loses nothing. The price is **latency**, since every commit waits on the network and a replica, and **availability**: if the required replicas are down or slow, writes stall.

With **asynchronous replication**, the primary acknowledges writes before replicas apply them. Writes are faster and unaffected by slow replicas. But replicas fall behind, and if the primary fails before shipping its latest changes, a failover can **lose recently acknowledged writes**.

Many systems choose a middle ground, such as waiting for one synchronous replica while others stay asynchronous.

## Replication lag and read replicas

**Replication lag** is the delay between a write becoming authoritative on one node and another replica applying or exposing it. It is usually milliseconds, but it can grow to seconds or minutes under heavy load.

A **read replica** is a replica used to serve read traffic, taking load off the write leader. The trade-off is that its data can lag behind.

Lag breaks a guarantee users take for granted: **read-your-writes**. A user updates their profile, which goes to the primary, and the next page load reads from a replica that has not received the update yet. The old profile appears, and the user thinks the save failed. Common fixes include reading from the primary for a short time after a user writes, or routing a user's reads to a replica that has caught up to their last write.

## Partitioning

**Partitioning** divides one logical table or dataset into separate physical subsets according to a rule:

- **Range**: by value ranges, such as one partition per month of `created_at`.
- **Hash**: by a hash of a key, spreading rows evenly.
- **List**: by explicit values, such as one partition per region.

A major benefit is **partition pruning**. When a query's predicate identifies which partitions can contain matching rows, the database skips the rest entirely:

```sql
-- With monthly range partitions, only the September partition is scanned
SELECT COUNT(*) FROM events
WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01';
```

## Sharding

**Horizontal sharding** takes partitioning across machines. Rows are distributed across separate database servers, so total storage and traffic can exceed what any single node can handle.

The **shard key** decides which shard stores each row. A good shard key also lets the application send most requests to exactly one shard. If orders are sharded by `customer_id`, "show this customer's orders" goes to one node. A query that does not include the shard key, such as "all orders over 1000 today", must fan out to every shard and merge the results. Choosing the shard key means choosing which queries will be cheap.

## Distributed transactions

Things get harder when one operation must change data on several shards. A **distributed transaction** is one whose atomic outcome spans multiple independent nodes or resource managers, so they must coordinate to agree on commit or abort.

**Cross-shard transactions are expensive** because that coordination adds network round trips, which raise latency, and involves more machines, any of which can fail mid-transaction.

The classic protocol is **two-phase commit (2PC)**:

1. **Prepare**: a coordinator asks every participant to prepare. Each one makes its changes durable and votes yes or no, promising it can commit if asked.
2. **Commit**: if all vote yes, the coordinator tells everyone to commit; if any votes no, it tells everyone to abort.

This guarantees that participants **all commit or all abort**. Its weakness is blocking: a participant that voted yes cannot decide on its own. If the coordinator fails at that point, the participant must wait, holding locks, until the coordinator recovers. For this reason, many systems design their shard keys to keep most transactions on a single shard.

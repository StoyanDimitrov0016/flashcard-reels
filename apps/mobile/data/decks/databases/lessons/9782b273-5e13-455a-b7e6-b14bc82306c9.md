# Normalization

Imagine an orders spreadsheet where every row repeats the customer's name, email, and address. It is easy to read, but when a customer moves, you must find and fix every one of their rows. Miss one, and the data now contradicts itself: which address is right? Normalization is the discipline of arranging tables so that each fact is stored once, and denormalization is the deliberate, measured decision to break that rule for speed.

## Why duplication hurts

**Normalization** decomposes data into related tables so that each fact has a clear single home. It reduces unnecessary duplication and, more importantly, the **update anomalies** that duplication causes:

- **Update anomaly**: a fact stored in many rows must be changed in all of them, or the copies disagree.
- **Insert anomaly**: you cannot record one fact without inventing another, such as being unable to add a product until someone orders it.
- **Delete anomaly**: deleting one fact destroys another, such as losing a product's price when its last order is deleted.

The **normal forms** are a series of increasingly strict conditions that rule out specific kinds of redundancy. The first three cover almost everything you will meet in practice. Each builds on the previous one.

## First normal form

**First normal form (1NF)** requires each column to hold a single scalar value rather than a **repeating group** packed into one row. This table violates it:

```text
customers
 id | name | phones
----+------+---------------------------
  1 | Ada  | 555-0101, 555-0102
```

Finding the customer with phone 555-0102 means parsing strings, and a phone cannot have its own type or constraints. The same problem appears as columns `phone1`, `phone2`, `phone3`. The 1NF fix is a separate table with one row per phone:

```sql
CREATE TABLE customer_phones (
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  phone       TEXT   NOT NULL,
  PRIMARY KEY (customer_id, phone)
);
```

Now every value is addressable by row and column, and queries, indexes, and constraints work on it directly. (Modern databases do support array and JSON columns. They are reasonable for data you always read as a whole, but data you search, join, or constrain belongs in rows.)

## Second normal form

**Second normal form (2NF)** matters for tables with a **composite key**. It removes non-key columns that depend on only part of that key.

```text
order_items   key: (order_id, product_id)
 order_id | product_id | quantity | product_name
----------+------------+----------+-------------
       10 |        501 |        2 | Desk lamp
       11 |        501 |        1 | Desk lamp
```

`quantity` depends on the whole key: how many of this product are in this order. `product_name` depends only on `product_id`, so it repeats on every line that includes the product, and renaming the product means updating all of them. The fix moves it to where it belongs:

```sql
CREATE TABLE products (
  id   BIGINT PRIMARY KEY,
  name TEXT NOT NULL
);
-- order_items keeps (order_id, product_id, quantity)
```

A 1NF table whose only key is a single column automatically satisfies 2NF, because no column can depend on "part" of a one-column key.

## Third normal form

**Third normal form (3NF)** removes non-key columns that depend on other non-key columns rather than directly on the key. This chain is called a **transitive dependency**.

```text
employees   key: id
 id | name  | department_id | department_name
----+-------+---------------+----------------
  1 | Ada   |             7 | Research
  2 | Grace |             7 | Research
```

`department_name` depends on `department_id`, which depends on the employee. The name is a fact about the department, not the employee, so it moves to a `departments` table, and `employees` keeps only `department_id`.

A common summary of the three forms: every non-key column must depend on **the key** (1NF gives you a key to depend on), **the whole key** (2NF), and **nothing but the key** (3NF).

## Denormalization

A normalized schema answers some questions with many joins. If a product page needs data from eight tables on every request, or a dashboard recomputes totals over millions of rows, reads can become the bottleneck.

**Denormalization** intentionally duplicates or combines data to reduce read-time joins or computation. Examples: storing `order_total` on `orders` instead of summing its line items every time, or copying `customer_name` onto an order for display.

The cost moves to writes. Every copy must be updated whenever the source changes, in the same transaction or through some background process, and if that logic has a bug, the copies drift apart. You take on the consistency work that normalization gave you for free. Denormalize on purpose, for a measured read problem, and know which copy is the source of truth.

## Materialized views

A **materialized view** is a way to let the database manage one kind of denormalization. It stores the precomputed output of a query, so repeated reads avoid recomputing the full query:

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS day, SUM(total) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY 1;

-- later, to bring it up to date (PostgreSQL):
REFRESH MATERIALIZED VIEW daily_revenue;
```

Reading `daily_revenue` is as cheap as reading a small table. The trade-off is freshness: the stored result reflects the data as of the last refresh. **Refresh logic** keeps it acceptably current, whether a scheduled job, a refresh after each batch load, or, in some databases, incremental maintenance. In PostgreSQL, a plain refresh recomputes the whole query and blocks reads while it runs; `REFRESH MATERIALIZED VIEW CONCURRENTLY` avoids blocking readers but requires a unique index on the view.

An ordinary (non-materialized) view is different: it is just a stored query, re-run every time you select from it.

## Common mistakes

- **Normalizing only by instinct.** Ask of each column: does it depend on the whole key, and only on the key?
- **Denormalizing before measuring.** Joins on indexed keys are usually fast; duplicate data only for a real, observed problem.
- **Forgetting that a materialized view is stale.** It shows the data as of its last refresh, not now.

## Key points

- Normalization decomposes data into related tables so each fact has a clearer single home, reducing update anomalies and duplication.
- First normal form requires columns to hold scalar values rather than repeating groups inside one row.
- Second normal form, for tables with composite keys, removes non-key attributes that depend on only part of the key.
- Third normal form removes non-key attributes that depend on other non-key attributes rather than directly on the key.
- Denormalization intentionally duplicates or combines data to reduce read-time joins or computation, at the cost of write complexity and consistency work.
- A materialized view stores precomputed query output so reads avoid recomputing it, while refresh logic keeps the result acceptably current.

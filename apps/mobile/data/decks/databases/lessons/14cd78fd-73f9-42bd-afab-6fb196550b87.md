# Advanced queries

Filtering, grouping, and joining answer many questions, but some common ones do not fit. "Customers whose latest order is over 100." "Each customer's three most recent orders." "Every order next to its customer's average order value." Written with only the basic clauses, these turn into tangles of self-joins, or tempt you to pull data into application code. SQL has tools built for them: subqueries, common table expressions, and window functions.

The examples use the same `customers` and `orders` tables as the previous lessons.

## Subqueries

A **subquery** is a query nested inside another query. It can produce a single value, a list, or a whole table:

```sql
-- orders larger than the overall average
SELECT id, total
FROM orders
WHERE total > (SELECT AVG(total) FROM orders);
```

This inner query does not depend on the outer one. It can be computed once, and its result used for every row.

## Correlated subqueries

A **correlated subquery** references values from the outer query. Logically, it is evaluated once for each outer row, with that row's values plugged in:

```sql
-- orders larger than that customer's own average
SELECT o.id, o.customer_id, o.total
FROM orders AS o
WHERE o.total > (
  SELECT AVG(o2.total)
  FROM orders AS o2
  WHERE o2.customer_id = o.customer_id   -- refers to the outer row
);
```

A frequent use is `EXISTS`, which asks whether any matching row exists:

```sql
SELECT c.name
FROM customers AS c
WHERE EXISTS (
  SELECT 1 FROM orders AS o
  WHERE o.customer_id = c.id AND o.total > 100
);
```

"Evaluated per outer row" describes the meaning, not necessarily the execution. The optimizer is free to transform a correlated subquery, for example turning an `EXISTS` into a **semi-join** that processes both tables in one pass. Whether it can depends on the database and the query shape, so if a correlated subquery is slow, the execution plan tells you whether it really ran once per row.

## Common table expressions

A **common table expression** (CTE) gives a query expression a temporary name within one statement, using `WITH`:

```sql
WITH customer_totals AS (
  SELECT customer_id, SUM(total) AS spent
  FROM orders
  GROUP BY customer_id
)
SELECT c.name, t.spent
FROM customer_totals AS t
JOIN customers AS c ON c.id = t.customer_id
WHERE t.spent > 1000;
```

The CTE exists only while this statement runs. Its value is **composition**: a complicated query becomes a sequence of named, readable steps, and a step can be referenced more than once. This is exactly the tool for the row-multiplication problem from the joins lesson: aggregate payments in one CTE and shipments in another, then join the per-order results.

In older PostgreSQL versions, a CTE was always computed separately, which blocked some optimizations. Since PostgreSQL 12, a simple CTE referenced once is inlined into the main query like a subquery; `MATERIALIZED` and `NOT MATERIALIZED` let you choose explicitly.

CTEs also enable **recursive queries** with `WITH RECURSIVE`, where a CTE refers to itself. That is how SQL walks hierarchies such as an org chart or a category tree:

```sql
WITH RECURSIVE reports AS (
  SELECT id, name FROM employees WHERE id = 1          -- start: the CEO
  UNION ALL
  SELECT e.id, e.name
  FROM employees AS e
  JOIN reports AS r ON e.manager_id = r.id             -- step: their reports
)
SELECT * FROM reports;
```

## Window functions

Grouping collapses rows: `GROUP BY customer_id` returns one row per customer, and the individual orders are gone. Often you want the aggregate **and** the rows. A **window function** computes a value across a related set of rows, the **window**, while preserving one output row per input row:

```sql
SELECT id, customer_id, total,
       AVG(total) OVER (PARTITION BY customer_id) AS customer_avg
FROM orders;
```

```text
 id | customer_id | total | customer_avg
----+-------------+-------+-------------
 10 |           1 | 25.00 |       18.75
 11 |           1 | 12.50 |       18.75
 12 |           2 | 40.00 |       40.00
```

The `OVER` clause defines the window. `PARTITION BY` splits rows into independent groups, like `GROUP BY` but without collapsing them. `ORDER BY` inside `OVER` orders the rows within each partition, which enables running totals (`SUM(total) OVER (PARTITION BY customer_id ORDER BY created_at)`) and functions like `LAG` and `LEAD` that look at the previous or next row.

Window functions are computed after `WHERE`, `GROUP BY`, and `HAVING`, so they cannot be used in a `WHERE` clause directly. To filter on one, compute it in a subquery or CTE and filter outside.

## ROW_NUMBER

`ROW_NUMBER()` assigns sequential numbers, 1, 2, 3, and so on, within an ordered result or within each partition. It is the standard tool for three recurring problems:

- **Ranking**: number rows by some ordering.
- **Top-N per group**: keep the first N rows of each partition.
- **Deduplication**: number duplicate rows and keep only number 1.

Here is the "three most recent orders per customer" query:

```sql
WITH ranked AS (
  SELECT id, customer_id, created_at,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY created_at DESC, id DESC
         ) AS rn
  FROM orders
)
SELECT id, customer_id, created_at
FROM ranked
WHERE rn <= 3;
```

`ROW_NUMBER` never produces ties: two rows with the same `created_at` still get different numbers, chosen arbitrarily unless the `ORDER BY` breaks the tie, which is why `id` is included. Its relatives `RANK()` and `DENSE_RANK()` give tied rows the same number.

## Key points

- A correlated subquery references values from the outer query and may logically be evaluated for each outer row, though the optimizer can transform it.
- A CTE gives a query expression a temporary name within one statement, improving composition.
- `WITH RECURSIVE` lets a CTE refer to itself, enabling recursive queries over hierarchies.
- A window function computes a value across a related set of rows while preserving one output row per input row, unlike ordinary aggregation.
- `ROW_NUMBER()` assigns sequential numbers within an ordered result or partition, useful for ranking, deduplication, and top-N-per-group queries.

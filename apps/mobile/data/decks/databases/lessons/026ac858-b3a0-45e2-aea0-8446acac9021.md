# Transactions and isolation

Real operations rarely touch a single row. Moving money between accounts means subtracting from one balance and adding to another, and both changes must happen or neither. A **transaction** groups several database operations into one logical unit that either commits together or is rolled back, according to the guarantees the database provides.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

## ACID

Transaction guarantees are usually summarized as **ACID**.

- **Atomicity**: a transaction's changes are committed as a unit or not at all. If anything fails before commit, the database rolls back, and no caller ever sees a partially committed transaction.
- **Consistency**: a committed transaction leaves the database satisfying the constraints and invariants it enforces, such as foreign keys, unique constraints, and checks. The database can only protect rules it knows about; rules that live only in application code are the transaction's own responsibility.
- **Isolation**: concurrent transactions are prevented from observing or producing certain invalid interleavings. Exactly which ones depends on the selected isolation level.
- **Durability**: once the database acknowledges a commit, the change survives the failures its durability model covers, such as a process crash or power loss.

## Concurrency anomalies

When transactions run at the same time, their reads and writes interleave. Some interleavings produce results that could never happen if the transactions ran one after another. These are the classic **anomalies**.

**Dirty read.** A transaction reads data another transaction has written but not yet committed. If that other transaction rolls back, the reader has acted on data that never officially existed.

**Non-repeatable read.** A transaction reads the same row twice and gets different committed values, because another transaction updated and committed the row between the two reads.

**Phantom read.** A transaction repeats a query with a condition, such as `WHERE status = 'open'`, and gets a different set of matching rows. Another transaction has inserted, deleted, or changed rows so that they now qualify or no longer qualify. The individual rows did not change under the reader; the set did.

**Lost update.** Two transactions read the same value, each computes a new value from it, and both write. The second write overwrites the first, and the first change silently disappears:

```text
T1 reads stock = 10          T2 reads stock = 10
T1 writes stock = 9          T2 writes stock = 9
Result: 9, although two items were sold
```

Writing `SET stock = stock - 1` in a single statement, or locking the row when reading it, avoids this particular case.

## Isolation levels

A **transaction isolation level** chooses which effects of concurrent transactions may become visible, and therefore how much coordination the database performs to prevent anomalies. The SQL standard names four levels, from weakest to strongest:

1. **Read uncommitted**: dirty reads may occur.
2. **Read committed**: only committed data is visible, but non-repeatable reads and phantoms can occur. This is the default in many databases.
3. **Repeatable read**: rows read once will read the same again; phantoms are allowed by the standard, though many implementations prevent them too.
4. **Serializable**: the strongest level.

Real databases implement these differently, so check what your database's levels actually prevent.

## Serializable isolation

**Serializable** isolation aims for a simple promise: the outcome of committed concurrent transactions is **equivalent to some serial order**, as if they had run one at a time. Any anomaly that could not happen in a one-at-a-time execution is prevented. It does not promise a particular order, only that some valid order exists.

## The cost of stronger isolation

Stronger isolation is not free. To prevent more anomalies, the database must do more coordination: hold more locks for longer, track read and write dependencies, or abort transactions that would break the guarantee. Under workloads with many conflicting transactions, this means more **waiting, aborts, and retries**, and less concurrency.

Applications running at serializable isolation should expect some transactions to fail with a serialization error and be ready to retry them. Choosing an isolation level is a trade-off between correctness guarantees and throughput under contention.

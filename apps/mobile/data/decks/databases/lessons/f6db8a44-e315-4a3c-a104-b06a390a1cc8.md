# Defining and evolving a schema

A relational database does not accept just any data. Before the first row is stored, you tell it what tables exist, what each column holds, and which rules must always be true. That declaration is the schema. Getting it right matters twice: once when you choose column types that can represent your data correctly, and again every time the application changes and the schema has to change with it, often while the application is running.

## What a schema is

A **schema** defines the stored structures and rules of a database: tables, columns, data types, indexes, constraints, and the relationships between tables. It is written in SQL's data definition statements:

```sql
CREATE TABLE payments (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id    BIGINT        NOT NULL REFERENCES orders (id),
  amount      NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  currency    CHAR(3)       NOT NULL,
  paid_at     TIMESTAMPTZ   NOT NULL
);

CREATE INDEX payments_order_id_idx ON payments (order_id);
```

Every piece of this statement is part of the schema: the table and column names, the types, the primary key, the foreign key, the check constraint, and the separate index. (PostgreSQL also uses the word "schema" for a namespace that groups tables, such as `public`; this lesson means the structure itself.)

## Choosing column types

A column's data type decides which values it can hold and how they compare, sort, and do arithmetic. Most types are straightforward, but three kinds of data are regularly stored wrongly.

### Money

Binary floating-point types such as `REAL`, `DOUBLE PRECISION`, and `FLOAT` store numbers as binary fractions. Many ordinary decimal fractions, like 0.1, have no exact binary representation, so every such value carries a tiny error, and errors accumulate:

```sql
SELECT 0.1::float8 + 0.2::float8;    -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;  -- 0.3
```

For money, those errors break totals, reconciliations, and legally defined rounding rules. Store money in a **fixed-precision decimal** type such as `NUMERIC(12,2)`, or as **integer minor units**, for example cents in a `BIGINT`, and apply rounding explicitly where the business rules require it. Store the currency alongside the amount.

### Timestamps

Local wall-clock times are ambiguous. When daylight saving time ends, a local time such as 02:30 happens twice; when it begins, some local times never happen at all. A value like `2026-10-25 02:30` with no zone does not identify a single moment.

Give timestamps an **explicit time-zone strategy**. The usual one: store **instants** in a timezone-aware form, and convert to a local zone only at the boundaries, when accepting user input or displaying a value. In PostgreSQL, `TIMESTAMPTZ` (`timestamp with time zone`) is that form: it converts input to UTC and stores the instant, then renders it in the session's time zone. Plain `TIMESTAMP` stores a wall-clock reading with no zone at all.

An exception worth knowing: for future events defined in local time, such as "every day at 09:00 in Berlin", store the local time and the zone name, because the zone's rules may change before the event.

### Text and collation

Text columns have a **collation**: the rules for comparing and sorting text. Collation decides whether `'apple'` equals `'Apple'` (case sensitivity), whether `'e'` and `'é'` compare as equal, and where letters like `'ö'` or `'ch'` fall in sorted order for a given language. It affects `ORDER BY`, `=` comparisons, unique constraints, and which indexes a text comparison can use.

```sql
SELECT name FROM cities ORDER BY name COLLATE "sv-SE-x-icu";   -- Swedish ordering
```

Collations are set per database and can be overridden per column or per expression. Choose deliberately: changing a column's collation later means rebuilding its indexes.

## Migrations

Schemas change as the application grows: a new column, a new table, a missing index, a split of one column into two. A **schema migration** is a controlled change to database structure or data shape, applied in a known order so every environment evolves consistently.

In practice, migrations are files checked into version control, numbered or timestamped, and applied by a tool that records which ones have run:

```text
0001_create_customers.sql
0002_create_orders.sql
0003_add_orders_status.sql
```

Development, staging, and production all move through the same steps in the same order, so "it works on my machine" does not turn into a schema mismatch in production. Some migrations change data, not just structure, such as backfilling a new column from existing values.

## Backward-compatible migrations

During a deployment, old and new versions of the application often run at the same time: some servers have the new code, others still run the old code, and the migration has already been applied. If a migration renames a column that the old code still reads, the old servers start failing mid-rollout.

**Backward-compatible migrations** avoid this by making changes additive first, so both versions keep working while the rollout completes. Adding a nullable column or a new table is safe: the old code simply ignores it. Removing or renaming is not. A rename becomes a sequence of safe steps, often called **expand and contract**:

1. Add the new column.
2. Deploy code that writes to both columns, and backfill the new column from the old one.
3. Deploy code that reads from the new column.
4. Once no running version uses the old column, drop it in a later migration.

At every step, whichever application versions are running find the columns they expect.

## Common mistakes

- **Storing money as `FLOAT`.** Totals drift by fractions of a cent, and rounding cannot be made exact.
- **Storing local times without a zone.** Values around daylight-saving changes become ambiguous or impossible.
- **Destructive migrations in the same release as the code change.** Dropping or renaming a column before every old server is gone breaks the rollout.

## Key points

- A schema defines stored structures and rules such as tables, columns, data types, indexes, constraints, and relationships.
- Binary floating point cannot represent many decimal fractions exactly; store money as fixed-precision decimals or integer minor units.
- Local times can repeat or disappear around daylight-saving changes; store instants in a timezone-aware form and convert at the boundaries.
- Collation defines rules for comparing and sorting text, such as case sensitivity and locale-specific ordering.
- A schema migration is a controlled change to structure or data shape, applied in a known order so environments evolve consistently.
- Old and new application versions may run at the same time during deployment; additive, backward-compatible migrations keep both working.

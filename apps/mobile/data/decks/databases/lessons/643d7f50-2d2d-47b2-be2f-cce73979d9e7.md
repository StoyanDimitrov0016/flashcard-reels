# Integrity constraints

Every application has rules about its data. An email may belong to only one account. A quantity must be positive. An order must belong to a customer who exists. You can check these rules in application code, but then every service, script, and admin console that writes to the database must check them too, and must do it correctly even when two requests race each other. Constraints move these rules into the database, where every write has to pass through them.

## Unique constraints

A **unique constraint** prevents two rows from having the same value, or the same combination of values, in the constrained columns.

```sql
CREATE TABLE accounts (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email    TEXT NOT NULL UNIQUE,
  team_id  BIGINT NOT NULL,
  username TEXT NOT NULL,
  UNIQUE (team_id, username)
);
```

Here no two accounts can share an email, and within one team no two accounts can share a username, although different teams may reuse the same username.

Unique constraints are subject to the database's **null semantics**. In SQL, null means "unknown", and two unknowns are not considered equal. So in standard SQL and in PostgreSQL by default, a unique column may hold many nulls: none of them conflict. PostgreSQL 15 added `UNIQUE NULLS NOT DISTINCT` for when you want at most one null. Other databases differ, so check yours.

Unique constraints are also what makes check-then-insert logic safe. If two requests both check "is this email free?" and both see yes, only the constraint stops them from both inserting. The database enforces it with a unique index, so the second insert fails no matter how the requests interleave.

## Check constraints

A **check constraint** rejects any row whose values do not satisfy a declared Boolean condition:

```sql
CREATE TABLE order_items (
  order_id   BIGINT        NOT NULL,
  product_id BIGINT        NOT NULL,
  quantity   INT           NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(12,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);
```

An `INSERT` or `UPDATE` that would make `quantity` zero or negative fails. A check may compare columns of the same row, such as `CHECK (ends_at > starts_at)`, but it cannot look at other rows or other tables; rules like that need a unique constraint, a foreign key, or other mechanisms. One subtlety: a check passes when its condition is null, so combine it with `NOT NULL` when the column must have a value.

## Foreign keys

A **foreign key** is a constraint requiring the values in one table's columns to reference valid key values in another table, or to be null when the column allows it. The referenced columns must be a primary key or have a unique constraint.

```sql
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  coupon_id   BIGINT REFERENCES coupons (id)   -- nullable: an order may have no coupon
);
```

`customer_id` must match an existing `customers.id`. `coupon_id` must match an existing coupon or be null, meaning "no coupon". A foreign key can even point at its own table, as when `employees.manager_id` references `employees.id`.

## Referential integrity

The guarantee foreign keys provide is **referential integrity**: the database never stores a reference to a row that does not exist. That is enforced from both sides:

- Inserting or updating a referencing row fails if the referenced key does not exist.
- Updating or deleting a referenced row is controlled by the foreign key's **referential action**.

The actions say what should happen to referencing rows when the row they point at is deleted (`ON DELETE`) or its key is updated (`ON UPDATE`):

- `NO ACTION` or `RESTRICT` (the default is `NO ACTION`): reject the change while references exist.
- `CASCADE`: delete or update the referencing rows too.
- `SET NULL` or `SET DEFAULT`: clear the reference or reset it to the column default.

```sql
CREATE TABLE order_items (
  order_id BIGINT NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  product_id BIGINT NOT NULL REFERENCES products (id) ON DELETE RESTRICT,
  quantity INT NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, product_id)
);
```

Deleting an order deletes its line items, which make no sense alone. Deleting a product that appears on any order fails, because silently rewriting order history would be worse.

## Upserts

A common write needs both "insert" and "update": save this user's settings, creating the row if it is missing. Doing it as two statements (look up, then insert or update) has a race: two concurrent requests can both see "missing" and both try to insert.

An **upsert** solves this in one statement. It inserts a row when no conflicting key exists, or updates the existing row when a defined conflict occurs. The conflict is detected by a primary key or unique constraint. In PostgreSQL:

```sql
INSERT INTO user_settings (user_id, theme)
VALUES (42, 'dark')
ON CONFLICT (user_id)
DO UPDATE SET theme = EXCLUDED.theme;
```

`EXCLUDED` refers to the row that failed to insert. `ON CONFLICT DO NOTHING` is the variant that simply skips duplicates. Standard SQL has `MERGE` for similar work, and MySQL uses `INSERT ... ON DUPLICATE KEY UPDATE`.

## Common mistakes

- **Enforcing uniqueness only in code.** A "check first, then insert" test passes for two concurrent requests. Only a unique constraint closes the race.
- **Assuming `UNIQUE` means at most one null.** In PostgreSQL by default, many nulls are allowed.
- **Using `CASCADE` everywhere.** A cascading delete on the wrong relationship can wipe out data far from the row you meant to delete.

## Key points

- A unique constraint prevents two rows from having the same value or value combination in the constrained columns, subject to the database's null semantics.
- A check constraint rejects rows whose values do not satisfy a declared Boolean condition.
- A foreign key requires values in one table to reference valid key values in another table, or be null when allowed.
- Referential integrity prevents references to rows that do not exist.
- Referential actions such as `RESTRICT`, `CASCADE`, and `SET NULL` control what happens when referenced rows are updated or deleted.
- An upsert inserts a row when no conflicting key exists or updates the existing row when a defined conflict occurs.

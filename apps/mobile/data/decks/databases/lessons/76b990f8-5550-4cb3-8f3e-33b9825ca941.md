# Isolation levels

If transactions ran one at a time, concurrency bugs could not happen. But databases serve thousands of transactions at once, and making every one wait for the others would be far too slow. So databases let transactions overlap and offer a menu of isolation levels: how much interference you are willing to accept in exchange for concurrency. To choose well, you need to know the specific anomalies interference can cause.

In the timelines below, T1 and T2 are two concurrent transactions, and time runs downward.

## Dirty read

A **dirty read** happens when a transaction reads data written by another transaction that has **not committed** and may still roll back:

```text
T1: UPDATE accounts SET balance = 0 WHERE id = 1;
T2:                         SELECT balance FROM accounts WHERE id = 1;  -- sees 0
T1: ROLLBACK;
```

T2 acted on a balance of 0 that never officially existed. Nearly every database prevents dirty reads by default.

## Non-repeatable read

A **non-repeatable read** happens when a transaction reads the same row twice and sees a **different committed value**, because another transaction updated it between the reads:

```text
T1: SELECT price FROM products WHERE id = 7;     -- 100
T2: UPDATE products SET price = 120 WHERE id = 7; COMMIT;
T1: SELECT price FROM products WHERE id = 7;     -- 120
```

Nothing uncommitted was read, yet T1's view of the world shifted mid-transaction. A report that computes a subtotal in one query and a grand total in another can come out inconsistent.

## Phantom read

A **phantom read** happens when repeating a **predicate query** returns a different **set** of matching rows, because another transaction inserted, deleted, or changed rows so that they now match or no longer match:

```text
T1: SELECT COUNT(*) FROM orders WHERE status = 'open';   -- 5
T2: INSERT INTO orders (..., status) VALUES (..., 'open'); COMMIT;
T1: SELECT COUNT(*) FROM orders WHERE status = 'open';   -- 6
```

No row that T1 read changed. A new row, the "phantom", appeared in the result. Locking the rows you have read cannot prevent this, because the new row did not exist when you read.

## Lost update

A **lost update** happens when two transactions read the same value and both write updates derived from it, so one write overwrites the other's effect:

```text
T1: SELECT stock FROM products WHERE id = 7;      -- 10
T2: SELECT stock FROM products WHERE id = 7;      -- 10
T1: UPDATE products SET stock = 9 WHERE id = 7; COMMIT;
T2: UPDATE products SET stock = 9 WHERE id = 7; COMMIT;
-- two items sold, stock is 9 instead of 8
```

This read-modify-write pattern is everywhere in application code: counters, balances, inventory, editing a document. Ways to prevent it include doing the arithmetic in one statement (`SET stock = stock - 1`), locking the row when reading it (`SELECT ... FOR UPDATE`, covered in the next lesson), or using an isolation level that detects the conflict.

## Isolation levels

A **transaction isolation level** selects which effects of concurrent transactions may become visible, and so how much coordination the database performs to prevent anomalies. The SQL standard defines four levels by the anomalies they allow:

1. **Read uncommitted**: dirty reads are possible.
2. **Read committed**: every statement sees only committed data, but non-repeatable and phantom reads are possible.
3. **Repeatable read**: rows already read will read the same again; the standard still allows phantoms.
4. **Serializable**: none of these anomalies are possible.

Real databases implement these differently, so always check your own. In PostgreSQL:

- **Read committed** is the default. Each statement sees a fresh snapshot of committed data. Asking for read uncommitted gives you read committed.
- **Repeatable read** gives the whole transaction one snapshot taken at its first statement. That prevents non-repeatable reads and phantoms too. If two transactions try to update the same row, the second fails with a serialization error instead of losing the first update.
- **Serializable** adds detection of the remaining, subtler anomalies.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;
```

## Serializable isolation

**Serializable** isolation aims to guarantee that committed concurrent transactions have an outcome **equivalent to some serial execution order**: as if they had run one at a time, in some order. Any anomaly that cannot occur when transactions run one at a time is prevented.

That includes anomalies the other levels miss. The classic is **write skew**: a hospital requires at least one doctor on call. Two on-call doctors each check "is someone else on call?", both see yes, and both remove themselves, each updating a different row. No row was written twice, so repeatable read allows it, but no serial order produces zero doctors on call. Serializable prevents it.

Note what serializable does not promise: a particular order. It guarantees only that some valid serial order exists.

## The cost of stronger isolation

Stronger isolation is not free. To prevent more anomalies, the database must coordinate more: take more locks and hold them longer, or track which transactions read and wrote what, and **abort** transactions whose combination would be unsafe. Under conflicting workloads, this means more **locking**, **waiting**, **aborts**, and **retries**, and less concurrency.

PostgreSQL's serializable level, for example, does not block readers; it lets transactions proceed and aborts one with a serialization failure (SQLSTATE `40001`) when it detects a dangerous pattern. Applications that use repeatable read or serializable must be ready to **retry** such transactions from the start.

Choosing a level is a trade-off: the weakest level that still keeps your invariants correct, or the strongest level your workload's conflict rate can afford.

## Common mistakes

- **Assuming the default level is serializable.** It usually is read committed, which allows lost updates in read-modify-write code.
- **Relying on standard definitions.** Levels with the same name behave differently across databases.
- **Using a strong level without retry logic.** Serialization failures are expected, not exceptional.

## Key points

- A dirty read sees data written by another transaction that has not committed and may roll back.
- A non-repeatable read sees a different committed value when reading the same row twice.
- A phantom read returns a different set of matching rows when a predicate query is repeated.
- A lost update happens when two transactions read the same value and both write derived updates, so one overwrites the other.
- An isolation level selects which concurrent effects may become visible and how much coordination the database performs.
- Serializable isolation makes committed concurrent transactions equivalent to some serial execution order.
- Stronger isolation can increase locking, retries, aborts, or coordination, reducing concurrency under conflicting workloads.

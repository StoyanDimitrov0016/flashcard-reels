# Concurrency control

Isolation levels describe what transactions are allowed to see. Concurrency control is how the database, and your application, actually enforce it when two transactions want the same data. There are two basic attitudes: assume conflicts will happen and make transactions wait (pessimistic), or assume they are rare and check at the end (optimistic). Most modern databases also keep multiple versions of rows so that readers and writers rarely need to wait for each other at all. Each approach has a characteristic failure mode, and knowing them helps you write code that stays correct under load.

## Pessimistic concurrency control

**Pessimistic concurrency control** has transactions **acquire locks before accessing** data that could conflict. A competing operation that needs a conflicting lock **waits** until the holder commits or rolls back, instead of proceeding concurrently.

The classic example fixes the lost-update problem from the previous lesson:

```sql
BEGIN;
SELECT stock FROM products WHERE id = 7 FOR UPDATE;   -- lock the row
-- application checks stock > 0
UPDATE products SET stock = stock - 1 WHERE id = 7;
COMMIT;                                                -- lock released
```

A second transaction running the same `SELECT ... FOR UPDATE` on product 7 blocks at that line until the first commits, and then reads the updated stock. The read-modify-write sequences are forced to run one after the other. The cost is waiting: while one transaction holds the lock, everyone who needs it queues.

## Row locks

A **row lock** restricts conflicting operations on the selected rows while leaving unrelated rows concurrently accessible. Locking product 7 does not stop anyone from buying product 8. This fine granularity is what lets a busy database handle many writers at once; locking whole tables would serialize them.

Every `UPDATE` and `DELETE` takes row locks on the rows it changes, held until the transaction ends, so two transactions can never modify the same row at the same time. `SELECT ... FOR UPDATE` takes the same kind of lock explicitly, for rows you intend to modify later. In PostgreSQL, weaker variants exist, such as `FOR SHARE`, which blocks writers but lets other `FOR SHARE` readers in. `SKIP LOCKED` lets a query skip rows locked by others, which is useful for job queues where each worker should take a different row.

## Deadlocks

Locks introduce a new failure. A **deadlock** happens when transactions wait **cyclically** for locks held by one another, so none can proceed:

```text
T1: UPDATE accounts SET ... WHERE id = 1;    -- T1 locks row 1
T2: UPDATE accounts SET ... WHERE id = 2;    -- T2 locks row 2
T1: UPDATE accounts SET ... WHERE id = 2;    -- T1 waits for T2
T2: UPDATE accounts SET ... WHERE id = 1;    -- T2 waits for T1: cycle
```

Neither can ever finish on its own. The database typically **detects the cycle** and **aborts one transaction**, the deadlock victim, releasing its locks so the other can continue. In PostgreSQL, a waiting transaction checks for a cycle after `deadlock_timeout` (one second by default), and the victim receives a deadlock error (SQLSTATE `40P01`).

## Reducing deadlocks

Deadlocks cannot be ruled out entirely in a busy system, but they can be made rare and harmless:

- **Keep transactions short.** Fewer locks, held for less time, give cycles less chance to form. Never hold a transaction open across a network call or user interaction.
- **Access shared resources in a consistent order.** The example above deadlocks only because T1 and T2 lock rows 1 and 2 in opposite orders. If every transfer locks the lower account ID first, the cycle cannot form.
- **Use appropriate indexes.** Without an index, an `UPDATE ... WHERE email = ...` may have to scan and examine many rows, and some databases lock more than the target row in the process, widening contention.
- **Retry deadlock victims.** Being chosen as a victim is an expected outcome; the application should catch the error and rerun the whole transaction.

## Optimistic concurrency control

**Optimistic concurrency control** takes the opposite bet. Transactions proceed **without locking** every potential conflict, then **validate** before commit that nothing they depended on changed. If a conflict is detected, the transaction is **aborted or retried**.

Applications often implement it with a version column:

```sql
-- read
SELECT id, title, body, version FROM documents WHERE id = 5;   -- version = 3

-- later, write only if nobody else has written in between
UPDATE documents
SET body = 'new text', version = version + 1
WHERE id = 5 AND version = 3;
```

If the update affects one row, the write succeeded. If it affects zero rows, someone else changed the document first; the application reloads and retries, or asks the user to merge. No lock is held while the user edits, which could take minutes.

Databases use the same idea internally: PostgreSQL's serializable isolation tracks dependencies and aborts at conflict time rather than blocking. Optimistic control works best when conflicts are rare. When they are frequent, repeated aborts and retries waste more work than waiting would have.

## MVCC

Locks make writers wait for writers, but readers would also have to wait for writers if there were only one copy of each row. **Multi-version concurrency control** (MVCC) avoids that by keeping **multiple versions of each row**. An update does not overwrite the row in place; it creates a newer version and marks the old one as superseded, tagged with which transactions can see each.

Each transaction or statement reads from a **consistent snapshot**: it sees the versions that were committed when its snapshot was taken and ignores newer ones. So a long report can read while writers keep creating newer versions, and **readers do not block writers, and writers do not block readers**. Writers still block writers on the same row. PostgreSQL, Oracle, MySQL's InnoDB, and SQL Server's snapshot modes all use forms of MVCC, and it is what makes snapshot-based repeatable read possible.

## The cost of MVCC

Old versions do not disappear on their own. A superseded version must be kept as long as **any active snapshot might still need it**, and only then can it be removed. Until cleanup happens, dead versions consume storage and make scans read more pages, which is called **bloat**.

Databases therefore need **cleanup maintenance**. In PostgreSQL this is **VACUUM**, run automatically by autovacuum, which marks space from dead row versions as reusable. InnoDB stores old versions in undo logs and purges them in the background. One long-running transaction, even an idle one left open by a forgotten session, holds back cleanup for the whole database while it lives, so bloat grows. Monitoring for long-running transactions is a basic operational habit for MVCC databases.

## Key points

- Pessimistic concurrency control acquires locks before accessing conflicting data, so competing operations wait.
- A row lock restricts conflicting operations on selected rows while unrelated rows remain concurrently accessible.
- A deadlock is a cycle of transactions waiting for each other's locks; the database typically detects it and aborts one transaction.
- Reduce deadlocks with short transactions, a consistent access order, appropriate indexes, and retries of deadlock victims.
- Optimistic concurrency control proceeds without locking and validates versions or dependencies before commit, aborting or retrying on conflict.
- MVCC keeps multiple row versions so readers see a consistent snapshot while writers create newer versions, reducing read-write blocking.
- Old MVCC versions consume storage until no active snapshot needs them, requiring cleanup such as vacuum and creating possible bloat.

# Practical details

Some of the most expensive database mistakes are small ones: the wrong type for money, a timestamp without a time zone, a search that cannot use an index, a backup that turns out not to exist. This lesson collects practical details that are easy to get wrong and costly to fix later.

## Money and floating point

Binary floating-point types such as `FLOAT` and `DOUBLE` store numbers as binary fractions. Many ordinary decimal values, like 0.10, **cannot be represented exactly** in binary, so tiny errors appear and accumulate:

```text
0.1 + 0.2 = 0.30000000000000004
```

For money, those errors break totals and rounding rules. Use a fixed-precision **decimal** type, such as `NUMERIC(12, 2)`, or store **integer minor units**, such as cents, and apply the required rounding rules explicitly.

## Timestamps and time zones

Local times are ambiguous. When daylight saving time ends, a local time such as 02:30 can happen twice; when it begins, some local times never happen at all. A column holding "2026-10-25 02:30" with no zone does not identify a single moment.

Give timestamps an **explicit time-zone strategy**. The usual approach is to store instants in a timezone-aware form, often normalized to UTC, and convert to a user's local zone at the boundaries, when displaying or accepting input. For future events defined by local wall-clock time, such as a meeting at 9:00 in Berlin, it is common to also keep the local time and the zone name, because time-zone rules can change before the event.

## Collation

A **collation** defines how text is compared and sorted. It decides whether `'apple'` equals `'Apple'`, whether accented and unaccented letters are treated as the same, and where letters like "ö" fall in sorted order in a given language. Collation affects `ORDER BY`, equality, unique constraints, and which indexes a text comparison can use, so choose it deliberately per database or column.

## Why LIKE with a leading wildcard is slow

A B-tree index on a text column keeps values in sorted order, which makes a **prefix** search efficient:

```sql
SELECT * FROM products WHERE name LIKE 'lamp%';   -- can use a B-tree range
SELECT * FROM products WHERE name LIKE '%lamp%';  -- usually cannot
```

`'lamp%'` means "values starting with lamp", which is one contiguous range in sorted order. A **leading wildcard** removes that fixed prefix. Matching values could be anywhere in the index, so the engine cannot navigate to a single key range and typically scans instead. Specialized indexes, such as trigram indexes or full-text search, handle this kind of query.

## Full-text search and inverted indexes

Searching prose is different from comparing scalar values. Users expect to find "running shoes" when the text says "shoes for runners", and to see the best matches first.

**Full-text search indexing** builds structures designed for this. Text is broken into **tokens**, normalized (for example lowercased and reduced to word stems), and indexed so the database can match words and phrases and rank results by **relevance**.

The core structure is the **inverted index**. Instead of mapping each document to its words, it maps each **term to the documents** that contain it:

```text
"database" -> doc 3, doc 8, doc 21
"index"    -> doc 3, doc 14
"replica"  -> doc 8
```

A search starts from the query terms and looks up their document lists directly, combining them for multi-word queries, instead of scanning every document.

## Backups

A **backup** is a separately recoverable copy of data, used to restore after accidental deletion, corruption, or loss of infrastructure. A backup has only proven its worth once it has been restored successfully, so test restores regularly.

**Replication is not a backup.** A replica copies every legitimate write quickly, and it copies mistakes just as quickly. If someone runs `DELETE FROM customers` without a `WHERE` clause, or a bug corrupts rows, every replica faithfully applies the damage within moments. A backup preserves **historical state independent of the live replicas**, so it still holds the data after the replicas have lost it.

## Point-in-time recovery

Daily backups alone would lose everything since the last one. **Point-in-time recovery (PITR)** combines a **base backup** with archived **write-ahead logs**. To recover, the database restores the base backup and replays the logs **up to a chosen moment**, such as one second before the bad `DELETE` ran. You recover almost everything, without the change that caused the damage.

## Measure before adding an index

When a query is slow, adding an index is tempting. But every index costs storage and slows every write, so it should answer a real need. Before adding one, measure:

- the **slow query** itself and how long it takes
- its **execution plan**, and where estimated and actual **row counts** diverge
- how **frequently** it runs, since a nightly report and a per-request query deserve different effort
- the **write cost** the new index would add to the table

An index should match a real, observed access pattern. Indexes added speculatively tend to cost more than they return.

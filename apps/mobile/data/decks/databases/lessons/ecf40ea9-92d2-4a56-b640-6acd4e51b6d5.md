# Writing SQL queries

**SQL** is the language relational databases use to define, query, and modify data. It is **declarative**: a query describes the result you want, not the steps to compute it. The database's optimizer decides how to produce that result, which index to use, which join algorithm to run, in what order. This lesson walks through the core parts of a query.

## SELECT, WHERE, and ORDER BY

`SELECT` produces a **result set**. It computes output expressions from one or more data sources and can optionally filter, join, group, and order rows along the way.

```sql
SELECT id, email
FROM customers
WHERE country = 'DE' AND created_at >= '2026-01-01'
ORDER BY created_at DESC, id;
```

A `WHERE` clause filters individual input rows using a Boolean condition. Rows for which the condition is not true are dropped before any grouping and before the output columns are computed.

`ORDER BY` requests a defined order for the result, by one or more expressions. This is the only thing that guarantees order. Without `ORDER BY`, a database may return rows in whatever order is convenient, and that order can change when data, indexes, or plans change. Even with `ORDER BY`, rows that tie on every sort expression can come back in any order, which is why the example adds `id` as a tie-breaker.

## Grouping and aggregates

`GROUP BY` partitions input rows into groups that share the same grouping values. Aggregate functions such as `COUNT`, `SUM`, and `AVG` then compute one result per group.

That creates two different places to filter:

- `WHERE` filters **rows before grouping**. It cannot refer to aggregates, because they do not exist yet.
- `HAVING` filters **groups after aggregation**, so it can test aggregate values.

```sql
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'paid'          -- rows
GROUP BY customer_id
HAVING COUNT(*) >= 5;          -- groups
```

## Joins

A join combines rows from two inputs.

- An **inner join** returns the row combinations where the join condition matches on both sides. Rows without a partner are dropped.
- A **left join** (left outer join) returns every row from the left side, plus matching right rows. When no right row matches, the right-side columns are filled with null.
- A **cross join** returns every combination of a left row with a right row, the Cartesian product. Ten rows crossed with ten rows gives a hundred.

```sql
SELECT c.email, o.id AS order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
```

Customers with no orders still appear, with a null `order_id`.

Joins can **multiply row counts** unexpectedly. The result contains one row per matching combination, so a customer with three orders appears three times. Joining that customer to both orders and addresses at once gives orders times addresses rows, and any `SUM` over the result will count values more than once. When totals look inflated, check whether a join matched more rows than you assumed.

## Subqueries and CTEs

A subquery is a query nested inside another. A **correlated subquery** refers to values from the outer query, so it is logically evaluated once for each outer row:

```sql
SELECT c.id, c.email
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 1000
);
```

"Logically" matters: the optimizer is free to rewrite it, for instance into a join, so it does not necessarily run row by row.

A **common table expression (CTE)** gives a query expression a temporary name for the duration of one statement, introduced with `WITH`. CTEs make long queries easier to build in named steps, and the `WITH RECURSIVE` form can walk hierarchies such as an org chart or a category tree.

```sql
WITH big_spenders AS (
  SELECT customer_id, SUM(total) AS spent
  FROM orders
  GROUP BY customer_id
  HAVING SUM(total) > 10000
)
SELECT c.email, b.spent
FROM big_spenders b
JOIN customers c ON c.id = b.customer_id;
```

## Window functions

Ordinary aggregation collapses each group into one row. A **window function** also computes over a set of related rows, but it keeps one output row per input row. The `OVER` clause defines the window: which rows to `PARTITION BY` and how to order them.

`ROW_NUMBER()` assigns sequential numbers within each ordered partition. That makes it the standard tool for ranking, for **deduplication** (keep row number 1, discard the rest), and for **top-N-per-group** queries, such as each customer's three most recent orders:

```sql
SELECT *
FROM (
  SELECT o.*,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY created_at DESC
         ) AS rn
  FROM orders o
) ranked
WHERE rn <= 3;
```

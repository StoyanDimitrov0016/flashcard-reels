# Concurrency and durability

Isolation levels describe what a database promises. This lesson looks at how it keeps those promises: how it coordinates transactions that touch the same data, and how it makes committed changes survive a crash.

## Optimistic and pessimistic concurrency

There are two broad strategies for handling conflicts.

**Pessimistic concurrency control** assumes conflicts are likely. A transaction acquires **locks** before touching data that others might change, and competing transactions wait until the lock is released. Conflicts are prevented up front, at the cost of waiting.

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- lock the row
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Optimistic concurrency control** assumes conflicts are rare. Transactions proceed without locking every possible conflict, then **validate before commit** by checking versions or tracked dependencies. If something they relied on has changed, the transaction is aborted or retried. Applications often use the same idea with a version column:

```sql
UPDATE documents
SET body = 'new text', version = version + 1
WHERE id = 7 AND version = 3;
-- 0 rows updated means someone else changed it first: reload and retry
```

Optimistic approaches shine when conflicts are rare; pessimistic ones avoid wasted work when conflicts are frequent.

## Row locks

Locks can cover different amounts of data. A **row lock** restricts conflicting operations on the selected rows only, while every other row in the table stays available. Two transactions updating different customers do not block each other; two transactions updating the same customer do.

## Deadlocks

Locks introduce a new failure. Suppose transaction A locks row 1 and then wants row 2, while transaction B has locked row 2 and wants row 1. Each waits for the other, forever. That cycle of transactions waiting on each other's locks is a **deadlock**.

Databases typically detect the cycle and break it by aborting one transaction, the **deadlock victim**, which receives an error. Applications can make deadlocks rarer and less harmful:

- Keep transactions **short**, so locks are held briefly.
- Access shared resources in a **consistent order**, for example always locking accounts in ascending id order, so cycles cannot form.
- Use appropriate **indexes**, so statements lock only the rows they need instead of scanning and locking many.
- **Retry** transactions chosen as deadlock victims, since the retry usually succeeds.

## MVCC

If readers had to lock rows, every long report would block writers, and every writer would block readers. **Multi-Version Concurrency Control (MVCC)** avoids most of this. Instead of overwriting a row in place, a writer creates a **new version**, and the old version stays around. Each reader sees a consistent **snapshot**: the versions that were committed when its snapshot was taken. Readers do not block writers, and writers do not block readers.

The cost is the old versions. They consume storage until no active snapshot could still need them. The database must then clean them up, through **vacuum**-style or purge maintenance. If cleanup falls behind, perhaps because a long-running transaction pins an old snapshot, tables and indexes grow with dead versions. This is known as **bloat**.

## The write-ahead log

Data lives in pages on disk, and a single transaction can modify pages scattered all over the files. Writing all of them safely before acknowledging every commit would be slow. Instead, databases use a **write-ahead log (WAL)**.

The rule is in the name: changes are recorded durably in the log **before** the modified data pages are considered safely persisted. A commit is acknowledged once its log records are on durable storage. The data pages themselves can be written later, in the background.

After a crash, the database replays the log to redo committed changes that had not yet reached the data files. The same log stream is often shipped to other servers for replication.

WAL improves write efficiency because **appending sequential log records** is much cheaper than synchronously writing many scattered data pages. The log turns random writes on the commit path into sequential ones.

## Checkpoints

If recovery had to replay the log from the very beginning, it would take longer every day. A **checkpoint** fixes this by advancing a known recovery point: the database flushes modified pages, or records enough state, so that everything before the checkpoint is known to be safely in the data files. Crash recovery then only needs to replay the log from the last checkpoint onward, and older log segments can be recycled or archived.

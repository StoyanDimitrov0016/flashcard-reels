# Distributed transactions

On one database server, atomicity is simple: one write-ahead log, one commit record, and the transaction either happened or it did not. Now move money between two accounts that live on different shards, or save an order in the database and publish an "order placed" event to a message broker. Two independent systems must agree on one outcome, and either can fail at any moment, including halfway through. This lesson covers what it takes to make that atomic, why it is expensive, and the patterns most systems use instead.

## What makes a transaction distributed

A **distributed transaction** is a transaction whose atomic outcome spans **multiple independent resource managers or nodes**: several database servers, several shards, or a database and a message broker. Each participant can commit or roll back its own part, but nothing inside any single participant knows what the others did. Making the whole thing atomic therefore **requires coordination** between them.

## Why cross-shard transactions are expensive

Inside one shard, a transaction is as cheap as on any single database. A transaction touching two shards is a distributed transaction, and it pays for coordination:

- **Latency**: extra network round trips between the participants and a coordinator, on top of each participant's own durable writes, before the transaction can commit.
- **Locks held longer**: each participant keeps its changed rows locked across those round trips, blocking other transactions.
- **More failure modes**: any participant, the coordinator, or the network between them can fail at any point, and every combination has to be handled correctly.

This is why sharded designs try hard to choose a shard key that keeps most transactions on a single shard.

## Two-phase commit

The classic coordination protocol is **two-phase commit** (2PC). It ensures that all participants either **all commit or all abort**. A coordinator drives two phases:

```text
Phase 1: prepare
  coordinator -> each participant: "prepare T"
  participant: make T's changes durable but not yet visible,
               promise it can commit, reply "yes" (or "no")

Phase 2: commit
  if every participant voted yes:
    coordinator durably records "commit T", tells everyone "commit"
  otherwise:
    coordinator tells everyone "abort"
```

The key move is the **prepare** vote. A participant that votes yes has written everything it needs to commit, even after a crash, and has given up the right to abort on its own. Once the coordinator records the decision, that decision is final. PostgreSQL exposes the participant side with `PREPARE TRANSACTION` and `COMMIT PREPARED`.

2PC's well-known weakness is **blocking**. A participant that has voted yes but not yet heard the decision cannot commit (others might have voted no) and cannot abort (the coordinator might have decided commit). If the coordinator fails at that point, the participant stays **in doubt**, holding its locks, until the coordinator recovers. Consensus-based systems reduce this problem by replicating the coordinator's decision, but the latency cost of coordination remains.

## The dual-write problem

A very common case is not two databases but a database and a message broker. After saving an order, the service must publish `OrderPlaced` for other services. Doing both directly is a **dual write**:

```text
1. INSERT order, COMMIT     -- succeeds
2. publish OrderPlaced      -- process crashes first: event lost
```

Publish first instead, and a failed commit leaves an event for an order that does not exist. Most brokers cannot take part in a 2PC with your database anyway.

## The outbox pattern

The **outbox pattern** avoids the distributed transaction by turning the message into data. The application commits its domain changes **and an outgoing message record** in **one local database transaction**:

```sql
BEGIN;
INSERT INTO orders (id, customer_id, total) VALUES (981, 42, 120.00);
INSERT INTO outbox (id, topic, payload)
VALUES (gen_random_uuid(), 'OrderPlaced', '{"orderId": 981, "total": 120.00}');
COMMIT;
```

Atomicity is now the ordinary single-database kind: either the order and its message both exist, or neither does. A separate **publisher** process later reads unsent outbox rows, sends each message to the broker, and then **marks the record as sent or deletes it**.

If the publisher crashes after sending but before marking, it sends the message again after restarting. So the outbox gives **at-least-once** delivery, and consumers must handle duplicates, typically by deduplicating on the message ID.

## Change data capture

The publisher can poll the outbox table, but there is a more general mechanism. **Change data capture** (CDC) emits a stream of **committed row or log changes** from a database, so downstream systems can react **without the application writing a separate event for every mutation**.

CDC tools read the database's own change log. In PostgreSQL that is **logical decoding** of the WAL; tools such as Debezium turn it into a stream of events like "row 981 inserted into `orders` with these values", published to a broker such as Kafka. Because the log contains only committed changes, in commit order, the stream reflects exactly what the database committed.

CDC is used to keep search indexes, caches, analytics warehouses, and other services in sync with the database. It also pairs naturally with the outbox: CDC can stream the `outbox` table itself, so every committed outbox row becomes a published message without a polling loop.

The difference between the two is intent. Raw CDC exposes table-level changes, so consumers become coupled to your schema. An outbox message is a deliberate, stable event contract. Many systems use CDC for data replication into other stores, and outbox events for communication between services.

## Key points

- A distributed transaction's atomic outcome spans multiple independent resource managers or nodes and therefore requires coordination.
- Cross-shard transactions are expensive because coordination across independent nodes adds latency and exposes the transaction to more failure modes.
- Two-phase commit coordinates participants so they all commit or all abort, but participants can remain blocked if the coordinator fails at certain points.
- The outbox pattern commits domain changes and an outgoing message record in one database transaction; a publisher later sends the message and marks or removes the record.
- Change data capture emits a stream of committed row or log changes so downstream systems can react without the application writing a separate event for every mutation.

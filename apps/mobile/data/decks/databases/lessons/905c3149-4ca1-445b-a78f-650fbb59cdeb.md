# Indexes

Without help, the only way to find the rows matching a condition is to look at every row. An **index** is an additional data structure, kept alongside the table, that lets the database jump to matching rows instead of scanning the whole table. It is the single most important tool for query performance, and it is not free.

## The cost of an index

An index takes storage, and it must stay in sync with the table. Every insert and delete must also update each index on the table, and an update to an indexed column must move the entry within that index. That is extra I/O and CPU on every write. A table with ten indexes pays for ten extra structures on each insert.

So indexes trade **faster reads for slower writes and more storage**. The goal is not to index everything, but to index what real queries need.

## B-tree indexes

The default index in most relational databases is a **B-tree**. It keeps keys in sorted order in a shallow, balanced tree, so the database can reach any key in a few page reads. Because the keys are ordered, a B-tree supports much more than exact matches:

- equality lookups, such as `WHERE email = 'a@example.com'`
- range queries, such as `WHERE created_at >= '2026-01-01'`
- ordered scans that satisfy `ORDER BY` without a separate sort
- prefix matching on the leading columns of a composite key

## Hash indexes

A **hash index** runs each key through a hash function to find its bucket. That makes equality lookups very fast. But hashing scatters neighboring values across unrelated buckets, so a hash index generally **cannot serve range scans or ordering**. It fits workloads that only ever ask "which row has exactly this key?"

## Composite indexes and column order

A **composite index** covers several columns in a defined order:

```sql
CREATE INDEX orders_customer_created_idx
  ON orders (customer_id, created_at);
```

The B-tree is sorted by the **leading column** first, and only then by the next column within each value of the first. Think of a phone book sorted by last name, then first name. Finding everyone named "Smith" is easy, and so is finding "Smith, Anna". Finding every "Anna" regardless of last name is not, because the Annas are scattered across the whole book.

The same applies here:

- `WHERE customer_id = 42` can use the index.
- `WHERE customer_id = 42 AND created_at > '2026-06-01'` can use it very well, navigating straight to one contiguous range.
- `WHERE created_at > '2026-06-01'` alone skips the unconstrained leading column, so the database usually cannot navigate directly to a range. It may scan the whole index or ignore it.

Choose column order to match the queries you actually run, typically equality columns first and range or sort columns after them.

## Covering indexes

Normally an index lookup finds a matching entry and then fetches the full row from the table to read the other columns. A **covering index** contains every column the query needs, so the database can answer from the index alone and skip fetching base table rows.

```sql
-- Answers "SELECT created_at, status FROM orders WHERE customer_id = ?"
CREATE INDEX orders_customer_cover_idx
  ON orders (customer_id, created_at, status);
```

Some databases can also attach non-key columns to an index for this purpose, for example with an `INCLUDE` clause.

## Selectivity

**Selectivity** describes how narrowly a condition reduces the rows. `WHERE id = 123` matches one row and is highly selective. `WHERE is_active = true` might match 95% of the table and is barely selective at all.

Indexes help most with highly selective conditions. When a predicate matches most of the table, using an index means performing a random lookup for almost every row, which can be slower than simply reading the table.

## When the index is ignored

That is why a database may **ignore an available index**. The optimizer estimates the cost of each plan, and it may decide a full table scan is cheaper. This is common for small tables, which fit in a few pages anyway, and for predicates that match a large fraction of the rows. An unused index is not necessarily a bug; it may be the optimizer making the right call. The next lesson looks at how to see and question those decisions.

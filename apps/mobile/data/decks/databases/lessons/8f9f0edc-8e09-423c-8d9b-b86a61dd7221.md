# Querying a single table

Most questions you ask a database start with one table: which orders are still open, how much each customer has spent, what the ten most recent signups are. Answering them well needs only a handful of clauses, but each clause runs at a specific point in the query's logic, and most confusing SQL results come from misunderstanding that order. This lesson builds a query clause by clause and shows where each one acts.

## The example table

```sql
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT        NOT NULL,
  status      TEXT          NOT NULL,   -- 'open', 'paid', 'cancelled'
  total       NUMERIC(12,2) NOT NULL,
  created_at  TIMESTAMPTZ   NOT NULL
);
```

## SELECT: producing a result set

`SELECT` produces a **result set** from expressions and data sources. In its simplest form it picks columns from a table:

```sql
SELECT id, total FROM orders;
```

The list after `SELECT` is not limited to column names. It can contain any expression, such as `total * 1.2 AS total_with_tax` or `upper(status)`, and `SELECT 1 + 1;` works with no table at all. Around that core, optional clauses filter, join, group, and order the rows. The result of every `SELECT` is itself a table of rows and columns, which is why queries can be nested and combined.

## WHERE: filtering rows

A `WHERE` clause filters **individual input rows** using a Boolean condition. Only rows for which the condition is true continue through the query:

```sql
SELECT id, total
FROM orders
WHERE status = 'open' AND total > 100;
```

Rows where the condition is false or **null** are both dropped. That matters with nullable columns: `WHERE discount <> 0` does not return rows where `discount` is null, because comparing null to anything yields null, not true. Use `IS NULL` or `IS NOT NULL` to test for null.

## GROUP BY: one result per group

`GROUP BY` partitions the input rows into groups that share the same values in the grouping expressions, so **aggregate functions** such as `COUNT`, `SUM`, `AVG`, `MIN`, and `MAX` can compute one result per group:

```sql
SELECT customer_id, COUNT(*) AS order_count, SUM(total) AS spent
FROM orders
WHERE status = 'paid'
GROUP BY customer_id;
```

The output has one row per customer. Because each output row stands for a whole group, the `SELECT` list may contain only the grouping expressions and aggregates. Selecting `created_at` here would be an error: a customer has many orders, so which date would the row show? (PostgreSQL allows other columns of a table when you group by its primary key, since they are then determined by it.)

Without `GROUP BY`, an aggregate treats the whole filtered input as one group: `SELECT COUNT(*) FROM orders` returns a single row.

## HAVING: filtering groups

Sometimes the condition you want depends on an aggregate: customers who spent more than 1,000. `WHERE` cannot express that, because `WHERE` runs on individual rows before any groups exist. `HAVING` filters **groups after aggregation**:

```sql
SELECT customer_id, SUM(total) AS spent
FROM orders
WHERE status = 'paid'            -- row filter: which orders count
GROUP BY customer_id
HAVING SUM(total) > 1000;        -- group filter: which customers qualify
```

The difference in one sentence: **`WHERE` filters rows before grouping; `HAVING` filters groups after aggregation.** A condition that does not involve an aggregate, like `status = 'paid'`, belongs in `WHERE`. It filters earlier and gives the database less work.

## ORDER BY: the only ordering guarantee

`ORDER BY` requests a defined result ordering by one or more expressions:

```sql
SELECT id, total, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

Here `id` breaks ties between orders created at the same instant, so the ordering is fully determined.

The important half of this clause is what happens without it: **without `ORDER BY`, row order is not guaranteed.** A table is a set of rows, not a list. Results often appear to come back in insertion order or primary key order, but that is an accident of the current execution plan. After an update, a parallel scan, a new index, or a different plan, the order can change without warning. If order matters, including for `LIMIT` and pagination, say so with `ORDER BY`.

## The logical order of evaluation

The clauses are written in one order but evaluated, logically, in another:

```text
FROM      choose the source rows
WHERE     keep rows that satisfy the condition
GROUP BY  form groups
HAVING    keep groups that satisfy the condition
SELECT    compute the output expressions
ORDER BY  sort the result
LIMIT     keep the first N rows
```

This explains several rules at once. `WHERE` cannot use aggregates, because groups do not exist yet. `WHERE` usually cannot refer to an alias defined in `SELECT`, because `SELECT` has not been computed yet. `ORDER BY` can use those aliases, because it runs after `SELECT`. The database may execute the steps in a different physical order, but it must return the result this logical order describes.

## Common mistakes

- **Relying on default row order.** It works in development and breaks later. Always use `ORDER BY` when order matters.
- **Putting an aggregate condition in `WHERE`.** `WHERE SUM(total) > 1000` is an error; use `HAVING`.
- **Putting row conditions in `HAVING`.** It works, but filters after grouping instead of before.
- **Comparing with null using `=`.** `WHERE col = NULL` never matches; use `IS NULL`.

## Key points

- `SELECT` produces a result set from expressions and data sources, optionally filtering, joining, grouping, and ordering rows.
- `WHERE` filters individual input rows with a Boolean condition, before grouping and projection.
- `GROUP BY` partitions input rows into groups so aggregate functions compute one result per group.
- `WHERE` filters rows before grouping; `HAVING` filters groups after aggregation.
- `ORDER BY` requests a defined result ordering; without it, row order is not guaranteed.

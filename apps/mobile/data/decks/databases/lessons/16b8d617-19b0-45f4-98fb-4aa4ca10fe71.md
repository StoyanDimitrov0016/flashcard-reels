# Relational modeling

A **database** is more than a place to put data. It is an organized system for storing and retrieving data that also enforces rules you choose: what shape the data must have, how concurrent users may change it, and how durable a change is once it is saved. This lesson covers how relational databases structure data and how that structure evolves safely.

## Tables, rows, and keys

A **relational database** stores data in **tables** made of rows and columns. Each column has a name and a data type. A **row** is one record: a single customer, a single order, holding a value for each of the table's columns.

Tables become useful together because rows can refer to rows in other tables through shared values, usually keys.

- A **primary key** is a column, or a set of columns, whose value uniquely identifies each row in its table. No two rows share it, and it is how other tables point at a row.
- A **foreign key** is a constraint on a column in one table that requires its values to match an existing key in another table. If the column is nullable, it may also be null, meaning "no reference".

```sql
CREATE TABLE customers (
  id    BIGINT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE
);

CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id) ON DELETE RESTRICT,
  quantity    INT NOT NULL CHECK (quantity > 0)
);
```

## Constraints protect the data

Foreign keys enforce **referential integrity**: the database refuses to store a reference to a row that does not exist. It also decides what happens when a referenced row is updated or deleted. Options such as `RESTRICT`, `CASCADE`, or `SET NULL` block the change, propagate it, or clear the reference.

Two other common constraints appear in the example above:

- A **unique constraint** stops two rows from having the same value, or the same combination of values, in the constrained columns. Nulls need care: in many databases, nulls are not considered equal to each other, so several rows may hold null in a unique column.
- A **check constraint** declares a Boolean condition, such as `quantity > 0`, and rejects any row that does not satisfy it.

Constraints move rules out of scattered application code and into one place that every writer must pass through.

## Normalization

**Normalization** is the practice of decomposing data into related tables so that each fact has one clear home. If a customer's address is copied into every order row, changing it means updating many rows, and missing one leaves the data contradicting itself. These are called **update anomalies**. Normalization reduces them and removes unnecessary duplication.

The normal forms are a series of steps:

1. **First normal form (1NF)** requires each column to hold a single scalar value rather than a repeating group, such as a comma-separated list of phone numbers in one cell. Every value is then consistently addressable by row and column.
2. **Second normal form (2NF)** matters for tables with a composite key. It removes non-key columns that depend on only part of that key. In an `order_items` table keyed by `(order_id, product_id)`, a `product_name` column depends only on `product_id`, so it belongs in a `products` table.
3. **Third normal form (3NF)** removes non-key columns that depend on other non-key columns instead of directly on the key. If an `employees` table stores `department_id` and `department_name`, the name depends on the department, not the employee, so it moves to a `departments` table.

## Denormalization

Normalized data can require many joins to read. **Denormalization** deliberately duplicates or combines data, for example storing a precomputed order total or a copied customer name, so reads need fewer joins or less computation. The cost moves to writes: every copy must be kept in sync, and the application takes on consistency work that the normalized design avoided. Denormalize on purpose, for a measured read problem, not by accident.

## Schemas and migrations

A **schema** is the definition of what the database stores and the rules it enforces: tables, columns, data types, indexes, constraints, and relationships.

Schemas change as applications grow. A **schema migration** is a controlled change to structure or data shape, such as adding a column, creating an index, or backfilling values. Migrations are applied in a known order and recorded, so development, staging, and production all evolve through the same steps.

## Backward-compatible migrations

During a deployment, old and new versions of the application often run at the same time. If a migration renames a column that the old version still reads, the old version breaks mid-rollout.

**Backward-compatible migrations** avoid this by making additive changes first. A rename, for example, becomes a sequence of safe steps:

1. Add the new column, and have the new code write to both columns.
2. Backfill the new column from the old one.
3. Switch reads to the new column once every running version supports it.
4. Drop the old column in a later release.

At every step, both the old and the new application versions keep working.

# Transactions

Transferring 100 from one account to another takes two writes: subtract from one balance, add to the other. If the server crashes between them, 100 has vanished. If another request reads both balances between them, it sees money missing. Real operations are made of several statements, and they must behave as one. That is what a transaction provides, and its guarantees are summarized by four letters you will hear constantly: ACID.

## What a transaction is

A **transaction** groups database operations into one logical unit that either **commits** together or is **rolled back**, according to the database's guarantees:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

Between `BEGIN` and `COMMIT`, the changes are provisional. `COMMIT` makes them permanent and visible to others. `ROLLBACK` discards them, and so does an error the application does not recover from, or a crash before commit. In PostgreSQL, a statement run outside an explicit transaction is its own single-statement transaction (autocommit).

## Atomicity

**Atomicity** means a transaction's changes are committed as a unit or not committed at all. Callers never get a partially committed transaction.

If the second `UPDATE` above fails, because of a violated constraint, a lost connection, or a crash, the first update is undone as well. Account 1 keeps its money. The application does not have to write compensating code to reverse half-finished work; it only has to decide whether to retry the whole transaction.

"Atomic" here means indivisible with respect to failure. It does not, by itself, say anything about what concurrent transactions see; that is isolation.

## Consistency

**Consistency** means a committed transaction preserves the constraints and invariants the database enforces: primary keys, unique constraints, foreign keys, checks, `NOT NULL`. If any statement would leave the data violating one of them, the statement fails, and the transaction cannot commit with that change.

The important qualification: the database can only enforce the rules it knows about. "The total of all balances never changes during a transfer" is a real invariant of a bank, but no constraint declares it. The database preserves it only if the transaction itself is written correctly. So consistency is a shared responsibility: the database guarantees its declared constraints, **assuming the transaction respects the application rules that are not encoded as constraints.** This is a good argument for encoding more rules as constraints, such as `CHECK (balance >= 0)`.

## Isolation

Many transactions run at the same time, and their reads and writes interleave. **Isolation** means concurrent transactions are prevented from observing or producing certain invalid interleavings, and which ones depends on the selected **isolation level**.

At the strongest level, every transaction behaves as if it ran alone. Weaker levels allow some interference, such as seeing another transaction's committed change halfway through your own work, in exchange for more concurrency. The next lesson covers exactly which anomalies each level allows. For now, the key idea: isolation is not all-or-nothing, and the default level in most databases (read committed in PostgreSQL) is not the strongest one.

## Durability

**Durability** means that once the database acknowledges a commit, it preserves the transaction against the failures its durability model covers. For a single server, that typically means a process crash, an operating system crash, or a power loss: when `COMMIT` returns, the change is on durable storage, and it will be there after a restart.

The phrase "failures covered by its durability model" matters. A single server's durability does not survive the disk itself being destroyed; that needs replication or backups. And durability can be traded for speed: PostgreSQL's `synchronous_commit = off` acknowledges commits before they are flushed, risking the last fraction of a second of commits in a crash. Durability is implemented with a write-ahead log, covered in the lesson on recovering from failures.

## A transaction in application code

```text
begin transaction
    read balance of account 1
    if balance < 100: rollback, report "insufficient funds"
    subtract 100 from account 1
    add 100 to account 2
commit
on serialization or deadlock error: retry the whole transaction
```

Two habits follow from ACID. Keep transactions short, because a transaction that stays open while the application calls an external API holds resources and blocks others. And be ready to retry: under concurrency, the database may abort a transaction to protect its guarantees, as later lessons show.

## Key points

- A transaction groups database operations into one logical unit that commits together or is rolled back.
- Atomicity: a transaction's changes are committed as a unit or not at all; callers never get a partially committed transaction.
- Consistency: a committed transaction preserves the constraints and invariants the database enforces, assuming the transaction respects application rules not encoded as constraints.
- Isolation: concurrent transactions are prevented from observing or producing certain invalid interleavings, according to the selected isolation level.
- Durability: after a commit is acknowledged, the database preserves it against the failures covered by its durability model.

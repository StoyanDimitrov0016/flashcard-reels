# Finding the bottleneck

Every earlier lesson in this deck described a mechanism that can make a program slow: branch mispredictions, cache misses, context switches, TLB misses, page faults, lock contention, slow storage, remote NUMA memory. In a real program, usually one of them dominates, and effort spent anywhere else is wasted. A program that waits on the network will not get faster on a faster CPU; a program that is computing flat out will not get faster with more threads if it already uses every core. This final lesson is about recognizing what limits a workload, using concurrency to fix the right problem, and measuring instead of guessing.

## CPU-bound workloads

A **CPU-bound** workload spends most of its time executing computations, so additional CPU capacity or more efficient algorithms can increase its throughput. Compressing files, encoding video, compiling code, and training models are typical. Its CPU sits near 100% for as long as it runs.

The levers are: a better algorithm or data layout (often the biggest win, as the lessons on caches and branch prediction showed), a faster core, or more cores, but only if the work can actually be split into parallel pieces.

## I/O-bound workloads

An **I/O-bound** workload spends much of its elapsed time waiting for storage, the network, or other devices rather than executing on the CPU. A web backend that spends 5 ms computing and 95 ms waiting on a database is I/O-bound; so is a script that downloads a thousand files. Its CPU is mostly idle, and a faster CPU barely changes its running time.

A quick first check on Linux is the `time` command, which compares wall-clock time with CPU time:

```sh
$ time ./compress-archive        # CPU-bound
real    0m10.21s
user    0m9.87s
sys     0m0.29s

$ time ./fetch-reports           # I/O-bound
real    0m10.18s
user    0m0.41s
sys     0m0.22s
```

When `user + sys` is close to `real` for a single-threaded program, it was computing the whole time. When it is a small fraction, the program spent most of its life waiting.

## Why concurrency helps I/O-bound programs

**Concurrency helps an I/O-bound program** because while one operation waits for I/O, another runnable task can use the CPU, which increases resource utilization and throughput.

A worked example: a program fetches 100 URLs, and each request takes 200 ms, almost all of it waiting for the remote server.

```text
sequential:      request 1 [200 ms] -> request 2 [200 ms] -> ... -> request 100
                 total ≈ 100 x 200 ms = 20 s, CPU idle about 99% of the time

20 concurrent:   requests 1-20 wait together, then 21-40, and so on
                 total ≈ 5 rounds x 200 ms = 1 s
```

The waits overlap instead of adding up. The CPU does the same small amount of work either way; it just no longer idles while nothing is happening. Threads, asynchronous I/O, and event loops are different ways to express this, and the principle is the same for all of them.

## Why too many runnable threads hurt

If some concurrency helps, is more always better? No. **Too many runnable threads hurt performance** because excess threads increase scheduling work, context switching, cache disruption, memory use, and contention, without adding any CPU cores.

Suppose a CPU-bound job on an 8-core machine starts 200 worker threads. Only 8 can run at any moment; the other 192 wait in run queues. The extra threads add costs and no capacity:

- **Scheduling and context switches**: the kernel keeps rotating 200 threads through 8 cores.
- **Cache disruption**: each switch brings in a different working set, so every thread keeps running on cold caches.
- **Memory**: every thread needs its own stack and kernel bookkeeping.
- **Contention**: more threads compete for the same locks and cache lines, and contended locks put threads to sleep and wake them up again.

Throughput often goes down, not up. A useful rule for sizing a thread pool: CPU-bound work wants about one thread per core. Work that waits wants more, roughly cores x (1 + wait time / compute time). With 8 cores and tasks that compute for 10 ms and wait for 90 ms, that is 8 x (1 + 9) = 80 threads. Past that point, extra threads only add overhead. In practice, confirm with measurement.

## Measure before optimizing

**Low-level performance work should be measurement-driven**, because modern CPUs, kernels, allocators, and storage stacks interact in complex ways, and profiling plus hardware and OS counters reveal the actual bottleneck better than assumptions do. A change that ought to help in theory, such as adding threads, switching allocators, or reordering a loop, can do nothing, or even hurt, when the real limit is somewhere else.

Linux offers a tool for nearly every mechanism in this deck:

- `top`, `htop`, and `vmstat 1`: CPU utilization, run queue, context switches, swapping.
- `iostat -x 1`: per-device I/O latency and utilization.
- `perf record` and `perf report`, often viewed as flame graphs: where CPU time actually goes, function by function.
- `perf stat`: hardware counters for instructions per cycle, cache misses, and branch mispredictions.
- `pidstat -w` and `/proc/pressure/`: per-process context switches and how long tasks stall on CPU, memory, or I/O.

```sh
$ perf stat -e cycles,instructions,cache-misses,branch-misses ./app
    12,408,113,520      cycles
     4,951,337,002      instructions     #    0.40  insn per cycle
       310,522,871      cache-misses
         2,114,090      branch-misses
```

Here the core completes only 0.4 instructions per cycle, when modern cores can sustain several, and cache misses are high. That points at memory access patterns, not at the arithmetic, and certainly not at a need for more threads.

The workflow is the scientific method: form a hypothesis, measure, change one thing, and measure again. The concepts in this deck tell you what to look for; measurement tells you which one is actually the problem.

## Common mistakes

- Adding threads to a CPU-bound program that already saturates every core.
- Buying faster CPUs for an I/O-bound service.
- Optimizing the code that looks slow instead of the code a profiler shows is slow.
- Measuring once, on a cold cache or an idle system, and trusting the number.

## Key points

- A CPU-bound workload spends most of its time computing, so more CPU capacity or better algorithms increase throughput.
- An I/O-bound workload spends much of its elapsed time waiting for storage, network, or other devices.
- Concurrency helps I/O-bound programs because another task can use the CPU while one waits for I/O.
- Too many runnable threads add scheduling, context switches, cache disruption, memory use, and contention without adding cores.
- Performance work should be measurement-driven: profilers and hardware and OS counters find the real bottleneck better than assumptions.

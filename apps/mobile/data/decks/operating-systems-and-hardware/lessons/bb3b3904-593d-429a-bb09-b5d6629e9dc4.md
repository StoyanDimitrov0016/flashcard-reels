# File descriptors

A program on Linux reads a configuration file, writes to a terminal, receives HTTP requests over the network, and passes data to another process through a pipe. These are four very different kinds of object, yet the program uses the same few system calls, `read`, `write`, and `close`, for all of them. The thing that makes this uniformity possible is the file descriptor. Understanding it explains shell redirection, "too many open files" errors, and how processes talk to each other.

## What a file descriptor is

A **file descriptor** is a small, process-local integer handle that refers to an open file, socket, pipe, or similar kernel-managed object. The kernel keeps the real state; the process just holds a number such as 3 or 17 and passes it to later system calls.

"Process-local" matters: descriptor 5 in one process and descriptor 5 in another usually refer to completely different objects. Each process has its own **descriptor table**, which maps its small integers to kernel **open-file objects**. An open-file object holds the state of one opening: the current read/write offset, the access mode, and flags such as append mode. It in turn points at the underlying file's inode, or at a pipe or socket.

By convention every process starts with three descriptors already open:

```text
0   standard input
1   standard output
2   standard error
```

On Linux you can see any process's descriptors under `/proc`:

```sh
$ ls -l /proc/self/fd
lrwx------ 1 ana ana 64 Sep 12 11:02 0 -> /dev/pts/1
lrwx------ 1 ana ana 64 Sep 12 11:02 1 -> /dev/pts/1
lrwx------ 1 ana ana 64 Sep 12 11:02 2 -> /dev/pts/1
lr-x------ 1 ana ana 64 Sep 12 11:02 3 -> /proc/4121/fd
```

Descriptors are a limited resource. Each process has a limit, shown by `ulimit -n` and often 1,024 by default for interactive shells, and a server that leaks descriptors eventually fails with `EMFILE`, "Too many open files".

## What opening a file does

**Opening a file** asks the kernel to do several things at once. It resolves the path, checks permissions, creates or references open-file state, and returns a handle that later I/O calls use. Step by step, for `open("/home/ana/notes.txt", O_RDONLY)`:

1. **Resolve the path**: walk the directories component by component to find the file's inode. A missing component fails with `ENOENT`.
2. **Check permissions**: compare the inode's owner, group, and mode bits with the process's user and group IDs. Insufficient rights fail with `EACCES`.
3. **Create open-file state**: allocate an open-file object with offset 0 and the requested mode, or with `O_CREAT`, create the file first.
4. **Return a descriptor**: install a pointer to that object in the lowest free slot of the descriptor table and return its number.

```c
#include <fcntl.h>
#include <unistd.h>

int fd = open("/home/ana/notes.txt", O_RDONLY);   /* e.g. returns 3 */
if (fd < 0) { perror("open"); return 1; }

char buf[4096];
ssize_t n = read(fd, buf, sizeof buf);   /* reads from offset 0, advances it by n */
close(fd);                               /* frees slot 3 for reuse */
```

Doing the expensive work once, at open time, keeps each later `read` cheap: the kernel does not resolve the path or recheck permissions on every call.

Descriptors are inherited across `fork` and, unless marked close-on-exec, kept across `exec`. That is how a shell implements redirection. For `./app > out.log 2>&1`, it forks, opens `out.log` in the child, uses `dup2` to install it as descriptor 1, duplicates 1 onto 2, and then executes `app`, which simply writes to descriptors 1 and 2 without knowing where they lead.

## Pipes

A **pipe** is a kernel buffer that lets one process or thread write a byte stream that another reads, commonly used for local inter-process communication. The `pipe` system call returns two descriptors, a read end and a write end.

The shell's `|` is exactly this:

```sh
$ grep -r "TODO" src | wc -l
```

The shell creates a pipe, forks two children, connects `grep`'s descriptor 1 to the write end and `wc`'s descriptor 0 to the read end, and runs both programs concurrently. Neither program knows it is talking to another process. The same thing in C:

```c
int fds[2];
pipe(fds);                     /* fds[0]: read end, fds[1]: write end */
if (fork() == 0) {
    close(fds[0]);
    write(fds[1], "ping\n", 5);
    _exit(0);
}
close(fds[1]);
char buf[16];
ssize_t n = read(fds[0], buf, sizeof buf);   /* receives "ping\n" */
```

The kernel buffer is bounded, 64 KB by default on Linux. A writer blocks when it is full and a reader blocks when it is empty, so a fast producer is automatically slowed to the consumer's pace. When every write end is closed, the reader gets end-of-file. A pipe is a one-way stream of bytes with no message boundaries.

## Sockets

A **socket** is an endpoint abstraction for sending and receiving data through a communication protocol, either locally or across a network. A TCP socket connects to a process on another machine; a Unix domain socket connects two processes on the same machine through a path such as `/run/postgresql/.s.PGSQL.5432`, often faster than going through the network stack.

Setting up a socket takes its own system calls, `socket`, `connect` on the client, and `bind`, `listen`, `accept` on the server, but the result is again a file descriptor. Once connected, a program can use the same `read` and `write` calls it uses for files. `ss -tanp` on Linux lists open TCP sockets together with the processes that own them.

Because files, pipes, sockets, and even timers and signals can all be descriptors, a single thread can wait on thousands of them at once with `poll` or Linux's `epoll`, which is the foundation of event-driven servers.

## Common mistakes

- Treating a descriptor number as meaningful across processes. It only has meaning in its own process's table.
- Forgetting to close descriptors, especially in error paths, until the process hits its limit.
- Expecting a pipe or TCP socket to preserve message boundaries. Both are byte streams; one `write` may arrive as several `read`s, or several writes as one.

## Key points

- A file descriptor is a small, process-local integer handle referring to an open file, socket, pipe, or similar kernel object.
- Opening a file makes the kernel resolve the path, check permissions, create or reference open-file state, and return a descriptor for later I/O calls.
- A pipe is a kernel buffer through which one process or thread writes a byte stream that another reads, commonly for local IPC.
- A socket is an endpoint for sending and receiving data through a protocol, locally or across a network.

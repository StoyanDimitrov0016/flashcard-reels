# CPU scheduling

A typical Linux machine has a few hundred threads and a handful of cores. Most of those threads are asleep, waiting for a network packet, a timer, or a key press, but at any moment several may be ready to run, and some of them would happily run forever. Something must decide who runs where, and for how long, in a way that keeps the machine both responsive and efficient. This lesson covers that decision and the two numbers people use to judge whether the CPUs are keeping up.

## The scheduler

The **scheduler** is the part of the kernel that chooses which runnable thread or process receives CPU time on each processor. Two words in that definition matter:

- A thread is **runnable** when it could make progress if given a core. It is either running or waiting in a queue for its turn.
- A thread is **blocked** (sleeping) when it is waiting for an event, such as data from a disk, a message on a socket, or a lock. Blocked threads are not candidates at all until the event arrives and the kernel marks them runnable again.

Linux keeps a run queue per CPU and picks from it using a policy that aims to give each runnable thread a fair share of CPU time, weighted by its priority (its "nice" value). Since kernel 6.6 the default policy is called EEVDF; before that it was CFS. The scheduler also moves threads between CPUs to balance load, while trying not to move them so often that they lose their warm caches.

In `ps` or `top`, the `STAT` column shows these states: `R` for running or runnable, `S` for sleeping, and `D` for uninterruptible sleep, usually waiting on disk I/O.

## Preemptive scheduling

What if a runnable thread never blocks? A loop like `while (1) { x++; }` never asks the kernel for anything.

With **preemptive scheduling**, the OS can interrupt a running thread and schedule another, which prevents any one thread from keeping the CPU indefinitely. The mechanism is the hardware timer interrupt: it fires periodically, hands control to the kernel whatever the thread was doing, and the scheduler then decides whether to keep the current thread running or switch.

The alternative, cooperative scheduling, lets a thread run until it voluntarily yields. Early Windows and classic Mac OS worked this way, and a single misbehaving program could freeze the entire machine. All mainstream general-purpose operating systems today are preemptive. (Cooperative scheduling survives inside programs: an event loop in Node.js or an `async` runtime runs each task until it awaits, so one CPU-heavy task can stall all the others in that loop.)

## Time slices

A **time slice** (also called a quantum) is a bounded interval for which a runnable task may execute before the scheduler can preempt it for another task. Here is a timeline for one core with three runnable threads and 4 ms slices. A and B are CPU-bound; C handles keystrokes and runs briefly, then blocks:

```text
time (ms)   0    4    8   9   13   17   18   22
running     A    B    C   A   B    C    A    B ...
            |<4->|<4->|1->|
            A and B use their full slice and are preempted
            C runs 1 ms, then blocks waiting for input; its unused slice is given up
```

The slice length is a trade-off:

- **Short slices** make the system feel responsive, because a thread that becomes runnable waits less for its turn.
- **Long slices** waste less time on context switches and let each thread keep its caches warm for longer.

Modern schedulers do not use one fixed number. Linux computes slices dynamically, typically a few milliseconds, and favors threads that have recently been sleeping, such as the one handling your keyboard, so interactive work gets on a CPU quickly.

## CPU utilization

**CPU utilization** is the fraction of processor time spent doing non-idle work over an interval. A core that was busy for 600 ms of the last second was 60% utilized. On a multi-core machine the number is reported per core or averaged across all of them, and tools disagree about scaling: `top` shows a single process using four full cores as 400%.

`top` breaks the busy time down further: `us` for user-mode code, `sy` for kernel code, and `wa` for iowait, which is idle time during which some I/O was outstanding. Iowait is idle time, not work, despite its name.

## Load average

Utilization tells you how busy the CPUs were, but not how much work was waiting. A machine at 100% utilization might have exactly enough work, or a long queue of threads waiting for a turn.

**Load average** measures demand: it counts tasks that are runnable, and on some systems tasks blocked in certain uninterruptible states, and averages that count over time. The exact definition varies by operating system. Linux counts tasks that are running, runnable, or in uninterruptible sleep (state `D`), and reports exponentially smoothed averages over 1, 5, and 15 minutes:

```sh
$ uptime
 14:02:11 up 12 days,  3:41,  2 users,  load average: 7.93, 6.10, 4.02
```

Read it against the number of CPUs. On an 8-CPU machine, a load of about 8 means demand roughly matches capacity. A load of 20 means that, on average, about 12 tasks were waiting at any moment. The rising sequence from 4.02 to 7.93 says demand has grown over the last quarter hour.

Because Linux includes tasks stuck in uninterruptible I/O waits, a high load average does not always mean busy CPUs. A server with a failing disk or a hung network filesystem can show a load of 50 while its CPUs sit idle. Always check utilization and load together.

## Common mistakes

- Reading load average as a percentage. It is a count of tasks, to be compared with the number of CPUs.
- Assuming a high load on Linux always means CPU pressure. It can come from tasks blocked on storage.
- Counting iowait as busy CPU time. The CPU was idle; something else was slow.

## Key points

- The scheduler chooses which runnable thread or process receives CPU time on each processor.
- Preemptive scheduling lets the OS interrupt a running thread and run another, so no thread can keep the CPU indefinitely.
- A time slice is the bounded interval a runnable task may run before the scheduler can preempt it.
- CPU utilization is the fraction of processor time spent on non-idle work over an interval.
- Load average measures demand by counting runnable, or on some systems uninterruptibly blocked, tasks over time; definitions vary by OS.

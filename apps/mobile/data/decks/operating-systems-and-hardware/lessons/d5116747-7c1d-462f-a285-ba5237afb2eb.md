# Stack and heap memory

Inside a process's address space, not all memory is used the same way. Some data lives exactly as long as one function call; some must outlive the function that created it and be released later, in no predictable order. Programs handle these two lifetimes with two different regions, the stack and the heap, managed in very different ways. Knowing how each works explains stack overflows, why allocation has a cost, and why a long-running server can seem to run out of memory it has not used.

## The layout of a process

On Linux, a typical process address space contains, from low addresses to high:

```text
code (text)       machine instructions of the program, read-only and executable
data and bss      global and static variables
heap              dynamically allocated objects, growing upward
memory mappings   shared libraries, mmap'd files, large allocations
stack             the main thread's stack, growing downward from high addresses
```

Every additional thread gets its own stack, placed somewhere in the mappings region. You can see a live process's layout with `cat /proc/<pid>/maps`.

## The stack

A **stack** stores call frames, return addresses, and many local values in last-in, first-out call order. Each thread has its own. When a function is called, a new **frame** is pushed holding its return address, saved registers, and local variables; when the function returns, its frame is popped. Allocation is just moving the stack pointer by a fixed amount, so it costs almost nothing, and the memory is released automatically on return.

That automatic release is also the stack's limitation: a value on the stack lives only as long as the call that created it.

```c
int *broken(void) {
    int local = 42;
    return &local;        /* dangling: the frame is gone after return */
}

int *works(void) {
    int *p = malloc(sizeof *p);
    *p = 42;
    return p;             /* heap memory outlives the call; caller must free it */
}
```

## Stack overflow

Stacks are not unlimited. On Linux the main thread's stack is limited by `ulimit -s`, commonly 8 MB, and threads created with `pthread_create` get a fixed-size stack, by default also typically 8 MB with glibc. Many language runtimes use much smaller defaults for their threads.

A **stack overflow** happens when a thread consumes more stack space than its allocated limit. The usual causes:

- **Very deep or unbounded recursion.** A recursive function with a 100-byte frame that recurses 1,000,000 levels deep needs about 100 MB of stack, far past an 8 MB limit. A missing base case recurses forever.
- **Unusually large stack allocations.** A local array such as `char buf[16 * 1024 * 1024];` overflows an 8 MB stack in a single frame.

The kernel places an unmapped guard region below each stack, so running off the end causes a page fault that the kernel cannot satisfy, and the process receives `SIGSEGV` instead of silently overwriting neighboring memory. The fixes are to convert deep recursion into iteration with an explicit data structure, move large buffers to the heap, or, if truly needed, request a bigger stack.

## The heap

The **heap** is process memory used for dynamically allocated objects whose lifetime is not tied to one function call frame. An object created with `malloc` in C, `new` in C++, or almost any object in Java, Python, or JavaScript lives on the heap. It stays until the program frees it explicitly or, in garbage-collected languages, until the runtime decides it is unreachable.

The heap's flexibility, any size, any lifetime, freed in any order, is exactly what makes managing it hard.

## Memory allocators

A **memory allocator** manages regions of process memory, returns blocks for dynamic allocation, and tracks free space for later reuse. `malloc` and `free` are not system calls. They are functions in the C library's allocator, which works in two layers:

1. It obtains large regions from the kernel with system calls: `brk` to extend the traditional heap, or `mmap` for large requests and additional arenas.
2. It carves those regions into blocks for individual requests and keeps free lists so that freed blocks can be reused without asking the kernel again.

Because most allocations never enter the kernel, they are fast, typically tens of nanoseconds. Allocators trade off speed, memory overhead, and behavior under many threads. glibc's allocator is the Linux default; alternatives such as jemalloc, tcmalloc, and mimalloc use per-thread caches and size classes, and swapping one in can noticeably change the throughput and memory footprint of a multithreaded server.

## Fragmentation

**Fragmentation** leaves free memory divided into pieces or creates unused space inside allocations, making allocation less efficient even when total free capacity seems sufficient. It comes in two forms:

- **Internal fragmentation**: an allocated block is larger than what was requested. If the allocator rounds sizes up to classes of 16, 32, 48, 64 bytes and so on, a 33-byte request occupies a 48-byte slot, and 15 bytes are wasted inside it.
- **External fragmentation**: free memory exists but is scattered in small gaps between live blocks.

A worked example of external fragmentation: a server allocates 1,000 buffers of 100 KB, using 100 MB, then frees every other one. Now 50 MB is free, but it consists of 500 separate 100 KB holes. A request for a 200 KB buffer fits in none of them, so the allocator must obtain new memory from the kernel while 50 MB sits unused. Over days, a server that allocates and frees objects of many sizes can grow its resident memory steadily even though its live data does not grow, which often looks like a leak but is not one.

Mitigations include allocators with size-class slabs, which keep objects of similar size together, object pools for hot fixed-size objects, and garbage collectors that compact the heap by moving live objects together.

## Common mistakes

- Returning a pointer to a local variable. The stack frame is reclaimed when the function returns.
- Assuming `free` returns memory to the operating system immediately. Allocators usually keep freed memory for reuse.
- Diagnosing every growth in resident memory as a leak. Fragmentation produces the same symptom.

## Key points

- The stack stores call frames, return addresses, and many local values in last-in, first-out order; each thread has its own.
- A stack overflow happens when a thread exceeds its stack limit, usually from very deep recursion or large stack allocations.
- The heap holds dynamically allocated objects whose lifetime is not tied to a single function call.
- A memory allocator manages process memory regions, hands out blocks, and tracks free space for reuse.
- Fragmentation, internal or external, wastes memory so allocation becomes less efficient even when total free space looks sufficient.

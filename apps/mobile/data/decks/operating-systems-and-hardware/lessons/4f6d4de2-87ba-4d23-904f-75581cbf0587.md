# Paging to disk

Physical memory is finite, but the demands on it are not. Processes allocate more than they touch, caches grow to fill free RAM, and sometimes the programs running simply need more memory than the machine has. Virtual memory gives the kernel a way out: since programs only see virtual addresses, it can quietly move some of their pages to disk and bring them back when needed. Done occasionally, this is invisible. Done constantly, it can bring a powerful machine to a crawl. This lesson explains both outcomes and the concept that separates them.

## Swapping

**Swapping**, or paging to disk, means the OS moves inactive memory contents to secondary storage to free physical RAM, then reloads them if they are accessed again. Historically "swapping" meant writing out an entire process at once; modern systems work page by page, and the terms are now used interchangeably.

On Linux, when free memory runs low, the kernel's reclaim code (the `kswapd` background thread, or the allocating thread itself under pressure) looks for pages that have not been used recently, using the accessed bits in the page tables. What happens to a chosen page depends on where its contents came from:

- **Clean file-backed pages**, such as program code or cached file data that has not been modified, are simply dropped. The data is still in the file and can be read again.
- **Dirty file-backed pages** are written back to their file, then dropped.
- **Anonymous pages**, such as heap and stack memory, have no file behind them, so they are written to a **swap area**, a dedicated partition or swap file, before the frame is reused.

In each case the page-table entry is marked not present. If the program touches the page again, a major page fault occurs, and the kernel reads the page back in from the file or the swap area. On Linux, `swapon --show` lists swap areas, `free -h` shows how much swap is in use, and the `si` and `so` columns of `vmstat 1` show pages swapped in and out per second.

Swapping out memory that is genuinely idle, such as the pages of a daemon that runs once a day, is a good trade: that RAM can hold something useful instead.

## Why heavy swapping is slow

**Heavy swapping is slow** because storage latency is far higher than RAM latency, so frequent page-in and page-out operations can dominate execution time. The gap is enormous:

```text
DRAM access           ~100 ns
NVMe SSD read         ~20-100 µs    (200-1,000 times slower)
hard disk read        ~5-10 ms      (50,000-100,000 times slower)
```

A worked example shows how quickly faults dominate. Suppose normal memory accesses take 100 ns and a page-in from an SSD takes 50 µs (50,000 ns). The effective access time is the weighted average:

```text
1 access in 10,000 faults:  0.9999 x 100 + 0.0001 x 50,000 =   105 ns   ( 5% slower)
1 access in  1,000 faults:  0.999  x 100 + 0.001  x 50,000 ≈   150 ns   (1.5x slower)
1 access in    100 faults:  0.99   x 100 + 0.01   x 50,000 ≈   600 ns   (6x slower)
```

With a hard disk at 8 ms per page-in, even one fault per 1,000 accesses makes memory about 80 times slower. The program is barely running; it is waiting for storage.

## Working sets

What decides whether swapping is harmless or disastrous? Not how much memory a program has allocated, but how much it uses right now.

A **working set** is the memory a workload actively uses during a time window. A 16 GB database whose queries this hour touch only 2 GB of hot indexes has a working set of about 2 GB. If the working set fits in RAM, and ideally the hottest part in the CPU caches, the workload avoids frequent costly misses. The remaining 14 GB can live on disk, or never be loaded at all, and performance barely suffers.

Working sets change over time. A nightly batch job that scans every table has a working set of the whole database while it runs, which is why such jobs can suddenly push out the pages that daytime traffic relied on.

## Thrashing

**Thrashing** occurs when a system spends most of its time moving pages between RAM and storage because the active working sets exceed available memory. Every page brought in forces out another page that some process needs moments later, which faults it back in, which forces out yet another. No amount of clever reclaim helps, because there is no idle memory left to evict.

The symptoms are distinctive:

- the machine becomes extremely unresponsive, even to typing;
- `vmstat` shows high, sustained `si` and `so`;
- CPU utilization is low while load average is high, because tasks are blocked waiting for disk;
- on Linux, `/proc/pressure/memory` shows a large share of time stalled on memory.

The only real remedies reduce demand or add supply: run fewer programs at once, shrink their memory use, or add RAM. Linux's out-of-memory killer, or a user-space daemon such as `systemd-oomd`, ends thrashing brutally by killing a process. Many servers run with little or no swap precisely so that memory exhaustion fails fast instead of slowly thrashing.

## Common mistakes

- Treating any swap usage as a problem. Idle pages sitting in swap are fine; high ongoing swap-in and swap-out rates are the warning sign.
- Sizing memory by total allocation instead of by working set.
- Expecting a faster CPU to fix a thrashing machine. The bottleneck is storage latency.

## Key points

- Swapping, or paging to disk, moves inactive memory contents to secondary storage to free RAM and reloads them when accessed.
- Heavy swapping is slow because storage latency is far higher than RAM latency, so page-ins and page-outs dominate execution time.
- A working set is the memory a workload actively uses during a time window; if it fits in RAM and caches, costly misses stay rare.
- Thrashing is when the system spends most of its time moving pages between RAM and storage because working sets exceed available memory.

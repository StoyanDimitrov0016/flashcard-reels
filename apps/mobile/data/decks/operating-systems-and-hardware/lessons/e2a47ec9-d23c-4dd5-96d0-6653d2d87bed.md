# Inside a CPU core

The mental model most programmers carry is that a CPU executes one instruction, then the next, then the next. Real processors have not worked that way for decades. A modern core overlaps dozens of instructions, guesses which way code will branch, and runs work out of order, all while pretending to the program that it is doing things one at a time. You never see these tricks in the results of a correct program, but you see them in its speed: two loops doing the "same" amount of work can differ by a factor of five because of how well they fit the machinery described here.

## Cores

A **core** is an independent hardware execution engine capable of running its own instruction stream. It has its own instruction fetch and decode logic, its own execution units (integer arithmetic, floating point, loads and stores), its own registers, and usually its own small, fast caches. A chip with eight cores can genuinely execute eight instruction streams at the same instant. On Linux, `nproc` reports how many logical CPUs the kernel can schedule on, and `lscpu` shows how they map to physical cores.

The rest of this lesson looks at what happens inside a single core.

## Pipelining

Executing one instruction involves several steps: fetch it from memory, decode what it means, execute it, and finally commit its result. If a core did all of those for one instruction before starting the next, most of its circuitry would sit idle most of the time.

An **instruction pipeline** overlaps the stages of multiple instructions, such as fetch, decode, execute, and retire, so several instructions are in progress at once. It works like an assembly line:

```text
cycle:     1        2        3        4        5
instr 1    fetch    decode   execute  retire
instr 2             fetch    decode   execute  retire
instr 3                      fetch    decode   execute
instr 4                               fetch    decode
```

Each instruction still takes four cycles from start to finish, but once the pipeline is full, one instruction completes every cycle. Real cores have pipelines of 10 to 20 stages and are also superscalar: they fetch, execute, and retire several instructions per cycle.

## Dependencies

A pipeline only helps if there is independent work to overlap. An **instruction-level dependency** exists when one instruction needs a value or resource produced or constrained by another. A dependent instruction cannot execute until its input is ready, which limits how much the CPU can reorder or parallelize.

```c
a = x * y;     /* 1 */
b = a + 1;     /* 2: needs a, must wait for 1 */
c = z * 2;     /* 3: independent, can run alongside 1 */
```

Dependencies are why the shape of a computation matters. Summing an array into one accumulator creates a chain in which every addition waits for the previous one. Splitting the sum across four accumulators creates four independent chains the core can run in parallel, and on floating-point data this can make the loop several times faster. (Compilers do this for integers automatically, but not for floating point, because it changes rounding.)

## Out-of-order execution

Sometimes an instruction stalls, most often because it is waiting for data from memory, which can take hundreds of cycles. Later instructions that do not depend on it could still run.

With **out-of-order execution**, the CPU executes independent instructions before older stalled instructions when dependencies allow, then retires their results in the original program order. Instructions enter a buffer in program order, execute whenever their inputs are ready, and are committed in program order at the end. That final in-order step, called **retirement**, is what keeps the architecturally visible result correct: registers and memory look exactly as if each instruction ran one after another, even though the work underneath happened in a different order.

In the example above, if `x` must be loaded from memory and misses the cache, instruction 3 runs and finishes while 1 and 2 wait. It retires only after they do.

## Branch prediction

Pipelines create a problem at every `if`, loop, and function return. The core fetches instructions many cycles before earlier ones finish executing, but a conditional branch is not resolved until its condition has been computed. Waiting would stall the pipeline at every branch, and typical code has a branch every five or so instructions.

With **branch prediction**, the CPU predicts the outcome and target of branches so it can keep fetching and executing speculatively instead of waiting for the branch to resolve. Predictors learn from history and are extremely accurate on regular patterns: a loop that runs 1,000 times is predicted "taken" and is wrong only once, at the exit.

When the guess is wrong, the **branch misprediction cost** is paid: the speculative work done on the wrong path must be discarded and the pipeline refilled from the correct path, wasting cycles. On current cores that costs roughly 15 to 20 cycles per miss, time in which the core could have completed dozens of instructions.

The classic demonstration:

```c
long sum = 0;
for (int i = 0; i < n; i++) {
    if (data[i] >= 128)   /* random bytes: about 50% mispredicted */
        sum += data[i];
}
```

With random byte values the branch is a coin flip, and about half the iterations mispredict. Sort `data` first and the branch becomes "false, false, ..., true, true", which the predictor gets almost entirely right. The same loop over the same values can run several times faster. (An optimizing compiler may remove the branch altogether with a conditional-move instruction, which is one reason to measure rather than guess.)

## Simultaneous multithreading

Even with out-of-order execution, a single instruction stream rarely keeps every execution unit busy. It waits on memory, mispredicts branches, or simply lacks enough independent work.

**Simultaneous multithreading (SMT)**, which Intel calls Hyper-Threading, lets one physical core maintain multiple hardware thread contexts, typically two, and issue instructions from all of them to use otherwise idle execution resources. Each hardware thread has its own registers and program counter, so the operating system sees it as a separate logical CPU. When one thread stalls on a cache miss, the other thread's instructions fill the gap.

## Why two hardware threads are not two cores

**Two hardware threads are not the same as two full cores**, because SMT threads share most of the core: execution units, caches, branch predictors, and internal buffers. The throughput gain depends on whether their workloads contend for the same resources.

- Two threads that both run tight floating-point loops compete for the same units and mostly take turns. The pair may deliver only slightly more than one thread alone.
- A thread that often stalls on memory paired with a compute-heavy thread can overlap well, and the pair may get 20 to 30 percent more total throughput, sometimes more.

So a machine reported by `nproc` as 16 CPUs with SMT enabled has 8 physical cores, and a CPU-bound job will not run twice as fast on 16 threads as on 8.

## Common mistakes

- Believing that out-of-order execution produces out-of-order results within a thread. Retirement is in program order; a single thread always sees its own operations in order.
- Counting logical CPUs as cores when estimating capacity.
- Assuming branches are cheap or expensive in general. Predictable branches are nearly free; unpredictable ones are costly.

## Key points

- A core is an independent execution engine that runs its own instruction stream, usually with its own execution units and caches.
- A pipeline overlaps stages such as fetch, decode, execute, and retire, so several instructions are in progress at once.
- An instruction-level dependency means one instruction needs a value or resource from another, limiting reordering and parallelism.
- Out-of-order execution runs independent instructions ahead of stalled older ones, then retires results in architecturally correct order.
- Branch prediction guesses branch outcomes and targets so the core can keep executing speculatively.
- A misprediction discards the wrong-path work and refills the pipeline, wasting cycles.
- SMT keeps multiple hardware thread contexts on one core to use idle execution resources, but those threads share units and caches, so they are not equivalent to separate cores.

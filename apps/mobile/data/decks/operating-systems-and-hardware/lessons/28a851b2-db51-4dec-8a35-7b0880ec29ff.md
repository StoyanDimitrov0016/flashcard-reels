# Device I/O

Disks, network cards, keyboards, and timers all work at their own pace, independently of the CPU. A disk read takes microseconds to milliseconds; a network packet can arrive at any moment; a key press comes whenever a human feels like it. The kernel needs answers to two questions: how does it find out that a device has something to report, and how does data get between the device and memory without wasting the processor's time? This lesson covers the standard answers: interrupts, polling, direct memory access, and device drivers.

## Interrupts

An **interrupt** is a hardware or software signal that causes the CPU to stop what it is doing and transfer control to an operating-system handler for an event that needs attention. The CPU saves enough state to resume later, switches to kernel mode, and jumps to the handler registered for that kind of event. When the handler finishes, the interrupted code continues as if nothing happened.

Interrupts come from two directions:

- **Hardware interrupts** are raised by devices through an interrupt controller: "the disk read finished", "a packet arrived", "the timer fired".
- **Software interrupts** and exceptions are triggered by the running instruction stream itself, such as an instruction that deliberately traps into the kernel, a division by zero, or an access to memory that is not mapped.

One hardware interrupt matters everywhere: the **timer interrupt**. The kernel programs a hardware timer to interrupt the CPU periodically, which guarantees that the kernel regains control even if a program runs an infinite loop. Preemptive scheduling depends on it.

On Linux you can see how many interrupts each device has raised on each CPU:

```sh
$ cat /proc/interrupts
            CPU0       CPU1
  0:          42          0   IO-APIC    2-edge      timer
 27:     1832211     904117   PCI-MSI    nvme0q1
 30:     5521043    6012770   PCI-MSI    eth0-rx-0
```

## Hardware interrupts versus polling

Devices use **hardware interrupts** to notify the CPU about events such as completed I/O, arriving data, or a key press. The alternative would be constant checking. With interrupts, the CPU runs other work and reacts only when something actually happens.

That alternative is **polling**: repeatedly checking a device status register or some condition for changes. Polling wastes CPU while nothing changes, because every check that finds nothing is lost work. Imagine polling a keyboard 1,000 times per second when a person types five keys per second: 995 of every 1,000 checks are wasted.

Polling is not always worse, though. Taking an interrupt has a fixed cost: saving state, running the handler, and disturbing whatever was running. When events are very frequent, or when the lowest possible reaction latency matters, checking in a loop can react faster and cost less than taking one interrupt per event. A network card receiving a million packets per second would drown the CPU in interrupts.

Real systems mix the two. Linux network drivers use a scheme called NAPI: the first packet raises an interrupt, the driver then switches that interrupt off and polls the card for as long as packets keep coming, and re-enables the interrupt once the queue is empty. High-performance storage and networking frameworks go further and poll continuously on dedicated cores.

## Direct memory access

Knowing that data is ready is half the problem; the data still has to reach RAM. In the simplest design, called programmed I/O, the CPU copies it itself: read a word from the device, store it in memory, repeat. For a 4 KB disk block that is hundreds of loads and stores, and reads from device registers are slow. The CPU is fully occupied just moving bytes.

**Direct Memory Access (DMA)** lets a device transfer data to or from main memory with limited CPU involvement after the transfer is configured. The CPU's job shrinks to setting it up: it tells the device where the buffer is in memory, how large it is, and which direction to move data. The device then reads or writes memory on its own.

A typical disk read with DMA and interrupts looks like this:

```text
t = 0 µs     driver writes a command: "read block 812 into buffer at 0x3a7f000, 4096 bytes"
t = 1 µs     CPU switches to another thread; the reading thread sleeps
t = 1-80 µs  SSD fetches the data and writes it into RAM via DMA; no CPU instructions involved
t = 80 µs    SSD raises a hardware interrupt: "command done"
t = 81 µs    interrupt handler marks the request complete and wakes the reading thread
```

**DMA improves I/O efficiency** because the CPU does not have to copy every byte through instructions. While the device and the memory controller move whole blocks, the CPU is free to run other work. The pattern of "configure DMA, do something else, get interrupted when it finishes" is how virtually all disks and network cards work today.

## Device drivers

Every piece of hardware has its own registers, command formats, and quirks. An NVMe SSD, a SATA disk, and a USB stick all store blocks, but each is controlled differently. A **device driver** is operating-system code that translates generic kernel operations, such as "read these blocks" or "send this packet", into the commands and data handling specific to one hardware device. It programs the device's registers, sets up DMA buffers, and handles the device's interrupts.

Drivers let the rest of the kernel, and every program above it, use one uniform interface regardless of which vendor built the hardware. A program calls `read` on a file; the filesystem asks the block layer for blocks; the block layer hands the request to whichever driver owns the disk. On Linux most drivers are kernel modules loaded on demand, which you can list with `lsmod`.

Because drivers usually run in kernel mode with full privileges, a driver bug can crash or corrupt the whole system. Drivers make up a large share of kernel code and a large share of kernel bugs.

## Common mistakes

- Assuming polling is always wasteful. Under very high event rates or strict latency targets, polling can beat interrupts.
- Thinking DMA means the CPU is not involved at all. The CPU still configures each transfer and handles its completion; it just does not copy the bytes.
- Picturing a driver as a user program. Most drivers run inside the kernel with full privileges.

## Key points

- An interrupt is a hardware or software signal that makes the CPU transfer control to an operating-system handler for an event needing attention.
- Devices use hardware interrupts to report events such as completed I/O, so the CPU does not have to poll constantly.
- Polling repeatedly checks a device or condition; it can lower reaction latency under heavy load but burns CPU while nothing changes.
- DMA lets a device move data to or from main memory with limited CPU involvement once the transfer is configured.
- DMA improves I/O efficiency because the CPU does not copy every byte and can run other work during the transfer.
- A device driver is OS code that translates generic kernel operations into commands specific to one hardware device.

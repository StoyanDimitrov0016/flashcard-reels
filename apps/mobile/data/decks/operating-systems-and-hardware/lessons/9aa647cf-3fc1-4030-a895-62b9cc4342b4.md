# Virtual memory

When a program reads address `0x7ffd1000`, it is not naming a spot on a RAM chip. It is using a **virtual address**, which the hardware and operating system translate into a physical one on every access. This layer of indirection is one of the most important ideas in operating systems, and it explains page faults, swapping, and why a machine can grind to a halt when memory runs out.

## What virtual memory is

**Virtual memory** gives each process its own logical address space. The OS and hardware map pieces of that space to physical memory, or to other backing storage such as a file or swap space. Two processes can both use address `0x400000` and see completely different data, because each has its own mapping.

## What problem it solves

Virtual memory does several jobs at once:

- **Isolation.** A process can only reach memory that is mapped into its own address space, so it cannot read or corrupt another process's memory.
- **Convenient address ranges.** Programs see large, contiguous ranges even if the physical memory behind them is scattered.
- **Controlled sharing.** The OS can deliberately map the same physical memory into several processes, for example shared libraries.
- **Independent management.** The OS can move, reclaim, or back physical memory with storage without the program's addresses changing.

## Pages and page tables

Translation is not done byte by byte. Memory is divided into **pages**, fixed-size blocks of virtual memory, commonly 4 KB, which are the unit for address translation and many memory-management operations. Physical memory is divided into matching **frames**.

A **page table** maps virtual page numbers to physical frames. Each entry also stores permissions and status bits: whether the page is present, writable, executable, accessible from user mode, recently accessed, or modified. The **memory-management unit (MMU)** in the CPU reads these entries to translate addresses and enforce permissions. On 64-bit systems page tables are multi-level trees, so a full lookup takes several memory reads.

## The TLB

Walking a multi-level page table on every memory access would be far too slow. The **translation lookaside buffer (TLB)** is a small cache inside the CPU that holds recent virtual-to-physical translations, so most accesses translate instantly.

On a **TLB miss**, the needed translation is not in the TLB, so hardware (or on some architectures the OS) must walk the page tables before the access can proceed. Programs that jump around huge amounts of memory suffer many TLB misses, which is one reason large pages exist: each entry then covers more memory.

## Page faults and demand paging

A **page fault** happens when an access cannot proceed with the current page-table entry. The CPU traps into the kernel, which decides what the fault means. It may be harmless, such as a page that simply has not been loaded yet, in which case the kernel loads or allocates it, fixes the entry, and resumes the program. Or it may be invalid, such as writing to read-only memory or touching an unmapped address, in which case the kernel rejects the access, typically by killing the process with a segmentation fault.

Harmless faults are a normal part of **demand paging**. Instead of eagerly loading a whole program or allocating all requested memory up front, the OS loads or physically allocates pages only when they are first touched. A program that maps a 1 GB buffer but uses 10 MB of it only consumes about 10 MB of RAM.

## Swapping

When RAM fills up, the OS can **swap** or **page to disk**: it moves the contents of inactive pages to secondary storage, frees the physical frames for other uses, and reloads the pages later if they are accessed again. This lets the system run more than fits in RAM, as long as the swapped-out pages stay mostly unused.

**Heavy swapping is slow** because storage latency is far higher than RAM latency. A RAM access takes around 100 nanoseconds; even a fast SSD read is tens of microseconds, and a spinning disk is milliseconds. When page-ins and page-outs become frequent, they dominate execution time.

## Working sets and thrashing

A **working set** is the memory a workload actively uses during a time window. What matters is not how much memory a program has allocated in total, but how much it touches right now. If the working set fits in RAM, and ideally in the caches, the workload avoids frequent costly misses.

When the combined working sets of running programs exceed available memory, the system starts **thrashing**: every page it brings in pushes out another page that is needed moments later. The machine spends most of its time moving pages between RAM and storage and very little doing useful work. The symptoms are dramatic: the disk is busy, the CPU is mostly waiting, and everything responds slowly. The remedies are reducing memory demand, running fewer things at once, or adding RAM.

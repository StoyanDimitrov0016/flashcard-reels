# Virtualization and measurement

Much of today's software runs inside containers or virtual machines rather than directly on an operating system installed on bare hardware. Both provide isolation, but they work at different levels, and the difference affects security, startup time, and overhead. This final lesson also covers the habit that ties the whole deck together: measure before you optimize.

## Containers

From the operating system's point of view, a **container** is not a special kind of machine. It is one or more ordinary processes running on the host kernel, isolated and resource-controlled using kernel features. On Linux, the two key features are:

- **Namespaces**, which give a group of processes its own view of system resources, such as process IDs, network interfaces, mount points, and hostnames. A process inside a container can believe it is process 1 on a machine of its own.
- **Control groups (cgroups)**, which limit and account for resource use, such as CPU time, memory, and I/O bandwidth.

Because there is no separate guest kernel to boot, containers start in milliseconds and add little overhead.

## Virtual machines and hypervisors

A **virtual machine** goes a level lower. It presents virtual hardware, meaning virtual CPUs, memory, disks, and network cards, and runs a complete guest operating system with its own kernel on top of that hardware.

That is the core **difference between a VM and a container**. A container normally shares the host kernel and isolates processes within it, while a VM runs its own guest kernel on virtual hardware. VMs therefore offer stronger isolation, since a guest kernel bug does not directly expose the host, and they can run a different operating system than the host. They also cost more memory and take longer to start.

The software that creates and manages virtual machines is the **hypervisor**. It multiplexes the physical CPUs, memory, and devices among the guest operating systems, much as a kernel multiplexes hardware among processes. Some hypervisors run directly on the hardware; others run on top of a host operating system. Modern CPUs include virtualization extensions that let guests run most instructions directly at near-native speed.

## Measure before you optimize

Every lesson in this deck has described a mechanism that affects performance: context switches, cache lines, branch prediction, TLB misses, page faults, lock contention, the page cache, SSD garbage collection, NUMA placement. These mechanisms interact in complex ways across CPUs, kernels, allocators, and storage stacks. A change that should help in theory can make no difference, or even hurt, because the real bottleneck was somewhere else.

That is why low-level performance work should be **measurement-driven**. Instead of guessing, use tools that show what is actually happening:

1. **Profilers** show where CPU time is spent.
2. **Hardware performance counters** reveal cache misses, branch mispredictions, and stalled cycles.
3. **OS counters and tracing** reveal context switches, page faults, run-queue lengths, and I/O waits.

Form a hypothesis, measure, change one thing, and measure again. The concepts in this deck tell you what to look for; measurement tells you which one is actually the problem.

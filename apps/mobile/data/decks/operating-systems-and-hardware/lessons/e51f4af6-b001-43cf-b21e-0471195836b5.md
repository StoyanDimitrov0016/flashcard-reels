# Atomics and memory ordering

Locks are built from something smaller. Underneath every mutex, semaphore, and lock-free queue are a few hardware instructions that update memory indivisibly, plus rules about the order in which one core's memory operations become visible to another. Most code should use locks and never touch these directly. But understanding them explains how locks work, what lock-free data structures promise, and why a "simple" flag variable shared between threads can fail in ways that seem impossible when you read the source code.

## Atomic operations

An **atomic operation** appears indivisible with respect to relevant concurrent observers under the architecture's memory model. No other thread can see it half done or slip a conflicting update into the middle of it.

The lost-update race on `hits++` happened because the increment was three separate steps. An atomic increment does all three as one:

```c
#include <stdatomic.h>

atomic_long hits = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        atomic_fetch_add(&hits, 1);   /* x86-64: one "lock xadd" instruction */
    return NULL;
}
```

Two workers now always produce exactly 2,000,000, with no mutex. CPUs provide atomic loads, stores, exchanges, and read-modify-write operations such as fetch-and-add, typically on naturally aligned values up to 8 or 16 bytes. Atomic operations are not free, since the core must own the cache line exclusively while updating it, but an uncontended one costs a few nanoseconds to a few tens of nanoseconds.

## Compare-and-swap

The most important atomic building block is **compare-and-swap (CAS)**. It atomically compares a memory location with an expected value and replaces it with a new value only if they match, reporting whether the update succeeded. In C11 it is `atomic_compare_exchange_weak` or `_strong`, which return `true` on success and, on failure, write the value actually found back into `expected`. On x86-64 the underlying instruction is `lock cmpxchg`.

CAS turns any "read, compute, write" step into a safe one through a retry loop. Here is an atomic "store the maximum" that no single instruction provides:

```c
void atomic_max(atomic_long *target, long value) {
    long seen = atomic_load(target);
    while (seen < value &&
           !atomic_compare_exchange_weak(target, &seen, value)) {
        /* another thread changed *target; seen now holds its value, retry */
    }
}
```

The loop reads the current value, decides what it should become, and tries to install it. If another thread changed the value in between, the CAS fails, `seen` is refreshed, and the loop tries again with up-to-date information. Nothing is ever lost, and no thread ever holds a lock.

## Lock-free progress

Locks have an uncomfortable property: if the thread holding a lock is descheduled, page-faults, or crashes, every thread that needs the lock is stuck. Algorithms built on atomics can promise more.

In a **lock-free** algorithm, the system as a whole is guaranteed to make progress even if individual threads may repeatedly fail and retry. The CAS loop above is lock-free. Whenever one thread's CAS fails, it is because another thread's CAS succeeded, so some operation always completes. What lock-freedom does not promise is fairness: an unlucky thread could, in principle, lose the race forever while others keep winning.

## Wait-free progress

In a **wait-free** algorithm, each participating operation is guaranteed to complete within a bounded number of its own steps, regardless of what other threads do. This is the strongest guarantee: no thread can starve. On x86-64, `atomic_fetch_add` is wait-free, because the hardware completes each `lock xadd` without retries. General wait-free data structures are much harder to design and often slower on average than lock-free ones, so they are used mainly where worst-case latency matters, such as real-time systems.

The progress guarantees form a ladder: blocking (a stalled thread can stop everyone), lock-free (the system always progresses), and wait-free (every thread progresses).

## Why source order is not observed order

Atomicity is only half the story. The other half is ordering. Consider a producer publishing data with a flag:

```c
int data = 0;
int ready = 0;

/* thread 1 */          /* thread 2 */
data = 42;              while (ready == 0) { }
ready = 1;              printf("%d\n", data);   /* can print 0 */
```

Reading the code, thread 2 cannot possibly see `ready == 1` but `data == 0`. It can. **Source-code order can differ from observed memory order** because compilers and CPUs may reorder independent operations for performance, while caches and store buffers delay the visibility of writes. The memory model's rules define what other threads may observe.

- The **compiler** sees two unrelated stores and may emit them in either order, or keep `ready` in a register so thread 2's loop never rereads it at all.
- The **CPU** may let stores and loads complete out of order. Each core puts its writes into a **store buffer** before they reach the cache, so its own later reads can run ahead of those writes becoming visible to other cores. ARM and POWER allow even two stores to become visible out of order; x86-64 keeps stores ordered but still lets a later load pass an earlier store.

A single thread always sees its own operations in program order. The surprises appear only when another thread watches. The **memory model**, of the language (C11, C++, Java, Go) and of the hardware, is the contract that says which orderings other threads may observe.

## Memory barriers

A **memory barrier**, or fence, constrains how memory operations may be reordered or observed across threads, providing the ordering that synchronization algorithms need. The fix for the example above is to make the flag atomic with release and acquire ordering:

```c
atomic_int ready = 0;

/* thread 1 */
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);

/* thread 2 */
while (atomic_load_explicit(&ready, memory_order_acquire) == 0) { }
printf("%d\n", data);   /* guaranteed to print 42 */
```

The release store guarantees that every write before it becomes visible before the flag does. The acquire load guarantees that reads after it cannot be performed before it. Together they establish a "happens-before" relationship: if thread 2 sees `ready == 1`, it sees `data == 42`. The compiler emits whatever barrier instructions the target CPU needs, which might be none on x86-64 and dedicated instructions on ARM. Standalone fences such as `atomic_thread_fence` exist for more unusual patterns.

This is also why locks work: acquiring a mutex has acquire semantics, releasing it has release semantics, so everything written inside one critical section is visible to the next thread that takes the lock. Code that uses locks correctly never has to think about barriers.

## Common mistakes

- Using `volatile` for thread communication in C or C++. It stops some compiler optimizations but provides neither atomicity nor ordering between threads.
- Assuming code that works on x86-64 is correct. Its relatively strong ordering hides bugs that appear on ARM.
- Equating lock-free with fast. Lock-free code avoids blocking, but contended atomics and retry loops can be slower than a good mutex.

## Key points

- An atomic operation appears indivisible to concurrent observers under the architecture's memory model.
- Compare-and-swap atomically replaces a value only if it still equals the expected value and reports whether it succeeded.
- A lock-free algorithm guarantees that the system as a whole makes progress, though individual threads may retry repeatedly.
- A wait-free algorithm guarantees each operation completes in a bounded number of its own steps, regardless of other threads.
- Compilers and CPUs reorder independent operations and store buffers delay visibility, so other threads may observe a different order than the source; the memory model defines what is allowed.
- A memory barrier constrains reordering and visibility across threads, giving synchronization the ordering it needs.

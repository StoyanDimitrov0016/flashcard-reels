# Main memory

A CPU core can finish several instructions per nanosecond, but it can only work on data that it has fetched from somewhere. That somewhere is main memory: gigabytes of storage that hold every running program's code and data. How memory is built, how values are laid out in it, and where it sits physically relative to each core all show up in both correctness and performance. This lesson covers the physical memory itself; the next one covers the caches that hide its slowness.

## DRAM

**Main memory**, usually DRAM (dynamic random-access memory), stores active program code and data. Compared with the caches inside the CPU, it has much higher capacity, gigabytes instead of megabytes, but much higher latency.

Some rough numbers for a current desktop or server:

```text
register access                  < 1 ns
L1 cache hit                     ~ 1 ns     (about 4 cycles)
DRAM access                     ~ 80-100 ns (hundreds of cycles at 3-4 GHz)
```

A single load that must go all the way to DRAM can cost as much time as several hundred simple instructions. DRAM is also volatile: its contents vanish when power is lost, which is why data meant to survive must eventually be written to storage.

Memory is addressed in bytes. Every byte has a numeric address, and a multi-byte value such as a 4-byte `int` or an 8-byte `double` occupies several consecutive addresses. That raises two questions: in which order are the bytes stored, and at which addresses may a value start?

## Endianness

**Endianness** defines the byte order used to represent multi-byte numeric values in memory or in protocols. Take the 32-bit value `0x12345678` stored at address `0x1000`:

```text
address          0x1000  0x1001  0x1002  0x1003
big-endian         12      34      56      78     most significant byte first
little-endian      78      56      34      12     least significant byte first
```

x86-64 and, in practice, ARM systems run little-endian. Many network protocols, including IP and TCP headers, use big-endian, which is why it is also called network byte order. Endianness never matters while a program works with whole values in its own memory. It matters the moment bytes cross a boundary: writing a binary file read on another machine, parsing a network header, or reinterpreting a byte buffer as an integer.

```c
#include <arpa/inet.h>
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint32_t x = 0x12345678;
    unsigned char *p = (unsigned char *)&x;
    printf("first byte in memory: %02x\n", p[0]);   /* 78 on x86-64 */
    uint32_t wire = htonl(x);                          /* convert to network byte order */
    printf("first byte on the wire: %02x\n", ((unsigned char *)&wire)[0]);  /* 12 */
    return 0;
}
```

The rule for portable code is simple: convert explicitly at the boundary, with functions such as `htonl` and `ntohl`, and never assume the other side shares your byte order.

## Alignment

**Memory alignment** places data at addresses preferred or required by the CPU for its type or access width. For most types that means an address that is a multiple of the value's size: a 4-byte `int` at an address divisible by 4, an 8-byte `double` at a multiple of 8.

Why does the hardware care? Memory is moved in fixed, aligned chunks, not byte by byte. An aligned value always lies inside one chunk; a misaligned one can straddle two, turning one access into two. The effect depends on the architecture:

- On some architectures, a misaligned access is a **correctness** problem: the CPU raises a fault. Older ARM and SPARC cores behave this way, and even on tolerant CPUs, atomic instructions usually require aligned operands.
- On others, including x86-64, misaligned accesses work but can be slower, especially when a value crosses a cache-line or page boundary.

Compilers handle alignment for you by inserting padding. The layout of this struct on x86-64 Linux shows it:

```c
struct record {
    char   tag;     /* offset 0, then 7 bytes of padding */
    double value;   /* offset 8 */
    char   flag;    /* offset 16, then 7 bytes of padding */
};                  /* sizeof(struct record) == 24 */
```

Reordering the fields to put `value` first and both `char` fields after it shrinks the struct to 16 bytes. Alignment problems appear mainly when code bypasses the compiler, for example by casting a pointer into the middle of a byte buffer: `*(uint32_t *)(buf + 1)` may fault on a strict architecture and is undefined behavior in C either way. Copying with `memcpy` is the portable fix.

## NUMA

On a laptop, every core reaches every byte of RAM at the same speed. Large servers are different. A two-socket machine has two processor packages, each with its own memory controllers and its own DIMMs attached.

**Non-Uniform Memory Access (NUMA)** systems have multiple memory regions, called nodes, where a CPU accesses its local memory faster than memory attached to another socket or node. Reaching remote memory means crossing the interconnect between sockets. On Linux, `numactl --hardware` shows the layout, including a table of relative distances:

```text
$ numactl --hardware
available: 2 nodes (0-1)
node 0 cpus: 0-15
node 1 cpus: 16-31
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

Here remote memory is described as about twice as far as local memory. In measured latency, a remote access typically costs something like 1.5 times a local one.

## Why NUMA locality matters

**NUMA locality matters** because threads that frequently access remote memory pay higher latency on every miss and add traffic to an interconnect that has limited bandwidth. Placing threads near their working data can noticeably improve performance.

Linux helps by default with a first-touch policy: a page of memory is physically allocated on the node of the CPU that first writes to it. That works well when each thread initializes and then uses its own data. It works badly when one thread initializes a large buffer and then 32 threads spread across both sockets read it, because half of them now access remote memory for everything. The kernel's automatic NUMA balancing can migrate pages toward the threads using them, and performance-sensitive services pin themselves explicitly:

```sh
numactl --cpunodebind=0 --membind=0 ./server
```

## Common mistakes

- Assuming endianness affects arithmetic inside a program. It only matters when bytes are exchanged or reinterpreted.
- Concluding that alignment does not matter because x86-64 tolerates misaligned loads. Other architectures fault, atomics need alignment, and misaligned accesses can still be slower.
- Treating all RAM on a large server as equally close to every core.

## Key points

- Main memory, usually DRAM, holds active code and data with far more capacity but far higher latency than CPU caches.
- Endianness is the byte order used for multi-byte values in memory or protocols; convert explicitly at boundaries.
- Alignment places data at addresses preferred or required for its type or access width.
- Misalignment can be a correctness problem on some architectures and a performance problem on others.
- In a NUMA system, a CPU reaches its local memory faster than memory attached to another socket or node.
- Remote memory access costs extra latency and interconnect traffic, so keeping threads near their data improves performance.

# Deadlock and priority inversion

Locks solve race conditions by making threads wait. But waiting is itself a source of failure. Threads can end up waiting for each other forever, or an urgent thread can end up waiting behind work that has nothing to do with it. Neither problem corrupts data, and neither shows up in single-threaded tests; the program just stops making progress, or misses its deadlines. This lesson covers both failures and the standard defenses against them.

## Deadlock

**Deadlock** is a cycle of waiting where each participant needs a resource or event held by another participant in the cycle. Nobody in the cycle can proceed, so nobody ever releases what the others need.

The classic example is a bank transfer that locks both accounts:

```c
void transfer(struct account *from, struct account *to, long amount) {
    pthread_mutex_lock(&from->lock);
    pthread_mutex_lock(&to->lock);
    from->balance -= amount;
    to->balance += amount;
    pthread_mutex_unlock(&to->lock);
    pthread_mutex_unlock(&from->lock);
}
```

This looks correct, and it works almost every time. Now two transfers run at once in opposite directions:

```text
thread 1: transfer(A, B)           thread 2: transfer(B, A)
lock A                 (ok)
                                   lock B                 (ok)
lock B                 (waits for thread 2)
                                   lock A                 (waits for thread 1)
... both wait forever
```

Thread 1 holds A and needs B; thread 2 holds B and needs A. That is a cycle of length two. Longer cycles through three or more threads work the same way, and so do cycles that involve events rather than locks: two services each waiting for the other's reply, or a task in a fixed-size thread pool waiting for another task that cannot start because every pool thread is busy waiting.

Deadlock requires four conditions to hold together: resources are held exclusively; a thread holds one resource while waiting for another; resources cannot be taken away from their holder; and the waiting forms a **circular wait**. Remove any one and deadlock is impossible. The first three are usually inherent to using locks, so practical prevention targets the fourth.

## Lock ordering

**Lock ordering** defines a global order for acquiring multiple locks, so threads cannot create circular wait dependencies. If every thread that needs both A and B always locks A first, then no thread can hold B while waiting for A, and the cycle above cannot form.

For the bank transfer, a natural order is the account ID:

```c
void transfer(struct account *from, struct account *to, long amount) {
    struct account *first  = from->id < to->id ? from : to;
    struct account *second = from->id < to->id ? to : from;
    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);
    from->balance -= amount;
    to->balance += amount;
    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}
```

Both threads now lock the lower-numbered account first; one of them simply waits for the other to finish. Large codebases document lock hierarchies, such as "the table lock before any row lock", and check them with tools. The Linux kernel's `lockdep` validator records the order in which locks are taken and warns about any potential inversion, even if no deadlock actually occurred during the run. ThreadSanitizer does the same for user-space programs.

Other defenses exist: hold only one lock at a time where possible, use `pthread_mutex_trylock` and back off if the second lock is busy, or use timeouts so that a stuck thread at least reports the problem. When a deadlock does happen, a stack dump of all threads, for example `thread apply all bt` in `gdb`, shows exactly which locks each thread holds and awaits.

## Priority inversion

Schedulers that support priorities add a subtler trap. **Priority inversion** occurs when a high-priority task is indirectly blocked by a low-priority task that holds a resource it needs, while medium-priority work prevents the low-priority task from running.

Consider three tasks on one core, with high (H), medium (M), and low (L) priority:

```text
t=0   L runs and locks mutex X
t=1   H wakes, preempts L, tries to lock X -> blocks (L holds it)
t=2   L resumes, still inside its critical section
t=3   M wakes, preempts L (M outranks L), runs a long computation
...   H waits for L, L waits for M: H is effectively blocked by M
t=50  M finally finishes, L releases X, H runs
```

H should have waited only for L's short critical section. Instead it waits for all of M, which it has no relationship with. The inversion is unbounded: as long as medium-priority work keeps arriving, H can wait indefinitely.

This is not a theoretical concern. In 1997 NASA's Mars Pathfinder lander kept resetting itself on Mars: a high-priority data-bus task waited on a mutex held by a low-priority meteorological task, which medium-priority communication tasks kept preempting, so a watchdog timer concluded the system had hung. Engineers fixed it remotely by enabling priority inheritance on that mutex.

## Priority inheritance

With **priority inheritance**, the OS temporarily raises the priority of a lock holder to that of the highest-priority task waiting for the lock, which helps it release the contested resource sooner. In the timeline above, when H blocks on X at t=1, L runs at H's priority. M can no longer preempt it, L finishes its critical section and releases X, drops back to its normal priority, and H runs immediately.

On Linux, POSIX mutexes can use it via the `PTHREAD_PRIO_INHERIT` protocol, set with `pthread_mutexattr_setprotocol`, and the kernel implements it internally for its real-time mutexes. It matters most in real-time and latency-critical systems that use strict priorities; under Linux's normal fair scheduler, a low-priority task still gets some CPU time, so inversions tend to cause delays rather than indefinite stalls.

## Common mistakes

- Assuming code is deadlock-free because it has never deadlocked in testing. Deadlocks depend on timing and may need rare interleavings.
- Acquiring locks in an order that depends on the arguments, such as "from" then "to", instead of a fixed global order.
- Believing priorities alone guarantee that urgent work runs first. Shared locks can make high-priority tasks wait on low-priority ones.

## Key points

- Deadlock is a cycle of waiting where each participant needs a resource or event held by another participant in the cycle.
- Lock ordering sets a global order for acquiring multiple locks so threads cannot form circular waits.
- Priority inversion is when a high-priority task is blocked by a low-priority lock holder while medium-priority work keeps that holder from running.
- Priority inheritance temporarily raises the lock holder to the waiter's priority so it releases the resource sooner.

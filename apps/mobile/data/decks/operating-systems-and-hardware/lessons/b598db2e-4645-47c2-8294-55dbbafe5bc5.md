# Virtual memory

Print the address of a variable in two different running programs and you may see the same number, say `0x55d4a0c02010`, in both, yet each program sees its own value there. That is possible because addresses in a program do not name locations on RAM chips. They are virtual addresses, which the hardware translates to physical ones on every single memory access, using tables the kernel maintains. This layer of indirection underpins process isolation, page faults, copy-on-write, memory-mapped files, and swapping, so it is worth understanding in detail.

## What virtual memory is

**Virtual memory** gives each process a logical address space that the OS and hardware map to physical memory or to other backing storage. On x86-64 Linux, a process's address space spans 128 TB of possible user addresses, most of it unused. The parts that are in use are mapped piece by piece to physical RAM, to files on disk, or to swap space, or they are marked as not yet backed by anything.

The program just issues loads and stores to virtual addresses. The CPU's **memory-management unit (MMU)** translates each one to a physical address using the current process's mappings.

## The problems it solves

Virtual memory solves several problems at once:

- **Isolation.** A process can only reach memory that is mapped into its own address space. There is no address it can form that reaches another process's memory or the kernel's, unless the kernel deliberately maps it.
- **Convenient, contiguous ranges.** A program can have a 1 GB array at contiguous virtual addresses even if the physical memory behind it is scattered across thousands of unrelated locations.
- **Controlled sharing.** The kernel can map the same physical memory into several processes. Every process that uses the C library shares one physical copy of its code.
- **Independent physical management.** The kernel can move pages, reclaim them, or back them with disk without the program's addresses ever changing.

## Pages and frames

Mapping every byte individually would need enormous tables, so memory is managed in blocks. A **page** is a fixed-size block of virtual memory used as the unit for address translation and many memory-management operations, such as setting permissions, loading from disk, and sharing. The standard page size on x86-64 and most ARM Linux systems is 4 KB. Physical memory is divided into blocks of the same size, called **frames**.

With 4 KB pages, the low 12 bits of an address (2^12 = 4096) are the **offset** within the page, and the remaining high bits are the **virtual page number**. Translation replaces the virtual page number with a physical frame number and keeps the offset unchanged.

## Page tables

A **page table** maps virtual page numbers to physical frames and stores permission and status bits used by the MMU. Each entry holds a frame number plus flags such as:

- **present**: whether the page is currently in physical memory;
- **writable**: whether stores are allowed;
- **user**: whether user-mode code may access it, or only the kernel;
- **no-execute**: whether instructions may be fetched from it;
- **accessed** and **dirty**: set by hardware when the page is read or written, which the kernel uses to decide what to evict.

A worked translation, using a simplified single-level table and 4 KB pages:

```text
virtual address        0x00403A7C
offset (low 12 bits)        0xA7C
virtual page number    0x00403
page table[0x00403]    frame 0x1F2B7, present, writable, user
physical address       0x1F2B7A7C   = frame 0x1F2B7 followed by offset 0xA7C
```

If the entry had lacked the writable bit, a store to this address would stop and hand control to the kernel instead.

A flat table covering 128 TB would be absurdly large, so real page tables are trees. x86-64 splits a 48-bit virtual address into four 9-bit indexes plus the 12-bit offset. Each index selects an entry in one level of the tree, and only the parts of the tree that cover mapped memory need to exist. The kernel switches between processes by pointing the MMU at a different tree root.

## The TLB

A four-level tree means that one translation could need four extra memory reads before the real access even starts. Doing that on every load and store would make programs several times slower.

The **translation lookaside buffer (TLB)** caches recent virtual-to-physical address translations, so most memory accesses do not require a full page-table walk. It is small and very fast: a typical core has around 64 entries in its first-level data TLB and one or two thousand in a second-level TLB. Thanks to locality, the vast majority of accesses hit it.

## TLB misses

On a **TLB miss**, the requested translation is absent from the TLB, so hardware or the OS must walk the page tables before the memory access can proceed. On x86-64 and ARM, a hardware page walker does this automatically, reading each level of the tree, often from the data caches. Some architectures, such as MIPS, instead trap to the kernel and let software fill the TLB. Either way, the access is delayed, sometimes by tens of cycles, sometimes by hundreds if the page-table entries themselves are not cached.

The amount of memory the TLB can cover without missing is its **reach**. With 1,536 entries of 4 KB each, reach is only 6 MB. A program that randomly touches a 20 GB in-memory index will miss the TLB constantly. That is why Linux supports **huge pages** of 2 MB (and 1 GB): each entry then covers 512 times more memory. Databases and JVMs often enable them, and Linux's transparent huge pages feature uses them automatically where it can.

## Common mistakes

- Thinking virtual memory means "using disk as extra RAM". Swapping is one use; translation, isolation, and sharing happen on every access even on machines with no swap at all.
- Confusing the TLB with the data caches. The TLB caches translations, not data; an access can hit one and miss the other.
- Assuming a large virtual size means large memory use. Mapped but untouched pages cost almost no physical memory.

## Key points

- Virtual memory gives each process a logical address space that the OS and hardware map to physical memory or other backing storage.
- It provides isolation, convenient contiguous address ranges, controlled sharing, and physical memory management independent of virtual addresses.
- A page is a fixed-size block of virtual memory, the unit of address translation and many memory-management operations.
- A page table maps virtual page numbers to physical frames and stores permission and status bits used by the MMU.
- The TLB caches recent virtual-to-physical translations so most accesses skip a full page-table walk.
- On a TLB miss, hardware or the OS must walk the page tables before the access can proceed.

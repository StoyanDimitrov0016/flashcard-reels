# Scheduling

A machine usually has far more threads than CPU cores. Most of them are asleep, waiting for input, a timer, or a disk, but at any moment several may be ready to run. Deciding who gets the CPU, and for how long, is the job of scheduling. Understanding it explains why some programs speed up with more threads and others slow down.

## The scheduler

The **scheduler** is the part of the kernel that chooses which runnable thread or process gets CPU time on each processor. A thread is **runnable** when it could make progress if given a core; a thread waiting for a disk read or a lock is **blocked** and is not a candidate until the event it waits for happens.

## Preemption and time slices

Modern general-purpose operating systems use **preemptive scheduling**: the OS can interrupt a running thread and switch to another, whether or not the running thread is willing to give up the CPU. A timer interrupt periodically hands control back to the kernel, which can then decide to run something else. Without preemption, one thread stuck in a long loop could keep the CPU indefinitely and starve everything else.

A **time slice** (also called a quantum) is the bounded interval a runnable task may execute before the scheduler can preempt it for another task. Short slices make the system feel responsive because waiting tasks get a turn quickly. Long slices waste less time on context switches. Schedulers balance the two, and a thread that blocks early simply gives up the rest of its slice.

## Measuring CPU demand

**CPU utilization** is the fraction of processor time spent doing non-idle work over an interval. A core that was busy for 600 ms out of a second was 60% utilized. On a multi-core machine the number is either reported per core or averaged across cores.

Utilization tells you how busy the CPUs were, but not how many tasks were waiting for them. **Load average** captures that demand. Conceptually it counts tasks that are runnable, plus on some systems tasks blocked in certain uninterruptible waits such as disk I/O, and smooths that count over time. A load average well above the number of cores means work is queuing. Exact definitions vary by operating system; Linux, for instance, includes tasks in uninterruptible sleep, so a high load can reflect slow storage rather than busy CPUs.

## CPU-bound and I/O-bound work

Workloads fall on a spectrum between two poles:

- A **CPU-bound** workload spends most of its time executing computations: compressing files, rendering, number crunching. It goes faster with more CPU capacity or a more efficient algorithm.
- An **I/O-bound** workload spends much of its elapsed time waiting for storage, the network, or other devices rather than running on the CPU. A web server waiting on database queries is typical. A faster CPU barely helps it.

Knowing which kind you have tells you where to look for improvements.

## Why concurrency helps I/O-bound programs

Imagine a program that fetches 100 web pages one after another, each taking 200 ms mostly spent waiting on the network. Sequentially, it takes 20 seconds while the CPU sits idle almost the whole time. If it issues many requests concurrently, **while one operation waits for I/O, another runnable task can use the CPU**. The waits overlap, the CPU and network are both used better, and throughput goes up dramatically. This works with threads, asynchronous I/O, or event loops; the principle is the same.

## Why too many threads hurt

Concurrency is not free, and more runnable threads do not create more cores. If a CPU-bound program on an 8-core machine starts 200 busy threads, only 8 can run at once. The rest wait, and the extra threads add cost:

- more **scheduling** decisions and **context switches**,
- more **cache disruption**, because each switch brings in a different working set,
- more **memory use**, since every thread needs its own stack,
- more **contention** for locks and shared data structures.

Throughput often drops instead of rising. A common rule is to size pools of CPU-bound workers near the number of cores, and to use more concurrency only when tasks spend much of their time waiting.

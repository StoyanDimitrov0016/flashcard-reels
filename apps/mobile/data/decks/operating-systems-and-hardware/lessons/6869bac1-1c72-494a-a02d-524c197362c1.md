# Containers and virtual machines

Much of today's software does not run directly on an operating system installed on bare hardware. It runs inside a container, a virtual machine, or a container inside a virtual machine. Both technologies let many isolated workloads share one physical machine, but they draw the isolation boundary at different levels. That difference decides how fast they start, how much memory they cost, what they can run, and how well they contain a compromised or misbehaving workload.

## Containers are processes

A **container** is one or more ordinary processes that are isolated and resource-controlled using operating-system features, such as namespaces and control groups, rather than a separate guest kernel. There is no "container" object in the Linux kernel. A process in a container is a normal process on the host, scheduled by the host kernel alongside everything else; it simply sees a restricted view of the system and is subject to resource limits.

Two Linux features do most of the work.

**Namespaces** give a group of processes its own view of a kind of system resource:

- **PID** namespace: the container's processes see their own process-ID space, where the first process is PID 1.
- **Mount** namespace: its own filesystem tree, typically built from an image.
- **Network** namespace: its own interfaces, IP addresses, routing table, and ports.
- **UTS**, **IPC**, and **user** namespaces: its own hostname, its own inter-process communication objects, and its own mapping of user IDs, so "root" inside can be an unprivileged user outside.

**Control groups (cgroups)** limit and account for resources: how much CPU time, memory, and I/O bandwidth a group of processes may use. When a container exceeds its memory limit, the kernel's out-of-memory killer acts within that cgroup only.

You can build the core of a container by hand on Linux:

```sh
$ sudo unshare --pid --fork --mount-proc --uts sh
# hostname sandbox
# ps -e
    PID TTY          TIME CMD
      1 pts/0    00:00:00 sh
      2 pts/0    00:00:00 ps
```

Inside, the shell believes it is PID 1 on a machine called `sandbox`. From the host, `ps` shows the same shell as an ordinary process with an ordinary PID. Container runtimes such as Docker and containerd add an image-based root filesystem, a network namespace, cgroup limits, and extra hardening such as dropped capabilities and `seccomp` system-call filters. With cgroup v2, a limit is just a file:

```sh
$ cat /sys/fs/cgroup/system.slice/docker-3f2a...scope/memory.max
536870912
```

Because nothing needs to boot, a container starts in milliseconds and costs little more memory than the processes inside it.

## Virtual machines

A **virtual machine** goes a level lower. It presents virtual hardware, meaning virtual CPUs, memory, disks, and network cards, and it runs a complete guest operating system, with its own kernel, on top of that hardware.

## How they differ

**A VM presents virtual hardware and runs a guest operating-system kernel, while a container normally shares the host kernel and isolates processes within it.** The consequences follow directly:

- **Kernel.** Every container on a host uses the host's kernel, so a Linux host runs Linux containers. A VM can run any operating system for that CPU architecture, such as Windows on a Linux host. Docker Desktop on macOS works by running Linux containers inside a small Linux VM.
- **Isolation.** A container's boundary is the host kernel's system-call interface, a large attack surface; a kernel vulnerability can let a process escape. A VM's boundary is the much narrower virtual hardware interface, so a compromised guest kernel still does not control the host. Multi-tenant clouds therefore put different customers in different VMs.
- **Cost.** A VM boots a whole kernel and reserves memory for it, taking seconds and hundreds of megabytes. Containers start in milliseconds and share one kernel's memory.

The line is blurring. Sandboxes such as gVisor interpose a user-space kernel between containers and the host, and lightweight VMs such as Firecracker, used by AWS Lambda, boot a minimal guest kernel in about a hundred milliseconds to give each function VM-level isolation with near-container speed. That is why a container is said to _normally_ share the host kernel: the common case, not a law.

## Hypervisors

A **hypervisor** creates and manages virtual machines by multiplexing physical CPU, memory, and devices among guest operating systems, much as a kernel multiplexes hardware among processes.

- **Type 1** hypervisors run directly on the hardware: Xen, VMware ESXi, Microsoft Hyper-V.
- **Type 2** hypervisors run as applications on a host OS: VirtualBox, VMware Workstation.
- **KVM** blurs the categories: it is a Linux kernel module that turns Linux itself into a hypervisor, with each VM running as a regular Linux process (often QEMU) whose threads act as virtual CPUs.

Modern CPUs make this efficient. Hardware virtualization extensions, Intel VT-x and AMD-V, let guest code, including the guest kernel, run directly on the real CPU at near-native speed, trapping to the hypervisor only for sensitive operations. Nested page tables add a second layer of address translation in hardware: guest virtual to guest physical, then guest physical to host physical. For devices, guests usually use paravirtualized drivers such as `virtio`, which exchange requests with the hypervisor through shared memory instead of emulating real hardware register by register.

## Common mistakes

- Thinking of a container as a lightweight VM with its own kernel. It is a set of host processes with a restricted view.
- Assuming containers provide the same isolation as VMs by default. For untrusted multi-tenant code, a shared kernel is a weaker boundary.
- Believing VMs are slow because they emulate the CPU. With hardware extensions, guest code runs natively; the overheads are in memory, startup, and I/O paths.

## Key points

- A container is one or more ordinary processes isolated and resource-controlled with kernel features such as namespaces and cgroups, not a separate guest kernel.
- A VM presents virtual hardware and runs its own guest kernel; a container normally shares the host kernel and isolates processes within it.
- A hypervisor creates and manages virtual machines by multiplexing physical CPU, memory, and devices among guest operating systems.
- Containers start fast and cost little; VMs cost more but offer a narrower isolation boundary and can run a different OS.

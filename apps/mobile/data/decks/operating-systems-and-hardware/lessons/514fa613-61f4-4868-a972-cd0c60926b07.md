# Processes and threads

When you run a program, the kernel does not just load its code and jump to it. It wraps the running program in a structure that owns memory, open files, and permissions, and it gives that structure one or more paths of execution that can be paused and resumed at any moment. These two ideas, the process and the thread, are how one machine with a handful of cores runs hundreds of programs at once. Choosing between them is one of the most common design decisions in concurrent software.

## Processes

A **process** is an executing program with its own virtual address space, resources, and operating-system bookkeeping. Concretely, on Linux a process owns:

- an **address space**: its private view of memory, holding code, global data, heap, and stacks;
- **resources** such as open file descriptors, network sockets, and memory mappings;
- **bookkeeping** the kernel keeps about it: a process ID, parent process, user and group IDs, signal handlers, resource limits, and accounting data.

A program is a file on disk; a process is one running instance of it. Run `python3` in three terminals and you get three processes with the same code and completely separate memory. On Linux, each process appears as a directory under `/proc`, such as `/proc/1234/`, where you can inspect its memory map, open files, and status.

## Threads

A **thread** is a schedulable execution path within a process. Every process starts with one thread, and it can create more. Each thread has its own:

- register values and program counter, meaning where it is in the code;
- stack, holding its function calls and local variables;
- scheduling state, such as whether it is running, runnable, or blocked.

Everything else is shared. Threads in the same process usually share the process's address space and many of its resources: global variables, the heap, open files, and the current directory. On Linux, threads and processes are both "tasks" created by the `clone` system call; a thread is simply a task created to share its parent's memory and file table. You can list the threads of all processes with `ps -eLf`.

## The main difference

The **main difference between processes and threads** is memory sharing. Processes have separate, protected address spaces by default, while threads within one process share memory and therefore need synchronization around shared mutable state.

This small C program makes the difference visible:

```c
#include <pthread.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int counter = 0;

void *bump(void *arg) { counter++; return NULL; }

int main(void) {
    if (fork() == 0) {          /* child process: gets its own copy of memory */
        counter++;
        return 0;
    }
    wait(NULL);
    printf("after child process: %d\n", counter);   /* prints 0 */

    pthread_t t;
    pthread_create(&t, NULL, bump, NULL);           /* thread: same memory */
    pthread_join(t, NULL);
    printf("after thread: %d\n", counter);          /* prints 1 */
    return 0;
}
```

The child process incremented its own copy of `counter`; the parent never sees it. The thread incremented the very same variable the main thread reads.

Each side of that trade-off has consequences:

- **Isolation versus cooperation.** A crash or memory corruption in one process cannot damage another; processes must communicate deliberately, through pipes, sockets, or explicitly shared memory. Threads communicate simply by reading and writing the same data, but a bug in one thread can corrupt data used by all of them, and one crashing thread takes down the whole process.
- **Cost.** Creating a thread is cheaper than creating a process, and switching between threads of one process is cheaper than switching between processes, because the address space stays the same.
- **Synchronization.** Two threads updating shared data without coordination can corrupt it. Later lessons cover the tools for this.

Browsers use processes to isolate tabs from each other; database servers and web servers often use threads to share caches and connections cheaply.

## Context switches

A core runs one instruction stream at a time, yet a machine may have hundreds of threads wanting to run. The kernel multiplexes them. A **context switch** saves the execution state of one running thread or process and restores another's, so the CPU can run different work.

The saved state includes the general-purpose registers, the program counter, the stack pointer, and floating-point and vector registers. When the kernel switches between threads of different processes, it also switches the active address space by pointing the memory-management hardware at the new process's page tables.

A context switch happens when the running thread blocks, for example waiting for a disk read or a lock, when it yields voluntarily, or when the kernel preempts it after its turn is used up. On Linux, `vmstat 1` shows the system-wide rate in its `cs` column, and a busy server can do tens of thousands of switches per second.

## Why context switches are not free

**Context switches are not free.** There are two kinds of cost:

- **Direct cost**: kernel work that does nothing for the application, such as entering the kernel, choosing the next thread, saving and restoring registers, and switching address spaces. This is typically on the order of a microsecond or a few microseconds.
- **Indirect cost**, which is often larger: the newly running thread finds the CPU caches, the translation caches that speed up address lookups, and the branch predictor's history filled with the previous thread's state. Until that state warms up again, the thread runs slower than it would have without the switch.

A thread that runs for 50 microseconds between switches may spend a meaningful fraction of that time just recovering from the last switch. That is why systems that handle huge numbers of concurrent connections often avoid one thread per connection and instead use a few threads with event loops, keeping each thread on its core longer.

## Common mistakes

- Assuming threads have private globals or heap objects. Only the stack and registers are per thread; everything else is shared.
- Thinking only process switches cost anything. Thread switches within a process skip the address-space change but still pay kernel work and cache disruption.
- Treating "process" and "program" as synonyms. One program can run as many processes.

## Key points

- A process is an executing program with its own virtual address space, resources, and OS bookkeeping.
- A thread is a schedulable execution path within a process; threads of one process share its address space and many resources.
- Processes have separate protected address spaces by default; threads share memory and need synchronization around shared mutable state.
- A context switch saves one thread's or process's execution state and restores another's so the CPU can run different work.
- Context switches cost kernel work and disrupt caches, translation caches, and branch prediction state, reducing useful execution time.

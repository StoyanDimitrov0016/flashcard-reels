# Devices and interrupts

Disks, network cards, keyboards, and timers all work at their own pace, independently of the CPU. The operating system needs ways to learn when a device has something to report, and ways to move data without wasting the processor's time. This lesson covers the basic mechanisms: interrupts, polling, direct memory access, and device drivers.

## Interrupts

An **interrupt** is a signal that makes the CPU pause what it is doing and transfer control to an operating-system handler for an event that needs attention. When the handler finishes, the interrupted work resumes as if nothing had happened.

Interrupts come from two directions:

- **Hardware interrupts** are raised by devices.
- **Software interrupts** are raised by instructions, for example to enter the kernel or to report an exception such as division by zero.

The timer interrupt is what makes preemptive scheduling possible: it periodically returns control to the kernel no matter what a thread is doing.

## Hardware interrupts versus polling

Devices use **hardware interrupts** to tell the CPU about events such as a completed disk read, an arriving network packet, or a key press. The CPU can do other work in the meantime and only reacts when something actually happens, instead of constantly asking.

The alternative is **polling**: repeatedly checking a device status register or condition for changes. Polling wastes CPU when nothing is happening, because every check that finds nothing is lost work. It is not always worse, though. Handling an interrupt has overhead, and when events arrive very frequently, or when the lowest possible reaction latency matters, checking in a tight loop can react faster and cost less than taking an interrupt per event. High-speed network and storage stacks often switch between the two, using interrupts when traffic is light and polling under heavy load.

## Direct memory access

Once a device has data, it still has to reach memory. Without help, the CPU would copy it one word at a time, executing instructions for every byte. **Direct Memory Access (DMA)** removes that burden. The CPU configures a transfer once, telling the device where in memory to read or write and how much, and the device then moves the data to or from main memory itself, with limited CPU involvement. When the transfer completes, the device typically raises an interrupt.

DMA **improves I/O efficiency** because the CPU no longer copies every byte through instructions. While the device and memory controller move whole blocks, the CPU is free to run other work. Combined with interrupts, this is the standard pattern for disks and network cards: set up DMA, go do something else, get interrupted when it is done.

## Device drivers

Every piece of hardware speaks its own language of registers, command formats, and quirks. A **device driver** is operating-system code that translates generic kernel operations, such as "read these blocks" or "send this packet", into the commands and data handling specific to one device. Drivers let the rest of the kernel, and every application above it, use a uniform interface regardless of which vendor made the hardware.

Because drivers usually run in kernel mode, they carry full privileges. A bug in a driver can crash the whole system, which is why driver quality matters so much to overall stability.

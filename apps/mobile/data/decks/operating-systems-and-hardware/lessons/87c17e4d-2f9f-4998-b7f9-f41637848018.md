# Synchronization primitives

Threads in one process share memory, which makes cooperation cheap and mistakes easy. When two threads touch the same data without coordination, the result depends on exactly how their instructions happen to interleave, and the scheduler can interleave them differently on every run. The resulting bugs appear once in a million runs, vanish under a debugger, and corrupt data silently. Synchronization primitives exist to take timing out of the correctness equation. This lesson covers the problem and the standard tools: mutexes, spinlocks, semaphores, condition variables, and reader-writer locks.

## Race conditions

A **race condition** occurs when program correctness depends on the timing or interleaving of concurrent accesses that are not properly synchronized. The classic example is two threads incrementing a shared counter:

```c
long hits = 0;
void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        hits++;              /* not one step: load, add, store */
    return NULL;
}
```

`hits++` compiles to three steps: load the value into a register, add one, store it back. Here is one possible interleaving on two cores:

```text
thread A                 thread B                 hits in memory
load hits  -> 5                                   5
                         load hits  -> 5          5
add        -> 6                                   5
                         add        -> 6          5
store 6                                           6
                         store 6                  6   (one increment lost)
```

Run two such workers and the final count is usually well below 2,000,000, and different each time. In C and C++, unsynchronized concurrent access where at least one side writes is called a **data race** and is undefined behavior outright, so the compiler is allowed to produce even stranger results.

## Critical sections

A **critical section** is code that accesses shared state in a way that must not overlap with conflicting concurrent execution. The load-add-store of `hits` is one. So is "check whether the key exists in the map, and insert it if not": if two threads both check before either inserts, both insert. The goal of synchronization is to make each critical section behave as if it ran all at once, with no other thread able to see or change the state halfway through.

## Mutexes

A **mutex** (mutual exclusion lock) is a synchronization primitive that allows only one execution path at a time to enter a protected critical section. A thread locks it on entry and unlocks it on exit; any other thread that tries to lock it in between must wait.

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&lock);
hits++;                      /* only one thread at a time runs this */
pthread_mutex_unlock(&lock);
```

With the lock, the two workers always produce exactly 2,000,000. The rule that makes mutexes work is discipline: every access to the protected data, reads included, must hold the same lock.

## Spinlocks and blocking mutexes

What does a thread do while it waits for a lock? There are two basic answers.

A **spinlock** repeatedly checks the lock in a tight loop instead of sleeping. Handing over the lock is as fast as it can be, because the waiter notices the moment it is released, but the waiting core does no useful work while it spins. Spinning can be efficient only when waits are expected to be extremely short, a few hundred nanoseconds, and when the lock holder is actively running on another core. The Linux kernel uses spinlocks for tiny critical sections, including ones in interrupt handlers, where sleeping is not an option.

A **blocking mutex** puts the waiting thread to sleep and lets the scheduler run something else on that core, then wakes the thread when the lock is released. Sleeping and waking cost a pair of context switches, microseconds of work. **A blocking mutex is preferable to a spinlock when contention may last long enough that yielding the CPU costs less than burning cycles repeatedly checking the lock**: when the critical section does I/O, when it is long, or when there are more runnable threads than cores. A spinning waiter can even prevent the lock holder from running if they share a core.

In practice the two are combined. On Linux, `pthread_mutex_lock` is built on the **futex** system call: an uncontended lock or unlock is a single atomic instruction in user space with no system call at all, and only a thread that actually has to wait asks the kernel to put it to sleep. Many implementations also spin briefly before sleeping, betting that the lock will be released soon.

## Semaphores

A **semaphore** maintains a count of permits. Acquiring consumes a permit or waits if none are left, and releasing returns a permit, which allows bounded concurrent access. A mutex allows exactly one thread in; a semaphore initialized to N allows up to N.

```c
#include <semaphore.h>

sem_t slots;
sem_init(&slots, 0, 3);      /* at most 3 concurrent connections */

sem_wait(&slots);            /* take a permit, or sleep until one is free */
use_database_connection();
sem_post(&slots);            /* return the permit */
```

Semaphores are a natural fit for limiting access to a pool of identical resources, such as connections, worker slots, or buffers.

## Condition variables

Sometimes a thread must wait not for a lock but for shared state to reach some condition, such as "the queue is not empty". A **condition variable** lets threads sleep until shared state may satisfy a condition. It is always used together with a lock that protects the state and a loop that rechecks the condition, called the **predicate**:

```c
pthread_mutex_lock(&lock);
while (queue_is_empty(&q))                 /* the predicate, rechecked in a loop */
    pthread_cond_wait(&not_empty, &lock);  /* atomically unlocks, sleeps, relocks */
item = queue_pop(&q);
pthread_mutex_unlock(&lock);

/* producer */
pthread_mutex_lock(&lock);
queue_push(&q, item);
pthread_cond_signal(&not_empty);
pthread_mutex_unlock(&lock);
```

`pthread_cond_wait` releases the lock while sleeping, so the producer can get in, and reacquires it before returning.

## Why the predicate must be rechecked

**A condition-variable wait must recheck the predicate** because returning from the wait proves nothing. Two things can go wrong:

- **Spurious wakeups.** The implementation is allowed to wake a waiter even though nobody signaled, and POSIX explicitly permits this.
- **Stolen wakeups.** The producer pushes one item and signals. Before the woken consumer reacquires the lock, a second consumer that was not even waiting grabs the lock and takes the item. When the first consumer finally runs, the queue is empty again.

With `if` instead of `while`, the consumer would pop from an empty queue. Correct code treats a notification as a reason to check again, never as proof that the condition holds.

## Reader-writer locks

Many shared structures, such as configuration, routing tables, and caches, are read constantly and written rarely. A mutex serializes readers that could safely run in parallel. A **reader-writer lock** allows multiple concurrent readers or one exclusive writer. It helps when reads dominate and critical sections are long enough for parallel reading to matter.

It has a known hazard: if readers keep arriving, there may never be a moment with zero readers, and a waiting writer starves. Good implementations avoid starvation, typically by blocking new readers once a writer is waiting. Check your platform's policy: glibc's `pthread_rwlock_t` prefers readers by default. Under heavy write contention, a reader-writer lock can also be slower than a plain mutex, because its own bookkeeping is shared state that every reader modifies.

## Common mistakes

- Protecting writes but not reads. A reader without the lock can see half-updated state.
- Waiting on a condition variable with `if` instead of `while`.
- Using a spinlock in user-space code with long or blocking critical sections.
- Believing a race that "never happens in testing" is harmless. It happens in production, under load.

## Key points

- A race condition is when correctness depends on the timing or interleaving of unsynchronized concurrent accesses.
- A critical section is code accessing shared state that must not overlap with conflicting concurrent execution.
- A mutex lets only one execution path at a time enter a protected critical section.
- A spinlock busy-waits instead of sleeping and pays off only for extremely short waits; a blocking mutex is better when yielding costs less than spinning.
- A semaphore holds a permit count: acquiring takes a permit or waits, releasing returns one, which bounds concurrent access.
- A condition variable lets threads sleep until a condition may hold, used with a lock and a loop that rechecks the predicate, because wakeups can be spurious or the state can change before the lock is reacquired.
- A reader-writer lock allows many concurrent readers or one exclusive writer, useful when reads dominate and starvation is avoided.

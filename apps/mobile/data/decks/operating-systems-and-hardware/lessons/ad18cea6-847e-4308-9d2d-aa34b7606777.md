# The operating system kernel

A computer is a pile of shared hardware: a few CPU cores, one pool of RAM, some disks, a network card. Dozens of programs want to use all of it at once, and none of them should be able to wreck the others. Something has to divide that hardware fairly, protect programs from each other, and hide the ugly details of every device behind simple interfaces. That something is the operating system, and its heart is the kernel. Almost every topic in this deck, from scheduling to file durability, is a detail of how the kernel does this job.

## What an operating system does

An **operating system** manages hardware resources and provides abstractions that programs use instead of raw hardware. Each abstraction replaces something messy with something a program can reason about:

- A **process** stands in for "a whole computer to myself". The program runs as if it owned a CPU and memory.
- **Virtual memory** stands in for physical RAM chips. Each process sees its own private range of addresses.
- A **file** stands in for disk blocks. A program asks for `/var/log/app.log`, not for sectors on a particular drive.
- A **socket** stands in for the network card. A program sends bytes to an address and port, not packets on a wire.
- **Device access** goes through uniform interfaces, so a program can print to a terminal without knowing which terminal it is.

Two jobs run through all of this: dividing resources among programs (who gets the CPU, how much memory) and making the hardware usable (abstractions instead of device registers).

## The kernel

The **kernel** is the privileged core of the operating system. It is the part that manages CPU scheduling, memory, devices, and protection, and it is the part programs call into through system calls when they need something done. On Linux, the kernel is the `vmlinuz` image loaded at boot; everything else you may think of as "the OS", such as the shell, `systemd`, `ls`, and the desktop, is ordinary programs running on top of it.

What makes the kernel special is not the code itself but the privilege it runs with. That privilege is enforced by the CPU.

## User mode and kernel mode

Modern CPUs can run in at least two execution modes:

- **User mode** is restricted. Applications run here. Code in user mode cannot directly execute privileged instructions, such as those that change memory mappings, disable interrupts, or talk to devices, and it cannot access protected kernel memory. If it tries, the CPU refuses and hands control to the kernel, which usually kills the offending process.
- **Kernel mode** is privileged. The operating system runs here so it can manage hardware and protected resources: program the memory-management unit, talk to device controllers, and switch between programs.

On x86 these modes are called ring 3 and ring 0; on ARM they are exception levels EL0 and EL1. The names differ, but the idea is the same: the hardware itself guarantees that only kernel code can touch the machine directly. This is why a buggy application crashes only itself rather than the whole computer, and why one program cannot read another program's memory.

## System calls

If user code cannot touch hardware, how does a program read a file or open a network connection? It asks the kernel. A **system call** is a controlled transition from user code into the kernel to request an operating-system service, such as reading a file, creating a process, or sending data on a socket.

"Controlled" is the key word. User code cannot jump to an arbitrary address inside the kernel. On x86-64 Linux, a program puts a system-call number in the `rax` register and the arguments in other registers, then executes the `syscall` instruction. The CPU switches to kernel mode and jumps to a single entry point the kernel registered at boot. The kernel looks up the requested service by number, checks the arguments, does the work, and returns to user mode with a result.

Most programmers never write that instruction by hand. C library functions such as `read`, `write`, and `open` are thin wrappers around it:

```c
#include <unistd.h>

int main(void) {
    const char msg[] = "hello\n";
    write(1, msg, sizeof msg - 1);   /* system call: write to fd 1 (stdout) */
    return 0;
}
```

On Linux you can watch the system calls a program makes with `strace`:

```sh
$ strace -e trace=write ./hello
write(1, "hello\n", 6)                  = 6
hello
```

## Why system calls cost more than function calls

An ordinary function call is a jump to other code in the same address space, with the same privileges, costing a nanosecond or two. A system call does more:

1. It **crosses a protection boundary**. The CPU switches privilege level on entry and exit, and saves and restores user state.
2. The kernel must **validate** everything it receives. A pointer from user space might point at kernel memory or at nothing, so the kernel checks it and copies data across carefully.
3. The call may involve **scheduling**. A `read` on an empty network socket puts the caller to sleep and runs something else until data arrives.
4. It may involve real **device work**, such as starting a disk read.

Even a system call that does almost nothing typically costs tens to hundreds of nanoseconds on current hardware, and security mitigations against CPU side-channel attacks have made the boundary crossing more expensive on many machines.

A concrete example: writing a 1 MB file one byte at a time with `write` makes 1,048,576 system calls. Writing it in 64 KB chunks makes 16. The data is identical, but the first version pays the boundary cost a million times. This is why buffered I/O libraries such as C's `stdio` collect small writes in memory and pass them to the kernel in large batches.

## Common mistakes

- Treating "the OS" and "the kernel" as the same thing. The kernel is the privileged core; shells, daemons, and utilities are user-mode programs.
- Thinking a library call is always a system call. `strlen` never enters the kernel; `printf` enters it only when its buffer is flushed.
- Assuming kernel mode is a special kind of process. It is a CPU privilege level; the same thread runs in user mode, enters kernel mode for a system call, and returns.

## Key points

- An operating system manages hardware resources and provides abstractions such as processes, virtual memory, files, sockets, and device access.
- The kernel is the privileged core of the OS, responsible for CPU scheduling, memory, devices, protection, and system calls.
- User mode is restricted: applications cannot execute privileged instructions or access protected kernel memory.
- Kernel mode is privileged: the OS uses it to manage hardware and protected resources.
- A system call is a controlled transition from user code into the kernel to request a service such as reading a file or creating a process.
- System calls cost more than function calls because they cross a protection boundary and may involve privilege transitions, argument validation, scheduling, or device work.

# Inside the CPU

A modern processor does far more than execute one instruction after another. It overlaps instructions, guesses where code will go next, runs work out of order, and keeps copies of memory close at hand. These tricks are mostly invisible to correct programs, but they shape performance, and knowing them explains why two programs doing the "same" amount of work can differ in speed by an order of magnitude.

## Cores and hardware threads

A **core** is an independent hardware execution engine that can run its own instruction stream. It usually has its own execution units and its own small caches. A chip with eight cores can genuinely run eight threads at the same instant.

**Simultaneous multithreading (SMT)**, which Intel markets as Hyper-Threading, lets one physical core hold several hardware thread contexts, typically two. The core can issue instructions from either context, filling execution resources that one thread alone would leave idle, for example while that thread waits on memory.

Two hardware threads are **not the same as two full cores**. SMT threads share most of the core's resources, including execution units and caches. If both threads want the same resources, such as two heavy floating-point loops, they mostly take turns and the gain is small. If their needs differ, or one often stalls, the gain can be substantial. The benefit depends on the workload.

## Pipelines

An **instruction pipeline** splits executing an instruction into stages, such as fetch, decode, execute, and retire, and overlaps them across instructions. While one instruction executes, the next is being decoded and the one after that fetched. Like an assembly line, several instructions are in progress at once, and throughput rises even though each instruction still takes several cycles.

## Branch prediction

Pipelines need to know which instruction comes next, but a conditional branch is not resolved until late in the pipeline. Rather than stall, the CPU uses **branch prediction**: it predicts both whether a branch is taken and where it goes, then keeps fetching and executing along the predicted path **speculatively**.

Predictors are very accurate on regular patterns, like a loop that runs many times. When the guess is wrong, the **branch misprediction cost** is paid: all speculative work on the wrong path is discarded and the pipeline refills from the correct path, wasting many cycles. Code with unpredictable branches on random data can run far slower than the same logic on sorted data.

## Out-of-order execution and dependencies

If an instruction stalls, for example waiting for a value from memory, later instructions that do not need that value could still run. With **out-of-order execution**, the CPU executes independent instructions ahead of older stalled ones when dependencies allow, then **retires** results in the original program order, so the architecturally visible result is as if everything ran in sequence.

What limits this is an **instruction-level dependency**: one instruction needs a value or resource produced or constrained by another. In the code below, the second line must wait for the first, while the third is independent and can run in parallel with both.

```c
a = x * y;
b = a + 1;  // depends on a
c = z * 2;  // independent
```

Long chains of dependent operations leave the CPU little to overlap; many independent operations let it keep all its units busy.

## CPU caches

Main memory is slow compared with the core: a trip to RAM can cost hundreds of cycles. A **CPU cache** is small, fast memory near the processor that keeps recently or predictably used blocks of memory, so most accesses avoid main memory.

There are **multiple cache levels** because of a physical trade-off. A small cache can be very fast but holds little; a large one holds more but is slower and costlier. A hierarchy balances latency, capacity, and hardware cost: a tiny L1 per core that answers in a few cycles, a larger L2, and often a big L3 shared among cores.

## Locality and cache lines

Caches work because programs show **cache locality**: they tend to access data used recently or located near recently used addresses. It comes in two forms:

- **Temporal locality**: data accessed recently is likely to be accessed again soon, like a loop counter.
- **Spatial locality**: memory near a recently accessed address is likely to be accessed soon, like the next element of an array.

Caches move data in fixed-size blocks called **cache lines**, commonly 64 bytes. Reading one byte brings its whole line into the cache, so walking an array sequentially is fast, while chasing pointers scattered across memory is slow.

## Sharing caches between cores

Each core has its own caches, so the same memory can be cached in several places. **Cache coherence** protocols keep these copies consistent enough that writes to a shared location become visible to other cores according to the architecture's memory model. Typically, a core must gain exclusive ownership of a line before writing it, which invalidates copies elsewhere.

That leads to **false sharing**. Suppose two threads each update their own counter, but the counters sit in the same cache line. Logically they share nothing, yet every write forces the line to bounce between cores. The fix is to pad or separate such data so each hot variable gets its own line.

## Main memory

Beyond the caches sits **main memory**, usually DRAM. It stores active program code and data with much higher capacity than caches, but with much higher latency. The whole cache hierarchy exists to hide that latency as often as possible.

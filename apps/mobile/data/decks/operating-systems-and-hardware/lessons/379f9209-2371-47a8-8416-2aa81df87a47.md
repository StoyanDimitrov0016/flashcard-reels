# Page faults

The page table does more than translate addresses. Because every access passes through it, the kernel can deliberately leave entries missing or read-only and get notified the moment a program touches that memory. That notification is the page fault, and it turns out to be one of the kernel's most useful tools. It lets memory be allocated lazily, processes be copied almost for free, and files be read simply by touching memory. This lesson explains the mechanism and the three techniques built on it.

## What a page fault is

A **page fault** occurs when a virtual-memory access cannot proceed with the current page-table entry, which causes the OS to handle the condition, for example by loading a page or by rejecting an invalid access. The entry might be marked not present, or the access might violate its permissions, such as a write to a read-only page.

The CPU stops the faulting instruction and transfers control to the kernel's page-fault handler, passing the faulting address and the kind of access. The kernel then checks what that address is supposed to be:

- **A legitimate access to memory that is not ready yet.** The kernel allocates or loads the page, fixes the page-table entry, and restarts the instruction. The program never notices, apart from the delay.
- **An invalid access**, such as a null pointer dereference, a write to a truly read-only region like program code, or a stray pointer into unmapped space. The kernel delivers a signal, on Linux `SIGSEGV`, which by default kills the process with the familiar "Segmentation fault".

Linux distinguishes **minor faults**, resolved without I/O (for example by handing out a zeroed page or mapping a page already in memory), from **major faults**, which must read from disk and are thousands of times slower.

## Demand paging

With **demand paging**, pages are loaded or physically allocated when first accessed instead of eagerly bringing an entire address space into memory. When a program starts, the kernel maps its executable file into the address space but loads nothing; each page of code is read in the first time it executes. When a program asks for memory, the kernel reserves an address range and allocates physical frames only as pages are touched.

A worked example on Linux:

```c
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *buf = malloc(1UL << 30);   /* reserve 1 GB of address space */
    memset(buf, 1, 10 << 20);        /* touch only the first 10 MB */
    return 0;
}
```

```sh
$ /usr/bin/time -v ./a.out
    Maximum resident set size (kbytes): 11688
    Minor (reclaiming a frame) page faults: 2627
```

The process reserved 1 GB but used only about 11 MB of physical memory. Touching 10 MB means touching 2,560 pages of 4 KB, and each first touch triggered a minor fault that supplied a zeroed frame; the rest of the faults come from program startup. The other 1,014 MB never cost anything.

Demand paging makes programs start quickly and lets them reserve generous address ranges cheaply. It is also why Linux can promise more memory than it has, a policy called overcommit, and why a process can be killed by the out-of-memory killer later, when it finally touches memory the system cannot supply.

## Copy-on-write

**Copy-on-write** means multiple users initially share the same read-only physical data; when one of them writes, the system creates a private copy of the affected page or object. Page faults make this cheap to implement: the kernel maps the shared frames read-only in every sharer, and the first write to a page raises a fault. The handler recognizes the page as copy-on-write, copies just that one page, maps the copy writable for the writer, and restarts the write.

## Copy-on-write when creating a process

On Unix-like systems, `fork` creates a child process whose memory is a duplicate of the parent's. Copying all of it immediately would be slow and usually pointless, since a common next step is `exec`, which throws the copy away to run a different program.

**Copy-on-write is useful when creating a process** because the child can initially share the parent's memory pages instead of copying all memory immediately, paying copying cost only for pages that are later modified. Linux copies only the page tables and marks the writable pages read-only in both processes:

```text
before fork     parent: 2 GB of private memory
fork            child shares all 2 GB; page tables copied, pages marked read-only
child writes    one page faults; kernel copies 4 KB for the child
exec            child's mappings discarded; total copied: a few pages
```

Redis uses this deliberately for snapshots. It forks, and the child writes the frozen dataset to disk while the parent keeps serving traffic. Memory grows only by the pages the parent modifies during the snapshot, not by the full dataset.

## Memory mapping

**Memory mapping** maps file contents or device regions into a process address space so that ordinary memory loads and stores access them. On Linux the system call is `mmap`:

```c
#include <fcntl.h>
#include <sys/mman.h>
#include <sys/stat.h>

int fd = open("data.bin", O_RDONLY);
struct stat st;
fstat(fd, &st);
const unsigned char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
unsigned char b = p[123456789];   /* may fault; kernel reads that page of the file */
```

No data is read by `mmap` itself. The first touch of each page faults, and the handler fills it from the file, which is demand paging applied to a file. Device drivers can also let processes map device memory, such as a GPU's buffers, directly into their address space.

## What memory-mapped files are useful for

**A memory-mapped file lets the OS page file regions in on demand** and lets applications access file data through memory addresses instead of explicit `read` calls for each region. That pays off in several situations:

- **Large files accessed randomly**, such as database indexes and search indexes. The program follows offsets like pointers, and only the pages it touches are read.
- **Sharing between processes.** Processes that map the same file with `MAP_SHARED` share the same physical pages.
- **Avoiding a copy.** The mapping points at the kernel's cached copy of the file, so there is no extra copy into a separate user buffer.

The trade-offs: I/O happens invisibly during ordinary memory accesses, so a slow disk stalls code that "just reads an array", and an I/O error or a file truncated by another process arrives as a `SIGBUS` signal rather than as an error code.

## Common mistakes

- Treating every page fault as an error. Most are routine and resolved invisibly; only invalid accesses end in a segmentation fault.
- Assuming `malloc` of a large size immediately uses that much RAM. Physical memory is committed page by page on first touch.
- Believing `fork` copies the whole address space. With copy-on-write it copies page tables and duplicates pages only when they are written.

## Key points

- A page fault happens when an access cannot proceed with the current page-table entry; the OS then loads or allocates the page or rejects the access.
- Demand paging loads or allocates pages on first access instead of bringing the whole address space into memory up front.
- Copy-on-write lets several users share read-only physical data and creates a private copy of a page only when one of them writes.
- Copy-on-write makes process creation cheap: the child shares the parent's pages and copies only those later modified.
- Memory mapping places file contents or device regions in the address space so ordinary loads and stores access them.
- Memory-mapped files let the OS page file regions in on demand and let programs use addresses instead of explicit read calls.

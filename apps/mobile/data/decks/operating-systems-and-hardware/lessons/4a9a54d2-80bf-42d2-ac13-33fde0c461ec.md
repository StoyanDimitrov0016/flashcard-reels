# Filesystems

A storage device offers only a huge array of numbered blocks. Nobody wants to remember that their thesis lives in blocks 88,112,640 through 88,113,151. A filesystem turns that raw array into named files in a tree of directories, keeps track of who may read them, and must keep all of its bookkeeping consistent even if the power fails in the middle of an update. This lesson looks at how Unix-like filesystems such as Linux's ext4 and XFS organize data, what links really are, and how journaling protects against crashes.

## What a filesystem does

A **filesystem** organizes persistent data into named files and directories and tracks the metadata needed to locate, protect, and update file contents. That metadata includes each file's size, owner, permissions, timestamps, and, crucially, which blocks on the device hold its data. The filesystem also tracks which blocks are free, so new data can be placed.

On Linux you can see which filesystems are mounted where with `df -T` or `findmnt`. Each has its own on-disk format, but they all present the same interface to programs: paths, directories, and the `open`, `read`, and `write` system calls.

## Inodes and directories

Unix-like filesystems separate what a file is from what it is called. An **inode** stores a file's metadata and references to its data blocks, but not its name. Each inode has a number that is unique within its filesystem. A **directory** is a special file whose contents are entries that map names to inode numbers.

```sh
$ stat notes.txt
  File: notes.txt
  Size: 1832        Blocks: 8          IO Block: 4096   regular file
Device: 259,2       Inode: 1319544     Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/     ana)   Gid: ( 1000/     ana)
Modify: 2026-09-12 10:31:07.000000000 +0200
```

Everything shown here except the name comes from inode 1319544. Resolving a path such as `/home/ana/notes.txt` means walking the tree: read the root directory to find the inode for `home`, read that directory to find `ana`, read that one to find `notes.txt`, and arrive at inode 1319544. The kernel caches these lookups so repeated resolution is fast.

## Hard links

Because names live in directories and files live in inodes, one inode can have more than one name. A **hard link** is another directory entry referring to the same underlying file object, so deleting one name does not remove the file while other links remain.

The inode keeps a **link count**, the `Links` field shown by `stat`. Removing a name with `rm` actually calls `unlink`, which deletes the directory entry and decrements the count. The file's data is freed only when the count reaches zero and no process still has the file open.

Hard links have restrictions: both names must be on the same filesystem, since inode numbers are only unique within one, and ordinary users cannot hard-link directories, which would allow loops in the tree.

## Symbolic links

A **symbolic link** (symlink) is a special file containing a path to another filesystem object; resolving it follows that path at access time. It has its own inode, and its content is just the text of the target path. Because it stores a path rather than an inode number, a symlink can cross filesystems and point to directories. It can also dangle: if the target is renamed or deleted, the symlink still exists but points at nothing.

A shell session makes the difference concrete:

```sh
$ echo "hello" > original.txt
$ ln original.txt hard.txt          # hard link: second name for the same inode
$ ln -s original.txt soft.txt       # symlink: a file containing the path "original.txt"
$ ls -li
1319560 -rw-r--r-- 2 ana ana  6 Sep 12 10:40 hard.txt
1319560 -rw-r--r-- 2 ana ana  6 Sep 12 10:40 original.txt
1319561 lrwxrwxrwx 1 ana ana 12 Sep 12 10:40 soft.txt -> original.txt
$ rm original.txt
$ cat hard.txt
hello
$ cat soft.txt
cat: soft.txt: No such file or directory
```

`hard.txt` and `original.txt` share inode 1319560 with a link count of 2, and removing one name leaves the data reachable through the other. `soft.txt` has its own inode and breaks as soon as the path it names disappears.

## Crash consistency

Even a simple operation changes several on-disk structures. Creating a file and writing to it means allocating an inode, marking it used in the inode bitmap, adding an entry to the directory, allocating data blocks, marking them used, and recording them in the inode. These are separate writes to different places on the device, and power can fail between any two of them. A crash halfway can leave a directory entry pointing at an uninitialized inode, or blocks marked used that no file owns.

Older filesystems repaired this after a crash by running `fsck`, which scans every structure on the disk, taking hours on a large volume.

## Journaling

**Journaling** records intended metadata or data updates in a recoverable log so the filesystem can restore a consistent state after a crash. Instead of updating structures in place directly, the filesystem:

1. writes a description of all the changes for one operation into the **journal**, a reserved area of the device;
2. writes a commit record once the whole description is safely on disk;
3. then applies the changes to their real locations, called checkpointing.

After a crash, recovery reads the journal. Transactions with a commit record are replayed, so their changes are completed; transactions without one are discarded, as if they never started. Either way the structures are consistent, and recovery takes seconds because only the journal is read.

ext4 by default journals only metadata, in a mode called `data=ordered`: it writes a file's data blocks before committing the metadata that points to them, so a crash never exposes stale data from another file. Journaling data as well is possible but writes everything twice. Some filesystems, such as Btrfs and ZFS, reach the same goal differently, by never overwriting live structures in place.

## Common mistakes

- Thinking a file's name is stored in the file. Names live in directory entries; the inode holds everything else.
- Assuming `rm` erases data. It removes one name; the data is freed only when no links and no open handles remain.
- Believing journaling protects application data. It keeps the filesystem's own structures consistent; making your data durable at the right moment is up to you, as the lesson on buffered I/O explains.

## Key points

- A filesystem organizes persistent data into named files and directories and tracks the metadata needed to locate, protect, and update contents.
- An inode stores a file's metadata and references to its data blocks; directory entries map names to inode numbers.
- A hard link is another directory entry for the same file object; deleting one name leaves the file while other links remain.
- A symbolic link is a special file containing a path that is followed at access time, so it can cross filesystems or dangle.
- Journaling records intended updates in a recoverable log so the filesystem can restore a consistent state after a crash.

# CPU caches

A trip to DRAM costs hundreds of CPU cycles. If every load and store paid that price, a modern core would spend almost all its time waiting. It does not, because nearly every access is answered by a cache instead. Caches are invisible to a program's results, which is exactly why they surprise people: two loops that touch the same data in a different order can differ in speed by ten times, and two threads that share nothing can still slow each other down. Understanding caches explains both.

## What a cache is

A **CPU cache** is a small, fast memory near a processor that keeps recently or predictably used memory blocks, so accesses can avoid slower main memory. When the core loads an address, the cache is checked first. A **hit** returns the data in a few cycles; a **miss** fetches the data from the next level down, keeps a copy, and evicts something older to make room. Hardware prefetchers also watch access patterns and fetch blocks before they are requested.

## Why there are several levels

Why not build one big fast cache? Because size and speed pull against each other. A small cache can be very fast, since signals travel short distances and lookups check few entries, but it holds little data. A larger cache holds more but is slower and costs more chip area and power. A hierarchy balances latency, capacity, and hardware cost:

```text
level   typical size           typical latency     shared by
L1      32-48 KB per core      ~4-5 cycles          one core
L2      1-2 MB per core        ~12-15 cycles        one core
L3      tens of MB             ~40-60 cycles        all cores on the chip
DRAM    gigabytes              hundreds of cycles   whole machine
```

Each level catches most of the misses from the level above it, so the average access costs close to the L1 latency as long as the program behaves well. On Linux, `lscpu` lists the sizes of each level.

## Locality

Caches only help because programs are predictable. **Cache locality** is the tendency to access data that was used recently or that is near recently accessed addresses, which lets hardware caches reuse the blocks they have already loaded. It comes in two forms:

- **Temporal locality**: data accessed recently is likely to be accessed again soon. A loop counter, a hot configuration object, or the top of the stack is used over and over.
- **Spatial locality**: memory near a recently accessed address is likely to be accessed soon. Walking an array element by element touches neighboring addresses in sequence.

## Cache lines

Caches do not store individual bytes. A **cache line** is the fixed-size block transferred between cache levels and memory, 64 bytes on current x86-64 and most ARM cores (Apple's M-series use 128 bytes). Accessing one byte brings the whole line into the cache, so its neighbors come along for free. That is how the hardware exploits spatial locality.

A worked example shows the effect. Consider a 4096 by 4096 array of 4-byte `int`s, stored row by row as C does:

```c
int grid[4096][4096];               /* 64 MB, far larger than any cache */
long sum = 0;

for (int r = 0; r < 4096; r++)      /* row order: consecutive addresses */
    for (int c = 0; c < 4096; c++)
        sum += grid[r][c];

for (int c = 0; c < 4096; c++)      /* column order: jumps 16 KB each step */
    for (int r = 0; r < 4096; r++)
        sum += grid[r][c];
```

A 64-byte line holds 16 `int`s. In row order, one miss loads a line and the next 15 accesses hit it: roughly one miss per 16 elements, and the prefetcher hides much of even that. In column order, consecutive accesses are 16,384 bytes apart, so each lands on a different line. By the time the loop returns to a line for the next column, it has long been evicted. Nearly every access misses, and the column loop typically runs several times slower although both loops add up exactly the same numbers.

The general lessons: arrays beat pointer-chasing structures such as linked lists, sequential access beats random access, and a working set that fits in cache beats one that does not.

## Cache coherence

Each core has its own L1 and L2, so the same line can be cached in several places at once. If core 0 writes to a line that core 1 also holds, core 1's copy is now stale.

**Cache-coherence** protocols keep multiple CPU caches consistent enough that writes to a shared memory location become visible according to the architecture's memory model. Most use a variant of the MESI protocol, which tracks each line as Modified, Exclusive, Shared, or Invalid. The central rule: before a core may write a line, it must own it exclusively, which invalidates every other core's copy. Another core that later reads the line must fetch the new version, often directly from the writer's cache.

Coherence is automatic, but it is not free. Every time ownership of a line moves between cores, it costs something like a cache miss.

## False sharing

That cost produces a trap. **False sharing** happens when threads modify different variables that happen to share one cache line. The line bounces between cores on every write, even though the threads are not logically sharing any variable.

```c
struct counters {
    long a;   /* thread 1 increments this */
    long b;   /* thread 2 increments this */
};            /* both fit in one 64-byte line */
```

Each thread touches only its own counter, so there is no data race. Yet every increment by thread 1 invalidates thread 2's copy of the line, and vice versa. Two threads can end up slower than one. The fix is to give each hot variable its own line:

```c
struct counters {
    _Alignas(64) long a;
    _Alignas(64) long b;   /* now 64 bytes apart */
};
```

On Linux, `perf c2c` is the tool that finds lines contended this way.

## Common mistakes

- Judging an algorithm only by operation counts. An O(n) pass over a linked list can lose badly to the same pass over an array because of cache misses.
- Believing that threads which never share a variable cannot interfere. They can if their variables share a cache line.
- Assuming coherence makes multithreaded code correct by itself. It keeps copies of a line consistent; ordering guarantees between different variables come from the memory model and synchronization.

## Key points

- A CPU cache is small, fast memory near the core that keeps recently or predictably used memory blocks to avoid main-memory accesses.
- Cache levels exist because small caches are fast but hold little and large caches are slower; the hierarchy balances latency, capacity, and cost.
- Cache locality means accesses cluster around recently used data or nearby addresses, which lets caches reuse loaded lines.
- Temporal locality: recently accessed data is likely to be accessed again soon. Spatial locality: data near a recent access is likely to be accessed soon.
- A cache line is the fixed-size block moved between cache levels and memory, so touching one byte loads its neighbors.
- Cache-coherence protocols keep per-core caches consistent so writes become visible according to the memory model.
- False sharing is when threads write different variables on the same cache line, making the line bounce between cores.

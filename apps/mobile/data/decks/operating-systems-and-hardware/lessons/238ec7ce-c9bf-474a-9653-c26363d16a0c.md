# Files and I/O

Programs treat files as simple named sequences of bytes, but behind every `open`, `read`, and `write` the kernel is resolving paths, checking permissions, caching data in memory, and deciding when bytes actually reach the disk. Understanding that machinery explains why writes can be lost in a crash and how programs talk to each other through the same interfaces they use for files.

## Filesystems and inodes

A **filesystem** organizes persistent data into named files and directories. Besides the file contents, it tracks the **metadata** needed to locate, protect, and update them: sizes, owners, permissions, timestamps, and where each file's data blocks live on the device.

Unix-like filesystems separate a file's identity from its name. An **inode** stores a file's metadata and references to its data blocks, but not its name. A **directory** is essentially a list of entries mapping names to inode numbers. Looking up `/home/ana/notes.txt` means walking directory entries, one path component at a time, to find the inode.

## Hard links and symbolic links

That separation makes links possible:

- A **hard link** is simply another directory entry referring to the same inode. Both names are equally real; neither is the "original". Deleting one name removes only that entry, and the file's data stays as long as any link remains.
- A **symbolic link** is a special small file that contains a path to another filesystem object. The kernel follows that path each time the link is accessed. If the target is moved or deleted, the symbolic link dangles and access fails.

## File descriptors and opening a file

Opening a file returns a **file descriptor**: a small integer, local to the process, that refers to an open kernel-managed object. The same kind of handle refers to files, sockets, pipes, and similar objects, so the same `read` and `write` calls work on all of them. By convention, descriptors 0, 1, and 2 are standard input, output, and error.

Conceptually, **opening a file** does several things at once. The kernel resolves the path to the underlying file, checks that the process has permission for the requested access, creates or references open-file state such as the current read position, and returns a descriptor that later I/O calls use. Doing this work once at open time keeps each later `read` cheap.

## Buffered I/O and the page cache

Devices are most efficient with large transfers, while programs often read and write a few bytes at a time. **Buffered I/O** bridges the gap: data is held temporarily in memory buffers so many small operations can be combined into fewer large transfers, and the producer of data is decoupled from the speed of the device. Buffering happens both in libraries inside the program, such as C's `stdio`, and inside the kernel.

The kernel's main buffer for file data is the **page cache**. The OS keeps recently accessed file data in otherwise unused RAM, so a later read of the same data is served from memory without touching storage. Writes usually land in the page cache too and are written back to the device later. This is why re-reading a file is often much faster the second time, and why free memory on a busy server is mostly "used" by cache.

## Durability and fsync

That write-back behavior has a consequence. A successful `write` often means only that the kernel has accepted the data into memory. The data may still sit in volatile buffers, in the page cache or even in the storage device's own cache, and a power failure at that moment would lose it. When an application needs data to be persistent before it continues, such as a database committing a transaction, it must synchronize explicitly.

The standard tool is **`fsync`**. It asks the operating system to flush the file's buffered data and metadata toward durable storage and not return until that is done, according to the platform's guarantees. Those guarantees differ between systems and devices, so robust software is careful here, but conceptually `fsync` is the line between "accepted" and "safely stored".

```c
write(fd, record, len);
fsync(fd); // do not acknowledge the commit until this returns
```

## Journaling

A crash can also happen halfway through a multi-step update, such as creating a file, which touches a directory, an inode, and free-space bookkeeping. **Journaling** protects against that. Before changing the real structures, the filesystem records the intended metadata updates, and on some configurations data updates too, in a recoverable log called the journal. After a crash, it replays or discards journal entries to restore a consistent state, instead of scanning the whole disk for damage.

## Pipes and sockets

File descriptors also connect programs. A **pipe** is a kernel buffer with two ends: one process or thread writes a byte stream into it, and another reads that stream out. It is a common form of local inter-process communication; the shell's `ls | grep txt` connects two processes with a pipe.

A **socket** is an endpoint for sending and receiving data through a communication protocol. Sockets can connect processes on the same machine or across a network, for example over TCP. To the program, a connected socket is again a file descriptor.

## Zero-copy I/O

A plain file-to-network transfer copies data several times: from the device into the page cache, from the page cache into a user buffer on `read`, and back into kernel socket buffers on `write`. **Zero-copy I/O** reduces those redundant copies between kernel and user buffers. Techniques include mapping pages instead of copying them, splicing data between kernel objects, and calls like `sendfile` that let the kernel and device send directly from kernel-managed pages without the data ever passing through the application.

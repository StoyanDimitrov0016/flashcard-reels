# Managing process memory

Virtual memory gives the operating system a powerful tool: because every access goes through a mapping, the OS can share, copy, and map memory in clever ways. Inside a process, memory is further organized into regions with different lifetimes, such as the stack and the heap, managed by an allocator. This lesson covers both sides.

## Copy-on-write

**Copy-on-write** is a lazy-copying technique. When several users need what starts out as the same data, they initially share the same physical copy, marked read-only. As long as everyone only reads, no copy is made. When one of them writes, the write triggers a fault, and the system creates a private copy of just the affected page or object for the writer. Everyone else keeps using the original.

Copy-on-write is especially useful when **creating a process**. On Unix-like systems, `fork` creates a child that starts as a duplicate of the parent. Copying all of the parent's memory immediately would be slow and often pointless, since the child frequently calls `exec` right away to run a different program. Instead, the child shares the parent's pages copy-on-write, and copying cost is paid only for pages either side later modifies.

## Memory mapping

**Memory mapping** places file contents or device regions directly into a process's address space. After mapping, ordinary loads and stores read and write the file or device; there is no explicit `read` call for each region.

```c
char *data = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
char first = data[0]; // may page-fault and load from the file
```

A **memory-mapped file** is useful because the OS can page file regions in on demand, using the same page-fault machinery as demand paging. The application just uses memory addresses. This is convenient for large files that are accessed randomly, and it lets several processes share one cached copy of the file's data. The trade-off is that I/O errors and page faults now show up during ordinary memory accesses, which can make behavior harder to predict.

## The heap

The **heap** holds dynamically allocated objects whose lifetime is not tied to one function call. An object created with `malloc` in C, `new` in C++, or any object in a garbage-collected language usually lives on the heap and stays until it is freed or collected, regardless of which function created it.

## The stack

Each thread has its own **stack**. It stores call frames: the return address, saved registers, and many local variables for each active function. Frames are pushed on call and popped on return, in last-in, first-out order, so allocation on the stack is just moving a pointer and is extremely cheap. Values on the stack live only as long as the function call that created them.

A thread's stack has a fixed size limit, often a few megabytes for a main thread and sometimes less for others. A **stack overflow** happens when the thread uses more than that limit. The usual causes are very deep or unbounded recursion and unusually large local allocations, such as a big array declared inside a function. The OS typically places an unmapped guard page past the end of the stack, so overflowing it causes a fault instead of silently corrupting other memory.

## Allocators

A **memory allocator** manages the heap. It obtains large regions of memory from the OS, hands out smaller blocks when the program asks, and tracks freed blocks so they can be reused. Allocators balance speed, memory overhead, and behavior under many threads, which is why programs sometimes swap in a different allocator for better performance.

## Fragmentation

Allocators must cope with **fragmentation**, where memory is free but not usable efficiently. It comes in two forms:

- **External fragmentation**: free memory is split into many small, scattered pieces. The total free space may be large, yet no single piece is big enough for a request.
- **Internal fragmentation**: an allocated block is larger than what was requested, for example because sizes are rounded up, so space inside blocks goes unused.

Either way, a program can run short of usable memory even when total free capacity seems sufficient. Long-running programs that allocate and free objects of many different sizes are most prone to it.

# Storage and memory details

Performance and correctness at the lowest level depend on physical details: how storage devices actually write data, where memory sits relative to each CPU, how bytes are laid out, and in what order other threads see writes. This lesson collects those details, from disks to memory ordering.

## Hard disks and SSDs

A traditional **hard disk drive (HDD)** stores data on spinning magnetic platters read by a head on a moving arm. To reach a random location, the head must move to the right track and then wait for the platter to rotate the data underneath it, which takes milliseconds. That is why **sequential accesses are much faster than random ones on HDDs**: once positioned, consecutive blocks stream past the head with far less repositioning.

A **solid-state drive (SSD)** stores persistent data in flash memory with no moving parts. Its random-access latency is far lower than a mechanical disk's, often tens of microseconds instead of milliseconds. Flash cells wear out, though: each can only be erased and rewritten a limited number of times, so SSDs have finite **write endurance**.

## Why SSDs still care about access patterns

Flash has an awkward property: data is written in **pages** of a few kilobytes, but can only be erased in much larger **blocks** containing many pages, and a page cannot be overwritten in place. To update data, the SSD controller writes the new version to a fresh page and marks the old one stale. Later, **garbage collection** copies the still-valid pages out of a block so the whole block can be erased and reused.

As a result, SSD latency and throughput still depend on access pattern. Small random writes create more garbage-collection work than large sequential ones, and performance also depends on **queue depth**, meaning how many requests are outstanding at once for the controller to work on in parallel.

**Write amplification** is the name for this overhead: the device physically writes more data than the application logically asked for, often because valid data must be copied during garbage collection before blocks can be erased. High write amplification lowers throughput and wears the flash faster.

## NUMA

On large multi-socket servers, memory is not one uniform pool. In a **Non-Uniform Memory Access (NUMA)** system, each processor socket or node has memory attached directly to it. A CPU accesses its own local memory faster than memory attached to another socket, which must be reached over an interconnect.

**NUMA locality matters** because threads that frequently touch remote memory pay higher latency and add interconnect traffic. Operating systems try to allocate memory on the node where a thread runs, and performance-sensitive software pins threads and their data to the same node, keeping each thread near its working data.

## Endianness and alignment

**Endianness** is the byte order used to store a multi-byte number in memory or in a protocol. The 32-bit value `0x12345678` is stored as the bytes `12 34 56 78` in **big-endian** order, most significant byte first, and as `78 56 34 12` in **little-endian** order. Most modern CPUs are little-endian, while many network protocols use big-endian, often called network byte order. Code that writes binary data must agree on byte order.

**Memory alignment** means placing data at addresses the CPU prefers or requires for its type or access width, typically a multiple of the value's size: a 4-byte integer at an address divisible by 4. On some architectures a misaligned access is an error; on others it works but may be slower, especially if it spans two cache lines. Compilers add padding inside structures to keep fields aligned.

## Memory ordering and barriers

In single-threaded code, statements appear to run in the order written. Other threads may see something different. **Source-code order can differ from observed memory order** for two reasons. Compilers and CPUs reorder independent operations for performance, and caches and store buffers delay when a write becomes visible to other cores. A thread might set `data = 42` and then `ready = true`, and another core could observe `ready` as true while still seeing the old `data`. The language and hardware **memory model** defines exactly which orderings other threads may observe.

A **memory barrier** (or fence) constrains that reordering. It forces memory operations on one side of it to be ordered or made visible relative to operations on the other side, giving synchronization algorithms the ordering they need. Locks and atomic operations with acquire and release semantics include the necessary barriers, which is one reason to prefer them over hand-rolled flag variables.

# Computational hardness

Every algorithm in this deck so far has had a known, practical, polynomial-time solution. Not every problem does. Some problems appear to require checking an exponentially large number of possibilities no matter how cleverly you search, and recognizing that early — rather than spending months hunting for a fast exact algorithm that almost certainly does not exist — is itself a valuable engineering skill. This closing lesson is about recognizing hard problems, and about the practical judgment of matching an algorithm to the problem you actually have.

## Reductions

A **reduction** transforms instances of one problem into instances of another, so that solving the second would solve the first, allowing complexity or hardness results to transfer. If problem A reduces to problem B, then any algorithm that solves B can be used to solve A too — feed A's input through the transformation, run B's algorithm, translate the output back. Reductions are the connective tissue of complexity theory: they let a result proven about one problem (an efficient algorithm, or a hardness proof) transfer to every other problem it reduces to or from.

```text
"A reduces to B" (A ≤ B):

  input to A --[transform]--> input to B --[solve B]--> output --[translate]--> answer to A
```

If A reduces to B and B has a fast algorithm, A also has a fast algorithm — just route through the transformation. Conversely, if A is known to be hard, and A reduces to B, then B must be at least as hard as A: an easy algorithm for B would give an easy algorithm for A via the reduction, contradicting what is known about A.

## NP-completeness

A large family of problems — the traveling salesperson problem, boolean satisfiability, the knapsack problem, graph coloring, and hundreds of others — have been shown, via exactly this kind of reduction, to reduce to each other. This family is called **NP-complete**: informally, a proposed solution to any of these problems can be _checked_ quickly, but no known algorithm can _find_ a solution quickly for large inputs, and — because they all reduce to each other — discovering a genuinely fast algorithm for any single one of them would immediately give a fast algorithm for all of them.

Showing a problem is NP-complete is useful for engineering reasoning: it suggests no known polynomial-time exact algorithm is likely to scale generally, motivating approximation, heuristics, restricted inputs, or exponential search with pruning (backtracking and branch and bound, from the design strategies lesson, are the standard tools for the last of these) rather than continuing to search for a fast exact general-purpose algorithm. Nobody has proven that no such fast algorithm can ever exist — this is the famous open "P vs NP" question — but decades of failed attempts by a large research community are strong practical evidence that betting against it is a poor use of engineering time.

## What to actually do about a hard problem

Recognizing NP-completeness changes the question from "how do I solve this exactly and fast" to "which trade-off fits this situation":

- An **approximation algorithm** gives a solution provably within some bound of optimal, quickly — useful when "close to best" is good enough.
- A **heuristic** gives a solution that works well in practice on typical inputs, with no guaranteed bound — useful when average-case performance matters more than a worst-case guarantee.
- **Restricting the input** — small input sizes, special structure, bounded parameters — can make an otherwise-hard problem tractable in the cases that actually occur in practice, even without a general fast algorithm.
- **Exponential search with pruning** (backtracking, branch and bound) can still be practical when the input is small enough, or when pruning eliminates most of the search space in typical cases even though the worst case remains exponential.

## Matching the algorithm to the input

The same judgment applies even outside NP-complete territory: an `O(n²)` solution may be fine for hundreds of items and unusable for millions. Input size, memory, constants, and data distribution determine what is practical — the asymptotic complexity from the very first lesson of this deck is the starting point for that judgment, not the end of it. A correct, well-understood `O(n²)` algorithm that is simple and easy to verify can be the _better_ engineering choice than a complex `O(n log n)` one, if the actual inputs never get large enough for the difference to matter — and conversely, a beautifully proven-optimal algorithm is worthless if it never finishes on the input size the system actually needs to handle.

## Common mistakes

- **Trying to find an exact fast algorithm for a proven NP-complete problem instead of reaching for approximation, heuristics, or restricted-input reasoning.** This is time spent searching for something the field has strong evidence does not exist.
- **Treating "NP-complete" as "impossible to solve."** It is not — it means no known algorithm solves every instance quickly, not that no instance can be solved; many real-world instances are small or structured enough to solve exactly in practice.
- **Assuming a reduction proves two problems are equally practical to solve.** A reduction shows equivalence in difficulty class, not that a good algorithm for one automatically gives an efficient or simple algorithm for the other in practice.
- **Choosing an algorithm by asymptotic complexity alone, ignoring the actual input sizes and constants a system will really see.**

## Key points

- A reduction transforms instances of one problem into instances of another, letting complexity or hardness results transfer between them.
- NP-complete problems can have proposed solutions checked quickly, but have no known algorithm to find a solution quickly for large inputs, and all reduce to each other.
- Showing a problem is NP-complete is evidence, not proof, that no fast exact general algorithm exists, and should redirect effort toward approximation, heuristics, restricted inputs, or pruned exhaustive search.
- Algorithm choice should follow actual input constraints — size, memory, constants, and data distribution — not asymptotic complexity in isolation.

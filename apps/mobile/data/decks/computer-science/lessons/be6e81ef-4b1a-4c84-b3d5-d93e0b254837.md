# Proving algorithms correct

An algorithm that looks right and an algorithm that is provably right are different things. Testing a few inputs builds confidence, but it cannot rule out the input you did not think to try. This lesson covers two lightweight tools for reasoning about correctness without exhaustively testing every case: invariants, which pin down what must always be true as an algorithm runs, and the pigeonhole principle, a simple counting argument that proves certain outcomes are unavoidable.

## Invariants

An **invariant** is a condition that remains true at a defined point in every iteration or recursive step, and it helps prove correctness by giving you something fixed to reason about while everything else in the computation is changing. Rather than tracking every variable's exact value at every step, you identify one property that never breaks, and use it to argue that the algorithm must end up somewhere correct.

A **loop invariant** applies this idea specifically to loops, and it provides a structured, three-part proof:

1. **Initialization** — show the invariant holds before the loop's first iteration.
2. **Maintenance** — show that if the invariant holds before an iteration, it still holds after that iteration.
3. **Termination** — show that when the loop ends, the invariant (combined with the loop's exit condition) implies the result you actually wanted.

This is a small induction argument in disguise: initialization is the base case, maintenance is the inductive step, and termination cashes in the accumulated truth for the actual claim.

## A worked example: finding the maximum

```python
def find_max(items):
    current_max = items[0]
    for i in range(1, len(items)):
        if items[i] > current_max:
            current_max = items[i]
    return current_max
```

Claim the invariant: _before each iteration of the loop, `current_max` equals the maximum value among `items[0..i-1]`_ (the elements already looked at).

- **Initialization**: before the first iteration, `i = 1` and `current_max = items[0]`, which is trivially the maximum of the one-element slice `items[0..0]`. Holds.
- **Maintenance**: assume the invariant holds before some iteration, so `current_max` is the maximum of `items[0..i-1]`. The loop body compares `items[i]` against it and updates `current_max` to whichever is larger. Either way, `current_max` is now the maximum of `items[0..i]`, which is exactly the invariant for the next iteration. Holds.
- **Termination**: the loop ends when `i` reaches `len(items)`, so the invariant says `current_max` is the maximum of the whole array — the return value is correct.

No test case was run; the argument covers every possible array of any length, because it never depended on a specific value.

## Why this matters beyond simple loops

The same discipline scales to algorithms that are far less obviously correct on inspection. Binary search's boundary conditions (covered in the sorting and binary search lesson) are a classic place where an invariant — precisely which half of the range is guaranteed to still contain the answer — is the difference between a correct implementation and one that skips a candidate or loops forever. Sorting algorithms are typically proved correct by an invariant like "after processing the first `k` elements, they are sorted and no smaller than any element not yet processed." Recursive algorithms use an analogous idea: assume the recursive call is correct on a smaller input (an inductive hypothesis), then show the current step combines that assumed-correct result into a correct larger result.

## The pigeonhole principle

The **pigeonhole principle** is a different kind of tool: not a proof method for an algorithm's steps, but a counting argument for what must exist. If more items are placed into fewer containers, at least one container must hold more than one item. It sounds almost too simple to be useful, but it is often used to prove that a collision or repetition must exist, without having to construct or locate that collision directly.

For example, if a hash table has 10 buckets and 11 distinct keys are inserted, the pigeonhole principle guarantees at least one bucket receives two or more keys — a collision is not just possible, it is certain, regardless of how good the hash function is. The same reasoning proves that any function mapping a large input space to a smaller fixed-size output (such as any hash function, or any lossless compression scheme applied to all possible inputs of a given length) must produce the same output for at least two different inputs.

## Common mistakes

- **Confusing "an invariant that seems to hold" with "an invariant that is proven to hold."** The maintenance step must actually be checked against the loop body, not assumed by inspection.
- **Picking an invariant too weak to imply the final result.** Termination must connect the invariant plus the exit condition to the actual claim you wanted; a true but irrelevant invariant proves nothing useful.
- **Treating pigeonhole as telling you _which_ collision occurs.** It only guarantees that some collision exists somewhere; finding it still requires separate work.
- **Skipping invariant reasoning on "obviously correct" code.** Off-by-one errors and boundary bugs are exactly the failures invariant reasoning is designed to catch before they ship.

## Key points

- An invariant is a condition that stays true at a defined point in every iteration or recursive step, and is used to prove correctness.
- A loop invariant is proved with three parts: initialization (true before the loop starts), maintenance (true after each iteration if true before it), and termination (implies the desired result when the loop ends).
- Loop invariant proofs are a form of induction: initialization is the base case, maintenance is the inductive step.
- The pigeonhole principle says that placing more items than containers guarantees some container holds more than one item.
- Pigeonhole proves that a collision or repetition must exist without identifying where — useful for hash tables and any many-to-few mapping.

# Sorting and searching

Sorted data is easier to search, merge, deduplicate, and display. Sorting is one of the most studied problems in computer science, and it pairs naturally with binary search, one of the most useful algorithms of all.

## Sorting and stability

**Sorting** rearranges items into an order defined by a **comparison** or a **key**: numbers ascending, names alphabetically, orders by date.

A **stable sort** preserves the **relative order of records that compare equal**. Suppose you sort a list of people by last name, and two Smiths appear with Anna before Ben. A stable sort guarantees Anna still comes before Ben. Stability lets you sort by multiple keys in passes: sort by first name, then stably by last name, and people with the same last name stay ordered by first name.

## Three classic comparison sorts

**Merge sort** is divide and conquer. It recursively sorts each half of the input, then **merges** the two sorted halves by repeatedly taking the smaller front element. Its **worst-case time is O(n log n)**: there are about `log n` levels of splitting, each doing linear merge work. For arrays it commonly needs **O(n) auxiliary space** for the merge buffer. It is also stable when merges prefer the left half on ties.

**Quicksort** picks a **pivot**, **partitions** the elements into those smaller and those larger than it, then recursively sorts each partition. With reasonable pivots, such as random ones, its **expected time is O(n log n)**, and it is often very fast in practice. But if the pivot is repeatedly the smallest or largest element, for example always choosing the first element of already sorted input, the partitions are lopsided and time degrades to **O(n²)** in the worst case.

**Heapsort** first **builds a heap** from the input, then repeatedly **extracts the extreme element** (the maximum, for an ascending sort) and places it at the end of the array. It guarantees **O(n log n) worst-case time** and, in the common in-place implementation, needs only **O(1) auxiliary storage**.

## The comparison sorting lower bound

Can any comparison-based sort beat `n log n`? No. A comparison sort learns about the input only through yes-or-no comparisons. There are `n!` possible orderings of `n` items, and the algorithm must be able to tell them all apart.

Picture every possible run as a **decision tree**, where each comparison is a branch. The tree needs at least `n!` leaves, one per ordering, so its depth, the number of comparisons in the worst case, is at least `log₂(n!)`. That quantity grows like `n log n`, so comparison sorting is bounded below by **Ω(n log n)**.

## Beating the bound with counting sort

The bound only applies to algorithms that rely solely on comparisons. **Counting sort** uses the **numeric values** of keys directly. If keys are integers in a range of size `k`, it counts how many times each value occurs and then writes the values out in order. That runs in **O(n + k)** time, which beats `n log n` when `k` is manageable, such as sorting exam scores from 0 to 100. When `k` is huge, the counting array becomes impractical.

## Binary search

**Binary search** finds a target in a **sorted** range by comparing it with the **middle** element. If the target is smaller, the right half is discarded; if larger, the left half. Each step **halves** the range, so it needs only **O(log n)** comparisons. A million items take about twenty.

The real requirement is broader than "sorted". The search space needs a **monotonic ordering or predicate**, so that **one comparison tells you which half can be discarded**. For example, you can binary search for the smallest server count that handles a load, because if `c` servers suffice, any larger count does too.

## Getting the boundaries right

Binary search is famous for off-by-one bugs. The usual cause is **mixing inclusive and exclusive interval conventions**: treating `hi` as a valid candidate in one line and as one past the end in another. That can **skip candidates** or **loop forever** when the range stops shrinking.

The fix is to **define the interval invariant before coding** and keep every line consistent with it. Here the invariant is "the target, if present, lies in the half-open range `[lo, hi)`":

```js
function indexOf(sorted, target) {
  let lo = 0;
  let hi = sorted.length; // exclusive
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (sorted[mid] === target) return mid;
    if (sorted[mid] < target) lo = mid + 1;
    else hi = mid; // mid is excluded, and hi is exclusive
  }
  return -1;
}
```

# Hash tables

Looking up a value by key — a username, a product ID, a word in a dictionary — is one of the most common operations in software, and doing it by scanning every entry is too slow once a collection grows past a few dozen items. A **hash table** solves this by computing, from the key itself, roughly where in memory to look, turning "search for it" into "go directly to it."

## The basic idea

A hash table maps keys through a hash function to storage buckets, providing expected `O(1)` lookup, insertion, and deletion when collisions are controlled. A **hash function** takes a key of any size — a string, a tuple, an object — and deterministically produces a fixed-size number, the hash. That number is reduced (typically with a modulo operation) to an index into an array of buckets, and the key-value pair is stored there.

```text
key "alice" -> hash("alice") = 93284712 -> 93284712 mod 8 = 4 -> bucket 4
```

Because computing the hash and reducing it to an index takes time independent of how many other keys are already stored, both storing and retrieving a key take constant expected time — as long as keys are reasonably spread across buckets rather than piled into a few.

## Collisions

A **hash collision** occurs when distinct keys map to the same hash bucket or position. Collisions are not a bug or an edge case — with a fixed number of buckets and an unbounded number of possible keys, the pigeonhole principle (covered in the correctness lesson) guarantees that collisions must eventually happen. The table must resolve collisions while still distinguishing the keys that share a bucket, and there are two standard strategies for doing so.

### Separate chaining

With **separate chaining**, each hash bucket stores a collection of entries that hashed to that bucket, such as a linked list or small array. A collision just means a bucket's collection now holds two entries instead of one; lookup hashes the key to find the right bucket, then scans that bucket's short collection for a match.

```text
bucket 4: [("alice", 30)] -> [("alice", 30), ("dave", 22)]   (after a collision)
```

### Open addressing

With **open addressing**, all hash-table entries live in the main table itself — no per-bucket lists — and collisions are resolved by probing alternative slots according to a rule. Linear probing, for example, tries the next slot, then the next, until an empty one is found:

```text
insert "eve" -> hashes to bucket 4, occupied -> try bucket 5, empty -> store there
```

Lookup for a key follows the same probe sequence the insert did, stopping either when it finds the key or hits an empty slot (which proves the key was never inserted, since insertion would have stopped there too). Deletion is trickier under open addressing: simply emptying a slot can break the probe chain for other keys that probed past it, so implementations typically mark a slot as a "tombstone" rather than truly empty.

## Load factor

**Load factor** is the ratio of stored entries to table capacity (entries ÷ buckets). A low load factor means plenty of empty space, so collisions are rare and chains or probe sequences stay short. High load increases collision or probe costs — under separate chaining, average chain length grows with load factor; under open addressing, probe sequences get longer and, as the table approaches full, dramatically so. Tables often resize (allocate a larger backing array and reinsert every key) before load factor becomes too large, trading an occasional expensive `O(n)` resize for keeping average operations close to `O(1)` — the same amortized-cost reasoning as a dynamic array's resizing, covered in the linear data structures lesson.

## What makes a hash function good

A good hash function deterministically maps equal keys to equal hashes — this is not optional, since a hash table's whole scheme depends on being able to find a key again by re-hashing it — while distributing typical distinct keys across buckets to avoid clustering. A hash function that maps many real keys to the same few buckets defeats the point: those keys behave as if the table had far fewer buckets than it actually does, degrading toward linear-time lookup. Good general-purpose hash functions are designed to scatter even keys that differ by only one character (like `"cat"` and `"bat"`) into unrelated buckets.

## Sets

A **set** is an abstract data type — a specification of behavior, not an implementation — that stores unique values and supports membership, insertion, and deletion without attaching a separate value to each key. A hash table is the natural way to implement a set: store each element as a key with no associated value (or a placeholder), and membership testing becomes exactly the hash table's lookup operation. This is why "hash set" and "hash table" are so closely associated, even though a set and a table (key-value map) are different abstract data types.

## Common mistakes

- **Using a mutable object as a key without a stable hash.** If a key's hash can change after insertion, the table may look for it in the wrong bucket and silently fail to find it.
- **Ignoring load factor until performance degrades.** Waiting too long to resize turns every operation slow at once, right when the table is under the most load.
- **Assuming worst-case `O(1)`.** Hash table operations are _expected_ `O(1)` with a good hash function and controlled load factor; a pathological input (or a weak, exploitable hash function) can force many collisions and degrade toward `O(n)`.
- **Deleting under open addressing by simply clearing the slot.** This can break probe sequences for other keys and make them appear missing; a tombstone marker is needed instead.

## Key points

- A hash table maps keys through a hash function to buckets, giving expected `O(1)` lookup, insertion, and deletion.
- A hash collision happens when distinct keys map to the same bucket; the pigeonhole principle guarantees collisions are eventually unavoidable.
- Separate chaining stores colliding entries in a per-bucket collection; open addressing probes for another slot in the main table.
- Load factor is entries divided by capacity; high load factor increases collision or probe cost, so tables resize to keep it bounded.
- A good hash function maps equal keys to equal hashes and spreads distinct keys across buckets to avoid clustering.
- A set stores unique values without attached data, and is commonly implemented on top of a hash table.

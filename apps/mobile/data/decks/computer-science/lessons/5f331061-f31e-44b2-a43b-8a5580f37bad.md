# Sorting and binary search

Sorted data is easier to search, merge, deduplicate, and display, which makes sorting one of the most studied problems in computer science. It also pairs naturally with binary search, one of the most useful algorithms of all, because a sorted arrangement is exactly what makes binary search's core trick — throwing away half the remaining candidates with one comparison — possible in the first place.

## What sorting means

**Sorting** rearranges items into an order defined by a comparison or key — numeric order, alphabetical order, or any custom rule that can compare two items and say which comes first. A **stable sort** preserves the relative order of records that compare equal. Stability matters whenever records carry extra data beyond the sort key: sorting a list of orders by customer name, when several orders share the same customer, should not scramble the original order of that customer's own orders relative to each other — a stable sort guarantees it will not.

## Comparison sorts

Three classic algorithms sort by comparing elements against each other, with different trade-offs.

**Merge sort** recursively sorts halves and merges them, giving `O(n log n)` worst-case time and commonly `O(n)` auxiliary space for arrays.

```text
[5, 3, 8, 1]
split:  [5, 3]        [8, 1]
split:  [5] [3]       [8] [1]
merge:  [3, 5]        [1, 8]
merge:  [1, 3, 5, 8]
```

Merging two already-sorted halves takes one linear pass, comparing the fronts of each half and taking the smaller each time — the `log n` split levels times `O(n)` merge work per level give `O(n log n)` overall, and that bound holds no matter how the input is arranged, which is why merge sort's worst case is as good as its average case.

**Quicksort** partitions elements around a pivot and recursively sorts partitions, with expected `O(n log n)` time but `O(n²)` worst-case time under bad pivots.

```text
[5, 3, 8, 1], pivot = 5
partition: [3, 1 | 5 | 8]     (less-than-pivot | pivot | greater-than-pivot)
recursively sort [3, 1] and [8] the same way
```

If the pivot happens to split the array roughly in half each time, quicksort matches merge sort's `O(n log n)`. If the pivot is consistently the smallest or largest element — which happens on already-sorted input with a naive "always pick the first element" pivot rule — each partition only shrinks the problem by one element, giving `O(n²)`. Randomizing the pivot choice, or picking the median of a few sampled elements, makes the bad case extremely unlikely in practice.

**Heapsort** builds a heap and repeatedly extracts the extreme element, giving `O(n log n)` worst-case time and `O(1)` auxiliary array storage in common in-place implementations. Building a max-heap from the input, then repeatedly extracting the maximum (heaps are covered in an earlier lesson) into the end of the array, sorts the array in place without merge sort's extra `O(n)` buffer — at the cost of touching memory less predictably, which tends to make heapsort slower in practice than a well-tuned quicksort despite matching worst-case complexity.

## The comparison-sort lower bound

Why is comparison sorting generally bounded below by `Ω(n log n)`? A comparison sort must distinguish among `n!` possible input orders, requiring a decision tree with depth proportional to `log(n!)`. Every comparison sort can be modeled as a binary decision tree: each internal node is one comparison, and each leaf is one possible output ordering. To correctly sort every possible input, the tree needs at least `n!` leaves — one per distinct permutation — and a binary tree with `n!` leaves needs depth at least `log₂(n!)`, which is `Θ(n log n)`. No comparison-based algorithm can beat that bound in the worst case, no matter how cleverly it chooses comparisons.

## Beating the bound with counting sort

That lower bound applies specifically to algorithms that only ever compare elements to each other. **Counting sort** beats `O(n log n)` by using numeric key ranges rather than only comparisons, running in `O(n + k)` when keys fall in a manageable range of size `k` — for example, sorting exam scores from 0 to 100. Instead of comparing elements, it counts how many items have each possible key value, then reconstructs the sorted output directly from those counts.

```text
input: [3, 1, 3, 0, 2]
counts (index = value): [1, 1, 1, 2]   (one 0, one 1, one 2, two 3s)
output: [0, 1, 2, 3, 3]
```

This is not a contradiction of the `Ω(n log n)` bound — counting sort simply is not a comparison sort, so the decision-tree argument does not apply to it. Its `O(n + k)` cost becomes worse than `O(n log n)` once `k` (the key range) grows much larger than `n`, which is exactly the trade-off: counting sort wins when keys are small integers in a bounded range, and loses when the key range is large or the keys are not simple integers at all.

## Binary search

**Binary search** repeatedly halves a sorted search range by comparing the target with the middle element, giving `O(log n)` comparisons.

```text
sorted array: [1, 3, 5, 7, 9, 11, 13]
target: 9
compare with middle (7, index 3): 9 > 7, discard left half
remaining: [9, 11, 13]
compare with middle (11): 9 < 11, discard right half
remaining: [9]
compare with middle (9): match, found at original index 4
```

Each comparison discards half the remaining candidates, so the number of comparisons needed is proportional to how many times `n` can be halved before reaching one element — `log₂ n`.

The condition required for ordinary binary search is that the search space have a monotonic ordering or predicate, so one comparison tells which half can be discarded. This does not strictly require a sorted array of numbers: any search space where a single yes/no test is guaranteed to be false for a prefix and true for the rest (or vice versa) supports the same halving trick — searching for the smallest input that makes some condition first become true is a common generalized form.

## Binary search boundary bugs

A common bug in binary-search boundaries comes from mixing inclusive and exclusive interval conventions, which can skip candidates or loop forever. If `low` and `high` are meant to be an inclusive range `[low, high]`, the loop should continue `while low <= high`, and a "not found, go right" step should set `low = mid + 1` (excluding the already-checked `mid`); using `low = mid` instead can leave the loop stuck comparing the same middle index forever. Define the interval invariant before coding — decide explicitly whether `high` is included or excluded, and keep every update to `low` and `high` consistent with that choice, which is exactly the loop-invariant discipline from the correctness lesson applied to this one notoriously error-prone piece of code.

## Common mistakes

- **Forgetting to consider stability when it matters.** An unstable sort can silently reorder equal-key records in a way that breaks downstream assumptions.
- **Using naive quicksort pivot selection on nearly-sorted input.** Always picking the first or last element as pivot triggers the `O(n²)` worst case on exactly the input that looks "already easy."
- **Reaching for counting sort on a large or non-integer key range.** Its `O(n + k)` cost only beats comparison sorts when `k` stays small relative to `n`.
- **Mixing inclusive and exclusive bounds in binary search.** This is the single most common source of off-by-one and infinite-loop bugs in otherwise-correct-looking code.

## Key points

- Sorting rearranges items by a comparison or key; a stable sort preserves the relative order of equal-key records.
- Merge sort guarantees `O(n log n)` worst case with `O(n)` auxiliary space; quicksort is expected `O(n log n)` but `O(n²)` worst case; heapsort guarantees `O(n log n)` in place.
- No comparison sort can beat `Ω(n log n)` in the worst case, because it must distinguish among `n!` orderings.
- Counting sort escapes that bound by using key ranges instead of comparisons, running in `O(n + k)`.
- Binary search halves a sorted (or monotonically predicated) search range each comparison, giving `O(log n)`.
- Binary search boundary bugs almost always come from an inconsistent inclusive/exclusive interval invariant.

# Concurrency and networking

Programs rarely run alone. Threads inside one process share memory, and processes on different machines exchange messages across networks. Both situations raise the same underlying question: how do independent participants coordinate safely? This lesson covers the core ideas of concurrency and then the protocols that carry data across the internet.

## Race conditions and mutual exclusion

A **race condition** occurs when correctness **depends on the relative timing** of concurrent operations that are **not properly coordinated**. The classic case is two threads incrementing a shared counter. Each reads the value, adds one, and writes it back. If both read 5 before either writes, both write 6, and one increment is lost.

**Mutual exclusion** prevents this by ensuring that **only one execution path at a time** can enter a protected **critical section** that touches shared state. A lock, or mutex, is the usual tool: acquire it before the critical section and release it afterwards, and other threads wait their turn.

A **semaphore** generalizes the idea. Conceptually it is a **counter of permits**. Acquiring takes a permit, releasing returns one, and a participant that finds none waits. A semaphore initialized to 5 lets **up to five** holders proceed at once, which suits limiting concurrent connections to a database.

## Deadlock and starvation

Coordination brings its own failures. A **deadlock** is a state where a set of participants **each waits for something that only another waiting participant can provide**. Thread 1 holds lock A and wants B; thread 2 holds B and wants A. Neither can move, forever.

The classic model says four conditions must all be possible for a resource deadlock:

1. **Mutual exclusion**: a resource can be held by only one participant at a time.
2. **Hold and wait**: a participant holds one resource while waiting for another.
3. **No preemption**: resources cannot be forcibly taken away from their holder.
4. **Circular wait**: a cycle of participants each waits on the next.

Breaking any one prevents deadlock. A common practical fix breaks circular wait by always acquiring locks in the same global order.

**Starvation** is different. The system as a whole keeps making progress, but one runnable participant **repeatedly loses** access to a resource it needs and never advances. A low-priority thread that is always passed over by higher-priority ones is starving. Fair scheduling and queuing prevent it.

## Packets, addresses, and ports

Across a network, data travels in **packets**: bounded units of data sent through a **packet-switched** network. Each packet carries a **payload** plus **protocol headers** that routers and hosts use for delivery and processing. Large messages are split across many packets.

An **IP address** identifies a **network interface** endpoint so routers can forward packets across IP networks to the right machine, for example `192.0.2.10` in IPv4 or `2001:db8::1` in IPv6.

One machine runs many networked programs, so the address alone is not enough. A **port number** identifies a logical endpoint **on a host** at the transport layer, letting **multiple applications share one IP address**. A web server typically listens on port 443 while a database on the same machine listens on 5432.

## TCP and UDP

The two main transport protocols make opposite trade-offs.

**TCP** provides a **reliable, ordered byte stream** between two endpoints. It numbers data with **sequence numbers**, waits for **acknowledgments**, **retransmits** anything lost, and reassembles data in order. It also applies **flow control**, so a fast sender does not overwhelm a slow receiver, and **congestion control**, so senders back off when the network is overloaded.

**UDP** sends **independent datagrams** with **no built-in delivery guarantee, ordering, retransmission, or connection state**. That means lower protocol overhead and gives the application **more control**. Voice calls, games, and live video often prefer UDP, because a late packet is useless anyway, and protocols like QUIC build their own reliability on top of it.

## DNS, HTTP, and TLS

People use names, not numbers. **DNS** (the Domain Name System) is a **distributed, hierarchical** naming system that maps domain names to records, most commonly **resolving a name to an IP address**. Responsibility is split across root servers, top-level domain servers such as those for `.com`, and each domain's own authoritative servers, with caching at every level.

**HTTP** is the application protocol of the web. A client sends a **request**, with a method such as `GET` or `POST`, a path, and headers. The server returns a **response** containing a **status** code, **headers**, and an **optional body**.

```http
GET /decks/42 HTTP/1.1
Host: example.com

HTTP/1.1 200 OK
Content-Type: application/json
```

**TLS** secures that traffic over an untrusted network. It **authenticates** endpoints with **certificates**, so a browser can confirm it is really talking to the site it asked for, and then establishes communication that is **encrypted** (nobody can read it) and **integrity-protected** (nobody can alter it undetected). HTTPS is simply HTTP carried over TLS.

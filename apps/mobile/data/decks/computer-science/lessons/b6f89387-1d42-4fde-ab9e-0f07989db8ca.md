# Analyzing algorithm cost

Two programs can solve the same problem and produce the same answers, yet one finishes instantly on a million records while the other takes hours. Before you can choose between them, or even talk precisely about "fast" and "slow," you need a way to describe how much work a piece of code does that does not depend on which laptop it runs on today. That is what this lesson builds: a vocabulary for algorithm cost that stays meaningful as inputs grow and hardware changes.

## Algorithms and what they cost

An **algorithm** is a finite procedure that transforms inputs into outputs through a defined sequence of steps. "Finite" matters: an algorithm must terminate, and each step must be well-defined enough that it could, in principle, be carried out mechanically. Sorting a list, searching for a value, and computing a shortest route are all algorithms in this sense.

Every algorithm has two costs worth measuring separately. **Time complexity** describes how the number of basic operations it performs grows as the input size grows, usually expressed with asymptotic notation such as `O(n)`. **Space complexity** describes how the additional memory it uses grows with input size — not counting the input itself, but the extra structures the algorithm allocates along the way, such as a temporary array or a recursion stack.

Both are stated as functions of `n`, a stand-in for "how big is the input" (the length of an array, the number of vertices in a graph, and so on). The question is never "how many milliseconds," which depends on the machine, but "how does the operation count scale," which does not.

## Asymptotic notation

Three related notations describe growth rates precisely:

- **Big O** gives an asymptotic _upper bound_ on growth, ignoring constant factors and lower-order terms. Saying an algorithm is `O(n²)` means its cost grows no faster than some constant times `n²`, for large enough `n`.
- **Big Omega (Ω)** gives an asymptotic _lower bound_ on growth: the cost grows at least this fast.
- **Big Theta (Θ)** gives a _tight_ bound: the function grows within constant factors of the stated rate, both above and below. `Θ(n log n)` means the cost is sandwiched between two constant multiples of `n log n`.

In casual conversation people often say "Big O" when they mean the tight bound, because for most everyday algorithms the upper and lower bounds people care about coincide. But the three symbols answer different questions, and a rigorous claim about a lower bound (like "no comparison sort can beat `n log n`," covered in the sorting lesson) needs Ω or Θ, not O.

Consider linear search through an unsorted array of `n` elements. In the worst case it inspects every element once, so its worst-case cost is `Θ(n)`: it is both `O(n)` (never more) and `Ω(n)` (in the worst case, never less, since a matching element could be last).

## Why constants are ignored — and why they still matter

Asymptotic analysis deliberately looks past constant factors and lower-order terms, because it is asking a specific question: how does cost scale as the input grows without bound? An algorithm that does `5n` operations and one that does `500n` operations are both `O(n)`, because for large enough `n` the difference in constant factors becomes irrelevant next to the shape of the growth curve. This lets you compare an `O(n)` algorithm against an `O(n²)` one and know which will eventually win, no matter which language, compiler, or machine either one runs on.

But "eventually" is doing real work in that sentence. Two algorithms with the same Big O can have very different practical performance, because constants still matter in real systems. A `Θ(n log n)` sort with a large constant factor can be slower in practice, for the input sizes you actually see, than a `Θ(n²)` sort with a tiny constant and good cache behavior. Big O tells you which algorithm wins the race if it goes on long enough; it does not tell you who is ahead at the finish line you actually care about. Treat asymptotic complexity as the first filter for algorithm choice, and measure the real cases before trusting it as the final word.

## A worked comparison

Suppose you need to check whether an array contains a duplicate value.

```python
# O(n^2) time, O(1) extra space
def has_duplicate_naive(items):
    n = len(items)
    for i in range(n):
        for j in range(i + 1, n):
            if items[i] == items[j]:
                return True
    return False

# O(n) time, O(n) extra space
def has_duplicate_set(items):
    seen = set()
    for x in items:
        if x in seen:
            return True
        seen.add(x)
    return False
```

The first version does roughly `n²/2` comparisons: `O(n²)` time, `O(1)` extra space beyond the input. The second does one pass and one hash-table lookup per element: `O(n)` time, but it pays for that speed with `O(n)` extra space for the `seen` set. Neither version is "the" right answer — the choice depends on whether time or memory is scarcer for your input sizes, which is exactly the judgment asymptotic notation is meant to inform, not replace.

## Common mistakes

- **Treating Big O as an exact prediction of running time.** It describes a growth trend, not a stopwatch reading; two `O(n)` algorithms can differ by a large constant factor.
- **Using O when a tight bound is meant.** Saying "this algorithm is `O(n log n)`" is true but weak if the algorithm can never do better than `n log n` either — that claim needs Θ or Ω.
- **Ignoring space complexity.** A fast algorithm that also needs `O(n)` extra memory may be the wrong trade for a memory-constrained environment, even though it looks strictly better on a time-only comparison.
- **Assuming smaller Big O always wins.** For the actual input sizes a system will see, constants and implementation details can make a "worse" asymptotic algorithm the faster real choice.

## Key points

- An algorithm is a finite, well-defined procedure from inputs to outputs.
- Time complexity and space complexity separately describe how operation count and extra memory grow with input size `n`.
- Big O bounds growth from above, Big Omega from below, and Big Theta pins it down tightly in both directions.
- Asymptotic notation ignores constant factors and lower-order terms to focus on long-run growth.
- Constants still matter in practice: two algorithms with the same Big O can perform very differently on real inputs and real machines.

# Trees

Many kinds of data are naturally hierarchical: folders inside folders, elements inside a web page, managers and their reports. Trees capture that shape, and ordered trees also make searching fast.

## What makes a tree

A **tree** is a **connected, acyclic** hierarchy of nodes linked by parent-child relationships. One node, the root, has no parent; every other node has exactly one. Because a tree is connected and has no cycles, there is exactly **one path between any two nodes**. Nodes with no children are called leaves, and the **height** of a tree is the length of its longest root-to-leaf path.

A **binary tree** restricts each node to **at most two children**, usually called the left and right child.

## Binary search trees

A **binary search tree (BST)** is a binary tree with an ordering rule. For every node, the keys in its left subtree compare lower than the node's key, and the keys in its right subtree compare higher. That rule applies recursively all the way down.

Searching follows the rule directly: compare the target with the current node, then go left if it is smaller, right if it is larger, and stop when you find it or run out of nodes.

```js
function contains(node, key) {
  while (node !== null) {
    if (key === node.key) return true;
    node = key < node.key ? node.left : node.right;
  }
  return false;
}
```

## Why balance matters

Each comparison in a BST discards one whole subtree. In a **balanced** tree, where the two sides of each node have similar sizes, that eliminates about half of the remaining nodes every step. The height is about `log₂ n`, so search is **O(log n)**. A balanced tree with a million keys needs only around twenty comparisons.

A plain BST does nothing to stay balanced, though. Its shape depends entirely on insertion order. Insert keys that are already sorted, such as 1, 2, 3, 4, 5, and each new key becomes the right child of the previous one. The result is a **skewed** tree that is really a linked list in disguise. Its height approaches the number of nodes, and search **degrades to O(n)** linear traversal.

**Self-balancing search trees**, such as AVL trees and red-black trees, solve this. After insertions and deletions they restore balance through **rotations** or other local restructuring, keeping the height **logarithmic**. That guarantees lookup, insertion, and deletion all stay **O(log n)** no matter what order the keys arrive in. Ordered maps and sets in many standard libraries are built on such trees.

## Tries

A **trie**, also called a prefix tree, stores keys, usually strings, by their **prefixes**. Each edge represents one character, and a key is spelled out by the path from the root down to a node marked as the end of a word. Words that share a prefix share the same path for that prefix.

For example, "car", "cart", and "cat" all share the path `c → a`, after which "car" and "cart" continue through `r`, and "cat" branches off to `t`.

Looking up a key in a trie means following one edge per character, so the cost is **proportional to the key's length**, not to how many keys are stored. A trie holding ten words and one holding ten million both find "cart" in four steps.

## When to use a trie

Tries shine whenever **shared prefixes** matter:

- **Prefix search and autocomplete**: walk down to the node for the typed prefix, then list every word beneath it.
- **Dictionaries and spell checkers**, which store huge numbers of related words.
- **Routing structures**, such as IP routing tables that match the longest address prefix, or URL routers that match path segments.

The trade-off is memory: storing child links at every node can take more space than a hash table holding the same keys.

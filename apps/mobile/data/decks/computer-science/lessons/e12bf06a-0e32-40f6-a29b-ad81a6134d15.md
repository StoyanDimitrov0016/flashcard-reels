# Cryptography

Cryptography answers a small set of recurring questions: how do you tell whether data has been tampered with, how do you store a secret so that even someone who steals the storage cannot use it, and how do you let two parties who have never met establish a shared secret or verify each other's identity? Hash functions, password hashing, public-key encryption, and digital signatures each answer one of these.

## Cryptographic hash functions

A **cryptographic hash function** deterministically maps arbitrary input to a fixed-size digest, designed to make collisions, preimages, and related manipulations computationally difficult. Like the hash functions from the hash tables lesson, it always produces the same output for the same input and maps a huge input space onto a much smaller fixed-size output — so, by the pigeonhole principle, collisions (two different inputs with the same digest) must exist. What makes a hash function _cryptographic_ is that finding one is designed to be computationally infeasible, not merely unlikely by chance: no known algorithm should let an attacker find a collision, or find any input that produces a given digest (a **preimage**), meaningfully faster than trying inputs at random.

```text
sha256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e...
sha256("hallo") = 826bce50e3bbc41cd7ea89ec89f26d3b...
```

A single-character change produces a completely unrelated-looking digest — this **avalanche effect** is what makes hashes useful for detecting tampering: even a tiny modification to a file or message is caught, because its hash changes unpredictably rather than shifting slightly.

## Password hashing

Password hashing is intentionally different from a general-purpose fast hash. A password hash is different from a general fast hash because it intentionally uses salt and expensive computation or memory, so guessing each candidate password costs an attacker substantial resources. A **salt** is random data unique to each stored password, combined with the password before hashing, which defeats precomputed lookup tables (rainbow tables) that would otherwise let an attacker reverse many hashes at once by looking them up rather than computing them.

The "expensive" part is just as important, and is the opposite of what a general-purpose hash function optimizes for. `SHA-256` is deliberately fast, because file-integrity checks and cryptographic protocols need to hash large amounts of data quickly — but that same speed is exactly what makes a fast hash a poor choice for passwords: an attacker who steals a database of fast-hashed passwords can try billions of guesses per second. Password-hashing algorithms such as `bcrypt`, `scrypt`, and `Argon2` deliberately require significant CPU time or memory per guess, so trying billions of candidate passwords becomes prohibitively slow even though verifying one correct password remains fast enough for normal login.

## Public-key encryption

**Public-key encryption** uses a public key for an allowed operation, such as encryption, and a mathematically related private key for the corresponding protected operation, such as decryption. The public key can be shared with anyone, published openly even; the private key must never leave its owner's control. Anyone can encrypt a message using the recipient's public key, but only the holder of the matching private key can decrypt it — solving the problem of establishing secure communication with someone you have never exchanged a secret with in person.

```text
Alice encrypts message with Bob's PUBLIC key
   -> only Bob's PRIVATE key can decrypt it
```

This is fundamentally different from the shared-secret ("symmetric") encryption used for the bulk of TLS's actual data transfer (networking lesson) — public-key operations are typically much slower, so in practice, protocols like TLS use public-key cryptography briefly, to securely establish a shared symmetric key, and then switch to fast symmetric encryption for the rest of the connection.

## Digital signatures

A **digital signature** is produced when a signer uses their private key to produce a signature that others can verify with the public key, providing integrity and evidence that the private-key holder signed the message. This runs the public/private key relationship in the opposite direction from encryption: instead of "anyone can lock, only the key-holder can unlock," it is "only the key-holder can produce this signature, but anyone can check that it is valid."

```text
Alice signs message with her PRIVATE key -> signature
Anyone verifies the signature using Alice's PUBLIC key
   -> confirms: this exact message was signed by whoever holds Alice's private key
```

A signature covers a specific message: verifying it confirms both that the claimed signer's private key produced it, and that the message has not been altered since (because the signature is computed over the message's content, typically via a cryptographic hash of it, so any change to the message invalidates the signature). This is exactly what a certificate — mentioned in the networking lesson's discussion of TLS — actually is: a certificate authority's digital signature over a claim binding a public key to an identity, which is what lets a client verify a server's identity without having met that server before.

## Common mistakes

- **Using a fast general-purpose hash function to store passwords.** It is precisely the wrong property for this use case — fast verification for you means fast guessing for an attacker.
- **Reusing a salt across multiple passwords, or omitting it.** A shared or missing salt lets one precomputed table attack many stored passwords at once, defeating the point of salting.
- **Confusing encryption and signatures as "the same operation in different words."** Encryption protects confidentiality (only the private-key holder can read it); a signature protects authenticity and integrity (anyone can verify it, but only the private-key holder could have produced it) — they use the key pair in opposite roles.
- **Assuming a cryptographic hash function's collision resistance is absolute.** It means finding a collision is computationally infeasible with current knowledge and hardware, not mathematically impossible — which is why hash functions are occasionally deprecated once practical attacks are found.

## Key points

- A cryptographic hash function deterministically maps input to a fixed-size digest, designed to make collisions and preimages computationally infeasible to find.
- Password hashing intentionally adds salt and computational or memory cost, unlike a general-purpose fast hash, to make large-scale guessing expensive.
- Public-key encryption lets anyone encrypt with a public key while only the matching private key can decrypt.
- A digital signature lets only the private-key holder produce a valid signature, while anyone with the public key can verify it, providing integrity and authenticity.
- Public-key operations are typically much slower than symmetric encryption, so protocols like TLS use them briefly to establish a shared key rather than for all data transfer.

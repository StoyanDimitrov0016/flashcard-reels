# Networking

Every request a phone or browser makes — loading a page, sending a message, streaming a video — travels across a stack of protocols that each solve one piece of the "get this data from here to there" problem. This lesson walks that stack from the smallest unit of data up to the protocol that secures it.

## Packets

A **packet** is a bounded unit of data sent through a packet-switched network, carrying payload plus protocol headers used for delivery and processing. Rather than reserving a dedicated line for an entire conversation, a packet-switched network chops data into these bounded chunks, each stamped with the information needed to route and reassemble it, and sends them independently — possibly by different physical paths — toward their destination. Everything else in this lesson is, at bottom, a set of rules for what goes in those headers and what the receiving end is supposed to do with them.

## Addressing endpoints

An **IP address** identifies a network interface endpoint for routing packets across IP networks — it is what lets a packet-switched network know _where_ to deliver a packet, the way a street address tells a delivery service where a package goes. But a single machine usually runs many networked programs at once — a browser, a mail client, a background sync service — all sharing one IP address. A **port number** identifies a logical endpoint on a host so multiple networked applications can share one IP address: the IP address gets a packet to the right machine, and the port number gets it to the right program running on that machine.

```text
192.168.1.42:443    ->  IP address 192.168.1.42, port 443 (commonly HTTPS)
192.168.1.42:22     ->  same machine, port 22 (commonly SSH)
```

## TCP and UDP

Above addressing sits the transport layer, which decides what guarantees a connection makes about the data it carries.

**TCP** provides a reliable, ordered byte stream between endpoints, using acknowledgments, retransmission, sequencing, flow control, and congestion control. If a packet is lost, TCP notices (the receiver's acknowledgments reveal the gap) and arranges for it to be resent; if packets arrive out of order, TCP reorders them before handing data to the application, so the application sees one continuous, correctly-ordered stream regardless of what happened underneath.

**UDP** sends independent datagrams without built-in delivery, ordering, retransmission, or connection state, giving applications more control and lower protocol overhead. A UDP datagram that gets lost simply never arrives, silently, unless the application built its own mechanism to notice and recover — but that lack of bookkeeping means less overhead and lower latency, which is why UDP is preferred for real-time media (video calls, live game state) where a slightly stale or missing update is better than one that arrives late after retransmission.

```text
                reliable/ordered   overhead/latency   typical use
TCP                  yes                higher        web pages, file transfer
UDP                  no                 lower          video calls, DNS queries, games
```

Neither protocol is strictly better — the choice depends entirely on whether the application needs guaranteed delivery and ordering, or needs the lowest possible latency and can tolerate loss.

## DNS

**DNS** maps domain names and other records through a distributed hierarchical naming system, commonly resolving names to IP addresses. Typing a domain name into a browser triggers a DNS lookup that walks this hierarchy (broadly: root servers, then top-level-domain servers, then the domain's own authoritative servers) to translate a human-readable name into the IP address a connection can actually be made to. This indirection is what lets a service change which physical server (and IP address) it runs on without every client needing to be reconfigured — only the DNS record needs to change.

## HTTP

**HTTP** is an application protocol where clients send requests and servers return responses containing status, headers, and optional bodies. It runs on top of a reliable transport (TCP, historically and still commonly) and defines a request/response vocabulary — methods like `GET` and `POST`, status codes like `200 OK` and `404 Not Found`, and headers carrying metadata about the request or response — that essentially every web application, and much of the internet's application-layer traffic beyond browsers, is built on top of.

```text
GET /users/42 HTTP/1.1
Host: example.com

HTTP/1.1 200 OK
Content-Type: application/json

{"id": 42, "name": "Ada"}
```

## TLS

**TLS** authenticates endpoints using certificates and establishes encrypted, integrity-protected communication over an untrusted network. It sits between the transport layer and an application protocol like HTTP (HTTP running over TLS is what "HTTPS" means), and its handshake accomplishes two things at once: it lets the client cryptographically verify it is really talking to the server it intended to (using a certificate — see the cryptography lesson for digital signatures, which certificates rely on), and it establishes a shared encryption key so everything sent afterward is unreadable and tamper-evident to anyone intercepting the connection.

In the common case, only the server presents a certificate and is authenticated this way; the client is typically not required to prove its identity with a certificate of its own, though **mutual TLS** (mTLS), where both sides present certificates, is used in some higher-security settings such as service-to-service traffic inside a private network.

## Common mistakes

- **Assuming an IP address alone identifies "the connection."** A connection is identified by the combination of source IP, source port, destination IP, and destination port — the port is not a minor detail, it is half of what makes multiplexed connections on one machine possible at all.
- **Choosing UDP by default for reliability-sensitive data**, or TCP by default for latency-sensitive real-time data — each protocol's guarantees (or lack of them) exist for a reason, and picking against the grain of what an application actually needs causes real problems.
- **Treating DNS resolution as instantaneous or free.** DNS lookups add latency and can fail or be slow, which is why clients and intermediate resolvers cache DNS results rather than looking them up on every single request.
- **Assuming TLS authenticates both sides of a connection by default.** Standard TLS (as used by most HTTPS websites) authenticates the server to the client; authenticating the client to the server requires the separate mutual-TLS configuration.

## Key points

- A packet is a bounded unit of data carrying payload plus headers through a packet-switched network.
- An IP address identifies a network interface endpoint; a port number identifies a specific application on that endpoint, letting one IP address serve many programs.
- TCP gives a reliable, ordered byte stream with retransmission and flow/congestion control; UDP gives lightweight, unordered, unacknowledged datagrams.
- DNS resolves human-readable domain names to IP addresses through a distributed hierarchical system.
- HTTP is a request/response application protocol built on top of a reliable transport.
- TLS authenticates endpoints via certificates and encrypts communication; standard TLS authenticates the server, and mutual TLS additionally authenticates the client.

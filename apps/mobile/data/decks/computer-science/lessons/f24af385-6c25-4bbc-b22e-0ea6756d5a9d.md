# Recursion

Some problems are naturally defined in terms of smaller versions of themselves: a directory's total size is the size of its files plus the total size of its subdirectories; a tree's height is one plus the taller of its two children's heights. Writing code that mirrors that kind of definition directly, instead of unrolling it into an explicit loop, is what recursion is for. It is also the mechanism that later lessons on trees, graph traversal, divide and conquer, and dynamic programming all lean on, so it is worth understanding precisely before those topics build on top of it.

## What recursion is

**Recursion** solves a problem by calling the same function on smaller subproblems until a **base case** stops further calls. A base case is an input simple enough to answer directly, without recursing — it is what keeps the chain of calls finite.

```python
def factorial(n):
    if n == 0:          # base case
        return 1
    return n * factorial(n - 1)   # recursive case: smaller subproblem
```

Every recursive function needs both pieces. The recursive case must move strictly closer to a base case — here, `n - 1` is smaller than `n` — or the function never terminates. The base case must actually be reachable and must stop the recursion outright, returning a value without calling the function again.

Tracing `factorial(3)` shows the shape of the computation:

```text
factorial(3)
  -> 3 * factorial(2)
       -> 2 * factorial(1)
            -> 1 * factorial(0)
                 -> 1                (base case)
            <- 1 * 1 = 1
       <- 2 * 1 = 2
  <- 3 * 2 = 6
```

Calls go "down" until the base case, then results combine on the way back "up." This down-then-up shape — build up a chain of pending work, then resolve it in reverse order — is the signature of recursion, and it reappears whenever a problem is solved by combining answers to smaller instances of itself.

## The call stack

The reason recursive calls can "come back" to finish their pending multiplication is the **call stack**: it stores active function frames, including return locations and local execution state, in nested call order. Calling `factorial(3)` pushes a frame for `factorial(3)`, which pushes a frame for `factorial(2)`, and so on. Each frame remembers exactly where to resume and what local variables (like `n`) it was holding. When `factorial(0)` returns, its frame pops, execution resumes inside `factorial(1)` exactly where it left off, and the multiplication proceeds outward until the stack is empty again.

This is not a metaphor — it is the same call stack every function call uses, recursive or not. Recursion is just what happens when a function's own frame ends up on the stack more than once at a time.

## Why deep recursion can fail

Each recursive call consumes stack space for its frame. Sufficient depth can exceed the runtime's stack limit even when the algorithm is logically correct — the classic symptom is a stack overflow on an input that is merely large, not malformed. Computing `factorial(100000)` recursively, for example, is very likely to overflow the stack on typical language runtimes long before the arithmetic itself becomes a problem.

This is a real engineering constraint, not just a theoretical curiosity. When recursion depth scales with input size — a common case, since many recursive functions call themselves once per element — an `O(n)`-time algorithm can still fail in practice on large `n` purely because of stack depth. Two common responses are converting the recursion into an explicit loop with your own stack-like data structure (see the stack in the linear data structures lesson), or restructuring the recursion so the language runtime can reuse the current frame instead of stacking a new one — an optimization some languages perform automatically for **tail calls**, calls that are the very last action a function performs, though many mainstream runtimes do not guarantee it.

## Recursion versus iteration

Anything recursion computes can also be computed with an explicit loop and your own data structure to track pending work, and the two are not fundamentally different in what they can express — only in which bookkeeping they lean on. A loop tracks its own progress in ordinary variables; recursion lets the call stack track it instead. Recursion tends to read more directly like the mathematical definition of the problem (this is especially true for tree and graph structures, covered next), at the cost of stack depth and, in most languages, some function-call overhead per step.

## Common mistakes

- **Missing or unreachable base case.** If the recursive case never actually reaches an input the base case handles, the function recurses forever, or until the stack overflows.
- **Recursive case that does not shrink the problem.** Calling the function again with the same or a larger input guarantees non-termination even with a correct-looking base case.
- **Ignoring stack depth for large inputs.** A recursive function that is correct and even efficient in time can still crash on large `n` if its recursion depth is proportional to `n`.
- **Recomputing the same subproblem repeatedly.** Naive recursion can call itself with identical arguments many times over; this is the exact issue dynamic programming is built to fix.

## Key points

- Recursion solves a problem by calling the same function on smaller subproblems until a base case stops further calls.
- A base case is an input answered directly, without further recursive calls.
- The call stack stores active function frames, including return locations and local state, in nested call order, which is what lets a chain of recursive calls resume and combine results correctly.
- Each recursive call consumes stack space; sufficient depth can overflow the stack even for a logically correct algorithm.
- Recursion and iteration can express the same computations; recursion trades explicit loop bookkeeping for call-stack depth.

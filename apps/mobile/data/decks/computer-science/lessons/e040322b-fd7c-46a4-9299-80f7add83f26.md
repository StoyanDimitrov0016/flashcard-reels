# Concurrency fundamentals

A program with a single thread of execution does one thing at a time, and its correctness never depends on timing — the same input always produces the same sequence of steps. The moment multiple threads or processes run at once and touch shared state, that guarantee disappears, and a whole new category of bugs becomes possible: ones that depend on which participant happens to run first, and that can be nearly impossible to reproduce on demand.

## Race conditions

A **race condition** occurs when correctness depends on the relative timing of concurrent operations that are not properly coordinated. The classic example is two threads incrementing a shared counter:

```text
counter = 0

Thread A: read counter (0)     Thread B: read counter (0)
Thread A: add 1 -> 1
                                Thread B: add 1 -> 1
Thread A: write 1
                                Thread B: write 1
final counter value: 1   (should be 2 — one increment was lost)
```

Each thread's individual steps are correct; the bug only appears from the specific interleaving of steps across threads, which is what makes race conditions so hard to catch with ordinary testing — a slightly different scheduling of the same code can produce the correct answer instead.

## Mutual exclusion

**Mutual exclusion** ensures that only one execution path at a time can enter a protected **critical section** — the part of the code that touches shared state in a way that must not be interleaved. If the counter increment above were wrapped so that only one thread could execute "read, add, write" at a time, the lost update becomes impossible: the second thread would simply wait until the first thread's full read-add-write sequence finished.

```text
lock.acquire()
counter += 1
lock.release()
```

A **lock** (or mutex) is the most direct tool for mutual exclusion: acquiring it before entering a critical section, and releasing it after leaving, guarantees no two threads are ever inside that section at the same time.

## Semaphores

A **semaphore** is a counter used to control access to a limited number of permits, allowing up to a configured number of concurrent holders. Where a lock allows exactly one holder, a semaphore generalizes this to `N` holders — useful for capping access to a resource that can safely handle a fixed number of simultaneous users, such as a pool of database connections. `acquire` decrements the counter (blocking if it would go below zero), and `release` increments it back. A lock is really just a semaphore configured with a permit count of 1 — the two ideas share the same underlying mechanism at different granularities.

## Deadlock

A **deadlock** is a state where a set of participants each waits for a condition that only another waiting participant can satisfy — nobody is broken, but nobody can proceed either, because everyone is stuck waiting on everyone else.

```text
Thread A holds lock 1, wants lock 2.
Thread B holds lock 2, wants lock 1.
Neither can proceed. Neither will ever release what it holds.
```

Four conditions are classically necessary for this kind of resource deadlock, and all four must hold simultaneously for it to occur: **mutual exclusion** (a resource can only be held by one participant at a time), **hold-and-wait** (a participant holding one resource can wait for another), **no forced preemption** (a resource cannot be forcibly taken from whoever holds it), and a **circular wait** (a cycle of participants, each waiting on the next). Breaking any single one of these four conditions is enough to make that specific kind of deadlock impossible — for example, always acquiring locks in a fixed global order removes the possibility of a circular wait, since no participant can ever be waiting "backward" in that order.

## Starvation

**Starvation** occurs when a runnable participant repeatedly loses access to a needed resource and makes no progress, even though the system overall continues running fine for everyone else. Unlike deadlock, the system as a whole is not stuck — other participants keep making progress — but one unlucky participant keeps losing out, perhaps because a scheduling policy or a lock's acquisition order happens to always favor someone else. A first-come-first-served queue for a lock avoids starvation for waiters; a policy that always lets the "loudest" or most recent requester through does not.

## How these ideas relate

Mutual exclusion and semaphores are _tools_ used to prevent race conditions. Deadlock and starvation are _failure modes_ that can emerge from using those very tools carelessly — a lock prevents the race condition it wraps, but acquiring several locks in an inconsistent order across different code paths can introduce a deadlock that would not have existed without any locking at all. Correct concurrent code is not just "add locks until races disappear"; it also has to reason about whether the locking scheme itself can deadlock or starve some participant.

## Common mistakes

- **Assuming a race condition will show up in testing.** Many race conditions only manifest under rare timing, and can pass every test run while still being present in the code.
- **Acquiring multiple locks in inconsistent orders across different code paths.** This is the single most common real-world cause of deadlock, and often only appears under load, when timing makes the bad interleaving likely enough to actually occur.
- **Treating a semaphore with permit count 1 as fundamentally different from a lock.** They provide the same mutual-exclusion guarantee; a semaphore only adds generality when more than one concurrent holder is intended.
- **Confusing deadlock with starvation.** Deadlock is a total standstill among specific participants; starvation is an ongoing system that keeps making progress while unfairly denying one participant its turn.

## Key points

- A race condition occurs when correctness depends on the relative timing of uncoordinated concurrent operations.
- Mutual exclusion ensures only one execution path at a time enters a critical section touching shared state.
- A semaphore generalizes a lock to allow up to a configured number of concurrent holders.
- Deadlock requires all four of mutual exclusion, hold-and-wait, no preemption, and circular wait to hold at once; breaking any one prevents it.
- Starvation is a runnable participant repeatedly failing to make progress, even while the rest of the system continues running.

# Dynamic programming

Plain recursion is elegant but can be wasteful: computing the `n`th Fibonacci number recursively re-derives the same smaller Fibonacci numbers over and over, an exponential amount of repeated work for a problem that has an obviously linear amount of actual information in it. Dynamic programming is the fix — a way of noticing when recursion is repeating itself, and doing each piece of work exactly once.

## What dynamic programming is

**Dynamic programming** (DP) solves overlapping subproblems once and reuses their results to construct the final answer. It is not a specific algorithm but a strategy that applies whenever a problem has two properties, both worth understanding on their own.

## Optimal substructure

A problem has **optimal substructure** when an optimal solution can be built from optimal solutions to suitable subproblems. Shortest-path problems have this property: the shortest path from `A` to `C` through `B` is the shortest path from `A` to `B` plus the shortest path from `B` to `C` — you cannot do better by using a non-shortest sub-path partway through. Optimal substructure is what makes it _meaningful_ to build a global answer from cached pieces at all; without it, solving subproblems optimally would tell you nothing about solving the whole problem optimally.

## Overlapping subproblems

**Overlapping subproblems** are subproblems reached repeatedly from different branches of a naive recursive solution, making cached results reusable. Fibonacci makes this vivid:

```text
fib(5)
├── fib(4)
│   ├── fib(3)
│   │   ├── fib(2)
│   │   └── fib(1)
│   └── fib(2)          <- fib(2) computed again
└── fib(3)               <- fib(3) computed again
    ├── fib(2)           <- fib(2) computed a third time
    └── fib(1)
```

`fib(3)` and `fib(2)` each get recomputed from scratch multiple times. Overlapping subproblems is what makes it _worth_ caching — with no overlap, every subproblem is only ever needed once, and caching would just add bookkeeping overhead for no benefit. Both properties need to hold together: optimal substructure justifies building the answer from subproblem answers, overlap justifies caching them instead of recomputing.

## Memoization: top-down

**Memoization** is top-down DP that caches results of subproblems when recursive calls first compute them. The recursive structure stays exactly as natural as the naive version; the only change is checking a cache before recursing, and storing the result after.

```python
def fib(n, cache={}):
    if n <= 1:
        return n
    if n in cache:
        return cache[n]
    cache[n] = fib(n - 1, cache) + fib(n - 2, cache)
    return cache[n]
```

The first call to `fib(5)` still recurses down through `fib(4)`, `fib(3)`, and so on, but the second time any particular `n` is requested, the cache answers instantly instead of re-deriving it. This turns Fibonacci's exponential naive recursion into `O(n)` time, at the cost of `O(n)` cache space (and, notably, still `O(n)` recursion depth — memoization removes redundant _computation_, not the risk of deep recursion discussed in the recursion lesson).

## Tabulation: bottom-up

**Tabulation** is bottom-up DP that fills a table of smaller subproblem results in an order that makes later results available. Instead of starting from the big question and recursing down, tabulation starts from the smallest subproblems and builds up.

```python
def fib(n):
    table = [0, 1]
    for i in range(2, n + 1):
        table.append(table[i - 1] + table[i - 2])
    return table[n]
```

For Fibonacci specifically, only the last two values are ever needed, so this can be trimmed to `O(1)` extra space — a common further optimization once a tabulated solution's access pattern is understood. Tabulation avoids recursion entirely, which sidesteps the recursion-depth risk that memoization still carries, but it requires figuring out a processing order upfront (here, simply increasing `i`) that guarantees every subproblem a later step depends on has already been filled in.

## Choosing between them

Memoization tends to be easier to derive directly from a recursive definition of the problem, and it naturally skips subproblems that are never actually needed for the specific input given. Tabulation tends to run faster in practice (no function-call overhead per subproblem) and avoids stack-depth concerns, but it computes every entry in its table whether or not the final answer needs all of them, and it requires working out a valid fill order in advance. Both compute the same answers when applied to the same problem; the choice is about implementation convenience and constant-factor performance, not correctness.

## Common mistakes

- **Applying DP to a problem without optimal substructure.** Caching subproblem answers only helps if a correct global answer can actually be assembled from them; if it cannot, memoization just caches wrong partial reasoning faster.
- **Applying DP to a problem without overlapping subproblems.** Divide-and-conquer algorithms like merge sort recurse into genuinely disjoint subproblems — there is nothing to cache, and adding memoization would only add overhead.
- **Forgetting the cache key must capture every varying input.** If a recursive function depends on more than one changing parameter, the cache must be keyed on the full combination, not just one of them.
- **Assuming tabulation is always better because it avoids recursion.** For problems where only a small fraction of subproblems are ever actually reached, memoization can do meaningfully less total work.

## Key points

- Dynamic programming solves overlapping subproblems once and reuses the results to build the final answer.
- Optimal substructure means an optimal solution can be assembled from optimal solutions to subproblems.
- Overlapping subproblems means the same subproblem recurs across different branches of naive recursion, making caching worthwhile.
- Memoization is top-down: it keeps the natural recursive structure and caches results as they are first computed.
- Tabulation is bottom-up: it fills a table of subproblem results in an order that guarantees dependencies are ready first.
- Both techniques compute the same correct answer; they trade off differently on implementation style, recursion depth, and wasted work.

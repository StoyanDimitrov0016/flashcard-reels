# Recursion and algorithm design

Many algorithms are not one-off tricks but instances of a few general strategies. This lesson starts with recursion, the mechanism behind most of them, and then walks through the main design paradigms: dynamic programming, greedy choice, divide and conquer, backtracking, and branch and bound.

## Recursion and base cases

**Recursion** solves a problem by having a function call **itself on smaller subproblems**. Each call makes the problem a bit smaller until it reaches a **base case**, an input simple enough to answer directly, which **stops further calls**.

```js
function factorial(n) {
  if (n <= 1) return 1; // base case
  return n * factorial(n - 1); // smaller subproblem
}
```

Without a base case, or with one the recursion never reaches, the calls never stop.

## The call stack

Every function call needs somewhere to keep its state. The **call stack** stores the **active function frames** in nested call order. Each frame holds the call's **return location** and its local execution state, such as parameters and local variables. When a call finishes, its frame is popped and execution resumes where the caller left off.

This is why **deep recursion can fail**. Each recursive call pushes another frame, consuming stack space, and the runtime's stack has a fixed limit. Calling `factorial(100000)` may throw a stack overflow error even though the algorithm is **logically correct**. The usual fixes are rewriting the recursion as a loop, or managing an explicit stack on the heap.

## Dynamic programming

Some recursive solutions do the same work many times. A naive recursive Fibonacci computes `fib(3)` again and again from different branches of its call tree. **Dynamic programming (DP)** solves each **overlapping subproblem once** and **reuses** the result to build the final answer.

DP applies when a problem has two properties:

- **Optimal substructure**: an optimal solution can be **built from optimal solutions to suitable subproblems**. The shortest route from A to C through B contains a shortest route from A to B.
- **Overlapping subproblems**: the same subproblems are **reached repeatedly from different branches** of the naive recursion, so caching their results pays off.

There are two ways to implement it.

**Memoization** is **top-down**. You keep the natural recursive structure but **cache each subproblem's result** the first time a recursive call computes it. Later calls just look it up.

```js
function fib(n, memo = new Map()) {
  if (n <= 1) return n;
  if (!memo.has(n)) memo.set(n, fib(n - 1, memo) + fib(n - 2, memo));
  return memo.get(n);
}
```

**Tabulation** is **bottom-up**. You **fill a table** starting from the smallest subproblems, in an order that guarantees every result is ready before anything needs it. It avoids recursion entirely.

```js
function fibTable(n) {
  const table = [0, 1];
  for (let i = 2; i <= n; i++) table[i] = table[i - 1] + table[i - 2];
  return table[n];
}
```

## Greedy algorithms

A **greedy algorithm** repeatedly makes the **locally best choice** and **never revisits** earlier choices. Kruskal's and Prim's algorithms are greedy, and so is making change by always taking the largest coin that fits.

Greedy algorithms are simple and fast, but they are **correct only when the problem has a property that proves locally optimal choices extend into a globally optimal solution**. Coin change shows why this matters: with coins of 1, 3, and 4, making 6 greedily gives 4 + 1 + 1, three coins, while 3 + 3 uses only two. Any greedy solution needs a proof, not just a good feeling.

## Divide and conquer

**Divide and conquer** splits a problem into smaller **independent** subproblems, solves them recursively, and **combines** their results. Merge sort is the classic example: split the array, sort each half, merge.

The word "independent" separates it from dynamic programming. In divide and conquer, subproblems do not overlap, so there is nothing to cache.

## Backtracking

**Backtracking** builds a candidate solution **incrementally**, one choice at a time, and **abandons a partial candidate as soon as it cannot lead to a valid solution**. It then undoes the last choice and tries the next option.

Solving a Sudoku is a good picture: place a digit, move on, and as soon as a row, column, or box conflict appears, back up and try a different digit. Pruning dead ends early is what makes backtracking far faster than generating every complete candidate.

## Branch and bound

**Branch and bound** is used for **optimization** problems, where you want the best solution rather than any valid one. It explores the search space like backtracking, but for each branch it computes a **bound on the best result still possible** down that branch. If that bound **cannot beat the current best solution** found so far, the whole branch is **pruned**.

For a shortest-tour problem, if a partial route already costs more than the best complete tour found, no extension of it can win, so it is discarded immediately.

# Graphs

Trees model hierarchies, but many relationships have no single root and can loop back on themselves: road networks, social connections, links between web pages, dependencies between tasks. A graph is the general-purpose tool for modeling relationships like these, and it is general enough that trees themselves are a special case of it — a tree is simply a connected graph with no cycles.

## Vertices and edges

A **graph** is a set of vertices connected by edges that model relationships between entities. A vertex (or node) is an entity — a city, a person, a web page; an edge is a relationship between two vertices — a road, a friendship, a hyperlink. That is the entire vocabulary needed to describe an enormous range of problems: "is there a route from A to B," "how are these two people connected," "in what order must these tasks run" are all questions about vertices and edges.

```text
   A --- B
   |     |
   C --- D
```

Four vertices, four edges: `A-B`, `A-C`, `B-D`, `C-D`.

## Directed versus undirected

The difference between a directed and undirected graph is about whether relationships have direction. Directed edges have an orientation from one vertex to another — `A -> B` does not imply `B -> A`. Undirected edges represent a symmetric connection — an edge between `A` and `B` means the relationship holds both ways at once.

A friendship on a platform where following is mutual is naturally undirected; a followed-by relationship on a platform where following is one-directional (you can follow someone who does not follow you back) is naturally directed. Choosing the right one up front matters, because many graph algorithms (starting with the traversal algorithms in the next lesson) behave differently, or mean something different, depending on which kind of graph they run on.

```text
Undirected:  A --- B        Directed:  A --> B
             (A~B implies B~A)         (A->B does NOT imply B->A)
```

## Weighted graphs

A **weighted graph** assigns a cost, distance, capacity, or other numeric value to edges, rather than treating every edge as equally significant. A road network is naturally weighted by distance or travel time; an unweighted graph implicitly treats every edge as costing the same, which is a reasonable simplification when all that matters is _whether_ a connection exists, not how expensive it is. The shortest-path and spanning-tree algorithms two lessons ahead are specifically about weighted graphs — without weights, "shortest" reduces to "fewest edges," which breadth-first search already answers directly.

## Representing a graph in code

A graph's abstract picture (vertices and edges) needs a concrete data structure before any algorithm can run on it. The two standard choices trade memory for lookup speed in opposite directions.

An **adjacency list** stores, for each vertex, the edges or neighbors leaving that vertex. It is space-efficient for sparse graphs — graphs where the number of edges is much smaller than the maximum possible (`V²` for `V` vertices) — because it only stores space proportional to the edges that actually exist.

```text
A: [B, C]
B: [A, D]
C: [A, D]
D: [B, C]
```

An **adjacency matrix** stores a table indexed by vertex pairs, indicating whether — or with what weight — an edge exists between them. Edge lookup is `O(1)`: checking whether `A` connects to `D` is a single table access, `matrix[A][D]`. But storage is `O(V²)`, since the table has one entry for every possible pair of vertices whether or not an edge actually exists there.

```text
     A  B  C  D
  A [0, 1, 1, 0]
  B [1, 0, 0, 1]
  C [1, 0, 0, 1]
  D [0, 1, 1, 0]
```

## Choosing a representation

For a social network with millions of users but a manageable number of friendships per person (sparse), an adjacency list keeps memory proportional to the actual number of friendships. For a small, densely connected graph — or one where "is there an edge between these two specific vertices" is a frequent, performance-critical question — an adjacency matrix's `O(1)` edge lookup can be worth its `O(V²)` memory cost. Most of the traversal and shortest-path algorithms in the following lessons are usually described, and usually implemented, against an adjacency list, because they process "all neighbors of this vertex" far more often than "is there specifically an edge between these two vertices."

## Common mistakes

- **Treating a directed graph's edges as symmetric.** A path that exists `A -> B` does not mean a path exists `B -> A`; algorithms and reasoning that assume symmetry silently produce wrong answers on directed graphs.
- **Using an adjacency matrix for a large sparse graph.** A million-vertex graph with only a few edges per vertex would need a trillion-cell matrix — the memory cost of `O(V²)` becomes prohibitive long before an adjacency list's cost does.
- **Forgetting to store weights when they matter.** Treating a weighted graph as unweighted (or vice versa) changes what "shortest path" or "minimum cost" even means.
- **Conflating a tree with "any graph without cycles."** A tree additionally requires connectivity and exactly one path between any two nodes; a graph can be acyclic but disconnected, or acyclic with multiple disjoint components (a **forest**), without being a single tree.

## Key points

- A graph is a set of vertices connected by edges, modeling relationships between entities.
- Directed edges have an orientation between vertices; undirected edges represent a symmetric connection.
- A weighted graph assigns a numeric cost, distance, or capacity to its edges.
- An adjacency list stores each vertex's neighbors and is space-efficient for sparse graphs.
- An adjacency matrix stores a full table of vertex pairs, giving `O(1)` edge lookup at `O(V²)` storage cost.
- The right representation depends on graph density and which operation — listing neighbors or testing a specific edge — matters more.

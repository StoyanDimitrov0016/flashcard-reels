# Cryptography and hard problems

Some problems are hard to solve, and that can be a curse or a gift. Cryptography deliberately builds on problems that are computationally difficult, while algorithm designers need to recognize hard problems early so they stop searching for an exact fast solution that probably does not exist. This lesson covers both sides.

## Cryptographic hash functions

A **cryptographic hash function** **deterministically** maps input of any length to a **fixed-size digest**, such as the 256 bits of SHA-256. The same input always gives the same digest, but changing a single character produces a completely different one.

Unlike a hash table's hash function, it must also resist deliberate attack. It is designed to make these tasks **computationally difficult**:

- Finding a **collision**: two different inputs with the same digest.
- Finding a **preimage**: an input that produces a given digest.
- Related manipulations, such as finding a second input that matches the digest of a known one.

By the pigeonhole principle, collisions must exist, since there are infinitely many inputs and finitely many digests. The point is that nobody can feasibly find one. That makes digests useful for verifying downloads, detecting tampering, and as building blocks for signatures.

## Password hashing

Storing passwords needs a different kind of hash. General-purpose hashes are designed to be **fast**, and that is exactly the problem: an attacker who steals a password database can try billions of guesses per second against a fast hash.

**Password hashing** functions, such as bcrypt, scrypt, and Argon2, are **deliberately expensive**. They are tuned to use significant **computation or memory**, so **each guess** costs an attacker real resources, while a single legitimate login check remains quick enough. They also add a random **salt** to each password before hashing. Salts ensure two users with the same password get different hashes and stop attackers from using precomputed tables to crack many accounts at once.

## Public-key encryption

Traditional encryption uses one shared secret key. **Public-key encryption** uses a **pair** of mathematically related keys instead. The **public key** can be shared with anyone and allows one operation, such as **encryption**. The **private key** is kept secret and performs the corresponding protected operation, such as **decryption**.

Anyone can encrypt a message to you with your public key, but only your private key can decrypt it. The security rests on a hard problem: deriving the private key from the public one is computationally infeasible.

## Digital signatures

A **digital signature** runs the idea the other way. The signer uses the **private key** to produce a signature over a message, and anyone can **verify** it with the matching **public key**. A valid signature provides two things:

- **Integrity**: the message has not been changed since it was signed.
- **Evidence of origin**: it was produced by whoever holds the private key.

TLS certificates, software updates, and signed commits all rely on signatures.

## NP-completeness

Now for problems whose hardness is unwelcome. **NP-complete** problems, such as Boolean satisfiability, graph coloring, and the decision version of the traveling salesman problem, share a striking property: no polynomial-time exact algorithm is known for any of them, and finding one for any single problem would give one for all of them. Most researchers believe none exists.

In engineering, the value of this is practical. **Showing that a problem is NP-complete** tells you to stop hoping for an exact algorithm that scales to large general inputs, and to choose a different strategy:

- **Approximation** algorithms with a provable quality guarantee.
- **Heuristics** that work well on typical inputs.
- Exploiting **restricted inputs**, such as small parameters or special structure.
- **Exponential search with pruning**, such as backtracking or branch and bound, when instances are small enough.

## Reductions

Hardness results travel through **reductions**. A problem A **reduces** to a problem B when there is a way to **transform any instance of A into an instance of B** so that solving B gives the answer to A.

The direction matters. If A reduces to B efficiently, then B is **at least as hard** as A: a fast solver for B would also solve A. That is how NP-completeness spreads. Once one problem is known to be hard, reducing it to a new problem proves the new problem is hard too.

## Let the constraints choose the algorithm

Complexity classes are only part of the picture. An `O(n²)` algorithm is perfectly fine for a few hundred items, around a hundred thousand steps, and **unusable for millions**, around a trillion. A clever `O(n log n)` alternative may not be worth its complexity for tiny inputs.

Choosing well means looking at the actual **constraints**: the **input size**, the available **memory**, the **constant factors** of each approach, and the **distribution of the data**, such as whether it is nearly sorted or has many duplicates. Asymptotic analysis narrows the choices; real inputs decide.

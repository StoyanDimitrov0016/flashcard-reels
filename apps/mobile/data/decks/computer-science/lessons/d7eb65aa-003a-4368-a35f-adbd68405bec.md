# Trees

Many kinds of data are naturally hierarchical: folders contain files and other folders, an org chart has managers and their reports, a file system's directory structure branches from a single root. Arrays and linked lists model sequences well, but they have no natural way to express "this contains these, which each contain these." Trees are the structure built for hierarchy, and when a tree is kept ordered, it also makes searching fast.

## Trees and binary trees

A **tree** is a connected acyclic hierarchy of nodes with parent-child relationships and one path between any two nodes. "Acyclic" means no node is its own descendant; "one path between any two nodes" is what distinguishes a tree from a more general graph (covered in the next lesson), where multiple paths — or none at all — are possible. One node is designated the **root**; every other node has exactly one parent, and any node with no children is a **leaf**.

A **binary tree** is a tree where each node has at most two children, conventionally called the left and right child. Binary trees are the most common shape in practice, partly because two children are enough to build the ordering scheme described next, and partly because their branching structure maps neatly onto recursive code — the recursion lesson's "solve a smaller version of the same problem" pattern applies directly, since each child is the root of its own smaller binary tree.

## Binary search trees

A **binary search tree** (BST) orders nodes so that keys in one subtree compare lower and keys in the other compare higher, according to its ordering rule — conventionally, every node's left subtree holds smaller keys and its right subtree holds larger ones.

```text
        8
      /   \
     3     10
    / \      \
   1   6      14
      /
     4
```

Searching for `6`: start at the root (`8`); `6 < 8`, go left to `3`; `6 > 3`, go right to `6`; found. Each comparison eliminates one entire subtree from consideration, not just one node.

## Search cost, balance, and degradation

The search cost in a balanced binary search tree is `O(log n)`, because each comparison eliminates a large fraction of the remaining tree — with the tree above, one comparison rules out either everything under `3` or everything under `10`, roughly halving the remaining candidates each step, just like binary search over a sorted array (sorting lesson).

That guarantee depends entirely on the tree staying roughly balanced. A plain binary search tree can degrade to `O(n)` if insertions create a highly skewed tree, whose height can approach the number of nodes, turning search into effectively linear traversal. Inserting `1, 2, 3, 4, 5` in that order into an empty BST, with no rebalancing, produces this:

```text
1
 \
  2
   \
    3
     \
      4
       \
        5
```

Every node has only a right child — this is a linked list wearing a tree's clothing, and searching for `5` now takes five comparisons instead of the roughly three a balanced five-node tree would need.

## Self-balancing search trees

Self-balancing search trees maintain logarithmic height through rotations or restructuring, so lookup, insertion, and deletion remain `O(log n)` even in the presence of adversarial or unlucky insertion orders. A **rotation** is a local restructuring that changes which node is a subtree's root while preserving the BST ordering property, incrementally correcting imbalance as the tree grows instead of rebuilding it from scratch. Red-black trees and AVL trees are two well-known self-balancing schemes; both guarantee `O(log n)` height no matter what order keys arrive in, which is exactly what plain BSTs cannot promise. This is why production key-value structures (including many database indexes, covered in the databases deck) use a self-balancing or otherwise height-bounded tree rather than a plain BST.

## Tries

A **trie** stores keys by prefixes along tree edges, making lookup proportional to key length rather than the number of stored keys. Instead of comparing whole keys against each other the way a BST does, a trie spends one step per character (or per unit of the key), walking one edge deeper for each character consumed:

```text
root
 └─ c
     └─ a
         ├─ t   (end of "cat")
         └─ r
             └─ (end of "car")
```

Looking up `"cat"` walks `c -> a -> t`, three steps, regardless of how many thousands of other words share the trie. Keys with a common prefix — `"car"` and `"cat"` here — share the same path until they diverge, which is exactly what makes tries useful for prefix searches, autocomplete, dictionaries, and routing structures where shared prefixes matter: finding every word beginning with `"ca"` is just a matter of walking to the `"ca"` node and reading off everything reachable below it, without scanning unrelated words at all.

## Common mistakes

- **Assuming any binary search tree is `O(log n)`.** The bound holds for a _balanced_ tree; an unbalanced one built from sorted or adversarial input can degrade to `O(n)`.
- **Confusing "binary tree" with "binary search tree."** A binary tree only constrains the number of children; a BST additionally requires the ordering property that makes search fast.
- **Reaching for a trie for arbitrary key comparisons.** A trie's advantage is prefix structure; for keys with no meaningful shared-prefix relationship, a hash table or balanced BST is usually simpler and just as fast.
- **Forgetting self-balancing trees pay for their guarantee with extra bookkeeping.** Rotations and rebalancing add constant-factor overhead to insertions and deletions in exchange for the worst-case height guarantee.

## Key points

- A tree is a connected acyclic hierarchy with exactly one path between any two nodes; a binary tree limits each node to at most two children.
- A binary search tree orders each node's subtrees so one side holds smaller keys and the other holds larger keys.
- Search in a balanced BST is `O(log n)` because each comparison eliminates a large fraction of the remaining tree.
- An unbalanced BST can degrade to `O(n)` height, turning search into linear traversal.
- Self-balancing trees use rotations or restructuring to keep height logarithmic regardless of insertion order.
- A trie stores keys along edges by shared prefix, making lookup proportional to key length and enabling efficient prefix queries.

# Core data structures

An algorithm is only as fast as the way its data is stored. A **data structure** organizes values and the relationships between them so that selected operations, such as lookup, insertion, or removal, can be done with useful time and space costs. No structure is best at everything; each one trades some operations for others.

## Arrays and linked lists

An **array** stores elements in indexed order, usually in one contiguous block of memory. Because the position of element `i` can be calculated directly, access by index is `O(1)`. The cost appears when inserting or deleting in the middle: every later element has to shift over by one, which is `O(n)`.

A **linked list** stores each element in a separate node that holds a reference to the next node (and, in a doubly linked list, to the previous one). If you already hold a reference to a node, inserting or removing next to it is `O(1)`: you just rewire a few references. But there is no index arithmetic, so reaching the `n`th element means walking the list from the start.

## Stacks, queues, and deques

These structures are defined by _where_ items enter and leave.

- A **stack** is **last-in, first-out (LIFO)**. You `push` onto the top and `pop` from the top, like a pile of plates. Undo history and function calls behave this way.
- A **queue** is **first-in, first-out (FIFO)**. Items are added at the back and removed from the front, like a line at a counter. Print jobs and task buffers work this way.
- A **deque** (double-ended queue) supports insertion and removal at **both** the front and the back, so it can act as either a stack or a queue.

All three can be built on arrays or linked lists, with every core operation in `O(1)` time.

## Priority queues and heaps

A **priority queue** removes items by **priority** rather than by arrival order. A hospital emergency room is a priority queue: the most urgent patient is seen next, not the one who arrived first. Priority queues are commonly implemented with a heap.

A **binary heap** is a **nearly complete binary tree**: every level is full except possibly the last, which fills from left to right. That shape lets it live compactly in an array. It also maintains a **heap-order property** between parents and children, which gives:

- `O(1)` access to the minimum (or maximum) element, which is always at the root.
- `O(log n)` insertion and removal, because a new or displaced element only moves along one root-to-leaf path, and the tree's height is logarithmic.

In a **min-heap**, every parent is **no greater than** its children, so the smallest element sits at the root. A max-heap reverses the rule, putting the largest at the root.

## Hash tables

A **hash table** stores key-value pairs. A **hash function** turns each key into a number that selects a storage **bucket**. Looking up a key means hashing it and checking one bucket, so lookup, insertion, and deletion are **expected O(1)**, provided collisions stay under control.

A **hash collision** happens when two distinct keys map to the same bucket or position. Collisions are unavoidable when there are more possible keys than buckets, so the table must resolve them while still telling the keys apart, which is why it stores and compares the actual keys, not just their hashes.

There are two main strategies:

- **Separate chaining**: each bucket holds a small collection, such as a linked list or short array, of all entries that hashed there. Lookup hashes to the bucket and then searches that collection.
- **Open addressing**: every entry lives directly in the main table. On a collision, the table **probes** other slots according to a rule, such as checking the next slot along, until it finds the key or an empty slot.

The **load factor** is the number of stored entries divided by the table's capacity. As it rises, chains grow longer or probe sequences get longer, and operations slow down. Tables therefore **resize**, allocating a larger array and reinserting every entry, before the load factor gets too high.

A good hash function for a table has two properties:

1. It is **deterministic**: equal keys must always produce equal hashes, or a stored key could never be found again.
2. It **distributes** typical distinct keys evenly across buckets, avoiding **clustering** where many keys pile into a few slots.

## Sets

A **set** is an abstract data type that stores **unique** values. It supports membership tests, insertion, and deletion, but unlike a map it attaches no separate value to each key. Sets are often built on hash tables (fast unordered membership) or balanced trees (ordered membership).

```js
const seen = new Set();
seen.add("apple");
seen.add("apple"); // duplicate, ignored
seen.has("apple"); // true
seen.size; // 1
```

# Scope and hoisting

Before you can predict what a piece of JavaScript will do, you need to know which variables a given line of code can even see, and when those variables become usable. Get scope wrong and you write code that reads variables too early, leaks them where they shouldn't be visible, or shadows a variable you meant to reuse. This lesson covers where names are visible and how JavaScript prepares a scope before running it.

## Lexical scope

JavaScript uses **lexical scope**: which variables a piece of code can see is decided by _where that code is physically written_ in the source, not by which function happened to call it. An inner function can read any variable declared in a function or block that textually surrounds it, no matter when or how that inner function is eventually invoked.

```js
function outer() {
  const label = "outer";
  function inner() {
    console.log(label); // "outer" - inner is written inside outer
  }
  inner();
}
```

## Block scope vs. function scope

A **block** is any region delimited by `{ ... }` - the body of an `if`, a `for`, or a bare `{ }`. Declarations made with `let`, `const`, and `class` are **block-scoped**: each one exists only inside the nearest enclosing block.

`var` ignores ordinary blocks. It uses **function scope** instead: a `var` declared anywhere inside a function is visible throughout that entire function, including inside nested blocks, but not outside the function. Declared at the top level of a script, `var` becomes a global.

```js
function demo() {
  if (true) {
    var v = "function-scoped";
    let l = "block-scoped";
  }
  console.log(v); // "function-scoped": var ignores the if-block
  console.log(l); // ReferenceError: l only exists inside the if-block
}
```

This is the practical difference between `var` and `let`/`const`: `var` is scoped to the nearest function (or the global scope), while `let` and `const` are scoped to the nearest block.

## What const actually promises

**`const`** guarantees only one thing: the name cannot be **rebound** to a different value after initialization. It says nothing about whether the value itself can change. A `const` array or object can still be mutated through its methods or properties - only reassigning the variable itself is blocked.

```js
const list = [1, 2];
list.push(3); // fine: mutating the array's contents
console.log(list); // [1, 2, 3]
list = []; // TypeError: Assignment to constant variable.
```

## Hoisting

Before a scope actually starts executing, JavaScript walks through it and processes every declaration up front. This preparatory pass is called **hoisting**, and it treats each kind of declaration differently:

- **Function declarations** (`function greet() {}`) are fully created before execution begins, so you can call them earlier in the source than where they're written.
- **`var`** bindings are created and initialized to `undefined` immediately, so reading one before its line gives `undefined` rather than an error.
- **`let`, `const`, and `class`** bindings are created but left **uninitialized** until their declaration line actually runs.

```js
console.log(typeof greet); // "function" - fully hoisted
greet();

console.log(sum); // undefined - var hoisted, not yet assigned
var sum = 10;

function greet() {
  console.log("hi");
}
```

## The temporal dead zone

The stretch of a block from its start until a `let`, `const`, or `class` declaration actually initializes is called the **temporal dead zone (TDZ)**. Touching that binding anywhere in the TDZ - even just reading it - throws a `ReferenceError`, rather than silently returning `undefined`.

```js
{
  console.log(count); // ReferenceError: Cannot access 'count' before initialization
  let count = 0;
}
```

The TDZ exists on purpose: using a `let`/`const` variable before it has a real value is very likely a bug, so the language turns it into a loud error instead of a silent `undefined` that would corrupt later logic.

## Function declarations vs. function expressions

A **function declaration** (`function name() { ... }` as its own statement) is created during the hoisting pass described above, so it can be called before its source line. A **function expression** (`const name = function() { ... }`, including arrow functions) creates its function value only when execution actually reaches that line - the variable holding it follows the normal `var`/`let`/`const` hoisting rules for the _variable_, but the function itself doesn't exist until the assignment runs.

```js
sayHi(); // works: declaration is hoisted whole
function sayHi() {
  console.log("hi");
}

sayBye(); // TypeError: sayBye is not a function (var is hoisted as undefined)
var sayBye = function () {
  console.log("bye");
};
```

## Common mistakes

- **Assuming `const` makes objects immutable.** `const` only locks the binding, not the value; use `Object.freeze` if you need to prevent mutation of the object itself.
- **Reading a `let`/`const` variable "before" it's declared and expecting `undefined`.** Unlike `var`, this throws a `ReferenceError` from the temporal dead zone.
- **Calling a function-expression variable before its assignment runs.** Only function _declarations_ are callable early; function expressions are not created until their line executes.

## Key points

- Lexical scope means visibility is determined by where code is written, not by how it is called.
- `let`, `const`, and `class` are block-scoped; `var` is function-scoped (or global at the top level) and ignores ordinary blocks.
- `const` prevents rebinding a name to a new value; it does not make the value itself immutable.
- Hoisting processes declarations before execution: function declarations are fully usable early, `var` is initialized to `undefined`, and `let`/`const`/`class` are left uninitialized.
- The temporal dead zone is the region before a `let`/`const`/`class` initializes; accessing the binding there throws a `ReferenceError`.
- A function declaration is callable before its source line because it's hoisted whole; a function expression's value doesn't exist until its assignment runs.

# Iterators and generators

`for...of`, the spread operator, and destructuring all consume sequences of values - arrays, strings, `Map`s, `Set`s, even custom objects you write yourself. What makes all of that possible is one shared protocol, and generator functions are the easiest way to implement that protocol for your own data without hand-writing the bookkeeping. This lesson covers both, plus the older `for...in` loop they're easy to confuse with.

## Iterables and iterators

An **iterable** is any value that has a `[Symbol.iterator]()` method returning an **iterator**. An iterator is an object with a `next()` method that returns a **`{ value, done }`** record on every call: `value` is the next item, and `done` is `true` once the sequence is exhausted. Arrays, strings, `Map`s, and `Set`s are all built-in iterables. Constructs like `for...of`, spread (`...`), and destructuring all work by calling `[Symbol.iterator]()` and repeatedly calling `next()` on the result.

You can make your own values iterable by implementing the protocol yourself:

```js
const range = {
  from: 1,
  to: 3,
  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;
    return {
      next() {
        return current <= last
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      },
    };
  },
};

console.log([...range]); // [1, 2, 3] - spread consumes the iterable
for (const n of range) console.log(n); // 1, 2, 3
```

## for...of vs. for...in

These two loops consume completely different things, despite looking similar. **`for...of`** iterates the **values** produced by an iterable, using the protocol above. **`for...in`** iterates **enumerable string property keys**, including keys **inherited** through the prototype chain - it has nothing to do with the iterable protocol at all.

```js
const obj = { a: 1, b: 2 };
for (const key in obj) console.log(key); // "a", "b" - property keys

for (const value of obj) console.log(value); // TypeError: obj is not iterable
```

Plain objects aren't iterable by default, which is exactly why `for...of` throws on one. Use `for...in` for object keys (or better, `Object.keys`/`Object.entries` with `for...of`), and `for...of` for arrays, strings, and other genuine iterables.

## Generator functions

Implementing the iterator protocol by hand, as `range` did above, gets tedious for anything non-trivial. A **generator function** - declared with `function*` - returns an iterator automatically, and its body can **pause** at a `yield` expression and **resume** later from exactly that point when `next()` is called again.

```js
function* countUp(from, to) {
  for (let n = from; n <= to; n++) {
    yield n;
  }
}

const it = countUp(1, 3);
console.log(it.next()); // { value: 1, done: false }
console.log(it.next()); // { value: 2, done: false }
console.log(it.next()); // { value: 3, done: false }
console.log(it.next()); // { value: undefined, done: true }
```

Because the object a generator returns already implements `next()` correctly, it's automatically usable anywhere an iterable is expected: `for (const n of countUp(1, 3))`, `[...countUp(1, 3)]`, and destructuring all work without any extra code.

## What problem generators solve

The alternative to a generator is computing a full sequence up front and returning it as an array - which means doing all the work and holding all the results in memory before the caller sees anything. Generators let you produce a sequence **lazily**, one value at a time, while the function's local variables and position stay paused between calls. This is valuable for sequences that are expensive to compute in full, or that are conceptually infinite:

```js
function* naturals() {
  let n = 1;
  while (true) yield n++;
}

function* take(iterable, count) {
  let i = 0;
  for (const value of iterable) {
    if (i++ >= count) return;
    yield value;
  }
}

console.log([...take(naturals(), 5)]); // [1, 2, 3, 4, 5]
```

`naturals()` never terminates on its own and never builds an array - `take` only pulls as many values as it needs, and the rest are never computed.

## Common mistakes

- **Using `for...of` on a plain object.** Plain objects aren't iterable; iterate their keys with `for...in` or `Object.keys`/`Object.entries`.
- **Forgetting that `for...in` walks inherited enumerable properties.** It can surface properties from the prototype chain that `Object.keys` (own properties only) would not include.
- **Computing an entire sequence eagerly when a generator would do.** For large or unbounded sequences, this wastes memory and delays the first result; a generator can start yielding immediately.

## Key points

- An iterable provides a `[Symbol.iterator]()` method returning an iterator, which is how `for...of` and spread consume its values.
- An iterator is an object with a `next()` method returning `{ value, done }` records.
- `for...of` iterates values from an iterable; `for...in` iterates enumerable string property keys, including inherited ones, and is unrelated to the iterable protocol.
- A generator function (`function*`) returns an iterator automatically, pausing at `yield` and resuming on the next `next()` call.
- Generators let a sequence be produced lazily, preserving local execution state between values, instead of computing and storing the whole sequence up front.

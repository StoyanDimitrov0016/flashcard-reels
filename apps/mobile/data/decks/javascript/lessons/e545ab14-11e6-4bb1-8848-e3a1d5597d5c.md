# Values, scope, and closures

Every JavaScript program moves data around and decides which parts of the code can see which names. This lesson covers the building blocks: what a value is, how missing values are represented, where variables are visible, and how functions keep access to the variables around them.

## Values: primitives and objects

A **value** is any piece of data a program works with: a number, a string, a boolean, an object, a function, `null`, or `undefined`. Values fall into two groups.

**Primitives** are strings, numbers, bigints, booleans, symbols, `undefined`, and `null`. They are **immutable**: an operation like `name.toUpperCase()` returns a new string rather than changing the old one. Two primitives with the same content are equal.

**Objects** (including arrays and functions) are mutable collections of properties, and each one has its own **identity**. Two separately created objects can hold exactly the same data and still not be equal, because comparison checks whether both sides refer to the same object.

```js
"hi" === "hi"; // true: same primitive value
({ a: 1 }) === { a: 1 }; // false: two different objects
```

## Missing values: undefined and null

JavaScript has two primitives for "nothing here".

**`undefined`** is what the language produces on its own when no value exists yet: a declared variable that was never assigned, a property that does not exist, a missing function argument, or the result of a function that returns without a value.

**`null`** is a value you assign on purpose. It signals an **intentional absence**, such as "this user has no manager" or "no item is selected".

The practical rule: `undefined` usually means nothing was supplied or produced, while `null` means someone deliberately recorded "no value". Both are missing values, and both are treated as missing by operators such as `??` and `?.`.

One trap: `typeof null` reports `"object"`. This is a historical quirk kept for compatibility, not a sign that `null` is an object. To test for null, compare directly with `value === null`.

```js
let a;
typeof a; // "undefined"
typeof null; // "object" (quirk)
```

## Lexical scope

**Scope** decides where a name can be used. JavaScript uses **lexical scope**: visibility is fixed by where code is written in the source, not by where it is called from. An inner function can read variables from any function or block that surrounds it in the source text.

## Block scope and function scope

A **block** is any `{ ... }` region, such as the body of an `if` or a loop. Declarations made with `let`, `const`, and `class` are **block-scoped**: they exist only inside the nearest enclosing block.

Declarations made with `var` ignore ordinary blocks. They use **function scope**: a `var` inside a function is visible throughout the whole function, including inside nested blocks, but not outside the function. At the top level of a script, `var` creates a global binding.

```js
function demo() {
  if (true) {
    var v = 1;
    let l = 2;
  }
  console.log(v); // 1: var belongs to the function
  console.log(l); // ReferenceError: l belongs to the if block
}
```

## What const promises

**`const`** prevents **rebinding**: once initialized, the name cannot be pointed at a different value. It says nothing about the value itself. If a `const` holds an object or array, you can still change that object's contents.

```js
const list = [1, 2];
list.push(3); // allowed: the array is mutated
list = []; // TypeError: cannot reassign a const binding
```

## Hoisting and the temporal dead zone

Before a scope starts running, JavaScript processes the declarations inside it. This behavior is called **hoisting**. The effect differs by declaration kind:

- **Function declarations** are fully created up front, so you can call them before their line in the source.
- **`var`** bindings are created and set to `undefined`, so reading one early gives `undefined` instead of an error.
- **`let`, `const`, and `class`** bindings are created but left uninitialized.

The region from the start of the scope until the declaration line runs is the **temporal dead zone (TDZ)**. Touching a `let`, `const`, or `class` binding inside it throws a `ReferenceError`. The TDZ exists so that using a variable before it has a meaningful value is an error rather than a silent `undefined`.

```js
greet(); // works: function declaration is hoisted
console.log(count); // ReferenceError: count is in the TDZ
let count = 0;

function greet() {
  console.log("hello");
}
```

## Closures

A **closure** is a function together with access to the variables that were in scope where the function was created. Because scope is lexical, an inner function keeps that access even after the outer function has returned.

```js
function makeCounter() {
  let count = 0;
  return () => ++count;
}

const next = makeCounter();
next(); // 1
next(); // 2
```

`makeCounter` has finished, yet `next` still reads and updates `count`. The variable is private: no other code can reach it.

Closures are useful whenever a function needs to **remember state or context** without global variables. Common examples are counters and caches, functions preconfigured with settings, and event handlers or callbacks that need values from the code that registered them.

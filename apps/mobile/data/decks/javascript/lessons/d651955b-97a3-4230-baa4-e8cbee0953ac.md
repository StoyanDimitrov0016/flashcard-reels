# Primitive values

Every JavaScript program moves data around: numbers to add, strings to display, objects to update. Before any of the language's other rules make sense, you need a clear picture of what a **value** actually is, why some values behave completely differently from others, and how JavaScript represents "nothing" in more than one way. Get this wrong and later topics, especially equality and object identity, feel arbitrary instead of predictable.

## What a value is

A **value** is any piece of data a program works with: a number, a string, a boolean, an object, a function, `null`, or `undefined`. Every variable, every property, every function argument holds a value. JavaScript sorts all values into two families that behave in fundamentally different ways: **primitives** and **objects**.

## Primitives are immutable and compared by content

A **primitive** is one of: string, number, bigint, boolean, symbol, `undefined`, or `null`. Primitives are **immutable** - no operation changes a primitive value in place. Calling `"hi".toUpperCase()` does not modify the string `"hi"`; it produces a brand new string, `"HI"`, and leaves the original untouched.

Because primitives have no identity beyond their content, two primitives with the same content are simply the same value:

```js
"hi" === "hi"; // true
5 === 5; // true
```

## Objects are mutable and compared by identity

An **object** (including arrays and functions) is a mutable collection of properties, and every object has its own **identity** separate from its contents. Two objects can hold exactly the same data and still not be equal, because comparing objects checks whether both sides refer to the _same_ object in memory, not whether their contents match:

```js
({ a: 1 }) === { a: 1 }; // false: two different objects, same shape
const point = { a: 1 };
point === point; // true: same object
```

This distinction - compared by content versus compared by identity - resurfaces constantly: in equality checks, in memoization, and in how React-style frameworks detect changes. Keeping "primitive" and "object" straight now makes all of that click later.

## undefined: the language's own placeholder

**`undefined`** is the value JavaScript produces automatically when nothing else has supplied one. It shows up whenever code asks for a value that was never given:

```js
let score;
console.log(score); // undefined: declared, never assigned

const obj = {};
console.log(obj.name); // undefined: property does not exist

function noop() {}
console.log(noop()); // undefined: no explicit return value
```

You rarely assign `undefined` yourself; it is the default the language falls back to.

## null: an explicit "no value"

**`null`** is different in one crucial way: it is a value someone assigns _on purpose_. Where `undefined` means "nothing was supplied," `null` means "a value was considered, and there deliberately isn't one" - for example, `currentUser.manager = null` to record that this employee has no manager, or `selectedItem = null` to say nothing is currently selected.

## null vs. undefined in practice

Both represent "no value," but with different intent: `undefined` usually means a value was never supplied or produced, while `null` usually means a value was deliberately recorded as absent. A well-designed API tends to use `undefined` for "this field was never set" and `null` for "this field was explicitly cleared" - though nothing in the language enforces that convention, so you'll also see codebases that use only one of the two.

Both are treated as "missing" by the operators built for this exact situation: `??` (nullish coalescing) and `?.` (optional chaining) treat `null` and `undefined` the same way, regardless of which one shows up.

## The typeof null quirk

One long-standing trap: `typeof null` reports `"object"`, even though `null` is a primitive, not an object.

```js
typeof undefined; // "undefined"
typeof null; // "object" - a historical bug, kept for compatibility
```

This dates back to JavaScript's very first implementation and has never been fixed, because too much existing code would break if it changed. It means `typeof` is _not_ a reliable way to check for `null`. The reliable check is a direct comparison:

```js
function isNothing(value) {
  return value === null || value === undefined;
}
```

## Common mistakes

- **Using `typeof x === "object"` to detect `null`.** This also matches `null` itself, silently mixing it in with real objects. Compare with `=== null` directly.
- **Assuming `null` and `undefined` are interchangeable.** They both pass loose checks like `value == null`, but treating them identically everywhere can hide bugs where a caller forgot to supply an argument (`undefined`) versus intentionally clearing a field (`null`).
- **Expecting string methods like `toUpperCase()` to mutate the original string.** Primitives can't be mutated; the method always returns a new value.

## Key points

- A value is any piece of data JavaScript works with: numbers, strings, objects, functions, `null`, and `undefined` are all values.
- Primitives (strings, numbers, bigints, booleans, symbols, `undefined`, `null`) are immutable and compared by content.
- Objects are mutable, have identity, and are compared by reference - two separately created objects with identical contents are still not equal.
- `undefined` is what the language produces automatically for a variable, property, or return value that has no assigned value.
- `null` is an explicit value assigned deliberately to represent an intentional absence.
- `typeof null` reports `"object"`, a historical quirk; use `value === null` to test for null reliably.

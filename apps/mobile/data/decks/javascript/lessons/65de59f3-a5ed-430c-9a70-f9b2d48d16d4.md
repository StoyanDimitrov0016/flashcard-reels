# Cancellation and backpressure

Asynchronous operations don't always finish in the order they started, and nothing stops your code from starting a new one before an old one is done - that mismatch is where race conditions live. This lesson covers naming that problem precisely, the tool that lets you cancel obsolete work, and a related idea from streaming data: what happens when producing data is faster than consuming it.

## Race conditions

A **race condition** in asynchronous code occurs when the **visible result depends on which of several operations finishes last (or first)**, and the program hasn't defined how to handle a "stale" outcome that shows up after a more current one already has. Nothing is inherently broken about starting two asynchronous operations - the bug is in not deciding what should happen if they don't finish in the order they started.

## Stale responses overwriting newer state

The most common real-world version: a user searches for `"a"`, then quickly changes the search to `"b"`. If the request for `"a"` happens to take longer and resolves _after_ the request for `"b"`, and both requests blindly write their result into the same state, the **stale** `"a"` result can overwrite the **correct**, newer `"b"` result:

```js
let latestRequestId = 0;

async function search(query) {
  const requestId = ++latestRequestId;
  const result = await fetchResults(query);
  if (requestId !== latestRequestId) {
    return; // a newer search started while this one was in flight - discard it
  }
  applyResults(result);
}
```

Tracking a request's identity and comparing it against the _latest_ identity when the response arrives is one fix: **ignore results that are no longer current**. The alternative is to actively **abort** obsolete work instead of just ignoring its result.

## AbortController

**`AbortController`** provides an **`AbortSignal`** that asynchronous APIs can observe, so a caller can request that in-flight work be cancelled. You create a controller, pass its `signal` to whatever supports cancellation, and call `controller.abort()` when the work is no longer wanted:

```js
const controller = new AbortController();
const { signal } = controller;

function slowOperation(signal) {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => resolve("done"), 1000);
    signal.addEventListener("abort", () => {
      clearTimeout(timer);
      reject(new Error(`aborted: ${signal.reason}`));
    });
  });
}

slowOperation(signal).catch((e) => console.log(e.message)); // "aborted: user cancelled"
controller.abort("user cancelled");
```

This is a more direct fix for the stale-response problem than tracking IDs: instead of letting the old request finish and then discarding its result, you stop it from doing unnecessary work at all.

## fetch and abort signals

`fetch` is the most common built-in consumer of `AbortSignal`: passing `{ signal }` in its options lets you cancel an in-flight request. If the signal is aborted before the fetch completes, the operation is **canceled** and its Promise **rejects with an abort-related error** - unless the request had already finished, in which case the abort has nothing left to affect.

```js
const controller = new AbortController();
fetch("/api/search?q=b", { signal: controller.signal }).catch((e) => {
  if (e.name === "AbortError") console.log("request was cancelled");
});
// later, if a newer search starts:
controller.abort();
```

## What streams solve

Both fixes above assume a request eventually produces one final value. **Streams** target a different shape of problem: processing data **incrementally**, as chunks arrive, instead of buffering an entire payload before doing anything with it. This reduces peak memory use for large payloads and lets a consumer start acting on early data before the rest has even arrived - useful for large file downloads, video, or any data source that produces more than fits comfortably in memory at once.

## Backpressure

Streaming introduces its own coordination problem: what happens when the **producer is faster than the consumer**? Without any limit, a fast producer could keep pushing chunks into an ever-growing buffer while a slow consumer struggles to keep up, consuming unbounded memory. **Backpressure** is the mechanism that lets a **slower consumer signal (or enforce) that a faster producer should slow down** - so the pace of production matches the pace of consumption, instead of buffering without limit.

## Common mistakes

- **Assuming the last request started is the one that finishes last.** Network timing is not guaranteed to preserve request order; always compare against the _latest_ identity or use cancellation, don't assume ordering.
- **Calling `abort()` and assuming the operation stops instantly and silently.** The aborted operation's Promise still rejects (typically with an `AbortError`); that rejection needs a handler, or it becomes an unhandled rejection.
- **Treating streams as strictly "better" than buffering the whole response.** Streaming adds complexity (including backpressure) that's only worth it when payload size or latency actually calls for incremental processing.

## Key points

- A race condition happens when a visible result depends on which of several async operations completes last or first, with no defined handling for stale outcomes.
- Stale responses can overwrite newer state if a slower, earlier request finishes after a faster, later one; track request identity or abort obsolete work.
- `AbortController` provides an `AbortSignal` that async APIs can observe, letting callers request cancellation.
- An aborted `fetch` cancels the operation and rejects its Promise with an abort-related error, unless the request had already completed.
- Streams process data incrementally instead of buffering a full payload, reducing peak memory use and allowing earlier consumption.
- Backpressure lets a slower consumer signal or enforce that a faster producer slow down, preventing unbounded buffering.

# The event loop

JavaScript runs on a single thread, yet a program can juggle timers, network responses, and user input all without explicit threading. The event loop is the coordination model that makes this possible - and understanding it explains why `setTimeout(fn, 0)` doesn't run "immediately," why Promise callbacks always jump the queue ahead of timers, and why one runaway piece of code can freeze an entire page.

## What the event loop is

The **event loop** is the runtime's coordination model for executing queued work whenever the **call stack is empty**. Timers firing, network responses arriving, and user clicks don't interrupt running JavaScript directly - they queue up a task, and the event loop picks up queued tasks only once there's nothing currently executing. This is how a single-threaded language interleaves your code with host events like timers and I/O, without ever running two pieces of JavaScript at the same literal instant.

## Run-to-completion

A crucial guarantee underlies all of this: **run-to-completion**. Once a JavaScript job starts running, it runs **all the way to the end** before any other queued JavaScript job gets a turn on the same agent (thread). No other callback can interrupt it partway through, no matter how long it takes.

```js
setTimeout(() => console.log("timer callback"), 0);

function longSync() {
  console.log("sync start");
  for (let i = 0; i < 3; i++) console.log("sync step", i);
  console.log("sync end");
}
longSync();
console.log("after longSync call");
// logs: sync start, sync step 0, sync step 1, sync step 2, sync end,
//       after longSync call, timer callback
```

Even though the timer was scheduled first, its callback has to wait until `longSync()` and everything after it finish - run-to-completion means the timer callback can't cut in partway through.

## Microtasks

Not all queued work is equal. **Microtasks** are a special queue that runs **after the current stack finishes, but before the event loop moves on to the next ordinary task**. Promise reactions (`.then`, `.catch`, `.finally`, and resumption after `await`) are all scheduled as microtasks - which is why a `Promise.resolve().then(...)` reliably runs before a `setTimeout(..., 0)`, even though both were scheduled at the same point in the code:

```js
console.log("start");
setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("microtask"));
console.log("end");
// logs: start, end, microtask, timeout
```

The engine fully **drains** the microtask queue - runs every microtask, including any new ones queued while draining - before it lets the next ordinary task (like a timer callback) run.

## Why an endless microtask chain can freeze progress

That draining behavior has a sharp edge: if every microtask schedules another microtask, the queue **never finishes draining**, and the event loop never gets to move on to the next task. Timers, user input handling, and rendering can all be starved indefinitely, because the runtime is still busy honoring its "finish all microtasks first" rule:

```js
// Do not run this - illustrative only:
function loopForever() {
  Promise.resolve().then(loopForever);
}
loopForever();
// setTimeout(() => console.log("never runs"), 0) would wait forever
```

This is a real hazard in recursive `.then()` chains or `await` loops that never actually await anything meaningful - each iteration re-queues a microtask before the loop can ever hand control back to timers or the browser's rendering.

## Why setTimeout(fn, 0) isn't immediate

`setTimeout(fn, 0)` schedules `fn` to run as a **future task**, not synchronously - "0" is a _minimum_ delay, not a promise of instant execution. Before `fn` can run, the current job must finish (run-to-completion), every pending microtask must drain, and (in browsers) the delay is often clamped to a small minimum (commonly around 4ms for deeply nested timers). The result demonstrated above - the microtask logging before the "immediate" timer - is the direct, observable consequence: microtasks always get priority over the next task, no matter how small the requested timer delay is.

## Common mistakes

- **Assuming `setTimeout(fn, 0)` runs before Promise callbacks scheduled around the same time.** Microtasks always drain first; a timer callback is a task, always processed after the microtask queue is empty.
- **Writing a recursive `.then()` or async loop with no real asynchronous gap.** Without something that actually yields to the task queue (like a real `setTimeout` or `await` on genuine I/O), the microtask queue can starve everything else.
- **Expecting run-to-completion to make code "atomic" across `await`.** Run-to-completion only guarantees a single synchronous stretch of a job finishes uninterrupted; an `async` function's execution is split into multiple separate jobs at each `await`, and other code can run in between them.

## Key points

- The event loop executes queued tasks whenever the call stack is free, interleaving JavaScript with host events like timers and I/O.
- Run-to-completion means a job finishes entirely before another queued job starts on the same agent.
- A microtask runs after the current stack finishes and before the next ordinary task; Promise reactions use microtasks.
- An endless chain of self-queuing microtasks can starve timers, input handling, and rendering indefinitely.
- `setTimeout(fn, 0)` schedules a future task with at least the host's minimum delay - it cannot run until the current work and all pending microtasks finish first.

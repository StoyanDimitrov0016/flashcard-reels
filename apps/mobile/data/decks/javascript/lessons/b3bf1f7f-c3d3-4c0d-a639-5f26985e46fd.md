# Errors, immutability, and performance

The last group of ideas is about writing code that others can reason about and that runs well. It covers how errors travel in synchronous and asynchronous code, why consistent timing matters, how immutable updates make change easy to detect, and what JavaScript engines do to make code fast.

## Uncaught exceptions

An **uncaught exception** is an error that is thrown and never handled: it reaches the host without meeting a matching `catch` block, or, for Promises, without a rejection handler. The host reports it, in the console or as an `error` or `unhandledrejection` event in browsers, and the operation that threw fails. In Node.js, an uncaught exception or unhandled rejection terminates the process by default.

## Throwing versus rejecting

Errors move differently depending on whether code is synchronous or asynchronous.

A **synchronous throw** takes effect immediately. It unwinds the call stack, function by function, until it reaches a surrounding `try`/`catch`. If none exists, it becomes uncaught.

A **Promise rejection** is an **asynchronous result**, not a jump through the stack. By the time an async operation fails, the code that started it has usually finished, so there is no `try` around it to catch anything. The rejection instead flows through the Promise chain to the next rejection handler, or to a `try`/`catch` around an `await`.

```js
try {
  Promise.reject(new Error("late"));
} catch (err) {
  // never runs: the rejection is not a synchronous throw,
  // so it goes unhandled
}

async function main() {
  try {
    await Promise.reject(new Error("late"));
  } catch (err) {
    console.log("caught"); // runs: await turns the rejection into a throw
  }
}
```

## Consistent timing

An API that **sometimes calls its callback synchronously and sometimes later** is hard to use correctly. Code placed after the call may run before or after the callback depending on, say, whether a value was cached. Ordering bugs of this kind are intermittent and difficult to reproduce.

The fix is to make timing consistent: always asynchronous, even when the result is already available. **Promises enforce this**. A `then` callback always runs later as a microtask, never during the `then` call itself, even if the Promise is already fulfilled.

```js
const ready = Promise.resolve(42);
ready.then((v) => console.log("value", v));
console.log("after then");
// "after then" prints first, every time
```

## Immutability as a practice

JavaScript objects are mutable, but an application can choose to treat them as if they were not. **Immutability** as a practice means you never change existing values; to update, you create a new value that includes the change.

Two benefits follow. **Previous snapshots stay trustworthy**: any code holding an old value knows it will not change underneath it, which enables undo history and safe sharing. And **identity changes become meaningful**: if the data changed, the reference changed, so change detection is a simple `===`.

## Structural sharing

Copying an entire nested structure on every update would be expensive. **Structural sharing** avoids it: the new version copies only the objects along the path to the change and **reuses every unchanged part** by reference.

```js
const state = {
  user: { name: "Ada" },
  settings: { theme: "dark", fontSize: 14 },
};

const next = {
  ...state,
  settings: { ...state.settings, fontSize: 16 },
};

next.user === state.user; // true: shared, unchanged
next.settings === state.settings; // false: replaced
```

## When shallow equality is enough

A **shallow equality check** compares only the top-level references of two values, not their full contents. It is cheap, and it is correct **as long as updates replace changed nested values instead of mutating them in place**. Under that discipline, any change deep inside produces a new reference at every level above it, including the level being compared. If some code mutates a nested object directly, the reference stays the same and the shallow check misses the change. This is why UI libraries that compare props or state shallowly depend on immutable updates.

## JIT compilation

JavaScript engines do not simply interpret code line by line. They start by running code quickly in a baseline form while collecting information about it. Code that runs often ("hot" code) is handed to a **just-in-time (JIT) compiler**, which generates **optimized machine code at runtime**. The optimizer uses **observed types and patterns** to specialize: if a function has only ever received small integers, it can generate integer arithmetic without type checks.

Those specializations rest on assumptions. If an assumption stops holding, for example a string suddenly arrives where only numbers were seen, the engine must **deoptimize**: it discards or bails out of the optimized code and falls back to a slower, general version to keep behavior correct. It may re-optimize later with the new information.

## Shapes and hidden classes

Objects can gain and lose properties at any time, so property access looks expensive in principle. Engines speed it up with internal **shapes**, also called **hidden classes**. Objects with the same properties added in the same order share a shape, which records where each property is stored. Property access sites can then cache the shape they last saw and read from a **predictable offset** instead of doing a full dynamic lookup every time.

```js
function point(x, y) {
  return { x, y }; // every result shares one shape
}
```

## Measure before micro-optimizing

It is tempting to write code around these internals, but it is risky. **Engine heuristics are undocumented and change** between versions and between engines, so a trick that helps today may do nothing or even hurt tomorrow. And micro-level details usually matter far less than **algorithmic complexity, I/O, and allocation patterns**. Write clear code, **measure** with a profiler to find the real bottleneck, and optimize that.

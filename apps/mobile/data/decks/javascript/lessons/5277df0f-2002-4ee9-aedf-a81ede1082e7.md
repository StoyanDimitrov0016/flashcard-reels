# JIT compilation and optimization

JavaScript is often described as "interpreted," but modern engines like V8 (Chrome, Node.js) and SpiderMonkey (Firefox) don't just interpret your code line by line forever - they watch it run and compile the hot parts into fast machine code on the fly. Knowing roughly how this works explains why the same code can suddenly run slower after a change that looks unrelated, and why chasing engine-specific tricks is usually the wrong place to spend optimization effort.

## What a JIT compiler does

A **JIT (just-in-time) compiler** turns **frequently executed** JavaScript into **optimized machine code at runtime**, rather than compiling everything up front or running everything through a slow interpreter forever. The engine starts by interpreting code (or running a baseline compiler), watches which functions run often ("hot" functions), and then compiles those specifically - using the **types and shapes it has actually observed** so far to generate code specialized for that observed behavior, rather than code that has to handle every possibility JavaScript's dynamic typing theoretically allows.

## Hidden classes and shape optimization

A plain JavaScript object doesn't have to look up each property by name every time - that would be far too slow for hot code. Instead, engines can group objects that have the **same set of properties, added in the same order**, into an internal **hidden class** (also called a "shape" or "map," depending on the engine). Objects sharing a hidden class can have their properties accessed through **predictable, precomputed offsets or inline caches**, rather than through a fully dynamic, string-keyed lookup on every single access.

```js
function Point(x, y) {
  this.x = x;
  this.y = y;
}
const a = new Point(1, 2);
const b = new Point(3, 4);
// a and b likely share a hidden class: same properties, same order, same constructor
```

This is one reason consistently constructing similar objects (same properties, same order) tends to perform better than objects whose shape varies unpredictably from one instance to the next - varying shapes mean the engine can't reuse the same specialized access path.

## Deoptimization

Optimized code generated by the JIT is built on **assumptions** about the types and shapes it has seen: "this function's argument is always a number," "this object always has this hidden class." If code later runs in a way that **breaks one of those assumptions** - a function that always received numbers suddenly receives a string, an object gains a property in an order the engine didn't expect - the engine may have to **discard the specialized code** and fall back to a slower, more general version, a process called **deoptimization**. This exists precisely to preserve correctness: the engine would rather give up its speed optimization than produce a wrong result under an assumption that no longer holds.

## Why relying on micro-optimizations is risky

It's tempting to write code around specific, folk-knowledge JIT behaviors - a particular loop shape, a particular property order, avoiding some construct because "it deoptimizes." This is risky for a simple reason: **engine heuristics change** between versions, between browsers, and even between different JIT tiers within the same engine, so a trick that helped on one version or engine can do nothing (or even hurt) on another. More importantly, these micro-optimizations usually matter far less than the fundamentals that are true everywhere: **algorithmic complexity** (an O(n²) approach will eventually lose to an O(n log n) one on any engine), **I/O** (a network request dwarfs almost any in-process optimization), and **allocation patterns** (creating large numbers of short-lived objects pressures garbage collection regardless of JIT behavior). The reliable approach is to **measure** where time actually goes in your specific program, and optimize the bottleneck you found - not to code defensively against undocumented internals you can't verify and that may not even apply to the engine your users run.

## Common mistakes

- **Assuming a specific micro-optimization observed on one engine applies universally.** JIT heuristics are implementation details, not part of the language specification, and can change or differ across engines and versions.
- **Optimizing code that isn't actually a bottleneck.** Without profiling, effort often goes into a function that contributes negligibly to overall time, while the real cost - network calls, algorithmic complexity, excessive allocation - goes unaddressed.
- **Varying an object's shape unpredictably (adding properties in different orders, or adding some properties only conditionally) and being surprised property access is slower than expected.** Consistent object shapes give the engine more opportunity to specialize access.

## Key points

- A JIT compiler turns frequently executed JavaScript into optimized machine code at runtime, using observed types and execution patterns to specialize the generated code.
- Engines can group objects with the same property layout into internal hidden classes (shapes), enabling faster property access than fully dynamic lookup.
- If runtime assumptions behind optimized code stop holding, the engine can deoptimize - discarding or falling back from that specialization to preserve correct behavior.
- Engine-specific micro-optimizations are risky to rely on because heuristics change; algorithmic complexity, I/O, and allocation patterns usually matter more, so it's better to measure and optimize actual bottlenecks.

# Collections and garbage collection

Plain objects and arrays cover a lot of ground, but two problems keep coming up that they handle awkwardly: keeping a list of unique values, and using something other than a string as a lookup key. `Set` and `Map` exist to solve exactly those problems - and `WeakMap` exists because sometimes a collection needs to avoid interfering with the runtime's memory management. Understanding that connection to garbage collection is what makes weak collections make sense.

## Set

A **`Set`** stores a collection of **unique** values and gives you direct membership operations (`has`, `add`, `delete`), instead of manually scanning an array with `includes` or filtering out duplicates yourself.

```js
const tags = new Set(["js", "css", "js"]);
console.log(tags.size); // 2 - the duplicate "js" was dropped
console.log(tags.has("css")); // true
tags.add("html");
console.log([...tags]); // ['js', 'css', 'html'] - insertion order preserved
```

## Map

A **`Map`** solves a different problem: plain objects only cleanly support string and symbol keys, and every plain object already comes with inherited properties (like `toString`) that can collide with keys you didn't intend to add. `Map` stores key-value pairs where **keys can be any value** - including objects and functions - preserves **insertion order** for iteration, and has no inherited keys to collide with.

```js
const scores = new Map();
const player = { name: "Ada" };
scores.set(player, 99); // an object as a key - not possible with a plain object
scores.set("guest", 0);

console.log(scores.get(player)); // 99
console.log(scores.size); // 2
for (const [key, value] of scores) {
  console.log(typeof key, value); // "object" 99, then "string" 0
}
```

## WeakMap

A regular `Map` holding an object as a key keeps that object **reachable** for as long as the `Map` exists - even if nothing else in the program still references it, the `Map` entry alone keeps it alive. Sometimes that's exactly the wrong behavior: you want to attach extra data to an object (a cache, some metadata) _without_ that attachment being the reason the object never gets cleaned up.

**`WeakMap`** solves this: it associates data with **object keys** without preventing those keys from being **garbage-collected**. Once nothing else references a key object, both the key and its associated value can be reclaimed, even though the `WeakMap` technically still "contains" that entry until then.

```js
const metadata = new WeakMap();
let user = { name: "Ada" };
metadata.set(user, { lastSeen: Date.now() });
console.log(metadata.get(user)); // { lastSeen: ... }
// once nothing else references `user`, this WeakMap entry can be collected too
```

## Why weak collections aren't enumerable

Notice there's no way to list a `WeakMap`'s keys, iterate its entries, or ask its size - unlike `Map` and `Set`, `WeakMap` and `WeakSet` are **intentionally not enumerable**. This isn't an oversight: whether an object is still reachable can change at any moment because of garbage collection, which happens on the engine's own schedule. If you could enumerate a `WeakMap`'s contents, that list would change based on _when the garbage collector happened to run_ - an implementation detail the language deliberately keeps invisible. Hiding the contents keeps garbage collection an internal optimization rather than something a program can observe and depend on.

## Garbage collection

JavaScript manages memory automatically: the runtime periodically identifies objects that are no longer **reachable** from any live root - global variables, the current call stack, and closures still in use - and reclaims the memory those objects occupied. You cannot force collection to happen at a specific moment, and you cannot rely on exactly when it runs; it is scheduled by the engine, not the program.

## What causes memory leaks

Since collection depends entirely on reachability, a **memory leak** in JavaScript almost always means code is **unintentionally keeping a reference** to something it no longer needs, which keeps that object reachable (and therefore never collected) forever. Common sources:

- **Forgotten event listeners** that keep a reference to a DOM element or callback long after it should have been cleaned up.
- **Timers** (`setInterval`) that are never cleared and keep re-running, along with anything they capture.
- **Caches** with no eviction policy, growing without bound over the life of the program.
- **Closures** that retain a large structure just because one small piece of it is still needed.

`WeakMap` and `WeakSet` are a direct tool against this last category: caching data _about_ an object without that cache being the reason the object leaks.

## Common mistakes

- **Reaching for a `Map` keyed by objects when a `WeakMap` was the point.** If the collection itself is meant to just tag objects without extending their lifetime, `Map` will defeat that goal by keeping every key reachable indefinitely.
- **Expecting to iterate or measure the size of a `WeakMap`/`WeakSet`.** They deliberately offer no `size`, no iteration, and no `keys()` - only `get`, `set`, `has`, and `delete` (for `WeakMap`) or `add`, `has`, `delete` (for `WeakSet`).
- **Leaving event listeners or timers attached after the associated element or component is gone.** This is the most common real-world source of leaks; clean them up explicitly when they're no longer needed.

## Key points

- `Set` stores unique values and provides direct membership checks without manually scanning for duplicates.
- `Map` stores key-value pairs with keys of any type, preserves insertion order, and avoids collisions with inherited object properties.
- `WeakMap` associates data with object keys without preventing those keys from being garbage-collected.
- Weak collections are intentionally not enumerable, because exposing their contents would make garbage-collection timing observable.
- Garbage collection reclaims memory for objects no longer reachable from live roots, on a schedule you cannot control or predict exactly.
- Memory leaks come from unintentionally retained references - forgotten listeners, uncleared timers, unbounded caches, or closures holding onto more than they need.

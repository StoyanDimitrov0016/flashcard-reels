# async/await and error handling

`async`/`await` lets asynchronous code read almost like ordinary, top-to-bottom synchronous code - but it's still built on Promises underneath, and that has real consequences: `await` doesn't freeze the program while it waits, writing several `await`s in a row can be needlessly slow, and errors from asynchronous code behave differently from a plain `throw`. This lesson covers all three, and rounds out with why consistent error-propagation timing matters for any asynchronous API you design.

## What await does

**`await`** pauses execution of the **current `async` function** until the awaited value resolves through ordinary Promise semantics, then resumes the function - in a later microtask - with the fulfillment value, or throws the rejection reason if the awaited Promise rejected.

```js
async function run() {
  console.log("before await");
  await null; // resolves immediately, but resumption is still deferred
  console.log("after await");
}
run();
console.log("after run() call");
// logs: "before await", "after run() call", "after await"
```

Even awaiting an already-resolved value doesn't resume the function synchronously - the resumption is always scheduled as a microtask, which is why `"after run() call"` logs before `"after await"` above.

## Await does not block the thread

Crucially, `await` only suspends the **`async` function it appears in** - it does not block JavaScript's single thread. While one `async` function is paused on an `await`, the runtime is free to run other code: other functions, other event handlers, timers.

```js
async function slowTask() {
  await delay(1000);
  console.log("slowTask resumed");
}
slowTask();
console.log("this logs immediately, not after 1 second");
```

## Sequential await vs. Promise.all

Writing several unrelated `await`s one after another makes them run **sequentially**, even when nothing requires that ordering - each `await` waits for its own operation to finish before the _next line even starts_ its operation:

```js
async function sequential() {
  const a = await delay(50, "a"); // starts, waits 50ms
  const b = await delay(50, "b"); // only starts now, waits another 50ms
} // total: ~100ms
```

If the two operations don't depend on each other, starting them together and awaiting both with `Promise.all` lets them run **concurrently** instead:

```js
async function concurrent() {
  const [a, b] = await Promise.all([delay(50, "a"), delay(50, "b")]); // both start immediately
} // total: ~50ms
```

The difference isn't about `await` being slow - it's that sequential `await`s don't _start_ the second operation until the first has already finished, while `Promise.all` starts every operation up front and waits for all of them together.

## Synchronous throw vs. Promise rejection

A synchronous `throw` **immediately unwinds the call stack**, moving up through enclosing `try`/`catch` blocks right away, in the same turn of execution. A **Promise rejection** is fundamentally different: it's an asynchronous result that propagates through `.then()`/`.catch()` chaining (or through `await` inside an `async` function), not through the call stack, and not necessarily in the same turn.

```js
function throwsSync() {
  throw new Error("sync");
}
try {
  throwsSync();
} catch (e) {
  console.log("caught sync:", e.message); // runs immediately
}

Promise.reject(new Error("async")).catch((e) => console.log("caught async:", e.message));
console.log("this logs first - rejection handling is deferred");
```

Inside an `async` function, `await`ing a rejected Promise converts that rejection back into an ordinary `throw` you can catch with `try`/`catch` - which is part of what makes `async`/`await` feel synchronous, even though the underlying propagation mechanism is still Promise-based.

## Uncaught exceptions and consistent timing

An **uncaught exception** is an error that reaches the host without being caught by any matching `try`/`catch` or rejection handler - typically aborting the current operation and getting reported (a crash, a logged stack trace, or an "unhandled rejection" warning, depending on the environment).

This is exactly why **asynchronous APIs benefit from consistent timing behavior**. Imagine a function that sometimes calls its callback synchronously (if a result is cached) and sometimes asynchronously (if it has to fetch): callers can no longer reason reliably about ordering, because code right after the call might run either before or after the callback, depending on circumstances the caller can't see. Promise-based APIs sidestep this entirely by **always** scheduling their reactions asynchronously - even `Promise.resolve(x).then(fn)` defers `fn` to a microtask rather than running it immediately - so calling code can always assume the same ordering, regardless of how the result was produced internally.

## Common mistakes

- **Writing independent `await`s back-to-back out of habit.** This serializes work that could run concurrently; start independent operations together and await them with `Promise.all`.
- **Assuming `await` freezes the whole program.** It only pauses the current `async` function; everything else keeps running.
- **Wrapping an `async` function's `await` calls in a `try`/`catch` and forgetting that a plain (non-async) function returning a rejected Promise won't be caught the same way** - only `await`ing (or `.catch()`ing) a rejection routes it through error handling.
- **Building an API that sometimes resolves synchronously and sometimes asynchronously.** This is the exact inconsistency that makes an API's ordering unpredictable for every caller.

## Key points

- `await` pauses the current async function until the awaited value resolves through Promise semantics, then resumes in a later microtask with the value, or throws the rejection reason.
- `await` does not block the JavaScript thread; only the current async function is suspended.
- Sequential `await` calls run operations one after another; starting operations together and using `Promise.all` lets independent operations run concurrently.
- A synchronous throw unwinds the call stack immediately; a Promise rejection propagates asynchronously through chaining unless handled.
- An uncaught exception reaches the host without being handled by a matching catch or rejection handler.
- Consistent async timing matters because callers can't reliably reason about ordering if a callback sometimes runs synchronously and sometimes later; Promise-based APIs avoid this by always scheduling reactions asynchronously.

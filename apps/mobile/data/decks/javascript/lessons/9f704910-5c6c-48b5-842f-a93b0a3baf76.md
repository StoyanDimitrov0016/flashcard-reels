# Identity, races, and serialization

Real applications cache work, fire overlapping requests, move data through pipelines, and send values across the network. Each of these raises a practical question: is this the same value as before, which result wins, how much data can pile up, and what survives conversion to text? This lesson works through them.

## Memoization

**Memoization** caches a function's results, keyed by its inputs, so that a repeated call with the same inputs returns the stored result instead of recomputing it.

```js
function memoize(fn) {
  const cache = new Map();
  return (n) => {
    if (!cache.has(n)) cache.set(n, fn(n));
    return cache.get(n);
  };
}

const slowSquare = (n) => n * n; // imagine this is expensive
const fastSquare = memoize(slowSquare);
```

It pays off when the computation is **expensive**, the function is **pure** (same inputs, same output, no side effects), and the same inputs recur. It has costs: the cache uses memory and may need limits, and the way inputs are compared must match your data. A `Map` compares object keys by identity, so a new object with the same contents is a cache miss.

## Referential equality and identity

For objects, arrays, and functions, `===` compares **identity**, not contents. This is **referential equality**: two separately created objects are never equal, even when every property matches. A variable copied from another variable, however, refers to the same object.

```js
const a = { x: 1 };
const b = { x: 1 };
const c = a;
a === b; // false: different objects
a === c; // true: same object
```

Application code leans on identity in several ways:

- **Change detection**: if a value's reference is unchanged, you can treat it as unchanged; a new reference signals a replacement.
- **Map and set keys**: object keys are matched by identity.
- **Memoization**: a cache can reuse work only when it receives the same reference again.

That is why creating a fresh object or callback on every render, even with identical contents, can defeat caches and cause needless updates.

## Race conditions

A **race condition** happens when the visible result depends on the order in which asynchronous operations finish, and the program never decided how to handle a result that arrives out of order.

The classic case is a search box. The user types "ca", then "cat". Two requests are sent. If the "ca" response is slow and arrives last, it **overwrites the newer "cat" results** with stale data. Nothing threw an error; the code simply trusted whichever response finished last.

Defenses:

- **Track request identity**: tag each request with an ID or counter, and only apply a response if it belongs to the latest request.
- **Abort obsolete work** with an `AbortController` when a newer request starts.
- **Ignore results that are no longer current**, for example when a component has unmounted or the input has changed.

```js
let latest = 0;
async function search(query) {
  const id = ++latest;
  const results = await fetchResults(query);
  if (id !== latest) return; // a newer search started: drop this one
  render(results);
}
```

## Backpressure and streams

When a producer generates data faster than a consumer can handle it, the difference has to go somewhere. Without limits it piles up in buffers until memory runs out. **Backpressure** is the mechanism by which a slower consumer signals, or enforces, that the faster producer should **slow down**, keeping buffering bounded.

**Streams** process data **incrementally**, one chunk at a time, instead of waiting for an entire payload to be loaded. This lowers **peak memory use**, because only a few chunks are in memory at once, and it lets consumers **start working earlier**, before the last byte arrives. Stream APIs, such as web `ReadableStream` and Node.js streams, build backpressure in: a reader that stops pulling causes the source to pause.

```js
const response = await fetch("/large-file");
for await (const chunk of response.body) {
  process(chunk); // each chunk handled as it arrives
}
```

## Serialization and JSON

**Serialization** converts an in-memory value into a representation that can be stored or transmitted, such as a JSON string, and deserialization turns it back. The **format decides what can be represented**, and anything outside the format is changed or lost.

JSON knows only objects, arrays, strings, finite numbers, booleans, and `null`. `JSON.stringify` therefore loses information from ordinary JavaScript values:

- **Functions, symbols, and `undefined`** property values are omitted.
- **Prototypes** are lost: a class instance comes back as a plain object.
- **Identity** is lost: an object referenced twice becomes two separate copies.
- **Dates** turn into ISO strings through their `toJSON` method and are not turned back into `Date` objects on parse.
- `NaN` and `Infinity` become `null`, `Map` and `Set` become `{}`, and `BigInt` throws.

## Why JSON round-trips are poor clones

`JSON.parse(JSON.stringify(x))` is a popular deep-copy trick, but it is unsafe for general data. It **silently changes or drops** unsupported values, **throws on cyclic references**, loses **prototypes**, and splits **shared references** into duplicates. It is fine for data that is already plain JSON. Otherwise, pick a method suited to the data, such as `structuredClone` or a purpose-built copy function.

```js
const original = { when: new Date(0), note: undefined };
const copy = JSON.parse(JSON.stringify(original));
// copy is { when: "1970-01-01T00:00:00.000Z" }: a string, and note is gone
```

# The event loop and DOM events

JavaScript runs your code on a single thread, yet it handles timers, network responses, and user input without freezing. The event loop is the model that makes this work. This lesson explains how queued work is scheduled, how to cancel async operations, how browser events travel through the page, and how to control handlers that fire too often.

## The event loop

The **event loop** is the coordination model of a JavaScript runtime. The host (a browser or Node.js) handles timers, network I/O, and input outside JavaScript. When one of them has something for your code, it places a job in a queue. Whenever the **call stack is empty**, the loop takes the next job and runs it.

Each job has **run-to-completion** semantics: once a piece of JavaScript starts, it runs until it finishes before any other queued JavaScript job starts on the same thread. A timer callback or click handler can never interrupt your function halfway through. The flip side is that a long-running job blocks everything else, including rendering and input.

## Tasks and microtasks

There are two main kinds of queued work.

- **Tasks** (also called macrotasks) come from timers, I/O, and user events.
- **Microtasks** come mostly from Promise reactions (`then` callbacks and resumed `await`s) and `queueMicrotask`.

After the current task finishes and the stack is empty, the runtime **drains the entire microtask queue** before it moves to the next task. Microtasks queued while draining are run in the same pass.

```js
setTimeout(() => console.log("task"), 0);
Promise.resolve().then(() => console.log("microtask"));
console.log("sync");
// sync, microtask, task
```

That draining rule has a dark side. If every microtask queues another microtask, the queue never empties. The runtime never reaches the next task, so timers, input handling, and rendering are **starved** and the page appears frozen, even though no single piece of code is looping.

## Why setTimeout(fn, 0) is not immediate

`setTimeout(fn, 0)` does not run `fn` right away. It asks the host to queue `fn` as a **future task** once the delay has passed. The delay is a minimum, and hosts apply their own rules; browsers, for example, clamp deeply nested timers to at least about 4 ms. Even after the delay, `fn` waits until the current code finishes, all pending microtasks run, and earlier queued tasks are handled.

## Cancelling with AbortController

Promises have no built-in cancel method. **`AbortController`** fills the gap. A controller owns an **`AbortSignal`**; you pass the signal to an API that supports it, and calling `controller.abort()` requests cancellation.

```js
const controller = new AbortController();

fetch("/api/search?q=js", { signal: controller.signal })
  .then((res) => res.json())
  .catch((err) => {
    if (err.name === "AbortError") return; // cancelled on purpose
    throw err;
  });

controller.abort();
```

When `fetch` sees its signal aborted before the operation completes, it **cancels the request** and its Promise **rejects**, by default with a `DOMException` named `"AbortError"`. If the response has already fully arrived, there is nothing left to cancel. Many other APIs accept signals too, including `addEventListener`, where aborting removes the listener.

## Event propagation

When a DOM event such as a click happens on an element, it does not stay on that element. It travels along the path from the window down to the target and back up, in three phases:

1. **Capturing phase**: the event travels from the outermost ancestors **down toward the target**.
2. **Target phase**: the event reaches the target element itself.
3. **Bubbling phase**: the event travels **back up** through the ancestors.

Listeners run in the bubbling phase by default. Pass `{ capture: true }` to `addEventListener` to run during capturing instead. Most events bubble, though a few, like `focus`, do not.

## Event delegation

Bubbling enables **event delegation**: instead of attaching one listener to every child, attach one listener to a common parent and inspect `event.target` to see which child was involved. It uses less memory and automatically covers children added later.

```js
list.addEventListener("click", (event) => {
  const item = event.target.closest("li");
  if (item) select(item.dataset.id);
});
```

## preventDefault and stopPropagation

These two methods are often confused because they control different things.

**`preventDefault()`** asks the browser **not to perform the default action** of the event, such as following a link or submitting a form. It only works when the event is **cancelable**.

**`stopPropagation()`** stops the event from **continuing along its propagation path**, so listeners on later elements do not see it. It does not prevent the default action: a link whose click is stopped will still navigate unless you also call `preventDefault()`.

## Debouncing and throttling

Some events fire very rapidly: typing, scrolling, resizing. Two techniques keep handlers from running on every single one.

**Debouncing** waits until calls have **stopped** for a chosen interval, then runs once. A burst of triggers collapses into a single later call. It suits search-as-you-type, where only the final input matters.

**Throttling** lets the function run **at most once per interval** while triggers continue. It suits scroll or resize handlers that should keep updating at a controlled rate.

```js
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
```

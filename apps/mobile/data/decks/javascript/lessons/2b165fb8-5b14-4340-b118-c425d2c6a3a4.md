# Cloning and serialization

Copying data safely and converting it into a format you can send over a network or write to disk sound like related problems, and they're often reached for interchangeably - `JSON.parse(JSON.stringify(x))` is a famous shortcut for "just deep clone it." They're not actually the same problem, though, and understanding where each tool's assumptions break down prevents subtle data loss.

## What structuredClone solves

Earlier lessons established that object spread (`{ ...obj }`) only copies one level deep, leaving nested objects shared. **`structuredClone`** goes further: it produces a **deep clone** of many structured data types - including **cyclic object graphs**, where an object refers back to itself - without sharing any of the original's nested object references.

```js
const original = { name: "Ada" };
original.self = original; // a cycle: original refers to itself

const clone = structuredClone(original);
console.log(clone !== original); // true: a genuinely separate object
console.log(clone.self === clone); // true: the cycle is preserved *within* the clone
```

`structuredClone` isn't universal, though: it works for plain objects, arrays, `Map`s, `Set`s, `Date`s, and several other built-in types, but **cannot clone functions** (or a few other non-serializable values):

```js
structuredClone({ fn: () => {} }); // throws - functions cannot be structured-cloned
```

## Serialization

**Serialization** is a different operation: converting an **in-memory value** into a representation suited for **transport or storage**, such as JSON text sent over a network or written to a file. Unlike cloning, which stays inside the running program, serialization crosses a boundary - into a string, a byte stream, or a database row - and the **format you choose determines exactly which types and relationships survive the trip**.

## What JSON serialization loses

JSON is a common serialization format, but it's built around a small set of simple types, so converting an arbitrary JavaScript object through `JSON.stringify` **loses information** that doesn't fit that model:

```js
const data = {
  when: new Date(0),
  handler: undefined,
  greet() {},
  list: [1, undefined, 3],
};
console.log(JSON.stringify(data));
// {"when":"1970-01-01T00:00:00.000Z","list":[1,null,3]}
```

Notice what happened: `handler` and `greet` (an `undefined` value and a function) **disappeared from the object entirely** - JSON has no representation for either, so `JSON.stringify` just omits those keys. Inside the array, though, the `undefined` element became `null` instead of being dropped, because array _positions_ have to be preserved even when a value can't be represented. `Date` objects are converted to ISO **strings** through their own `toJSON` method - round-tripping through `JSON.parse` gives back a plain string, not a `Date` instance. More generally, JSON serialization does not preserve **symbols**, a value's **prototype**, or **object identity** (two properties that pointed at the same object before serializing become two independent copies after parsing).

## Why JSON.parse(JSON.stringify(x)) is an unsafe clone

Because of everything above, `JSON.parse(JSON.stringify(x))` is a tempting one-liner for "deep clone this," but it's **unsafe** as a general-purpose cloning technique:

- It **silently drops or changes** values JSON can't represent (functions, `undefined`, symbols).
- It **fails outright on cycles** - `JSON.stringify` throws a `TypeError` for circular references, where `structuredClone` succeeds.
- It does **not preserve prototypes**, so cloning a class instance this way gives back a plain object, not an instance of that class.
- It does **not preserve shared-reference identity** between properties that pointed at the same object.

```js
const shared = { count: 1 };
const original = { a: shared, b: shared };
const cloned = JSON.parse(JSON.stringify(original));
console.log(original.a === original.b); // true: same object
console.log(cloned.a === cloned.b); // false: two independent copies after round-tripping
```

`structuredClone` avoids all four of these problems for the types it supports, which makes it the better default for in-memory deep cloning; reach for JSON serialization when you specifically need a transportable, text-based representation, not merely a copy.

## Common mistakes

- **Reaching for `JSON.parse(JSON.stringify(x))` as a general deep-clone utility.** It quietly breaks on functions, `undefined` values, symbols, cycles, prototypes, and shared references - use `structuredClone` (or a library built for the specific data) instead.
- **Expecting a `Date` to survive a JSON round trip as a `Date`.** It becomes a string; code that consumes the parsed result needs to convert it back explicitly.
- **Assuming `structuredClone` can clone anything.** It cannot clone functions, and a few other values are excluded too; check what your data actually contains before relying on it.

## Key points

- `structuredClone` produces a deep clone of many structured types, including cyclic object graphs, without sharing nested references; it cannot clone functions.
- Serialization converts an in-memory value into a transport or storage representation, and the chosen format determines what survives.
- JSON serialization does not preserve functions, symbols, undefined-valued properties, prototypes, or object identity; `Date` values become strings.
- `JSON.parse(JSON.stringify(x))` is an unsafe deep-clone technique because it drops or changes unsupported values, fails on cycles, and loses prototypes and shared-reference identity.

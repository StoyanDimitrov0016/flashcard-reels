# Arrays, collections, and memory

Arrays are the everyday workhorse of JavaScript, and the built-in `Set`, `Map`, and weak collections cover the jobs arrays and plain objects do poorly. Weak collections lead naturally to garbage collection: how the runtime frees memory, and how programs accidentally keep memory alive.

## map, filter, and reduce

Three array methods cover most data transformations, and none of them change the source array.

**`map`** calls a callback for every element and returns a **new array of the results**. The output has the same length and order as the input.

**`filter`** returns a **new array with only the elements** for which the callback returned a truthy value. Elements are kept as they are, not transformed.

**`reduce`** walks the elements in order while carrying an **accumulator**. Each callback receives the accumulator and the current element and returns the next accumulator. The final accumulator is the result. Pass an initial value as the second argument; without it, `reduce` starts from the first element and throws on an empty array.

```js
const prices = [5, 12, 8, 20];

prices.map((p) => p * 2); // [10, 24, 16, 40]
prices.filter((p) => p > 10); // [12, 20]
prices.reduce((total, p) => total + p, 0); // 45
```

## Mutating while iterating

Changing an array while you loop over it is risky. Removing an element shifts the indexes of everything after it, so an index-based loop can **skip** the next element. Inserting can make the loop **revisit** elements or never finish. Callback methods like `forEach` and `map` read the length once at the start and look up each index when they reach it, so they may see partially updated data.

The safe patterns are to build a new array (for example with `filter`), iterate over a copy, or loop backward when removing by index.

## slice versus splice

The names differ by one letter and the behavior differs completely.

- **`slice(start, end)`** returns a **shallow copy** of a range and leaves the source untouched.
- **`splice(start, deleteCount, ...items)`** **changes the source array** in place by removing, replacing, or inserting elements, and returns the removed elements.

```js
const letters = ["a", "b", "c", "d"];
letters.slice(1, 3); // ["b", "c"]; letters unchanged
letters.splice(1, 2, "X"); // ["b", "c"]; letters is now ["a", "X", "d"]
```

Newer non-mutating alternatives exist too: `toSpliced`, `toSorted`, and `toReversed` return changed copies.

## Array.from

**`Array.from`** creates a real array from an **iterable** (such as a `Set` or a string) or an **array-like** value (anything with a `length` and numeric keys, such as `arguments` or a DOM `NodeList`). An optional second argument maps each item during creation.

```js
Array.from("abc"); // ["a", "b", "c"]
Array.from({ length: 3 }, (_, i) => i * i); // [0, 1, 4]
```

## Set and Map

A **`Set`** holds **unique values**. Adding a value that is already present does nothing, and `has` answers membership directly, without scanning an array. Removing duplicates becomes a one-liner: `[...new Set(items)]`.

A **`Map`** stores key-value pairs, and it fixes several weaknesses of using plain objects as dictionaries:

- **Keys can be any value**, including objects and functions. Object keys are always strings or symbols.
- **Iteration follows insertion order** for all keys.
- **No inherited keys**: a fresh map is empty, while a plain object inherits names like `toString` and `constructor` that can collide with your data.
- `size` gives the count directly.

```js
const visits = new Map();
const page = { url: "/home" };
visits.set(page, 3); // an object as a key
visits.get(page); // 3
```

## WeakMap and weak collections

A **`WeakMap`** also maps keys to values, but its keys must be objects (or non-registered symbols), and it holds them **weakly**: an entry does not keep its key alive. When nothing else references the key object, it can be garbage-collected and its entry disappears. This makes a `WeakMap` ideal for attaching extra data to objects you do not own, such as caching results per DOM node, without causing leaks. `WeakSet` does the same for membership.

Weak collections are deliberately **not enumerable**: there is no `size`, no `keys()`, and no iteration. The reason is that whether an object is still reachable can change at any moment as the collector runs. If you could list the contents, the output would depend on garbage-collection timing, making that timing observable and program behavior unstable. You can only look up entries with a key you already hold.

## Garbage collection

JavaScript manages memory automatically through **garbage collection**. The runtime starts from **roots**, such as global variables and the variables of functions currently running, and follows references outward. Any object that cannot be reached from a root is garbage, and its memory can be reclaimed.

The important consequence is that **reachability**, not usefulness, decides what stays in memory. Collection also happens whenever the engine chooses, so code must never depend on the exact moment an object is freed.

## Memory leaks

A **memory leak** in JavaScript happens when code keeps references to objects it no longer needs, so they stay reachable and are never collected. Common causes:

- **Event listeners** that are never removed, keeping their handlers and everything those handlers reference alive.
- **Timers** from `setInterval` that are never cleared.
- **Caches** or maps that grow forever without eviction.
- **Closures** that capture large structures and are stored somewhere long-lived.

```js
const cache = new Map();
function remember(key, bigValue) {
  cache.set(key, bigValue); // grows forever unless entries are removed
}
```

The fixes follow the causes: remove listeners and clear timers when done, bound caches or use weak collections, and avoid capturing more than a closure needs.

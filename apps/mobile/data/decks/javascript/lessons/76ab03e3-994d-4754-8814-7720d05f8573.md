# Modules

Before ES modules, splitting a program across files meant loading every script into one shared global scope and hoping nothing collided - a real problem once an application grew past a handful of files. Modules give each file its own scope and an explicit, checkable list of what it shares and what it needs, which is also what makes modern bundlers and tree-shaking possible.

## What a module is

A **module** is a file with its **own scope**: top-level variables in a module are private to that file by default. A module makes some of its bindings available to other files with `export`, and consumes bindings from other files with `import`.

```js
// counter.mjs
export let count = 0;
export function increment() {
  count++;
}
```

```js
// main.mjs
import { count, increment } from "./counter.mjs";
console.log(count); // 0
```

Without `export`, `count` and `increment` would simply not exist outside `counter.mjs` - there's no accidental leakage into a shared global scope the way classic `<script>` tags behaved.

## Why static import matters

**Static `import`** - the `import { x } from "./module.js"` form written at the top level of a file - names its dependencies with a literal string, in a fixed location, before any code runs. Because every module's dependencies are knowable **without executing anything**, tooling can build an exact dependency graph ahead of time. That's what enables reliable **bundling** (combining modules into fewer files) and **tree-shaking** (dropping exports nothing actually imports) - both rely on statically knowing the full import graph in advance.

## Live bindings

An ES module import is not a one-time copy of a value - it's a **live binding** to the exporting module's variable. If the exporting module later changes that variable, every importer sees the new value automatically, because they're reading the same binding, not a snapshot taken at import time.

```js
import { count, increment } from "./counter.mjs";
console.log(count); // 0
increment();
console.log(count); // 1 - the imported binding reflects the update in counter.mjs
```

The one restriction: an importer can **read** a live binding but cannot **reassign** it directly - `count = 5` inside `main.mjs` would be a syntax error. Only the exporting module can change its own exported bindings; everyone else just observes the current value.

## Dynamic import()

Static `import` is fixed at the top of a file and always runs, whether or not the module ends up being needed. **Dynamic `import()`** is a function call, usable anywhere in your code, that **loads a module asynchronously** and returns a **Promise** for the module's namespace object:

```js
async function loadFeature() {
  const mod = await import("./counter.mjs");
  console.log(mod.count); // 0 - same module, loaded on demand
}
```

This lets an application defer loading a module until it's actually needed - a common technique for code-splitting a large app so rarely used features don't add to the initial page load.

## Common mistakes

- **Trying to reassign an imported binding.** `import { count } from "./x.js"; count = 1;` is a syntax error - only the module that exports a binding may reassign it.
- **Expecting an import to be a frozen snapshot.** Because bindings are live, a value read early in a module's lifetime can change later if the exporting module updates it; don't cache an imported value if you actually need the current one.
- **Reaching for dynamic `import()` everywhere "just in case."** It adds an asynchronous step and a separate network/bundle chunk; static import is simpler and lets tooling optimize better when a dependency is always needed.

## Key points

- A module is a file with its own scope that explicitly exports and imports bindings, rather than sharing one global scope.
- Static `import` makes dependencies known before execution, which enables reliable bundling and tree-shaking.
- An imported binding is live: it reflects updates to the exported variable, but importers cannot reassign it directly.
- Dynamic `import()` loads a module asynchronously and returns a Promise for its module namespace object, letting code defer loading until needed.

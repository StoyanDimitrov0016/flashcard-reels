# Equality and numeric precision

"Are these two things equal?" sounds like a simple question, but JavaScript has two different equality operators that can disagree with each other, a special numeric value that is never equal to itself, and a number type that quietly loses precision on ordinary arithmetic. Knowing exactly which comparisons you can trust - and which numbers need special handling - prevents an entire class of hard-to-reproduce bugs.

## Strict equality

**`===`** (strict equality) compares two values **without converting either one to a different type**. If the operands have different types, they're simply not equal - no exceptions. For objects (including arrays and functions), `===` checks identity: two objects are equal only when both sides refer to the exact same object.

```js
1 === 1; // true
1 === "1"; // false: different types, no coercion
({}) === {}; // false: different objects
```

`===` is the equality operator you should reach for by default - its behavior never depends on a coercion table you have to remember.

## Why == can surprise you

**`==`** (loose equality) is allowed to **coerce** its operands to matching types before comparing them. This produces some results that feel intuitive (`"5" == 5` is `true`) and some that don't:

```js
0 == false; // true: false coerces to 0
"" == false; // true: both coerce to 0
null == undefined; // true: a special-cased pair
0 == "0"; // true
false == "0"; // true
```

The coercion rules that make these true are a fixed part of the specification, not randomness - but they're numerous enough that relying on `==` between mixed types means relying on memorized edge cases. That's why `===` is preferred almost everywhere; `== null` (matching both `null` and `undefined` at once) is one of the few loose-equality idioms used deliberately.

## NaN is never equal to itself

`NaN` ("Not a Number") is the numeric result of invalid operations like `0 / 0` or `Number("abc")`. Per the IEEE-754 floating-point standard that JavaScript numbers follow, `NaN` is defined as **unequal to every value, including itself**:

```js
NaN === NaN; // false
[NaN].includes(NaN); // true - includes uses a different check than ===
```

Because `NaN === NaN` is false, you cannot detect `NaN` with an equality check at all. That's what `Number.isNaN` is for.

## Number.isNaN vs. the global isNaN

The global `isNaN()` function **first coerces its argument to a number**, then checks if the result is `NaN` - so it reports `true` for values that aren't the numeric `NaN` at all, just things that fail to convert to a number:

```js
isNaN(undefined); // true: undefined coerces to NaN, so this "matches"
Number.isNaN(undefined); // false: undefined is not the value NaN

isNaN(NaN); // true
Number.isNaN(NaN); // true
```

`Number.isNaN` checks whether a value **is actually** the numeric `NaN`, with no coercion first. It is almost always the one you want.

## Floating-point precision

Most JavaScript numbers are stored as binary IEEE-754 double-precision floats. Binary floating point cannot represent every decimal fraction exactly, the same way `1/3` has no exact finite decimal representation. This shows up in ordinary arithmetic:

```js
0.1 + 0.2; // 0.30000000000000004, not exactly 0.3
0.1 + 0.2 === 0.3; // false
```

This isn't a JavaScript bug - it's how binary floating point works in essentially every mainstream language. The practical fix is to avoid comparing floats for exact equality; instead compare within a small tolerance (`Math.abs(a - b) < Number.EPSILON`) or work in integer units (cents instead of dollars) when exactness matters.

## BigInt for exact large integers

`Number` can only represent integers exactly up to `Number.MAX_SAFE_INTEGER` (2^53 − 1). Beyond that, or whenever you need exact arbitrary-size integer arithmetic (cryptography, large IDs, precise counters), use **`BigInt`**, written with an `n` suffix:

```js
9007199254740993n; // exact, beyond Number's safe integer range
10n + 5n; // 15n
```

`BigInt` cannot be mixed directly with `Number` in arithmetic - you must convert explicitly:

```js
10n + 5; // TypeError: Cannot mix BigInt and other types, use explicit conversions
10n + BigInt(5); // 15n
```

## Common mistakes

- **Using `==` out of habit.** It works fine for many common cases but forces every reader to recall coercion rules; default to `===` and reserve `==` for the deliberate `== null` idiom.
- **Testing for `NaN` with `=== NaN` or `== NaN`.** Both are always `false`; use `Number.isNaN(value)`.
- **Comparing floating-point sums for exact equality.** `0.1 + 0.2 === 0.3` is `false`; compare with a tolerance instead.
- **Mixing `BigInt` and `Number` in the same expression.** This throws a `TypeError`; convert one side explicitly first.

## Key points

- `===` compares without coercion; objects are equal only by reference.
- `==` may coerce operands to matching types first, producing results like `0 == false` and `"" == false` that `===` would reject.
- `NaN === NaN` is `false` because IEEE-754 defines `NaN` as unequal to everything, including itself.
- `Number.isNaN` checks for the actual `NaN` value with no coercion; the global `isNaN` coerces its argument first and can report `true` for non-numeric values.
- Binary floating point cannot represent every decimal fraction exactly, so sums like `0.1 + 0.2` can differ slightly from the expected decimal value.
- `BigInt` provides exact arbitrary-size integer arithmetic beyond `Number`'s safe integer range, but cannot be mixed directly with `Number` values.

# DOM events

A click on a button doesn't just notify that button - it travels through the entire DOM tree on the way in and back out again, which is what makes it possible to handle many elements' events with a single listener. This lesson covers how an event travels, how to control what it does by default, and two techniques for taming events that fire far more often than your code actually needs to react.

## Event capturing

When an event is dispatched, it doesn't jump straight to its target. **Capturing** is the first phase: the event travels from the outermost ancestor (typically the `window` or `document`) **downward** through each ancestor element, toward the target, before the target phase and bubbling begin. Listeners registered with `{ capture: true }` (the third argument to `addEventListener`) run during this phase, seeing the event before the target element does.

## Event bubbling

After the event reaches its target and fires there, most DOM events **bubble**: they propagate back **upward**, from the target through each ancestor in turn, all the way to the root. An ordinary listener added to an ancestor (without `capture: true`) fires during this phase, letting an ancestor observe an event that technically happened on one of its descendants.

```js
document.getElementById("toolbar").addEventListener("click", (event) => {
  console.log("bubbled up from:", event.target.tagName);
});
```

If a button inside `#toolbar` is clicked, that listener fires during bubbling, with `event.target` pointing at the button that was actually clicked - not at `#toolbar` itself.

## Event delegation

**Event delegation** takes advantage of bubbling directly: instead of attaching a listener to every individual descendant element, you attach **one listener to a shared parent**, and let events from any child bubble up to it. Inside the listener, `event.target` tells you which specific descendant the event actually started on.

```js
document.getElementById("list").addEventListener("click", (event) => {
  if (event.target.matches("li")) {
    console.log("clicked item:", event.target.textContent);
  }
});
```

This one listener handles clicks on every `<li>` inside `#list`, including ones added to the DOM later - there's nothing to re-attach when the list changes, because the listener lives on the parent, not on each item.

## preventDefault

Many events have a built-in **default action**: clicking a link navigates, submitting a form reloads the page, pressing space in a checkbox toggles it. **`event.preventDefault()`** tells the browser **not to perform that default action**, but only for events marked **cancelable** - calling it on a non-cancelable event has no effect.

```js
form.addEventListener("submit", (event) => {
  event.preventDefault(); // stop the normal full-page form submission
  submitViaFetch(form);
});
```

## stopPropagation

**`event.stopPropagation()`** is a different tool with a different job: it stops the event from continuing through the **rest of its propagation path** - so ancestor (or descendant, during capturing) listeners further along that path never see it. Crucially, `stopPropagation()` does **not** cancel the event's default action; that's `preventDefault()`'s job. The two are independent and often used together, but calling one does not imply the other.

## Debouncing

Some events - typing, scrolling, resizing - can fire dozens of times per second, far more often than a handler actually needs to respond. **Debouncing** delays running a function until calls have **stopped** for a chosen interval, collapsing a burst of rapid triggers into a single execution after things settle down.

```js
function debounce(fn, delayMs) {
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delayMs);
  };
}

const handleSearchInput = debounce((event) => runSearch(event.target.value), 300);
input.addEventListener("input", handleSearchInput);
```

Every keystroke resets the timer; `runSearch` only actually runs once typing pauses for 300ms - ideal for search-as-you-type, where firing a request on every single keystroke would be wasteful.

## Throttling

**Throttling** takes the opposite approach: instead of waiting for triggers to stop, it lets the function run at a **controlled maximum rate** throughout a burst of triggers, rather than collapsing them into one delayed call.

```js
function throttle(fn, intervalMs) {
  let lastCall = 0;
  return (...args) => {
    const now = Date.now();
    if (now - lastCall >= intervalMs) {
      lastCall = now;
      fn(...args);
    }
  };
}

window.addEventListener("scroll", throttle(updateScrollIndicator, 100));
```

`updateScrollIndicator` runs at most once every 100ms while scrolling continues, giving steady, bounded-frequency updates rather than one single delayed update at the very end.

## Common mistakes

- **Calling `stopPropagation()` expecting it to also prevent the default action.** They're unrelated; use `preventDefault()` for the default action and `stopPropagation()` for halting further propagation.
- **Attaching a listener to every list item instead of delegating to a parent.** This misses items added later and does more setup work than a single delegated listener on the parent.
- **Using debounce when throttle was needed, or vice versa.** Debounce is for "wait until things calm down" (search input); throttle is for "respond steadily throughout" (scroll position updates). Picking the wrong one either delays feedback too long or fires far more often than needed.

## Key points

- Capturing is the phase where an event travels from outer ancestors down toward the target, before the target and bubbling phases.
- Bubbling is the phase where an event propagates upward from its target through ancestor elements after reaching the target.
- Event delegation attaches one listener to a parent and relies on bubbling to handle events from any descendant, including ones added later.
- `preventDefault()` stops a cancelable event's default browser action; `stopPropagation()` stops the event from continuing through its remaining propagation path - the two are independent.
- Debouncing delays a function until triggers have stopped for an interval, collapsing rapid calls into one.
- Throttling limits how often a function runs during repeated triggers, allowing execution at a controlled maximum rate throughout.

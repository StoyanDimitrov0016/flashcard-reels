# Equality and numbers

JavaScript converts values between types more often than many languages, and its numbers follow a binary floating-point standard. Knowing when conversion happens, which values count as false, and how numbers behave at the edges prevents a whole family of subtle bugs.

## Strict and loose equality

**Strict equality**, `===`, compares two values without converting either one. Values of different types are never strictly equal. For objects, `===` checks identity: it is true only when both sides reference the same object.

**Loose equality**, `==`, may first apply **type coercion**, converting one or both operands before comparing. The rules are intricate, and they make values like `0`, `false`, and the empty string compare equal in combinations that are hard to predict:

```js
0 == false; // true
"" == 0; // true
"" == false; // true
"0" == false; // true
0 === false; // false
```

Most codebases use `===` everywhere. A common deliberate exception is `value == null`, which is true for both `null` and `undefined`.

## Truthiness

Conditions such as `if`, `while`, and the logical operators interpret any value as a boolean. This is **truthiness**. The list of **falsy** values is short and worth memorizing:

- `false`
- `0`, `-0`, and `0n`
- `NaN`
- `""` (the empty string)
- `null` and `undefined`

Everything else is truthy, including `"0"`, `"false"`, `[]`, and `{}`.

## Short-circuit evaluation

The logical operators `&&`, `||`, and `??` stop as soon as the result is known. This is **short-circuit evaluation**, and it means the right operand may never be evaluated at all.

- `a && b` evaluates `b` only if `a` is truthy.
- `a || b` evaluates `b` only if `a` is falsy.
- `a ?? b` evaluates `b` only if `a` is `null` or `undefined`.

Because the skipped side is not run, these operators double as compact conditionals: `user && save(user)` calls `save` only when there is a user.

## Nullish coalescing and optional chaining

The **nullish coalescing operator** `??` supplies a fallback only when the left side is `null` or `undefined`. It differs from `||`, which falls back on any falsy value and so throws away legitimate values like `0` and `""`.

```js
const settings = { volume: 0, title: "" };
settings.volume || 50; // 50: the valid 0 is lost
settings.volume ?? 50; // 0: kept
settings.title ?? "Untitled"; // "": kept
```

**Optional chaining** `?.` guards an access or call. If the value on its left is `null` or `undefined`, the whole expression stops and produces `undefined` instead of throwing a `TypeError`.

```js
const user = null;
user?.profile.name; // undefined, no error
user?.greet(); // undefined, greet is not called
```

The two combine naturally: `user?.name ?? "Guest"`.

## NaN

`NaN` ("not a number") is the number value produced by invalid numeric operations, such as `0 / 0` or `Number("abc")`. The IEEE-754 floating-point standard defines NaN as **unequal to every value, including itself**, so `NaN === NaN` is `false`.

To test for NaN, use **`Number.isNaN`**. The older global `isNaN` first coerces its argument to a number, so it returns `true` for many values that are not NaN at all:

```js
isNaN("hello"); // true: "hello" coerces to NaN
Number.isNaN("hello"); // false: it is a string, not NaN
Number.isNaN(NaN); // true
```

## Floating-point precision

JavaScript's `Number` type is a 64-bit **binary IEEE-754 floating-point** value. Binary fractions cannot represent most decimal fractions exactly, just as decimal cannot write one third exactly. Small representation errors appear in arithmetic:

```js
0.1 + 0.2; // 0.30000000000000004
0.1 + 0.2 === 0.3; // false
```

This is **floating-point precision error**. Compare with a small tolerance, round for display, or represent money as whole cents.

## BigInt

A `Number` stores integers exactly only within the **safe integer range**, up to `Number.MAX_SAFE_INTEGER` (2^53 - 1). Beyond it, neighboring integers can no longer be told apart.

**`BigInt`** represents integers of arbitrary size exactly. Write one with an `n` suffix, such as `10n`, or convert with `BigInt(value)`. Use it for very large identifiers, exact large-integer math, or any case where precision beyond the safe range matters.

BigInt and Number cannot be mixed in arithmetic. `1n + 1` throws a `TypeError`; convert one side explicitly first.

```js
2n ** 64n; // 18446744073709551616n
Number.MAX_SAFE_INTEGER + 2; // 9007199254740992 (wrong by one)
```

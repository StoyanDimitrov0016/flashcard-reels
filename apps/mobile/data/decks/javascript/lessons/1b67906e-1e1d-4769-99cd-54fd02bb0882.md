# Identity, memoization, and immutability

`state1 === state2` for two objects doesn't ask "do these hold the same data?" - it asks "are these literally the same object?" That single fact underlies three practical techniques: caching expensive work by input, detecting exactly what changed in a data structure, and using cheap reference comparisons instead of expensive deep comparisons. This lesson connects all three back to the same idea: object identity.

## Referential equality

For objects and functions, equality is about **identity**, not contents. Two separately created objects are never `===` to each other, even if every property matches exactly - `===` only returns `true` when both sides refer to the **same** object in memory.

```js
const a = { x: 1 };
const b = { x: 1 };
console.log(a === b); // false: different objects, same contents
console.log(a === a); // true: the same object
```

This is called **referential equality**, to distinguish it from comparing the _contents_ of two objects (sometimes called "deep" or "structural" equality), which requires walking through each property yourself or using a dedicated helper.

## Why identity matters in application code

Referential equality is genuinely useful, not just a quirk to work around. Identity is commonly used to:

- **Detect whether a value was reused or replaced.** If a reference is unchanged, the data behind it can be assumed unchanged too, without inspecting its contents.
- **Key `Map`s and `Set`s** by object, relying on the fact that the same object passed twice is recognized as the same key or member.
- **Decide whether memoized work can be reused** - if the input reference is the same as last time, a cached result can be returned without recomputing.

## Memoization

**Memoization** caches a function's results, keyed by its inputs, so that calling the function again with an **input it's seen before** can return the cached result instead of redoing the work:

```js
function memoize(fn) {
  const cache = new Map();
  return (arg) => {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

let calls = 0;
const slowSquare = memoize((n) => {
  calls++;
  return n * n;
});
slowSquare(5); // computes: calls = 1
slowSquare(5); // cached: calls stays 1
slowSquare(6); // computes: calls = 2
```

Memoization is worth it when the underlying computation is genuinely expensive and the cache's memory cost is acceptable - and it depends directly on identity: if `arg` were an object recreated fresh on every call (even with identical contents), `cache.has(arg)` would never find a match, because a `Map`'s default key comparison is referential equality, not deep equality.

## Immutability as an application-level practice

**Immutability**, as a practice, means treating existing values as **unchanged** and creating a **new value** for every update, rather than mutating data in place. This is a discipline you choose to follow - the language doesn't force it (as covered in an earlier lesson, even a `const` object can still be mutated). The payoff is that a previously captured snapshot of the data stays trustworthy: nothing can retroactively change it out from under code that's still holding a reference to it, and an identity change becomes a reliable signal that something changed.

## Structural sharing

Following immutability strictly would seem to demand a full deep copy on every update - expensive for large structures. **Structural sharing** avoids that: it creates a new top-level structure for the parts that changed, while **reusing the existing, unchanged nested parts by reference** instead of copying them.

```js
const state = { user: { name: "Ada" }, settings: { theme: "dark" } };
const next = {
  ...state,
  settings: { ...state.settings, theme: "light" },
};

console.log(next.user === state.user); // true - untouched branch reused, not copied
console.log(next.settings === state.settings); // false - changed branch replaced
```

`next` is a new object, but `next.user` is the _exact same_ object as `state.user` - there was no need to copy it, since nothing about it changed.

## When shallow equality is enough

That reuse is what makes a **shallow equality check** - comparing each top-level property with `===`, without recursing into nested values - a reliable way to detect changes, _as long as updates always replace changed values instead of mutating them in place_. Under that discipline, any changed data produces a changed reference at the boundary you're comparing, so a cheap shallow check (`next.settings === state.settings`) tells you exactly as much as an expensive deep comparison would - but this only holds if every update in the codebase follows the same immutable-update convention; a single spot that mutates in place breaks the guarantee everywhere.

## Common mistakes

- **Mutating a nested object in place and expecting a shallow equality check to notice.** If `state.settings.theme = "light"` was done in place instead of via structural sharing, `next.settings === state.settings` stays `true`, and change detection based on that check silently misses the update.
- **Memoizing on object arguments that are recreated fresh each call.** If the argument's identity changes even when its contents don't, a `Map`-based cache will treat every call as a new input and never hit.
- **Assuming immutability is enforced by the language.** It's a convention your code has to follow consistently (or a library has to enforce); nothing stops a mutation from slipping in and breaking every assumption built on top of it.

## Key points

- Referential equality compares identity for objects and functions; two separately created objects are never `===` even with identical contents.
- Object identity is used to detect reuse vs. replacement, to key maps and sets, and to decide whether memoized work can be reused.
- Memoization caches results by input so repeated calls with a previously seen input can skip recomputation.
- Immutability as a practice means treating values as unchanged and creating replacements for updates, so old snapshots stay trustworthy and identity changes become meaningful.
- Structural sharing creates a new structure while reusing unchanged nested parts by reference, avoiding a full deep copy.
- A shallow equality check is sufficient exactly when updates always replace changed values instead of mutating them in place.

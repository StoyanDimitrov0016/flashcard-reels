# You might not need an Effect

Once developers learn `useEffect`, it tends to spread: an Effect to copy one state into another, an Effect to react to a button click, an Effect to fetch whenever anything changes. Each one feels harmless, but together they make components slower, harder to follow, and full of timing bugs. Effects are an escape hatch for synchronizing with external systems. When no external system is involved, there is almost always a simpler place for the code.

## Two questions before writing an Effect

**Logic should not be put in an Effect** if **the value can be calculated during render**, or if **the action is directly caused by a user event**. In both cases, an Effect adds **unnecessary synchronization** and **extra renders**.

## Calculating during render

Here is a very common pattern:

```jsx
function Invoice({ items }) {
  const [total, setTotal] = useState(0);

  useEffect(() => {
    setTotal(items.reduce((sum, item) => sum + item.price * item.quantity, 0));
  }, [items]);

  return <p>Total: {total}</p>;
}
```

Trace what happens when `items` changes. React renders `Invoice` with the new items and the **old** total, commits that inconsistent screen, runs the Effect, sets the new total, and renders and commits a second time. The user may briefly see a total that does not match the list, and every change costs two renders.

The total is derived state, so compute it directly:

```jsx
function Invoice({ items }) {
  const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  return <p>Total: {total}</p>;
}
```

One render, always consistent, less code.

## Event-driven logic belongs in event handlers

The second question is about causes. If something happens **because the user did something**, put it in the handler for that event. An event handler knows exactly what happened. An Effect only knows that the component rendered with certain values, and has to reverse-engineer why.

```jsx
// Avoid: showing a toast from an Effect
useEffect(() => {
  if (product.isInCart) {
    showToast(`Added ${product.name} to the cart`);
  }
}, [product]);
```

This toast appears whenever the component renders with an in-cart product, including when the user refreshes the page and the cart is restored. What the user did was click "Add to cart", so that is where the toast goes:

```jsx
function handleAddClick() {
  addToCart(product);
  showToast(`Added ${product.name} to the cart`);
}
```

## Mutations come from events or Actions, not from mounting

The same reasoning applies with more force to requests that **change** data on the server. **A network mutation should usually originate from an event or Action rather than a mount Effect.** A mutation represents a **user or application action**, not merely the fact that a component **became visible**. Tying it to mount can **duplicate writes** during **remounts or navigation**.

```jsx
// Avoid
function CheckoutConfirmation({ order }) {
  useEffect(() => {
    submitOrder(order); // runs whenever this screen mounts
  }, [order]);
  return <p>Thank you!</p>;
}
```

If the user goes back and forward again, the component remounts and the order is submitted a second time. Strict Mode's extra development cycle, from the previous lesson, would submit it twice on every mount, which is the check doing its job. The order should be submitted by the "Place order" button's handler, or by an Action, the React 19 mechanism for mutations covered in a later lesson. Showing the confirmation screen is a _consequence_ of submitting, not the cause.

Contrast this with sending an analytics "screen viewed" event from an Effect. That _is_ caused by the component being displayed, so it fits an Effect.

## Infinite update loops

Effects that set state have one more trap. **An Effect can create an infinite update loop** if it **updates state** and that update **changes one of the Effect's dependencies on every render**. Each commit schedules the Effect, the Effect sets state, that state change produces a new dependency value, and the cycle repeats.

```jsx
function Report({ rows }) {
  const [summary, setSummary] = useState({ count: 0 });

  useEffect(() => {
    setSummary({ count: rows.length });
  }, [rows, summary]); // summary is a new object every time

  return <p>{summary.count} rows</p>;
}
```

`setSummary` stores a new object, so `summary` differs by identity after every update, which re-runs the Effect, which stores another new object. The same happens with a dependency that is an object or array literal created during render. The fix is usually to notice that `summary` is derived and delete the Effect. Where an Effect is genuinely needed, remove the self-triggering dependency, depend on primitives, or use a functional update.

## Fetching in an Effect and race conditions

Fetching data when a screen shows is a legitimate synchronization task: the component should display the results for the current query. But **fetching in an Effect is vulnerable to races**. Requests can **finish out of order**, and an **older request can resolve after a newer one** and overwrite current state unless **stale results are ignored or canceled**.

```jsx
function SearchResults({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    let ignore = false;
    fetchResults(query).then((data) => {
      if (!ignore) setResults(data);
    });
    return () => {
      ignore = true;
    };
  }, [query]);

  return (
    <ul>
      {results.map((r) => (
        <li key={r.id}>{r.title}</li>
      ))}
    </ul>
  );
}
```

Suppose the user types "re", then "rea". Two requests start. If the "re" response arrives last, it would replace the "rea" results with the wrong list. With the `ignore` flag, typing "rea" runs the cleanup of the "re" Effect, which marks that request as stale, so its late response is discarded. Only the latest query can set `results`. An `AbortController` can cancel the stale request outright instead of ignoring it.

Hand-written fetch Effects also lack caching and cannot start before the component renders. In real apps, prefer your framework's data loading or a data-fetching library, or the Suspense-based approach later in this deck, which handle races for you.

## Key points

- Do not put logic in an Effect when the value can be calculated during render or the action is caused by a user event; it adds synchronization and extra renders.
- Derived values computed during render stay consistent and avoid a second render.
- Network mutations should come from an event or Action, not a mount Effect, because remounts and navigation can duplicate the write.
- An Effect that updates state which changes one of its own dependencies every render creates an infinite loop.
- Fetch requests in an Effect can finish out of order; ignore or cancel stale results so an older response cannot overwrite newer state.

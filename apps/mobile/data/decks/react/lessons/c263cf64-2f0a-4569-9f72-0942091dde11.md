# Suspense and error boundaries

Every screen that loads something has three states: waiting, done, and failed. Handling them inside each component means every component carries `isLoading` and `error` variables, and a page with five data sources shows five spinners popping in at random. Suspense and error boundaries move the waiting and failed states out of individual components and into boundaries you place in the tree, where you decide what the user sees.

## Suspense

**Suspense** lets a subtree **declare that it cannot render yet** and allows React to **show a fallback** while the required **resource or code is pending**.

```jsx
import { Suspense } from "react";

function ProductPage({ productId }) {
  return (
    <>
      <ProductHeader productId={productId} />
      <Suspense fallback={<p>Loading reviews...</p>}>
        <Reviews productId={productId} />
      </Suspense>
    </>
  );
}
```

If anything inside the `Suspense` boundary is not ready, React renders the `fallback` in its place. When everything inside is ready, React swaps in the real content. `ProductHeader` sits outside the boundary, so it is unaffected. Components inside the boundary simply read their data as if it were already there; they do not manage loading flags at all.

A component does not suspend by calling some "wait" function. It suspends when it tries to use something that is not ready: a lazily loaded component, or a Promise read with `use`, both covered below. Only Suspense-enabled sources trigger it. Data fetched in an Effect does not.

Boundaries are a design decision. One boundary around the whole page shows a single loading state; boundaries around each section let sections appear independently. Nested boundaries reveal content progressively from the outside in.

## Code splitting

Loading can also mean loading code. A large app bundles many features, and most users need only a few on the first screen. **Code splitting** divides JavaScript into **chunks loaded on demand**, so users do not need to download **every feature before the initial interface can start**. Bundlers create a separate chunk wherever the code uses a dynamic `import()`.

## lazy

**`lazy`** **defers loading a component module until React needs to render it**, and the component **can suspend while that module is loading**:

```jsx
import { lazy, Suspense, useState } from "react";

const MarkdownEditor = lazy(() => import("./MarkdownEditor.js"));

function PostComposer() {
  const [showEditor, setShowEditor] = useState(false);
  return (
    <>
      <button onClick={() => setShowEditor(true)}>Write a post</button>
      {showEditor && (
        <Suspense fallback={<p>Loading editor...</p>}>
          <MarkdownEditor />
        </Suspense>
      )}
    </>
  );
}
```

At first, only the button renders, and the editor's code (perhaps a large Markdown library) has not been downloaded. Clicking the button renders `MarkdownEditor` for the first time. React calls the `import()` function, the component suspends, and the boundary shows "Loading editor...". When the chunk arrives, the editor appears. Later renders use the already loaded module immediately. Declare `lazy` components at the top level of a module, never inside another component, or their state resets on every render.

## Reading a Promise with use

**`use`** lets supported render code **read a resource such as a Promise or context**. When it reads a Promise, it **suspends while the Promise is pending** and **resumes when it settles**: with the value if it resolves, or by throwing to the nearest error boundary if it rejects.

```jsx
import { use } from "react";

function Reviews({ reviewsPromise }) {
  const reviews = use(reviewsPromise);
  return (
    <ul>
      {reviews.map((r) => (
        <li key={r.id}>{r.text}</li>
      ))}
    </ul>
  );
}
```

`use` is unusual among Hook-like APIs: it may be called inside conditions and loops, though still only in components and Hooks. With a context argument, it works like `useContext`.

## Suspense-compatible data sources

There is an important constraint on that Promise. **Render-time data sources must be compatible with Suspense semantics**, because **React may restart or replay rendering around suspension**. When a component suspends, React does not keep its half-finished render; it renders the component again from the start once the Promise settles. The resource therefore must provide **stable, cacheable behavior** rather than **launching uncontrolled side effects on every render**.

```jsx
// Broken: a new request and a new Promise on every render attempt
function Reviews({ productId }) {
  const reviews = use(fetch(`/api/products/${productId}/reviews`).then((r) => r.json()));
  // ...
}
```

Each attempt starts a new request and creates a new Promise, so the component suspends on a Promise it will never read again, over and over. Instead, the Promise must be created once and reused: passed down from a Server Component, provided by a framework's data loader, or kept in a cache by a Suspense-aware data library, so that re-rendering asks for the same resource and gets the same Promise back.

## Error boundaries

Suspense handles "not yet". An **error boundary** handles "failed": it is a component boundary that can **render fallback UI when a descendant throws during rendering or lifecycle processing**, instead of the error unmounting the whole app.

Error boundaries are written as class components, because the API exists only there (`static getDerivedStateFromError` to switch to the fallback, `componentDidCatch` to log). Most projects write one once or use the `react-error-boundary` package:

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary fallback={<p>Reviews could not be loaded.</p>}>
  <Suspense fallback={<p>Loading reviews...</p>}>
    <Reviews reviewsPromise={reviewsPromise} />
  </Suspense>
</ErrorBoundary>;
```

Together, these give `Reviews` all three states without a single flag: loading shows the Suspense fallback, success shows the list, and a rejected Promise, rethrown by `use` during render, shows the error fallback. The rest of the page keeps working.

An error boundary **does not catch every asynchronous or event-handler error**. An error thrown inside an `onClick` handler, a `setTimeout` callback, or a stray `fetch().then()` happens outside rendering, so React never sees it. Handle those with `try`/`catch` and state, or route them through rendering (for example, by reading a Promise with `use`, or with Actions, which surface errors to boundaries).

## Key points

- Suspense lets a subtree declare it cannot render yet, and React shows a fallback while the resource or code is pending.
- Code splitting divides JavaScript into chunks loaded on demand so users need not download every feature up front.
- `lazy` defers loading a component module until it first renders, suspending while the module loads.
- `use` reads a resource such as a Promise or context in render, suspending while the Promise is pending and resuming when it settles.
- Render-time data sources must be stable and cacheable because React may restart rendering around suspension.
- An error boundary renders fallback UI when a descendant throws during rendering or lifecycle processing, but it does not catch every asynchronous or event-handler error.

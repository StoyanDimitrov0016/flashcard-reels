# Managing state with reducers

As a component grows, its state updates spread out. One handler sets three variables, another sets two of the same ones, and a third forgets one. Reading the component no longer tells you how the state can change, because the rules are scattered across every event handler. A reducer gathers those rules into one place.

## useReducer

**`useReducer`** centralizes state transitions in a **reducer** function that receives the **current state** and an **action** and returns the **next state**.

```jsx
import { useReducer } from "react";

function cartReducer(state, action) {
  switch (action.type) {
    case "added":
      return { ...state, items: [...state.items, action.item] };
    case "removed":
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case "cleared":
      return { ...state, items: [] };
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

function Cart() {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });

  return (
    <>
      <ul>
        {state.items.map((item) => (
          <li key={item.id}>
            {item.name}
            <button onClick={() => dispatch({ type: "removed", id: item.id })}>Remove</button>
          </li>
        ))}
      </ul>
      <button onClick={() => dispatch({ type: "cleared" })}>Clear cart</button>
    </>
  );
}
```

`useReducer` takes the reducer and an initial state and returns the current state plus a **`dispatch`** function. Event handlers no longer say how to change the state; they describe **what happened** by dispatching an action, a plain object that conventionally has a `type` field. Clicking "Remove" dispatches `{ type: "removed", id }`. React calls `cartReducer` with the current state and that action, stores whatever it returns, and renders `Cart` again with the shorter list.

Like a state setter, `dispatch` queues an update for the next render, and the reducer runs with the latest queued state, just as a functional update does.

## What a reducer must avoid

A reducer must not **mutate existing state** and must not **perform side effects**. It should only **compute and return the next state from its inputs**.

This is the purity rule from the render lesson, applied to state logic. React may call reducers during rendering, and in development it calls them twice to help catch impurity. So a reducer must not send requests, set timers, write to storage, or log analytics events; those belong in event handlers or Effects. It must also return new objects instead of editing `state` in place, for the same identity reasons that make state immutable everywhere else. Written this way, a reducer is an ordinary function that is easy to test without rendering anything: pass a state and an action, check the result.

## When useReducer is preferable

`useState` and `useReducer` are equally capable; the choice is about how the logic reads. `useReducer` is preferable to several `useState` calls when:

- **Multiple fields change together.** One action updates them consistently in one place, instead of every handler calling several setters in the right order.
- **Transitions are action-oriented.** Updates are naturally described as events, such as "added", "submitted", or "retried".
- **Update logic is complex** enough to benefit from one explicit, state-machine-like function you can read top to bottom.

For a single toggle or a text field, `useState` is simpler. Reach for a reducer when you notice the same group of setters being called together from many places.

## The state machine approach

The previous lesson replaced a pile of booleans with one status value. A reducer lets you go one step further. A **state machine approach** to UI state models the UI as **explicit states** and the **allowed events or transitions** between them, preventing the impossible combinations that can arise from unrelated booleans.

The idea is to decide, for each state, which events mean something. A reducer can enforce this by checking the current status before handling an action:

```jsx
function uploadReducer(state, action) {
  switch (state.status) {
    case "idle":
      if (action.type === "start") return { status: "uploading", progress: 0 };
      return state;
    case "uploading":
      if (action.type === "progress") return { ...state, progress: action.progress };
      if (action.type === "succeed") return { status: "done", url: action.url };
      if (action.type === "fail") return { status: "failed", error: action.error };
      return state;
    case "failed":
      if (action.type === "retry") return { status: "uploading", progress: 0 };
      return state;
    case "done":
      return state;
    default:
      throw new Error(`Unknown status: ${state.status}`);
  }
}

function FileUpload() {
  const [state, dispatch] = useReducer(uploadReducer, { status: "idle" });

  if (state.status === "idle") {
    return <button onClick={() => dispatch({ type: "start" })}>Upload</button>;
  }
  if (state.status === "uploading") return <progress value={state.progress} max={100} />;
  if (state.status === "failed") {
    return (
      <p>
        {state.error} <button onClick={() => dispatch({ type: "retry" })}>Retry</button>
      </p>
    );
  }
  return <p>Uploaded to {state.url}</p>;
}
```

Each state carries only the data that makes sense in it: `progress` exists only while uploading, `error` only after a failure, `url` only when done. Events that do not apply are ignored: a stray "progress" message after the upload finished cannot drag the UI back to a progress bar, and "retry" does nothing unless the upload failed. (The actual upload request would be started from the event handler that dispatches `start`, not from inside the reducer.) The UI renders exactly one branch for each state, and the set of possible screens is visible at a glance.

## Common mistakes

- **Side effects in the reducer.** Fetching or logging inside a reducer runs at unpredictable times and twice in development.
- **Mutating `state`.** `state.items.push(item); return state;` returns the same reference, so the change can be skipped and snapshots are corrupted.
- **Vague actions.** Actions like `{ type: "setField" }` for everything turn the reducer back into a setter. Name actions after what happened.

## Key points

- `useReducer` centralizes state transitions in a reducer that receives current state and an action and returns the next state.
- Handlers dispatch actions describing what happened instead of setting state directly.
- A reducer must not mutate existing state or perform side effects; it computes the next state from its inputs.
- `useReducer` is preferable when multiple fields change together, transitions are action-oriented, or update logic is complex.
- A state machine approach models UI as explicit states and allowed transitions, preventing impossible combinations of unrelated booleans.

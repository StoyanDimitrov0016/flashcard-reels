# Passing data deeply with context

Props work well between a parent and its child. But some values are needed far down the tree: the current theme, the signed-in user, the active language. Passing them by hand through every layer is tedious and couples components that have nothing to do with the data. Context is React's answer, but it has costs of its own, and a well-designed app uses it deliberately rather than by default.

## Prop drilling

**Prop drilling** is passing data through intermediate components that do not use it themselves, solely so deeper descendants can receive it.

```jsx
function Page({ user }) {
  return <Layout user={user} />;
}
function Layout({ user }) {
  return <Sidebar user={user} />;
}
function Sidebar({ user }) {
  return <UserBadge user={user} />;
}
```

`Layout` and `Sidebar` never look at `user`. They only forward it. Every new intermediate component must accept and pass the prop, and renaming it touches every layer.

## When prop drilling is acceptable

Despite the name, prop drilling is not a bug. It is often the **simplest** option when the path is **short** and **ownership remains clear**. Explicit props make the data flow visible: you can see exactly which components depend on `user` by reading their signatures. Passing a prop through one or two components is normal React code.

**Context is not automatically better** for every shared value. It hides the dependency, and it changes how updates spread through the tree. Consider the alternatives below before reaching for it.

## Composition as an alternative

Often the need to drill disappears if components accept **children** or other JSX as props. Instead of passing data down so a deep component can render something, render that something at the top and pass the finished UI down:

```jsx
function Page({ user }) {
  return (
    <Layout sidebar={<UserBadge user={user} />}>
      <Feed />
    </Layout>
  );
}

function Layout({ sidebar, children }) {
  return (
    <div className="layout">
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}
```

`Layout` no longer knows `user` exists. **Component composition** is often preferable to broad context because it passes concrete UI or behavior **only where needed**, avoiding **hidden dependencies** and the **rerenders caused by a large shared context value**.

## Context

When a value really is needed by many components at many depths, use **context**. Context lets a **provider** make a value available to descendants without passing that value through every intermediate component as props.

```jsx
import { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");

function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext value={theme}>
      <Toolbar />
      <button onClick={() => setTheme(theme === "light" ? "dark" : "light")}>Toggle theme</button>
    </ThemeContext>
  );
}

function Toolbar() {
  return <SaveButton />;
}

function SaveButton() {
  const theme = useContext(ThemeContext);
  return <button className={`btn btn-${theme}`}>Save</button>;
}
```

`createContext("light")` creates the context and its default value, used when no provider is above a component. `App` renders the provider with the current theme; in React 19 you render the context itself as the provider, while older code writes `<ThemeContext.Provider value={theme}>`, which still works. `SaveButton` reads the nearest provider's value with `useContext`. `Toolbar` does not mention the theme at all.

## What happens when the value changes

When a consumed context value changes, React **schedules consumers** of that context to **render with the new value**. Clicking "Toggle theme" updates `theme` in `App`, the provider receives a new `value`, and `SaveButton` renders with `"dark"`. This happens even if components in between skip rendering, for example because they are memoized; the context update reaches consumers directly.

React compares the old and new provider values by identity. A primitive like `"dark"` changes only when it really changes. An object literal such as `value={{ user, setUser }}` is a new object on every render of the provider, so consumers render every time the provider does, even if nothing inside changed.

## Why frequently changing context causes broad rerenders

This leads to the main cost of context. Every consumer reading a context is **eligible to render when the provider value changes**, even if each consumer uses only **part of a large object**. `useContext` has no way to subscribe to one field.

Imagine one `AppContext` holding `{ user, theme, cart, notifications }`. A new notification arrives every few seconds; each time, the provider value changes, and every component that reads `AppContext`, including ones that only care about the theme, renders again. For rarely changing values this is fine. For large, frequently changing objects it can become a performance problem.

The usual remedies: split one large context into several focused ones, keep fast-changing values out of context, stabilize the provider value (the memoization lesson covers `useMemo`), or use composition so fewer components need the value in the first place.

## Compound components

Context is also a building block for component APIs. In the **compound component pattern**, several components cooperate through **shared context** or conventions to form one higher-level UI API, such as tabs with tab and panel children.

```jsx
const TabsContext = createContext(null);

function Tabs({ defaultTab, children }) {
  const [active, setActive] = useState(defaultTab);
  return <TabsContext value={{ active, setActive }}>{children}</TabsContext>;
}

function Tab({ id, children }) {
  const { active, setActive } = useContext(TabsContext);
  return (
    <button aria-selected={active === id} onClick={() => setActive(id)}>
      {children}
    </button>
  );
}

function TabPanel({ id, children }) {
  const { active } = useContext(TabsContext);
  return active === id ? <div>{children}</div> : null;
}

// Usage
<Tabs defaultTab="specs">
  <Tab id="specs">Specs</Tab>
  <Tab id="reviews">Reviews</Tab>
  <TabPanel id="specs">Weight: 1.2 kg</TabPanel>
  <TabPanel id="reviews">4.8 out of 5</TabPanel>
</Tabs>;
```

`Tabs` owns the active tab; `Tab` and `TabPanel` read and update it through context. The user of the API just arranges the pieces, and nobody passes `active` or `setActive` by hand. Initially the Specs panel is visible; clicking "Reviews" updates the shared state and the panels swap.

## Common mistakes

- **Context for everything.** Using context to avoid passing a prop one level down hides data flow for no benefit.
- **One giant context.** Unrelated values bundled together make every consumer render whenever any of them changes.
- **Forgetting the provider.** Without a provider above it, a consumer silently gets the default value from `createContext`.

## Key points

- Prop drilling passes data through intermediate components that do not use it, only so deeper descendants receive it.
- Prop drilling is often simplest when the path is short and ownership stays clear; context is not automatically better.
- Context lets a provider make a value available to descendants without passing it through every intermediate component.
- When a consumed context value changes, React schedules its consumers to render with the new value.
- A frequently changing context value can cause broad rerenders, because every consumer is eligible to render even if it uses only part of a large object.
- Composition can pass concrete UI or behavior only where needed, avoiding hidden dependencies and context-driven rerenders.
- Compound components cooperate through shared context or conventions to form one higher-level API, such as tabs with tab and panel children.

# Performance and robust components

A component is finished when it is fast enough, usable by everyone, and behaves correctly when React mounts, unmounts, and remounts it. This final lesson covers how to approach performance, why accessibility is part of correctness, a few habits that make effects robust, and the declarative idea that ties all of React together.

## Measure before optimizing

Performance work should be driven by evidence. Start by measuring **user-visible latency** and collecting **profiling data**. Then optimize only where a cost is actually significant, whether that is **rendering**, **computation**, **network** requests, or **bundle size**. A slow screen is just as often caused by a large download or a waterfall of requests as by rendering.

The **React Profiler**, available in React Developer Tools and as the `<Profiler>` component, **records render timing and commit information**. It shows which components rendered, how long they took, and how often. It helps you find **expensive renders** and renders that happen **more often than expected**.

## Memoization is not architecture

It is tempting to wrap everything in `memo`, `useMemo`, and `useCallback` when an app feels slow. That can **reduce the symptoms** while leaving the real cause untouched: state owned **too high** in the tree, **unstable data flow** that creates new objects on every render, or **expensive work in a parent** that runs regardless. Moving state down, splitting components, or passing children through composition often fixes the problem at its source and makes memoization unnecessary.

## Virtualizing long lists

Rendering thousands of rows creates thousands of DOM nodes, even though only a screenful is visible. **Windowing**, also called **list virtualization**, renders only the **visible portion** of the list plus a small **buffer** above and below. As the user scrolls, rows are recycled. This greatly reduces DOM nodes and rendering work.

The trade-off is complexity. Virtualization needs **scroll measurement**, which is harder when rows have varying heights. It complicates **focus and accessibility**, because off-screen items **do not exist in the DOM** until they approach the viewport, so the browser's find-in-page and assistive technology cannot see them, and focus can be lost when a focused row scrolls away.

## Accessibility is correctness

A component that looks right can still be **unusable**. If its **semantics**, **keyboard behavior**, **focus management**, accessible **names**, or **state** such as expanded or selected are not exposed, people using screen readers or keyboards cannot operate it. That makes accessibility part of whether a component is correct, not an optional polish step.

Prefer **semantic HTML** before reaching for **ARIA**. A native `<button>` is focusable, activates with Enter and Space, and announces itself as a button, all built in by the browser. ARIA attributes can **describe** missing semantics, but they **do not implement behavior**:

```jsx
// Announced as a button, but not focusable and ignores the keyboard
<div role="button" onClick={save}>Save</div>

// Correct by default
<button onClick={save}>Save</button>
```

## Idempotent effects

An effect's setup and cleanup should form an **idempotent pair**. Running setup, then cleanup, then setup again must leave the external system in the **same intended state** as a single correct setup. A connection is opened, closed, and opened again, ending with exactly one open connection. Effects written this way are robust to **remounting**, to navigation, and to the extra cycle that **Strict Mode** runs in development.

## Mutations belong to events

A **network mutation**, such as creating an order or sending a message, represents something the user or application **decided to do**. It should start from an **event handler** or an **Action**, not from an effect that runs on mount. A component becoming visible is not the same as the user asking for something to happen. If a write is tied to mount, remounts, Strict Mode checks, or navigating back and forth can **duplicate the write**.

```jsx
// Avoid: sends again whenever the component mounts
useEffect(() => {
  submitOrder(cart);
}, []);

// Prefer: sends once, because the user asked
<button onClick={() => submitOrder(cart)}>Place order</button>;
```

## The declarative model

Everything in this deck follows from one idea. In React's **declarative model**, your code **describes the UI** that corresponds to the **current state**. You do not write step-by-step instructions such as "find this element, change its text, add this class". React compares descriptions and **computes the host changes** needed to make the screen match.

This is why render should be pure, why state is a snapshot, why keys and tree position matter, and why effects are reserved for the systems React does not control. When you describe the right UI for every state, React takes care of getting the screen there.

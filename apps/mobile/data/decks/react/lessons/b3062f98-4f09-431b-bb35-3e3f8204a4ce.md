# Strict Mode

Two rules from earlier lessons are easy to state and easy to break without noticing: rendering must be pure, and every Effect setup needs a cleanup that undoes it. Violations often cause no visible problem on your machine, and then surface in production as duplicated requests, leaking connections, or glitches after navigation. Strict Mode exists to drag those bugs into the open while you are still developing.

## What Strict Mode does

**Strict Mode** adds **development-only checks** that intentionally exercise components and Effects in ways that reveal **impure rendering** and **missing cleanup**. You enable it by wrapping part or all of your app:

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

Many project templates turn it on by default. It renders no UI and has no effect in production builds. In development, for components inside it, React:

- **Renders components twice** (and calls state initializers, updater functions, and reducers twice) and uses one of the results. A pure component gives the same answer both times; an impure one shows its side effects twice.
- **Runs an extra setup and cleanup cycle for every Effect** when the component first mounts.
- Does the same for ref callbacks, and warns about deprecated APIs.

These are stress tests. They simulate things React is allowed to do anyway: render more than once, discard renders, and unmount and remount components (for example, when a future feature restores a hidden screen with its previous state).

## Why an Effect appears to run twice

In development you may see a connection open, close, and open again right after mount. React performs an **extra setup-and-cleanup cycle** to **verify that cleanup correctly reverses setup**. The sequence on mount is: setup, cleanup, setup.

This is a check, not the real behavior of your app. **Production does not simply "run every effect twice."** In production, the Effect sets up once on mount and follows the normal rules: cleanup and setup when dependencies change, and cleanup on unmount.

The right response to a double run is never to switch Strict Mode off or to add a flag that skips the second setup. The question to ask is: "Does my app behave correctly after setup, cleanup, setup?" If it does not, the same bug will appear in production whenever a user navigates away and back, or a component remounts for any other reason.

## Idempotent setup and cleanup

The property Strict Mode checks for has a name. An **idempotent Effect setup/cleanup pair** is one where running **setup, cleanup, and setup again** leaves the external system in the **same intended state as one correct setup**. This makes Effects **robust to remounting** and to **development checks**.

Here is an Effect that fails the test:

```jsx
function PriceTicker({ symbol }) {
  const [price, setPrice] = useState(null);

  useEffect(() => {
    const socket = new WebSocket(`wss://prices.example.com/${symbol}`);
    socket.onmessage = (e) => setPrice(JSON.parse(e.data).price);
    // no cleanup
  }, [symbol]);

  return (
    <p>
      {symbol}: {price ?? "..."}
    </p>
  );
}
```

In development, the extra cycle leaves two open sockets. Both deliver prices, and nothing ever closes either of them. In production, the same leak appears every time `symbol` changes. Adding the matching cleanup makes the pair idempotent:

```jsx
useEffect(() => {
  const socket = new WebSocket(`wss://prices.example.com/${symbol}`);
  socket.onmessage = (e) => setPrice(JSON.parse(e.data).price);
  return () => socket.close();
}, [symbol]);
```

Now setup, cleanup, setup ends with exactly one open socket for the current symbol, which is precisely the state a single setup would produce. The pattern generalizes: `addEventListener` pairs with `removeEventListener`, `setInterval` with `clearInterval`, `connect` with `disconnect`, `observe` with `disconnect`. For a non-React widget, create it in setup and destroy it in cleanup; for something that can only be initialized once per page, such as an analytics library, do it outside the component.

Some Effects are naturally fine without cleanup. Setting a map's zoom level to the current prop is idempotent on its own, because setting the same value twice changes nothing.

## Things Strict Mode deliberately exposes

- **Mutation during render.** A component that pushes to an array defined outside itself will push twice.
- **Setup without cleanup.** Subscriptions, listeners, and timers show up doubled.
- **Writes tied to mount.** An Effect that sends a POST request when a component mounts sends it twice. That is a sign the request should not be in an Effect at all; the next lesson explains where it belongs.

## Common mistakes

- **Disabling Strict Mode to "fix" double Effects.** The bug is still there, only hidden until a real remount.
- **Using a ref flag to skip the second setup.** This defeats the check and leaves remounts broken.
- **Assuming production runs Effects twice.** The extra cycle is development-only.

## Key points

- Strict Mode adds development-only checks that exercise components and Effects to reveal impure rendering and missing cleanup.
- In development, React runs an extra setup-and-cleanup cycle to verify that cleanup correctly reverses setup.
- Production does not simply run every Effect twice.
- An idempotent setup/cleanup pair leaves the external system in the same state after setup, cleanup, setup as after one correct setup.
- Idempotent Effects are robust to remounting and to development checks.

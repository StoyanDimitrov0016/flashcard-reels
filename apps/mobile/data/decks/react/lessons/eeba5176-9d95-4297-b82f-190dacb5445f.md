# Subscribing to external stores

Not all the data a component shows lives in React state. A state management library keeps its own store; the browser knows whether the network is online and how wide the window is; a WebSocket client holds the latest prices. Components need to read these values and update when they change. Doing that naively works most of the time, and then produces subtle glitches once concurrent rendering is involved. React provides one Hook designed to do it correctly.

## External store state

**External store state** is state **owned outside React**, such as a **library store** or a **browser-backed subscription source**, that components **subscribe to for updates**. React does not control when it changes; the store changes it, then notifies whoever subscribed.

A minimal store looks like this:

```jsx
function createStore(initialState) {
  let state = initialState;
  const listeners = new Set();
  return {
    getState: () => state,
    setState(update) {
      state = { ...state, ...update };
      listeners.forEach((listener) => listener());
    },
    subscribe(listener) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

export const cartStore = createStore({ items: [], currency: "EUR" });
```

Libraries such as Zustand and Redux follow the same shape: a way to read the current state, and a way to subscribe to changes.

## Why reading a mutable store during render is unsafe

The obvious approach is to read `cartStore.getState()` during render and subscribe in an Effect to force a re-render on change. The problem comes from the concurrent rendering described in the transitions lesson. A transition render can be split into pieces, with React yielding to the browser in between. During those pauses, other code keeps running, including code that updates the store.

**Directly reading a mutable external store during render can be unsafe** because **the store can change while React is preparing a render**, causing **different components to observe inconsistent versions** unless **subscription and snapshot semantics are coordinated**. React state does not have this problem, because React itself controls when state changes take effect. An external store changes on its own schedule.

## Tearing

The visible result has a name. **Tearing** is when **different parts of one visible UI reflect different versions of shared state** because **reads were not synchronized**.

Picture a cart badge in the header and a cart summary in the sidebar, both reading `cartStore` directly. React starts an interruptible render, renders the header (which reads "2 items"), and yields. While it is paused, a store update adds an item. React resumes and renders the sidebar, which now reads "3 items". It commits both. For a moment, one screen says 2 and 3 at the same time, like a torn photograph. Synchronous rendering cannot tear, because nothing else runs in the middle of a render; concurrent rendering can, if reads are not coordinated.

## useSyncExternalStore

**`useSyncExternalStore`** provides a **standard way to subscribe to an external store** and **read consistent snapshots** in rendering modes where **updates can be concurrent**:

```jsx
import { useSyncExternalStore } from "react";
import { cartStore } from "./cartStore.js";

function useCartItemCount() {
  return useSyncExternalStore(
    cartStore.subscribe,
    () => cartStore.getState().items.length,
    () => 0 // snapshot used during server rendering and hydration
  );
}

function CartBadge() {
  const count = useCartItemCount();
  return <span className="badge">{count}</span>;
}

function CartSummary() {
  const count = useCartItemCount();
  return <p>{count} items in your cart</p>;
}
```

It takes three functions:

1. **`subscribe`** receives a callback, registers it with the store, and returns an unsubscribe function. React calls it on mount and cleans up on unmount.
2. **`getSnapshot`** returns the current value from the store. It must return the same value when the store has not changed: returning a new object on every call makes React think the store is always changing, which re-renders endlessly. Returning a primitive, like the item count here, or an existing object from the store, avoids that.
3. **`getServerSnapshot`** (optional) returns the value to use on the server and during hydration, where the browser store does not exist.

With this Hook, React checks snapshots during rendering. If the store changes in the middle of a concurrent render, React notices that the snapshot is different and re-renders synchronously so that every component commits with the same version. `CartBadge` and `CartSummary` always agree. When the store notifies subscribers, React re-renders only the components whose snapshot actually changed.

The same Hook works for browser sources. For example, subscribing to the `online` and `offline` window events with `getSnapshot` returning `navigator.onLine` is a cleaner version of the online-status custom Hook from an earlier lesson.

## When to use it

Most apps never call `useSyncExternalStore` directly. State management libraries use it internally, and you consume it through their Hooks. Reach for it yourself when you connect a store or browser API that has no React bindings. Use regular React state, context, and reducers for data that React can own.

## Common mistakes

- **Reading a store in render and syncing with an Effect.** This can tear under concurrent rendering and briefly shows stale values after mount.
- **Returning a new object from `getSnapshot`.** It looks like a change on every read.
- **Defining `subscribe` inline inside the component.** A new function each render makes React resubscribe every time; define it outside the component or memoize it.

## Key points

- External store state is owned outside React, such as a library store or browser subscription source, and components subscribe to it for updates.
- Reading a mutable store directly during render is unsafe because it can change while React prepares a render, so components can see inconsistent versions.
- Tearing is when parts of one visible UI reflect different versions of shared state because reads were not synchronized.
- `useSyncExternalStore` is the standard way to subscribe to an external store and read consistent snapshots even when updates can be concurrent.

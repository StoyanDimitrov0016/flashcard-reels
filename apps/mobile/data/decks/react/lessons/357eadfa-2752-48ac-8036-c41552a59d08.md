# Reducers and refs

Components remember things in more than one way. `useState` is the everyday tool, `useReducer` organizes more complex state changes, and `useRef` holds values that should persist without affecting what is rendered. Choosing the right one keeps components predictable.

## useState

`useState` gives a component a **retained value** and a **setter**. The value survives between renders, and calling the setter **queues an update** and requests a future render with the new value.

```jsx
const [isOpen, setIsOpen] = useState(false);
```

This covers most local state: a toggle, the text of an input, the selected tab.

## useReducer

As state grows, update logic tends to spread across many event handlers. `useReducer` **centralizes state transitions** in one function called a **reducer**. The reducer receives the **current state** and an **action** describing what happened, and returns the **next state**. Components no longer set values directly; they **dispatch** actions.

```jsx
function reducer(state, action) {
  switch (action.type) {
    case "added":
      return { ...state, items: [...state.items, action.item] };
    case "cleared":
      return { ...state, items: [] };
    default:
      return state;
  }
}

const [state, dispatch] = useReducer(reducer, { items: [] });
dispatch({ type: "added", item: "Milk" });
```

## When a reducer is the better choice

Several `useState` calls work well for independent values. A reducer is preferable when:

- **Multiple fields change together**, such as `status`, `data`, and `error` during a request.
- Transitions are naturally **action-oriented**: "added", "removed", "submitted", "reset".
- The update logic is **complex** enough to benefit from one explicit function that works a bit like a **state machine**, listing every way the state can change.

A reducer also makes state logic easy to test, because it is just a function from inputs to output.

## Rules for reducers

A reducer must be **pure**. It must **not mutate** the existing state; it builds and returns a new object instead. It must not perform **side effects** such as network requests, timers, or logging to external services. Like render code, React may call it more than once, so it should only compute the next state from its inputs.

## Refs

A **ref** is a **stable object** with a single `.current` field. You can read and write `.current` freely, and the value persists across renders. Unlike state, **changing a ref does not cause a render**.

```jsx
const intervalRef = useRef(null);

function start() {
  intervalRef.current = setInterval(tick, 1000);
}

function stop() {
  clearInterval(intervalRef.current);
}
```

`useRef` returns **the same ref object** on every render for the whole lifetime of that component instance. That stability is what makes it useful as a place to keep things.

## When to use a ref instead of state

Use a ref for values that **imperative code** needs but that **rendering does not**:

- **DOM nodes**, for focusing an input, scrolling, or measuring size.
- **Timer handles** and subscription IDs, so you can clear them later.
- Mutable bookkeeping, such as a previous value or a flag that tracks whether something already happened.

```jsx
function SearchBox() {
  const inputRef = useRef(null);
  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current.focus()}>Focus</button>
    </>
  );
}
```

## Why UI data should not live only in a ref

If a value appears on screen, keep it in **state**. Changing a ref does **not request a render**, so the screen will not update to show the new value. It may appear later by accident, when some unrelated state change causes a render, which makes the bug confusing to track down.

A simple test: if the JSX reads it, it should be state. If only event handlers or Effects read it, a ref may be the right fit. As a related rule, avoid reading or writing `ref.current` during rendering, except for lazy initialization, because refs are not part of the render snapshot.

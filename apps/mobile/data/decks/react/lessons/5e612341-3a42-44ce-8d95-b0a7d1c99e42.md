# Reconciliation and pure rendering

Every render produces a fresh element tree, but React does not rebuild the screen from scratch. It compares the new tree with the previous one and reuses whatever it can. Understanding how that comparison works explains conditional rendering, list keys, when state is kept or reset, and why render code must be pure.

## Conditional rendering

**Conditional rendering** means returning different element trees depending on the current props or state. There is no special template syntax; you use ordinary JavaScript such as `if`, the ternary operator, or `&&`.

```jsx
function Inbox({ messages }) {
  if (messages.length === 0) {
    return <p>No messages</p>;
  }
  return <MessageList messages={messages} />;
}
```

## Keys give items identity

When you render a list, React needs to know which item is which from one render to the next. A **key** gives each sibling element a **stable identity**, so React can match old and new items when items **move, appear, or disappear**.

```jsx
<ul>
  {todos.map((todo) => (
    <TodoItem key={todo.id} todo={todo} />
  ))}
</ul>
```

A good key is **stable** and **unique among its siblings** for the whole lifetime of the item it represents. An ID from a database is the typical choice. Keys only need to be unique within one list, not across the entire app.

**Array indexes** make poor keys when the list can change. If an item is inserted at the top, every index shifts by one, and React matches each position with the wrong logical item. Any local state inside those rows, such as a half-typed input or an expanded panel, ends up attached to the **wrong item**. Index keys are acceptable only for lists that never reorder, insert, or delete.

Keys also work outside lists. When a component's **key changes**, React treats it as a **different instance**: it **unmounts** the old subtree and **mounts** a new one with fresh local state. This is a clean way to reset a form when the user switches to a different record:

```jsx
<ProfileForm key={userId} userId={userId} />
```

## Reconciliation

**Reconciliation** is React's process of comparing the newly rendered element tree with the previous one to decide which component instances and host nodes, such as DOM elements, can be **reused** and which must be created or removed.

Two rules drive it.

First, if the **element type changes** at the same position, for example from `<div>` to `<section>` or from `<LoginForm>` to `<SignupForm>`, React **replaces that whole subtree**. The old and new elements represent different things, so everything below that point is torn down and its local state is reset.

Second, React associates local state with a **component type and its position** in the rendered tree. If the same component stays at the same position, its state is usually **preserved**, even if its props change. State belongs to the position in the tree, not to the variable or JSX line that produced it.

```jsx
// Same type, same position: Counter keeps its state
{
  isFancy ? <Counter color="gold" /> : <Counter color="gray" />;
}
```

## Render and commit

React updates the UI in two phases.

- In the **render phase**, React calls your components and computes the next UI. Nothing on screen changes yet. React may run render code **more than once**, or start a render and **abandon** the result, for example when a more urgent update arrives.
- In the **commit phase**, React applies the chosen changes to the host environment, such as the DOM. It also **updates refs** and runs **layout effects** at this point, before the browser paints. Regular effects run after the commit.

## Purity

Because render code can be repeated or thrown away, it must be **pure**. A pure component, given the same **props, state, and context**, returns the same UI description every time, and it does not change anything outside itself while rendering.

**Side effects during render** are unsafe for exactly that reason. If a component sends an analytics event, writes to a global variable, or starts a network request while rendering, that effect can run **several times**, or run for a render that is **never committed** to the screen.

```jsx
let renderCount = 0;

function Impure() {
  renderCount++; // side effect during render: avoid
  return <p>{renderCount}</p>;
}
```

Side effects belong in **event handlers**, which run in response to a specific user action, or in **Effects**, which run after a commit. Render itself should only calculate.

# Synchronizing with Effects

Rendering must be pure, and event handlers only run when the user does something. But some work is caused by rendering itself: when a chat room screen is visible, it should be connected to the chat server, whether or not anyone has clicked anything. Connecting during render would be a side effect. Effects give that kind of work a proper place, after React has committed the UI.

## What useEffect is for

**`useEffect`** synchronizes a committed React component with an **external system**, such as a network connection, a browser API, a timer, or a non-React widget. "External" means anything React does not control. The Effect's job is to make that system match what the component currently renders.

```jsx
import { useEffect, useState } from "react";

function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("message", (msg) => setMessages((prev) => [...prev, msg]));
    connection.connect();
    return () => {
      connection.disconnect();
    };
  }, [roomId]);

  return (
    <ul>
      {messages.map((m) => (
        <li key={m.id}>{m.text}</li>
      ))}
    </ul>
  );
}
```

The function passed to `useEffect` is the **setup**. It runs after the component's render has been committed, so the UI is already on screen. The function it returns is the **cleanup**. The array at the end lists the **dependencies**: the values from the component that the Effect uses.

## Cleanup

**Cleanup runs before the Effect is set up again** after relevant dependency changes, and **when the component unmounts**. Walk through `ChatRoom`:

1. It mounts with `roomId` "general". After commit, setup connects to "general".
2. The user switches to "music". React renders, commits, then runs the old cleanup (disconnect from "general"), then runs setup with the new value (connect to "music").
3. The user leaves the chat screen. React runs the last cleanup, disconnecting from "music".

Every setup is matched by exactly one cleanup, and the cleanup always sees the values from its own render.

## Why subscriptions need cleanup

An Effect that **subscribes** must also **unsubscribe**. Without cleanup, old subscriptions **keep delivering events** after props change or after unmount, causing **duplicate work**, **stale updates**, or **leaks**. If `ChatRoom` never disconnected, switching rooms would leave it connected to both rooms, messages from "general" would keep appearing in "music", and a connection would stay open after the screen was gone. The same applies to event listeners, intervals, and observers: whatever setup starts, cleanup should stop or undo.

## The dependency array

The second argument decides when React re-synchronizes:

- **A list of values**, like `[roomId]`: setup runs after the first commit and again after any commit where one of those values changed (compared with `Object.is`), with cleanup in between.
- **An empty array** `[]`: this **declares that the Effect does not read reactive values that can change**. It normally sets up **after mount** and cleans up **on unmount**. In development, Strict Mode may exercise an extra setup-and-cleanup cycle, as the next lesson explains.
- **No array at all**: the Effect is **scheduled after every committed render** of that component.

## Every reactive value belongs in the dependencies

**Reactive values** are props, state, and anything calculated from them in the component body. They can change between renders. If an Effect reads one, it must appear in the dependencies. Otherwise the Effect **keeps using values captured by an older render** instead of re-synchronizing when those values change.

Suppose `ChatRoom` declared `[]` while still reading `roomId`. It would connect to the first room and stay there forever. The heading would say "music" while messages still come from "general", because the Effect never learned that `roomId` changed.

The React linter (`eslint-plugin-react-hooks`) checks this rule. When it complains, change the code so the Effect needs fewer values, rather than hiding values from the array.

## Stale closures

The bug above has a name. A **stale closure** is a callback or Effect that reads props or state **captured from an older render** when the programmer expected current values. Every render creates new functions, and each closes over that render's snapshot. A function kept from an earlier render still sees earlier values.

```jsx
function AutoCounter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // stale: count is always 0 here
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>;
}
```

The interval callback was created during the first render, when `count` was `0`, and the empty array means it is never replaced. Every second it sets the count to `0 + 1`, so the display sticks at 1. Adding `count` as a dependency fixes it, at the cost of resetting the interval every tick. The better fix removes the dependency altogether with a functional update, `setCount(c => c + 1)`, which reads the latest state instead of the captured one. React 19.2 also added `useEffectEvent` for reading the latest values inside an Effect without making them dependencies.

## useLayoutEffect

`useEffect` usually runs after the browser has painted. For most work that is ideal, because it does not delay the screen. But sometimes you need to measure something and adjust before the user sees it, like positioning a tooltip based on its own height.

**`useLayoutEffect`** runs **after DOM mutations but before the browser paints**, allowing code to **measure layout** or **synchronously adjust the DOM** when a visible intermediate frame would be wrong.

```jsx
function Tooltip({ targetRect, children }) {
  const ref = useRef(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    const height = ref.current.getBoundingClientRect().height;
    const above = targetRect.top - height;
    setTop(above < 0 ? targetRect.bottom : above);
  }, [targetRect]);

  return (
    <div ref={ref} className="tooltip" style={{ top }}>
      {children}
    </div>
  );
}
```

React commits the tooltip, the layout Effect measures its height and updates `top`, and React re-renders synchronously, all before the browser paints. The user only ever sees the tooltip in its final position. With `useEffect`, they might see it flash in the wrong place for a frame.

## Use useLayoutEffect sparingly

The price is that work in `useLayoutEffect` **blocks painting**. **Expensive synchronous logic** there delays visible updates and makes the interface feel unresponsive. Start with `useEffect`, and switch only for measurements that cause a visible flicker.

## Key points

- `useEffect` synchronizes a committed component with an external system such as a connection, browser API, timer, or non-React widget.
- Cleanup runs before the Effect sets up again after a dependency change, and when the component unmounts.
- An Effect that subscribes must unsubscribe, or old subscriptions cause duplicate work, stale updates, or leaks.
- An empty dependency array declares no changing reactive values: set up after mount, clean up on unmount, with possible extra development cycles.
- With no dependency array, the Effect runs after every committed render.
- Reactive values read by an Effect must be dependencies, or it keeps using values from an older render.
- A stale closure reads props or state captured from an older render when current values were expected.
- `useLayoutEffect` runs after DOM mutations but before paint, for measuring layout; use it sparingly because it blocks painting.

# Transitions

Not every update is equally urgent. When a user types in a search box, the letter must appear immediately; if it lags, the app feels broken. The filtered list below it can take a moment longer without anyone minding. By default React treats every state update as urgent and renders it to completion before handling the next keystroke. Transitions let you tell React which updates can wait.

## Urgent and non-urgent updates

**Urgent updates** reflect direct interaction: typing, clicking, pressing. Users expect them to show within a frame or two. **Non-urgent** updates move the UI from one view to another: showing search results, switching tabs, rendering a new page. Users tolerate a short delay, as long as the app stays responsive while it happens.

Rendering is normally synchronous: once React starts rendering an update, it finishes before doing anything else. If rendering the results list takes 200 ms, every keystroke during those 200 ms waits. Concurrent rendering, which transitions opt into, changes that.

## startTransition

**`startTransition`** marks the state updates inside it as **non-urgent**, so React can **keep urgent interactions responsive** while rendering the transition **in the background**:

```jsx
import { startTransition, useState } from "react";

function ProductSearch({ products }) {
  const [text, setText] = useState("");
  const [query, setQuery] = useState("");

  function handleChange(e) {
    setText(e.target.value); // urgent: update the input now
    startTransition(() => {
      setQuery(e.target.value); // non-urgent: results can wait
    });
  }

  return (
    <>
      <input value={text} onChange={handleChange} />
      <ProductGrid products={products} query={query} />
    </>
  );
}
```

On each keystroke, React first renders the urgent `text` update, so the input shows the letter immediately. Then it starts rendering the transition that updates `query`. That render is **interruptible**: React works on it in small pieces, checking between components whether something more urgent arrived. If the user types another letter before the grid is done, React abandons the unfinished grid render, handles the keystroke, and starts the transition again with the latest query. The user sees the old results until the new ones are ready, never a frozen input.

Only state updates can be marked this way ("supported" updates: state setters called synchronously inside the function). You cannot use a transition to control a text input's own value, since that must stay urgent. In React 19, the function passed to `startTransition` can also be async; that is the basis of Actions, covered later.

Transitions also interact with Suspense: if a transition causes a component to suspend, React keeps showing the current content instead of replacing already visible UI with a fallback.

## What a transition does not do

"In the background" is easy to misread. **A transition does not make slow computation free** or **move JavaScript work to another thread**. React still runs every component on the main thread. What it gains is the ability to _pause between components_ and let urgent work cut in.

That means **heavy synchronous work can still block the main thread**. If a single component runs a 300 ms loop during render, React cannot interrupt the middle of that loop; the page freezes for 300 ms, transition or not. Transitions help most when the slow part is many components each doing a reasonable amount of work. For one giant calculation, the fixes are different: make it cheaper, memoize it, move it to a Web Worker, or do less of it.

## useTransition

**`useTransition`** **starts transition updates** and **exposes whether transition work is pending**, so the UI can reflect that a non-urgent update is in progress:

```jsx
import { useTransition, useState } from "react";

function TabBar() {
  const [tab, setTab] = useState("overview");
  const [isPending, startTransition] = useTransition();

  function selectTab(nextTab) {
    startTransition(() => {
      setTab(nextTab);
    });
  }

  return (
    <>
      <nav style={{ opacity: isPending ? 0.6 : 1 }}>
        <button onClick={() => selectTab("overview")}>Overview</button>
        <button onClick={() => selectTab("analytics")}>Analytics</button>
      </nav>
      {tab === "overview" ? <Overview /> : <Analytics />}
    </>
  );
}
```

Clicking "Analytics" starts a transition. While `Analytics` is rendering (or loading, if it suspends), `isPending` is `true`, the tab bar dims, and the old tab stays on screen and stays interactive. If the user clicks "Overview" before Analytics finishes, React abandons the pending work. When the new tab is ready, it appears and `isPending` returns to `false`.

The standalone `startTransition` function works anywhere, including outside components; the Hook version adds the `isPending` flag.

## useDeferredValue

Sometimes you do not control the state update, for example because a value arrives as a prop. **`useDeferredValue`** lets a **non-urgent part of the UI lag behind a rapidly changing value**, allowing **urgent updates such as typing to render first**:

```jsx
import { useDeferredValue, useState } from "react";

function ProductSearch({ products }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        <ProductGrid products={products} query={deferredQuery} />
      </div>
    </>
  );
}
```

When the user types, React first renders with the new `query` but the old `deferredQuery`, so the input updates immediately and the grid shows the previous results. Then React renders again in the background with `deferredQuery` caught up, and that render is interruptible exactly like a transition. The `isStale` comparison dims the grid while it is behind. For this to help, `ProductGrid` should be wrapped in `memo`, so the urgent render can skip it when its `query` prop has not changed yet.

## Common mistakes

- **Expecting a transition to speed up one slow component.** It adds interruptibility, not raw speed or threads.
- **Wrapping an input's own value in a transition.** The field would lag behind typing.
- **Using `useDeferredValue` without memoizing the slow child.** The urgent render still renders it with the old value.

## Key points

- `startTransition` marks supported state updates as non-urgent so urgent interactions stay responsive while the transition renders in the background.
- Transition renders are interruptible: React can abandon them when an urgent update arrives.
- A transition does not make slow computation free or move work to another thread; heavy synchronous work still blocks the main thread.
- `useTransition` starts transition updates and exposes an `isPending` flag for showing that non-urgent work is in progress.
- `useDeferredValue` lets a non-urgent part of the UI lag behind a rapidly changing value so urgent updates like typing render first.

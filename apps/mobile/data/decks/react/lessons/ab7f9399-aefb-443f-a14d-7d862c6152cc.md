# Strict Mode, Suspense, and the server

This lesson covers the tools React gives you for the parts of an app that are not simply "render and show": checking your code during development, handling errors and loading states, splitting code, and rendering on the server before the browser takes over.

## Strict Mode

**Strict Mode** is a development-only wrapper that adds extra checks. It intentionally **exercises components and effects** in unusual ways so hidden problems surface early. For example, it renders components an extra time to reveal **impure rendering**, and it runs an extra **setup and cleanup** cycle for effects to reveal **missing cleanup**.

That is why an effect can appear to **run twice** in development. React mounts the component, runs setup, runs cleanup, then runs setup again. If your cleanup correctly reverses the setup, the user sees no difference. If something breaks, such as two chat connections staying open, the check has found a real bug that would otherwise appear when a component remounts. Production does not simply run every effect twice; these checks exist only in development.

## Error boundaries

An **error boundary** is a component that catches errors thrown by its descendants **during rendering** or lifecycle processing, and shows **fallback UI** instead of a blank screen.

It does not catch everything. Errors thrown in **event handlers**, in asynchronous code such as a `setTimeout` callback or a promise chain outside rendering, and errors in the boundary itself are not caught. Handle those with ordinary `try`/`catch` or by moving the error into state. React has no Hook for error boundaries; they are still written as class components, or taken from a small library.

## Suspense

**Suspense** lets part of the tree declare that it **cannot render yet** because something it needs, such as code or data, is still loading. React shows the nearest **fallback** until the resource is ready, then shows the real content.

```jsx
<Suspense fallback={<Spinner />}>
  <Comments postId={postId} />
</Suspense>
```

The loading state is declared once, at the boundary, instead of being handled with flags inside every component.

## Code splitting and lazy

**Code splitting** divides your JavaScript into **chunks** that are loaded **on demand**. Users download what the first screen needs, instead of every feature in the app before anything appears.

`lazy` applies this to components. It **defers loading** a component's module until React first needs to render it. While the module downloads, the component **suspends**, and the surrounding Suspense boundary shows its fallback.

```jsx
const Settings = lazy(() => import("./Settings"));
```

## Server-side rendering

**Server-side rendering (SSR)** produces **HTML on the server** for the initial request. Users see meaningful content, and search engine crawlers receive real markup, before the client JavaScript has finished loading.

The trade-off: SSR can improve how quickly content appears, but it adds **server work**, requires **coordinating data** between server and client, adds **hydration cost** in the browser, and restricts **browser-only code**. Anything that touches `window` or `localStorage` cannot run during the server render.

## Hydration

After the server HTML arrives, React runs on the client and **hydrates** it: it attaches event handlers and state to the **existing markup** instead of throwing it away and rebuilding the page.

To do that, React expects its first client render to produce exactly the same output as the server did. A **hydration mismatch** happens when they differ. Common causes are render logic that depends on the **current time**, **random values**, **browser-only state** such as window size or saved preferences, or **different data** on each side.

```jsx
// Mismatch: the server and client clocks disagree
<p>Rendered at {new Date().toLocaleTimeString()}</p>
```

That is why initial renders must be **deterministic**. Matching output lets React safely attach to the server markup. Divergence can trigger **warnings**, force React to **discard** the server markup and render that part again on the client, or leave the UI in an incorrect state. Values that only exist in the browser should be read after hydration, for example in an effect.

## Server Components

A **React Server Component** renders **only on the server**. It can read server-side resources directly, such as a database or the file system, and its implementation is **never sent to the client bundle**. Only its rendered output travels to the browser.

Server Components cannot use state, effects, or event handlers. Interactive behavior still requires **Client Components**, marked in frameworks with the `"use client"` directive at the top of a file. That directive marks a **client boundary**: the point where browser-only interactivity, state, effects, and event handlers are needed. Everything imported below it is sent to the browser, so client JavaScript stays limited to the interactive parts of the tree while the rest remains on the server.

```jsx
"use client";

export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return <button onClick={() => setLiked(!liked)}>Like</button>;
}
```

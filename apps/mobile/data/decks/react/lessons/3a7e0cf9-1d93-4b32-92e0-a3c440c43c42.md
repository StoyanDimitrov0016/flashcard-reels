# Components and state

React builds user interfaces out of small, reusable pieces. Each piece describes what should be on screen for the data it has, and React takes care of turning that description into real updates. This lesson covers the building blocks: components, props, JSX, elements, rendering, and the state that makes a component change over time.

## Components, props, and JSX

A **component** is a JavaScript function that receives **props** and returns React elements, usually written as JSX. Props are the component's inputs. A parent passes them to a child, and the child uses them to decide what UI to return. Props are **read-only**: a component should never modify the props it receives.

```jsx
function Greeting({ name }) {
  return <h1>Hello, {name}</h1>;
}

<Greeting name="Ada" />;
```

**JSX** is the markup-like syntax in that example. It lets you describe a tree of UI inside JavaScript, but it is not HTML. Build tooling transforms each JSX tag into a JavaScript call that creates an element description.

## Elements are descriptions

The result of that call is a **React element**: a plain, **immutable** object describing what should appear, with a **type** (such as `"h1"` or `Greeting`), **props**, and **children**. An element is not a DOM node. It is a lightweight description that React reads later to decide what the real screen should look like.

## Rendering

**Rendering** means React calls your components to compute the next element tree. Rendering by itself changes nothing on screen. Afterward, React **commits** the necessary host updates, such as creating, changing, or removing DOM nodes, so the screen matches the new tree.

A component renders again for three main reasons:

- Its own **state** was updated.
- Its **parent rendered** and included it in the output again.
- A **context** value it reads has changed.

## State and snapshots

**State** is data that React keeps for a particular component instance between renders. A normal local variable is recreated on every call, but state survives. Calling the state setter asks React for a new render with the new value.

Each render sees a **snapshot** of state. Calling a setter does not change the variable in the current render; it **queues an update** for a future render.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // still the old value
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

Because of snapshots, calling `setCount(count + 1)` three times in one handler still adds only one: every call reads the same `count`. A **functional update** fixes this. Passing a function like `setCount(c => c + 1)` tells React to compute the next value from the **latest queued state**, so each update builds on the previous one.

React also **batches** updates. When several state updates happen together, React processes them as a group and renders once, instead of producing a separate intermediate screen for each.

## Treat state as immutable

When state holds objects or arrays, replace them instead of changing them in place:

```jsx
setTodos([...todos, newTodo]); // new array
setUser({ ...user, name: "Ada" }); // new object
```

A new object gives React and memoization tools a reliable signal that something changed, because they compare by **identity**. Mutating the existing object keeps the same reference, so **shallow comparisons** can miss the change, and older render snapshots that still point to that object are silently corrupted.

## Controlled and uncontrolled inputs

Form inputs can keep their value in one of two places:

- A **controlled input** shows a value that comes from React state and reports every edit through an event handler, which updates that state. React is the single source of truth.
- An **uncontrolled input** keeps its current value in the **DOM**. Your code reads it when needed, typically through a ref or when the form is submitted.

```jsx
<input value={text} onChange={(e) => setText(e.target.value)} />
```

## Where state should live

When two components need the same data, **lift state up**: move it to their **nearest common ancestor** and pass it down through props. Both children then read one consistent **source of truth**.

Avoid storing what you can compute. **Derived state** is any value that can be calculated from existing props or state, such as a filtered list or a full name built from first and last name. Calculate it during render instead of storing it in its own state variable.

Storing the same fact twice creates a trap. With **duplicated state**, every update must keep all copies in sync, and missing a single update leaves the component showing contradictory values.

## One-way data flow

Data in React flows in one direction. Parents pass data **down** through props. Children cannot change a parent's state directly; they **request changes** by calling a callback prop or dispatching an action. This **one-way data flow** keeps it explicit which component owns each piece of state.

```jsx
function Parent() {
  const [on, setOn] = useState(false);
  return <Toggle on={on} onToggle={() => setOn(!on)} />;
}
```

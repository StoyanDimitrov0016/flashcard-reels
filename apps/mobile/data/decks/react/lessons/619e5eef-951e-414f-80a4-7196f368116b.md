# Rendering on the server

A React app that renders only in the browser sends an almost empty HTML page, then a JavaScript bundle, and the user sees nothing useful until that bundle downloads, runs, and fetches data. On a slow phone that can take seconds, and a search crawler may see no content at all. Rendering on the server attacks this problem, first by producing HTML ahead of time, and more recently by letting whole components run only on the server.

## Server-side rendering

**Server-side rendering** (SSR) produces **HTML on the server for an initial request**, so **users and crawlers** receive **meaningful markup before client JavaScript finishes loading**. The server runs your components, turns the resulting tree into an HTML string (or stream), and sends it. The browser can display the page immediately; the text is readable and the layout is in place.

That HTML is not interactive yet, though. Buttons do nothing until React runs in the browser.

## Hydration

**Hydration** is the step that brings the page to life. It **attaches React behavior to HTML that was already rendered on the server**, **reusing the existing markup** instead of rebuilding the whole page from scratch.

```jsx
// Server (simplified)
import { renderToPipeableStream } from "react-dom/server";
renderToPipeableStream(<App />).pipe(response);

// Client
import { hydrateRoot } from "react-dom/client";
hydrateRoot(document.getElementById("root"), <App />);
```

On the client, `hydrateRoot` renders `App` again, walks the existing DOM alongside the rendered tree, and attaches event handlers and state to the nodes that are already there. Nothing is recreated. From then on, the app behaves like any client-rendered React app. In practice, frameworks such as Next.js set all of this up for you.

## Why initial renders must be deterministic

Hydration only works if the client's first render produces **the same output as the server**. **Matching output lets React safely attach to server-rendered markup.** **Divergence** can trigger **warnings**, **discarded markup** (React throws away the server HTML for that part and re-renders it on the client, losing the benefit), or **incorrect UI assumptions**, such as event handlers attached to the wrong nodes.

## Hydration mismatches

A **hydration mismatch** occurs when **the client's initial rendered output differs from the server HTML**. Common causes are render logic that depends on **time**, **randomness**, **browser-only state**, or **different data**:

```jsx
function Greeting() {
  const hour = new Date().getHours(); // server and browser clocks and time zones differ
  const isMobile = typeof window !== "undefined" && window.innerWidth < 600; // browser-only
  return (
    <p>
      {hour < 12 ? "Good morning" : "Good afternoon"}
      {isMobile ? "!" : "."}
    </p>
  );
}
```

The server in UTC may render "Good afternoon." while a user in Tokyo renders "Good morning!" during hydration. Other frequent culprits are `Math.random()` IDs (use `useId` instead), reading `localStorage` during render, and the server and client fetching different data.

The fix is to render the same thing on both sides first, then update on the client:

```jsx
function Greeting() {
  const [hour, setHour] = useState(null);

  useEffect(() => {
    setHour(new Date().getHours());
  }, []);

  if (hour === null) return <p>Hello.</p>;
  return <p>{hour < 12 ? "Good morning." : "Good afternoon."}</p>;
}
```

The server and the hydrating client both render "Hello.", so hydration matches. Effects do not run on the server, so only after hydration does the Effect read the browser's clock and update the greeting.

## The trade-offs of SSR

**Server-side rendering can improve initial content delivery, but it adds server work**, **data coordination**, **hydration cost**, and **constraints around browser-only code**. Every request now renders on a server you must run and scale. Data must be fetched on the server and passed to the client so both render the same thing. The browser still downloads and runs the JavaScript for every component in order to hydrate, so the page can look ready before it responds to clicks. And code that touches `window` or `document` must be kept out of render.

## Server Components

That last cost, shipping and hydrating every component, is what **React Server Components** address. Conceptually, a **Server Component** **renders on the server** and can **access server-side resources**, such as a database or the file system, **without sending its component implementation to the client bundle**. Only its rendered output travels to the browser.

```jsx
// ProductPage.jsx (Server Component: the default in an RSC framework)
import { db } from "./db.js";
import AddToCartButton from "./AddToCartButton.jsx";

export default async function ProductPage({ id }) {
  const product = await db.products.find(id);
  return (
    <article>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <AddToCartButton productId={product.id} />
    </article>
  );
}
```

```jsx
// AddToCartButton.jsx
"use client";

import { useState } from "react";

export default function AddToCartButton({ productId }) {
  const [added, setAdded] = useState(false);
  return (
    <button
      onClick={() => {
        addToCart(productId);
        setAdded(true);
      }}
    >
      {added ? "Added" : "Add to cart"}
    </button>
  );
}
```

`ProductPage` is an async component that queries the database directly; no API endpoint, no loading state, and neither the query code nor the database library is ever sent to the browser. Server Components can also run once at build time for static content. What they cannot do is be interactive: no state, no Effects, no event handlers. **Interactive client behavior still requires Client Components.**

## Client component boundaries

The `"use client"` directive at the top of `AddToCartButton.jsx` marks a **client component boundary**. In a server-component architecture, these boundaries mark **where browser-only interactivity, state, effects, and event handlers are needed**, **limiting client JavaScript to the interactive parts of the tree**.

Everything imported from a `"use client"` file becomes part of the client bundle, and that component is server-rendered to HTML and then hydrated like a regular SSR component. Everything above the boundary stays on the server. In the example, the heading and description cost the browser no JavaScript; only the small button does. The skill is to push boundaries down to the leaves: keep pages and layouts as Server Components and make only the interactive pieces Client Components. Props passed across the boundary must be serializable, such as strings, numbers, plain objects, JSX, or Promises that a Client Component can read with `use`.

## Key points

- Server-side rendering produces HTML on the server for the initial request, so users and crawlers get meaningful markup before client JavaScript loads.
- SSR improves initial content delivery but adds server work, data coordination, hydration cost, and constraints on browser-only code.
- Hydration attaches React behavior to server-rendered HTML, reusing the existing markup instead of rebuilding the page.
- A hydration mismatch occurs when the client's initial render differs from the server HTML, often due to time, randomness, browser-only state, or different data.
- Server and client initial renders must be deterministic; divergence can cause warnings, discarded markup, or incorrect UI assumptions.
- A Server Component renders on the server and can access server resources without sending its implementation to the client bundle; interactivity requires Client Components.
- Client component boundaries mark where interactivity, state, Effects, and event handlers are needed, limiting client JavaScript to those parts.

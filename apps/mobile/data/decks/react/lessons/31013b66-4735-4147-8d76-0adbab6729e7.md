# Building accessible overlays

Modals, dropdown menus, tooltips, and toasts are some of the hardest components to get right. Visually, they must float above everything else, even when they are declared deep inside a scrolling card. Functionally, they must work for everyone, including people using a keyboard or a screen reader. This lesson covers both halves: what "working" means for a component, and how portals let an overlay escape its container without escaping React.

## Accessibility is part of correctness

A component is not correct just because it looks right. **Accessibility is part of component correctness**: a visually correct component can still be unusable if its **semantics**, **keyboard behavior**, **focus management**, **accessible names**, or **state** are not exposed to assistive technology.

Consider a "button" built from a `div` with an `onClick`. With a mouse, it looks and works fine. But a screen reader announces it as plain text, not a button. It is not in the tab order, so a keyboard user cannot reach it, and pressing Enter or Space does nothing. For those users the feature does not exist. That is a bug in the same sense as a crash, just one your mouse-driven manual test never hits.

## Semantic HTML before ARIA

The fix is usually not more code, but the right element. **Prefer semantic HTML before adding ARIA**: native elements already provide **browser-defined semantics and interaction behavior**. A real `<button>` is focusable, activates on Enter and Space, is announced as a button, and supports `disabled`, all for free. The same goes for `<a href>`, `<input type="checkbox">`, `<label>`, `<select>`, and headings.

ARIA attributes, such as `role="button"` or `aria-expanded`, can **describe missing semantics** to assistive technology, but ARIA **does not automatically implement keyboard or control behavior**. Adding `role="button"` to a `div` makes a screen reader call it a button, yet it still is not focusable and still ignores the keyboard, so you would have to add `tabIndex`, key handlers, and disabled logic yourself. ARIA is for cases no native element covers, and custom overlays are one of them.

## The problem overlays face

Suppose a product card has `overflow: hidden` to crop its image, and a "Delete" button inside it opens a confirmation modal. If the modal's DOM nodes are rendered inside the card, the card crops the modal too. A parent with a `transform` or its own `z-index` creates a stacking context that can trap the modal behind other content, no matter how high its own `z-index` is. CSS rules applied to ancestors leak into the overlay.

## Portals

A **portal** renders React children into a **different DOM container** while keeping them in the **same React tree** for **context** and **React event propagation**. You create one with `createPortal` from `react-dom`:

```jsx
import { createPortal } from "react-dom";

function ConfirmDialog({ title, message, onConfirm, onCancel }) {
  return createPortal(
    <div className="backdrop">
      <div
        role="dialog"
        aria-modal="true"
        aria-labelledby="confirm-title"
        className="dialog"
        onKeyDown={(e) => {
          if (e.key === "Escape") onCancel();
        }}
      >
        <h2 id="confirm-title">{title}</h2>
        <p>{message}</p>
        <button autoFocus onClick={onCancel}>
          Cancel
        </button>
        <button onClick={onConfirm}>Delete</button>
      </div>
    </div>,
    document.body
  );
}

function ProductCard({ product, onDelete }) {
  const [confirming, setConfirming] = useState(false);
  return (
    <div className="card">
      <img src={product.imageUrl} alt="" />
      <h3>{product.name}</h3>
      <button onClick={() => setConfirming(true)}>Delete</button>
      {confirming && (
        <ConfirmDialog
          title="Delete product?"
          message={`${product.name} will be removed permanently.`}
          onConfirm={() => onDelete(product.id)}
          onCancel={() => setConfirming(false)}
        />
      )}
    </div>
  );
}
```

When `confirming` becomes true, `ProductCard` renders `ConfirmDialog`, but its DOM nodes are appended to `document.body`, outside the card. The card's `overflow: hidden` and stacking context no longer apply, so the dialog can cover the whole page.

## Why portals suit modals and overlays

That is the core benefit: portals let visual content **escape clipping or stacking constraints** of an ancestor DOM container **without disconnecting it from the React component tree**. In React's eyes, `ConfirmDialog` is still a child of `ProductCard`. It receives props from it, its state lives in it, it unmounts when the card stops rendering it, and it can read any context provided above the card, such as the theme or the current language.

## Accessibility inside the dialog

The example also applies the first half of this lesson. The dialog uses native `<button>` and `<h2>` elements for everything a native element can do. ARIA fills the gaps no element covers for this custom dialog: `role="dialog"` announces it as a dialog, `aria-modal="true"` tells assistive technology that content behind it is inert, and `aria-labelledby` gives it an accessible name from its heading. `autoFocus` moves focus into the dialog when it opens, and Escape closes it. A production dialog would also trap Tab inside the dialog and return focus to the Delete button on close; the native `<dialog>` element opened with `showModal()` provides much of this behavior itself, which is another reason to check for a semantic element first.

## How events propagate through portals

Because a portal stays in the React tree, **React event propagation follows the React tree**, not only the physical DOM parent chain. An event fired inside a portal **can reach React ancestors outside the portal container**.

```jsx
<div className="card" onClick={() => console.log("card clicked")}>
  <ConfirmDialog /* ... */ />
</div>
```

Clicking "Cancel" inside the dialog logs "card clicked", even though in the DOM the dialog sits under `body`, nowhere near the card. This is usually what you want, since the component relationship is what matters, but it can surprise you: a card that navigates on click would navigate when the user clicks inside its dialog. Call `e.stopPropagation()` in the dialog, or move the handler, when that bubbling is unwanted.

## Common mistakes

- **Clickable `div`s.** They lack focus, keyboard activation, and a role; use `<button>`.
- **ARIA as a fix-all.** A role describes behavior; it does not implement it.
- **Assuming portal events stop at the DOM boundary.** They bubble to React ancestors.
- **Forgetting focus.** A modal that does not move focus in and restore it on close strands keyboard users.

## Key points

- Accessibility is part of correctness: a visually correct component is unusable if semantics, keyboard behavior, focus, names, or state are not exposed to assistive technology.
- Prefer semantic HTML: native elements provide built-in semantics and interaction; ARIA describes semantics but does not implement keyboard or control behavior.
- A portal renders children into a different DOM container while keeping them in the same React tree for context and event propagation.
- Portals let modals and overlays escape ancestor clipping and stacking constraints without leaving the React component tree.
- React events propagate along the React tree, so an event inside a portal can reach React ancestors outside the portal container.

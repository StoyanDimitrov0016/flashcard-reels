# How reconciliation preserves state

Every render produces a brand-new element tree, yet a text field keeps what you typed and a counter keeps its count. Somehow React decides which parts of the new tree are "the same thing" as parts of the old tree, so it can keep their state and reuse their DOM nodes. Knowing how it decides lets you predict when state survives, when it resets, and how to control both on purpose.

## Reconciliation

**Reconciliation** is React's process for comparing a newly rendered element tree with the previous one to decide which component instances and host nodes can be reused. Where an element matches what was there before, React keeps the existing instance, with its state, and updates only the props or DOM attributes that changed. Where it does not match, React throws the old part away and creates a new one.

React does not try to find the minimal edit between two arbitrary trees; that would be far too slow. Instead it relies on two cheap signals: **what type** of element it is and **where** it is in the tree.

## State belongs to a position in the tree

It is natural to think state lives "inside" a component, but React actually associates local state with a **component type and position in the rendered tree**. If the same component keeps rendering at the same position, React treats it as the same instance and preserves its state.

```jsx
function ScoreBoard({ isFancy }) {
  return <div>{isFancy ? <Counter fancy /> : <Counter />}</div>;
}
```

Toggling `isFancy` does not reset the counter. Both branches render a `Counter` as the first child of the `div`, so from React's point of view it is the same component at the same position that simply received a new `fancy` prop. What matters is the tree React sees, not where the JSX appears in your source code.

## Changing the type resets the subtree

The first signal is type. When an element type changes at the same tree position, React generally **replaces that subtree**, because the old and new elements represent different component or host types. The old instance unmounts, its state is destroyed, and everything below it is recreated from scratch.

```jsx
{
  isEditing ? <EditForm draft={draft} /> : <Preview draft={draft} />;
}
```

Switching between `EditForm` and `Preview` resets any local state inside them, because a different type now occupies that position. The same applies to host types: replacing a `<div>` wrapper with a `<section>` wrapper remounts all of its children and resets their state.

This also explains a rule you should always follow: never define a component inside another component. The inner function is re-created on every render, so each render produces a new type, and its state resets every time.

## Keys give list items identity

Position works well for fixed layouts, but lists are different. Items move, appear, and disappear, and the "third child" may be a different item from one render to the next. **Keys** give sibling elements stable identities across renders, so React can match old and new items when items move, appear, or disappear.

```jsx
function ContactList({ contacts }) {
  return (
    <ul>
      {contacts.map((contact) => (
        <ContactRow key={contact.id} contact={contact} />
      ))}
    </ul>
  );
}
```

With keys, React matches rows by `contact.id` instead of by index. If a contact is inserted at the top, React sees one new key and creates one new row, while every existing `ContactRow` keeps its state (an expanded panel, a half-typed note) and simply moves.

## What makes a good key

A good key is **stable and unique among siblings** for the lifetime of the underlying item, such as a **database ID**. Keys only need to be unique within one list, not across the whole app. They must not change between renders for the same item, which rules out values generated during render such as `Math.random()` or `crypto.randomUUID()` called inside `map`. Those produce a new key on every render, so every row remounts and loses its state every time. If your data has no IDs, generate them once when the item is created and store them with the item.

## Why array indexes can be poor keys

Using the array index as a key is tempting, and React uses the index by default when you give no key. It works while the list never changes order. But if items are **inserted, removed, or reordered**, index keys can make React associate existing component state with the **wrong logical item**.

Imagine a todo list where each row holds an uncontrolled checkbox or local "editing" state. With `key={index}`, deleting the first todo shifts every item up one position. The item that used to be at index 1 is now at index 0, so React gives it the state of the row that was at index 0, the deleted one. The text shows the right todo, but the checkbox or edit mode belongs to its old neighbor.

## Resetting state on purpose with a key

Keys work outside lists too. When a component's key changes, React treats it as a **different component instance**, unmounting the old subtree and mounting a new one with **fresh local state**. This turns keys into a tool for deliberate resets:

```jsx
function Messenger({ selectedContact }) {
  return <ChatComposer key={selectedContact.id} contact={selectedContact} />;
}
```

`ChatComposer` holds a draft message in state. Without the key, switching contacts would keep the same instance at the same position, and your half-written message to Alice would appear in the box for Bob. With `key={selectedContact.id}`, choosing another contact changes the key, React mounts a new composer, and the draft starts empty.

## Common mistakes

- **Random keys.** Generating keys during render remounts every item on every render.
- **Index keys on dynamic lists.** State ends up attached to the wrong item after inserts, deletions, or reordering.
- **Nesting component definitions.** A component declared inside another is a new type each render, so its state never survives.
- **Resetting with an Effect.** Clearing state in an Effect when a prop changes causes an extra render with stale values first. A key resets the whole subtree directly.

## Key points

- Reconciliation compares the new element tree with the previous one to decide which component instances and host nodes can be reused.
- React associates local state with a component type and position in the tree; the same component at the same position usually keeps its state.
- When the element type changes at the same position, React replaces that subtree and resets local state below it.
- Keys give siblings stable identities so React can match items when they move, appear, or disappear.
- A good key is stable and unique among siblings for the item's lifetime, such as a database ID.
- Index keys can attach existing state to the wrong item when items are inserted, removed, or reordered.
- Changing a component's key unmounts the old subtree and mounts a new one with fresh state.

# Component state

Props let a parent configure a component, but many components need to change on their own: a counter increments, a menu opens, a form field fills with text. A regular local variable cannot do this. It is recreated every time the component function runs, and changing it does not tell React that the screen is out of date. State solves both problems, and the way React handles state updates explains many behaviors that surprise newcomers.

## What state is

**State** is data retained by React between renders for a particular component instance. "Instance" matters: if you render two `<Counter />` components, each one has its own, independent count. React stores the value outside your function and hands it back every time the component renders.

Updating state does a second job: it **requests a new render**. React will call the component again so it can describe the UI for the new value.

## useState

The **`useState`** Hook gives a component a retained value and a setter that queues updates and future renders.

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

`useState(0)` returns a pair. `count` is the current value, starting at `0` on the first render. `setCount` is the setter. Clicking the button calls `setCount(count + 1)`, React queues the update, renders `Counter` again, and this time `useState` returns `1`.

Functions whose names start with `use` are called Hooks. They let components "hook into" React features like state. Hooks have a few rules, covered in the lesson on custom Hooks; for now, call them at the top of your component.

## Each render sees a snapshot

Here is the most important idea about state. Each render receives a **snapshot** of state values. Within that render, `count` is a plain constant. Calling a setter **queues an update for a future render**; it does not mutate the variable that the current render already captured.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // logs 0, not 1
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

The log prints the old value because `handleClick` belongs to the render where `count` was `0`. The new value only exists in the next render, when React calls `Counter` again.

## Functional updates

Snapshots cause a classic bug when several updates depend on the previous value:

```jsx
function handleTripleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
```

This adds one, not three. Every line reads the same snapshot, so every line asks React to set the count to `0 + 1`.

A **functional update** solves this. Instead of a value, pass a function such as `setCount(c => c + 1)`. React puts the function in a queue and, when it processes the queue, calls it with the **latest queued state**, not the snapshot:

```jsx
function handleTripleClick() {
  setCount((c) => c + 1); // 0 -> 1
  setCount((c) => c + 1); // 1 -> 2
  setCount((c) => c + 1); // 2 -> 3
}
```

Use the functional form whenever the next state is calculated from the previous state, especially when several updates may be queued before the next render. It avoids reading a stale snapshot value.

## Batching

You might expect the three calls above to cause three renders. They do not. React **batching** groups multiple state updates and processes them together before committing the next UI. React waits until the event handler finishes, applies all queued updates in order, and renders once. This avoids unnecessary intermediate renders and prevents the screen from briefly showing a half-updated state.

Since React 18, batching is automatic everywhere: in event handlers, timeouts, promises, and native event listeners alike.

## Treat state as immutable

State can hold objects and arrays, and this is where one more rule comes in: treat state as **immutable**. Do not change an existing object or array in place. Create a new one with the change and pass that to the setter.

```jsx
function TodoList() {
  const [todos, setTodos] = useState([]);

  function addTodo(text) {
    // Wrong: todos.push({ id: crypto.randomUUID(), text });
    setTodos([...todos, { id: crypto.randomUUID(), text, done: false }]);
  }

  function toggle(id) {
    setTodos(todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  return (
    <ul>
      {todos.map((t) => (
        <li key={t.id} onClick={() => toggle(t.id)}>
          {t.done ? "[done] " : ""}
          {t.text}
        </li>
      ))}
    </ul>
  );
}
```

Clicking an item calls `toggle`, which builds a new array where only the clicked todo is replaced by a copy with `done` flipped. React renders again and shows the "[done]" marker.

There are two reasons for this rule. First, replacing changed objects gives React and memoization tools a reliable **identity** signal. They check whether a value changed by comparing references, a **shallow comparison**. If you mutate the old array and pass the same reference back, the comparison says "unchanged", and the update can be skipped entirely. Second, older renders still hold references to the previous state. Mutating it **corrupts prior render snapshots**, so code that closed over the old value suddenly sees data it never had.

## Common mistakes

- **Reading state right after setting it.** The variable still holds the current render's snapshot. Use the value you just computed, or read the new value in the next render.
- **Using `setX(x + 1)` for repeated or queued updates.** Prefer `setX(x => x + 1)` when the next value depends on the previous one.
- **Mutating then setting.** `todos.push(item); setTodos(todos)` passes the same reference, so React may not re-render and old snapshots are altered.

## Key points

- State is data React retains between renders for a particular component instance; updating it requests a new render.
- `useState` returns a retained value and a setter that queues updates and future renders.
- Each render sees a snapshot of state. A setter queues an update for a future render instead of mutating the current render's variable.
- A functional update such as `setCount(c => c + 1)` computes from the latest queued state, avoiding stale snapshot values when several updates depend on previous state.
- Batching groups multiple state updates and processes them together, avoiding unnecessary intermediate renders.
- Treat state as immutable: replacing objects and arrays gives a reliable identity signal, while mutation can hide changes from shallow comparisons and corrupt prior snapshots.

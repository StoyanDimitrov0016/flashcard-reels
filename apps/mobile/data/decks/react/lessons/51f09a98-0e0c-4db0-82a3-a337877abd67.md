# Optimizing performance

Knowing the optimization tools is the easy part. The hard part is knowing when to use them, and which problem you actually have. A slow screen might be slow because of rendering, a heavy calculation, a slow network request, or a huge JavaScript bundle, and each needs a different fix. This lesson is about working like an engineer: measure, find the real cost, fix it at the right level, and understand the price of the fix.

## Measure before optimizing

**Whether React performance work is necessary** should be decided by **measuring user-visible latency and profiling data first**. Optimize components or data flow only where **rendering, computation, network, or bundle cost** is **actually significant**.

That means starting from symptoms a user would notice: typing that lags, a click that takes half a second to respond, a page that takes too long to become interactive. Then find out where the time goes. Guessing tends to produce memoization sprinkled everywhere while the real cost, perhaps a 2 MB bundle or a request waterfall, stays untouched. Measure with a production build, since development builds include extra checks that make everything slower, and ideally on hardware similar to your users' devices.

## The React Profiler

For rendering costs, the main tool is the **Profiler**, available as a tab in React Developer Tools (and as a `<Profiler>` component for measuring in code). It **records component render timing and commit information**, so developers can **locate expensive or unexpectedly frequent renders**.

You start recording, perform the slow interaction, and stop. The Profiler then shows each commit and, for each commit, which components rendered, how long each took, and what triggered the update. Two patterns usually stand out:

- **Expensive renders**: one component takes most of the time in each commit, such as a table formatting thousands of cells.
- **Unexpectedly frequent renders**: a component that should be idle renders on every keystroke, because the state it depends on lives too high or a prop changes identity each time.

## Fix the structure before reaching for memo

Memoization is a legitimate tool, but it can also paper over a design problem. **Wrapping many components in memoization may reduce symptoms** while leaving **oversized state ownership**, **unstable data flow**, or **expensive parent work** unchanged.

Consider a page where a search box's text lives in the top-level `App` state. Every keystroke renders the whole app. You could wrap dozens of components in `memo` and stabilize every prop with `useMemo` and `useCallback`. Or you could move the search state down into the search panel that uses it (state colocation), so the rest of the app never renders on a keystroke in the first place. The second fix is smaller, more robust, and does not break the next time someone adds an inline object prop.

Other structural fixes worth trying first: pass expensive subtrees as `children` so they are created by a parent that does not re-render, split a large context, and avoid heavy calculations in components that render often.

## Windowing long lists

Some screens are slow simply because they render too much. A list of 10,000 rows means 10,000 components and tens of thousands of DOM nodes, even though only twenty rows fit on screen.

**Windowing**, or **list virtualization**, **renders only the visible portion of a large list plus a small buffer**, **reducing DOM nodes and rendering work** compared with mounting every row. As the user scrolls, rows leaving the viewport unmount and rows entering it mount.

```jsx
import { useVirtualizer } from "@tanstack/react-virtual";

function TransactionList({ transactions }) {
  const scrollRef = useRef(null);
  const virtualizer = useVirtualizer({
    count: transactions.length,
    getScrollElement: () => scrollRef.current,
    estimateSize: () => 48,
    overscan: 5,
  });

  return (
    <div ref={scrollRef} style={{ height: 480, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((item) => {
          const tx = transactions[item.index];
          return (
            <div
              key={tx.id}
              style={{ position: "absolute", top: item.start, height: item.size, width: "100%" }}
            >
              {tx.date} · {tx.description} · {tx.amount}
            </div>
          );
        })}
      </div>
    </div>
  );
}
```

The outer container is 480 pixels tall and scrolls. The inner container is as tall as all rows combined would be, so the scrollbar looks right. But only the rows currently in view, plus five extra on each side (`overscan`), are actually rendered, each positioned absolutely where it would be in the full list. With 10,000 transactions, roughly 20 rows exist in the DOM at any time. On mobile, React Native's `FlatList` does the same job.

## The cost of virtualization

**List virtualization introduces trade-offs**: it adds **scroll measurement** and **focus and accessibility complexity**, and **off-screen items may not exist in the DOM** until they approach the viewport.

In practice: rows with varying heights must be measured, and a wrong estimate makes the scrollbar jump. The browser's find-in-page cannot find text in rows that are not rendered. A focused row that scrolls out of view unmounts, which can lose keyboard focus. Screen readers may announce a list of 20 items instead of 10,000 unless you add the right attributes. So virtualize lists that are genuinely large; for a list of 200 simple rows, rendering all of them is usually fine.

## Common mistakes

- **Optimizing by guesswork.** Profile the slow interaction first.
- **Measuring in development mode.** Development checks distort timings.
- **Memoizing around a structural problem.** Colocate state and fix data flow first.
- **Virtualizing small lists.** You pay the complexity without meaningful savings.

## Key points

- Decide whether performance work is needed by measuring user-visible latency and profiling data; optimize only where rendering, computation, network, or bundle cost is significant.
- The React Profiler records component render timing and commit information to locate expensive or unexpectedly frequent renders.
- Widespread memoization can hide oversized state ownership, unstable data flow, or expensive parent work instead of fixing them.
- Windowing (list virtualization) renders only the visible part of a large list plus a buffer, reducing DOM nodes and rendering work.
- Virtualization adds scroll measurement and focus and accessibility complexity, and off-screen items may not exist in the DOM.

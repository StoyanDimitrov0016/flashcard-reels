# Sharing state between components

State starts out local: one component owns a value and renders it. Real screens quickly need more. A filter box and a results list must agree on the search text; two accordion panels must know which one is open. Deciding which component owns a piece of state, and how others see and change it, is one of the main design decisions in any React app.

## One-way data flow

React moves data in one direction. **One-way data flow** means parents pass data down through props, while children request changes by calling callbacks or dispatching actions. A child never reaches up and edits its parent's state. It calls a function the parent gave it, and the parent decides what to do.

This keeps **ownership** explicit. For any value on screen, you can trace upward to the one component that holds it in state, and that component is the only place where it changes. When something looks wrong, you know where to look.

## Lifting state up

When two components need the same changing data, neither can own it privately. **Lifting state up** means moving shared state to the **nearest common ancestor**, so multiple descendants receive **one consistent source of truth** through props.

Here is an accordion where only one panel may be open at a time:

```jsx
function Accordion() {
  const [activeIndex, setActiveIndex] = useState(0);

  return (
    <>
      <Panel title="Shipping" isActive={activeIndex === 0} onShow={() => setActiveIndex(0)}>
        Orders ship within two business days.
      </Panel>
      <Panel title="Returns" isActive={activeIndex === 1} onShow={() => setActiveIndex(1)}>
        Items can be returned within 30 days.
      </Panel>
    </>
  );
}

function Panel({ title, isActive, onShow, children }) {
  return (
    <section>
      <h3>{title}</h3>
      {isActive ? <p>{children}</p> : <button onClick={onShow}>Show</button>}
    </section>
  );
}
```

If each `Panel` kept its own `isOpen` state, nothing would stop both from being open. Instead the state lives in `Accordion`, the common parent. On the first render the Shipping panel shows its text and the Returns panel shows a button. Clicking "Show" on Returns calls `onShow`, the parent sets `activeIndex` to `1`, and both panels render again with new props: Returns now shows its text and Shipping collapses. This is one-way data flow in action: data goes down as `isActive`, and change requests come up through `onShow`.

## Controlled and uncontrolled inputs

Lifting state up turns a component from self-managing to parent-driven. React calls a component **controlled** when important information comes from props or state owned elsewhere, and **uncontrolled** when it keeps that information internally. `Panel` above is controlled by `Accordion`.

The same distinction applies to form inputs, where you will meet it most often.

A **controlled input** gets its displayed value from React state and reports edits through an event handler that updates that state:

```jsx
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}
```

Each keystroke fires `onChange`, the handler updates `query`, React renders again, and the input displays the new value. React state is the single source of truth, so you can validate, transform, or share the value at any moment, for example by lifting `query` up so a results list can filter by it.

An **uncontrolled input** keeps its current value in the **DOM** rather than in React state. You can set a starting value with `defaultValue`, and after that the browser manages it. Code typically reads the value through a **ref** (refs get their own lesson) or from the form data when the form is submitted:

```jsx
function NewsletterForm({ onSubscribe }) {
  function handleSubmit(e) {
    e.preventDefault();
    const email = new FormData(e.currentTarget).get("email");
    onSubscribe(email);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" type="email" defaultValue="" />
      <button>Subscribe</button>
    </form>
  );
}
```

Uncontrolled inputs mean less code and no render per keystroke. Controlled inputs are the better fit when other UI must react to the value as it changes, such as live validation or a character counter.

## When to move state upward

Lifting is not free. The higher a piece of state lives, the more components render when it changes and the more props must be threaded down. So move state upward for a reason: when **multiple components need a coordinated value**, or when a **parent must control the lifecycle and consistency** of that state, for example resetting a form from outside, or guaranteeing that only one panel is open.

## State colocation

The opposite principle is just as important. **State colocation** means keeping state as close as practical to the components that actually use and update it. If only a dropdown cares whether it is open, that boolean belongs in the dropdown, not in the page component.

Colocated state reduces unnecessary dependencies: fewer props passing through components that do not care, and a smaller area to understand when the state changes. It also avoids **broad rerenders**. When state sits at the top of the app, every update renders the whole tree below it; when it sits in a leaf, only that leaf renders.

Good designs move in both directions over time. Start with state where it is used, lift it when a second component needs it, and push it back down when that need goes away.

## Common mistakes

- **Syncing two copies.** Keeping the same value in two sibling components and trying to keep them in step with Effects. Lift it to the common parent instead.
- **Lifting everything to the top.** A global-feeling page component that owns every toggle renders the whole page on each keystroke and becomes hard to follow.
- **Mixing modes on one input.** Passing `value` without an `onChange` makes the field read-only, and switching an input between `value` and `defaultValue` confuses React. Pick controlled or uncontrolled.

## Key points

- One-way data flow: parents pass data down through props, and children request changes through callbacks or dispatched actions, keeping state ownership explicit.
- Lifting state up moves shared state to the nearest common ancestor, giving descendants one consistent source of truth through props.
- A controlled input displays a value from React state and reports edits through a handler that updates that state.
- An uncontrolled input keeps its value in the DOM; code reads it through a ref or on form submission.
- Move state upward when multiple components need a coordinated value or a parent must control its lifecycle and consistency.
- State colocation keeps state close to the components that use it, reducing unnecessary dependencies and broad rerenders.

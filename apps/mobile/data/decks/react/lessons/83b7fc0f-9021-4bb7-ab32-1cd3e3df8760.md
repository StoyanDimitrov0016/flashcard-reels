# Choosing the state structure

Knowing where state lives is half the job; the other half is deciding what goes into it. Two components can show the same screen, yet one is easy to change while the other is full of bugs where values disagree. The difference is usually the shape of the state. A few principles keep state small, consistent, and unable to describe situations that should never happen.

## The goal: the minimal state

Think of state as the smallest set of facts from which the whole UI can be computed. Everything else should be calculated from those facts during render. Every extra piece of state is another thing that has to be updated correctly on every change, and another way for the screen to contradict itself.

## Derived state

**Derived state** is a value that can be computed from existing props or state. A full name built from a first and last name, the number of completed todos, a list filtered by a search query: none of these are new facts. They should usually be **calculated during render** rather than stored separately, which **avoids synchronization bugs**.

Compare two versions of a filtered list:

```jsx
// Fragile: visibleProducts is stored, so it must be kept in sync
function ProductList({ products }) {
  const [query, setQuery] = useState("");
  const [visibleProducts, setVisibleProducts] = useState(products);

  function handleChange(e) {
    setQuery(e.target.value);
    setVisibleProducts(products.filter((p) => p.name.includes(e.target.value)));
  }
  // ...
}
```

```jsx
// Robust: visibleProducts is derived during render
function ProductList({ products }) {
  const [query, setQuery] = useState("");
  const visibleProducts = products.filter((p) =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ul>
        {visibleProducts.map((p) => (
          <li key={p.id}>{p.name}</li>
        ))}
      </ul>
    </>
  );
}
```

In the first version, the list is only recalculated when the user types. If the parent passes a new `products` array, perhaps after a refresh, the stored `visibleProducts` keeps showing the old products until the next keystroke. In the second version, every render recomputes the list from the current `query` and the current `products`, so it can never go stale. It is also shorter. If the calculation ever becomes measurably slow, it can be cached with `useMemo`, covered in the memoization lesson, but it stays derived.

## Duplicated state

A closely related problem is **duplicated state**: storing the same fact in multiple state variables. If the same fact lives in two places, **every update must keep all copies synchronized**. Missing one update creates **contradictory values**.

A common example is storing a selected object alongside the list it came from:

```jsx
const [items, setItems] = useState(initialItems);
const [selectedItem, setSelectedItem] = useState(initialItems[0]);
```

Now the selected item's data exists twice: once inside `items` and once in `selectedItem`. If the user renames the selected item, the code must update both, or the list shows the new name while the details panel shows the old one. The fix is to store only what is unique, the ID, and derive the object:

```jsx
const [items, setItems] = useState(initialItems);
const [selectedId, setSelectedId] = useState(initialItems[0].id);
const selectedItem = items.find((item) => item.id === selectedId);
```

There is now one copy of each item, so a rename shows up everywhere at once.

The same trap appears when props are copied into state, as in `useState(props.color)`. The state is initialized once and then ignores later changes to the prop. Unless you deliberately want an initial value only (in which case naming the prop `initialColor` makes that clear), read the prop directly.

## Multiple booleans and impossible states

The last principle is about state that describes a mode or phase. It is natural to add a boolean for each situation:

```jsx
const [isIdle, setIsIdle] = useState(true);
const [isLoading, setIsLoading] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
const [isError, setIsError] = useState(false);
```

Four booleans allow sixteen combinations, but only four of them make sense. **Multiple booleans can produce impossible UI states**, because independent flags can form combinations the interface should never allow, such as simultaneously "idle" and "loading", or "success" and "error". Each handler must remember to flip every flag correctly, and forgetting one leaves the screen in a state no designer ever drew.

A **single status value** encodes that **mutual exclusivity** directly:

```jsx
function FeedbackForm() {
  const [status, setStatus] = useState("idle"); // "idle" | "submitting" | "success" | "error"
  const [message, setMessage] = useState("");

  async function handleSubmit(e) {
    e.preventDefault();
    setStatus("submitting");
    try {
      await sendFeedback(message);
      setStatus("success");
    } catch {
      setStatus("error");
    }
  }

  if (status === "success") {
    return <p>Thanks for your feedback!</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <textarea value={message} onChange={(e) => setMessage(e.target.value)} />
      <button disabled={status === "submitting"}>Send</button>
      {status === "error" && <p role="alert">Something went wrong. Please try again.</p>}
    </form>
  );
}
```

`status` can only hold one value at a time, so "submitting and error" simply cannot be represented. While the request is running the button is disabled; if it fails, the error line appears; if it succeeds, the whole form is replaced by a thank-you message. If you still want a convenient boolean, derive it: `const isSubmitting = status === "submitting";`.

## Common mistakes

- **Storing what you can calculate.** Filtered lists, totals, and formatted strings belong in render, not in state.
- **Syncing state with an Effect.** Using an Effect to copy one state variable into another adds an extra render and a window where they disagree.
- **Mirroring props in state.** The copy silently ignores later prop changes.
- **One boolean per phase.** Replace groups of related flags with a single status value.

## Key points

- Derived state is a value computable from existing props or state; calculate it during render rather than storing it, to avoid synchronization bugs.
- Duplicated state stores the same fact in several variables; every update must keep all copies in sync, and missing one creates contradictory values.
- Store unique facts, such as a selected ID, and derive the rest.
- Multiple independent booleans can form impossible combinations, such as being both idle and loading.
- A single status value encodes mutual exclusivity directly.

# Reusing logic with custom Hooks

After a few screens, patterns repeat. Three components track whether the browser is online; two subscribe to window size; several manage a form field with validation. Copying the same `useState` and `useEffect` lines into each one works until a bug fix has to be applied in five places. Custom Hooks let you extract that logic into a function, but they rely on rules that apply to every Hook, so this lesson starts there.

## Where Hooks can be called

**Hooks can be called from React function components and from custom Hooks**, following the **Rules of Hooks**. They cannot be called from regular JavaScript functions, class components, or code outside React. The reason is that a Hook reads and writes data React keeps for the component currently rendering; outside a component's render, there is no such component.

## Why Hooks must be called at the top level

The second rule is to call Hooks at the **top level** of the component or custom Hook: not inside conditions, loops, nested functions, or after an early `return`.

This follows from how React stores Hook state. A component does not name its Hooks; React simply keeps a list for each component instance and **matches Hook state by call order**. On every render, the first `useState` call gets the first slot, the second gets the second slot, and so on.

```jsx
function Form({ showNickname }) {
  const [name, setName] = useState("");
  if (showNickname) {
    const [nickname, setNickname] = useState(""); // breaks the rules
  }
  const [email, setEmail] = useState("");
  // ...
}
```

If `showNickname` is true on the first render and false on the next, the call sequence changes from name, nickname, email to name, email. React hands the email field the slot that held the nickname. **Conditional or looped Hook calls** can change the order between renders and **associate state with the wrong Hook**. Keep the Hook unconditional and put the condition in what you render. (The `use` API, covered in the Suspense lesson, is the one exception that may be called conditionally, though still only inside components and Hooks.)

The `eslint-plugin-react-hooks` linter enforces both rules.

## Custom Hooks

A **custom Hook** is a function whose name starts with **`use`** and that **composes React Hooks** to reuse **stateful or synchronization logic**.

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(() => navigator.onLine);

  useEffect(() => {
    function handleOnline() {
      setIsOnline(true);
    }
    function handleOffline() {
      setIsOnline(false);
    }
    window.addEventListener("online", handleOnline);
    window.addEventListener("offline", handleOffline);
    return () => {
      window.removeEventListener("online", handleOnline);
      window.removeEventListener("offline", handleOffline);
    };
  }, []);

  return isOnline;
}

function SaveButton({ onSave }) {
  const isOnline = useOnlineStatus();
  return (
    <button disabled={!isOnline} onClick={onSave}>
      {isOnline ? "Save" : "Reconnecting..."}
    </button>
  );
}

function StatusBar() {
  const isOnline = useOnlineStatus();
  return <p>{isOnline ? "Online" : "Disconnected"}</p>;
}
```

The listener setup now lives in one place. `SaveButton` and `StatusBar` just ask a question, "am I online?", and render the answer. When the network drops, the `offline` event fires, the Hook's state updates, and each component using it renders its offline UI.

The `use` prefix is not decoration. It tells readers and the linter that the function calls Hooks, so the Rules of Hooks apply to it and to its callers. A helper that calls no Hooks should be a regular function without the prefix.

## Custom Hooks share logic, not state

A frequent misconception is that two components calling `useOnlineStatus` share one `isOnline` variable. **They do not.** **Each call gets its own Hook state**, exactly as if each component had written the `useState` and `useEffect` itself. `SaveButton` and `StatusBar` agree only because both are synchronized with the same browser events.

This matters for Hooks like a hypothetical `useFormField()`: two fields using it have independent values. Callers only share state if the custom Hook **explicitly connects them** to shared **external state** (such as a store, covered in the external stores lesson) or to a **context** provided above them.

## Render props

Before Hooks existed, React developers shared logic through component patterns. The most common was the **render prop**: a **function passed as a prop** that a component **calls to decide what UI to render**, using data or behavior the component provides.

```jsx
function MousePosition({ render }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return (
    <div onPointerMove={(e) => setPos({ x: e.clientX, y: e.clientY })} className="area">
      {render(pos)}
    </div>
  );
}

<MousePosition
  render={({ x, y }) => (
    <p>
      Pointer at {x}, {y}
    </p>
  )}
/>;
```

`MousePosition` owns the tracking logic, and the caller decides the output. The pattern still has uses, especially when a component needs the caller to customize part of its own markup, such as how each row in a list renders.

## Why custom Hooks often work better

For sharing logic alone, custom Hooks often solve the problem better than render props. They share stateful logic **without adding extra wrapper elements** or **deeply nested callback rendering structure**. With two render-prop components, UI quickly nests: a `MousePosition` render function containing an `OnlineStatus` render function containing your markup, each layer adding indentation and often an extra DOM element. With Hooks, the same logic is two lines at the top of the component:

```jsx
function Cursor() {
  const { x, y } = useMousePosition();
  const isOnline = useOnlineStatus();
  return <p>{isOnline ? `Pointer at ${x}, ${y}` : "Offline"}</p>;
}
```

## Common mistakes

- **Conditional Hook calls.** Move the condition inside the Hook or into the returned JSX.
- **Expecting shared state from a custom Hook.** Each call is independent unless the Hook uses context or an external store.
- **Prefixing plain helpers with `use`.** It misleads readers and subjects the function to rules it does not need.

## Key points

- Hooks can be called from React function components and custom Hooks, following the Rules of Hooks.
- Hooks must be called at the top level because React matches Hook state by call order; conditional or looped calls can attach state to the wrong Hook.
- A custom Hook is a function whose name starts with `use` and composes Hooks to reuse stateful or synchronization logic.
- Custom Hooks do not share state between callers; each call gets its own state unless the Hook connects to external state or context.
- A render prop is a function prop that a component calls to decide what UI to render with data or behavior it provides.
- Custom Hooks share stateful logic without wrapper elements or deeply nested render callbacks.

# Portals, refs, and component patterns

Some UI does not fit neatly inside its parent's box, and some components need to expose more than props and children. This lesson covers portals, passing refs between components, and a few patterns for designing component APIs that stay flexible without leaking their internals.

## Portals

A **portal** renders React children into a **different DOM container**, such as a node attached directly to `document.body`, while keeping them in the **same place in the React tree**.

```jsx
import { createPortal } from "react-dom";

function Modal({ children }) {
  return createPortal(<div className="modal">{children}</div>, document.body);
}
```

Portals are the standard tool for **modals, tooltips, and overlays**. An ancestor element with `overflow: hidden`, or one that creates its own **stacking context**, can clip or bury content rendered inside it. A portal lets the visual content **escape those constraints** in the DOM while staying connected to the component that owns it.

Because the portal stays in the React tree, it still receives **context** from its React ancestors. **Events** also follow the React tree. A click inside a portal **bubbles to React ancestors** of the portal, even though the actual DOM node lives in a completely different container. A parent's `onClick` can therefore fire for a click inside a modal that is physically attached to `body`, which is usually convenient but sometimes surprising.

## Passing refs to components

Parents sometimes need a child's DOM node, for example to focus an input inside a custom `TextField`. Historically, function components could not receive a `ref` directly, so they were wrapped in **`forwardRef`**, which passed the parent's ref through to a child DOM node or to an imperative handle.

In **React 19**, function components receive `ref` as an **ordinary prop**, so new code can skip `forwardRef`:

```jsx
function TextField({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}
```

You will still see `forwardRef` in older code and libraries, and it continues to work.

## Imperative handles

Sometimes exposing the raw DOM node is too much. `useImperativeHandle` **customizes the value** a parent receives through a ref, so a component can reveal a **small imperative API** instead of its DOM node.

```jsx
function VideoPlayer({ ref, src }) {
  const videoRef = useRef(null);
  useImperativeHandle(ref, () => ({
    play: () => videoRef.current.play(),
    pause: () => videoRef.current.pause(),
  }));
  return <video ref={videoRef} src={src} />;
}
```

Keep these handles **narrow**. Every exposed operation is something a parent can come to depend on. If the parent can reach into the internal DOM structure, you can no longer change that structure safely. Exposing only `play` and `pause` preserves **encapsulation**.

## Compound components

In the **compound component** pattern, several components **cooperate** to form one higher-level API. They usually share state through **context** or a naming convention, so the parent can arrange the pieces freely.

```jsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Tab value="profile">Profile</Tabs.Tab>
    <Tabs.Tab value="billing">Billing</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel value="profile">...</Tabs.Panel>
  <Tabs.Panel value="billing">...</Tabs.Panel>
</Tabs>
```

`Tabs` owns which tab is selected; each `Tab` and `Panel` reads it from context. The user of the API gets full control over layout without having to wire up state.

## Render props

A **render prop** is a **function passed as a prop** that the component calls to decide what to render. The component provides data or behavior, and the caller decides how it looks.

```jsx
<MouseTracker
  render={({ x, y }) => (
    <p>
      {x}, {y}
    </p>
  )}
/>
```

Render props were a popular way to share logic before Hooks. Today **custom Hooks** usually do the job better. A Hook such as `useMousePosition()` shares the same **stateful logic** without adding **wrapper components** to the tree, and without the **nested callbacks** that build up when several render props are combined. Render props remain useful when a component needs to control where and when the caller's UI is rendered, as virtualized lists often do.

# Effects

Most React code only calculates UI. Sometimes a component also has to keep something outside React in step with what it renders: a chat connection, a browser API, a timer, or a third-party widget. Effects are the tool for that job, and they are also one of the easiest places to introduce bugs.

## What useEffect is for

`useEffect` **synchronizes a committed component with an external system**. It runs after React has committed the render to the screen, so it sees the final UI, and it usually runs after the browser has painted.

```jsx
useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

The function passed to `useEffect` is the **setup**. The function it returns is the **cleanup**.

## Cleanup

Cleanup runs in two situations:

- **Before the effect runs again** because one of its dependencies changed. React cleans up with the old values, then sets up with the new ones.
- When the component **unmounts**.

Any effect that **subscribes** to something should **unsubscribe** in its cleanup. Without it, old subscriptions keep delivering events after props change or after the component is gone. The result is **duplicate work**, state updates from stale sources, and **memory leaks**. In the example above, switching from room "general" to room "music" must disconnect from "general" first, or the component ends up listening to both.

## Dependency arrays

The second argument controls when the effect re-synchronizes:

- `[roomId]`: runs after mount and again whenever `roomId` changes.
- `[]`, an **empty array**: declares that the effect reads **no reactive values** that can change. It normally sets up after mount and cleans up on unmount. In development, Strict Mode may run an extra setup and cleanup cycle to check that cleanup works.
- **No array at all**: the effect runs after **every committed render** of the component.

## Every reactive value belongs in the dependencies

Props, state, and anything calculated from them during render are **reactive values**: they can change between renders. If an effect reads one, it must list it as a dependency. Otherwise the effect keeps using the value captured by an **older render** and never re-synchronizes when it changes. The React linter enforces this rule, and it is best to fix the code rather than silence the warning.

The underlying problem is called a **stale closure**: a callback or effect that reads props or state captured from an older render, while the programmer expected the current values. Every render creates new functions that close over that render's snapshot, and a function kept from an earlier render still sees earlier values.

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1); // stale: always reads the first count
  }, 1000);
  return () => clearInterval(id);
}, []);
```

Here a functional update, `setCount(c => c + 1)`, removes the need to read `count` at all.

## Infinite loops

An effect can trigger itself forever. If it **updates state**, and that update changes one of the effect's own **dependencies** on every render, each commit schedules the effect again. A common cause is a dependency that is a new object or array created on every render.

## When you do not need an Effect

Effects are for external systems. Two situations do not need one:

- If a value can be **calculated during render** from props or state, calculate it directly. Storing it with an effect adds an extra render and a chance for the copies to drift apart.
- If an action is caused by a **user event**, such as clicking Buy, put the logic in the **event handler**. The handler knows exactly what happened; an effect only knows that something rendered.

## Fetching and race conditions

Fetching data in an effect has a subtle trap: requests can **finish out of order**. If the user types "a" and then "ab", the response for "a" might arrive last and **overwrite** the newer result. The fix is to ignore or cancel stale results in cleanup:

```jsx
useEffect(() => {
  let ignore = false;
  fetchResults(query).then((data) => {
    if (!ignore) setResults(data);
  });
  return () => {
    ignore = true;
  };
}, [query]);
```

An `AbortController` can cancel the request itself. In real applications, a framework or data-fetching library usually handles this for you.

## useLayoutEffect

`useLayoutEffect` runs **after DOM mutations but before the browser paints**. It is for code that must **measure layout**, such as reading an element's size to position a tooltip, and then adjust the DOM synchronously, when showing an intermediate frame would look wrong.

Use it **sparingly**. Work inside it **blocks painting**, so expensive synchronous logic delays every visible update and makes the interface feel unresponsive. Reach for `useEffect` first, and switch only when you see a visible flicker.

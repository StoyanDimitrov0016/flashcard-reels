# Context, custom Hooks, and memoization

As an app grows, you need ways to share data without threading it through every component, to reuse logic between components, and occasionally to skip work that does not need repeating. Context, custom Hooks, and memoization address these three needs, and each comes with rules worth knowing.

## Context

**Context** lets a **provider** make a value available to all of its descendants, without passing that value through every intermediate component as props.

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext value="dark">
      <Toolbar />
    </ThemeContext>
  );
}

function Button() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>Save</button>;
}
```

In React 19 the context object itself can be rendered as the provider, as shown; older code writes `<ThemeContext.Provider>`.

When the provided value changes, React schedules **every consumer** of that context to render with the new value. This has a cost. If a context holds a large object that changes often, every component that reads it becomes **eligible to render** on each change, even if it only uses one small field. Splitting context into smaller pieces, or keeping fast-changing values out of broad context, limits these **broad rerenders**.

## Custom Hooks

A **custom Hook** is a function whose name starts with `use` and that calls other Hooks. It lets you **reuse stateful or synchronization logic**, such as tracking the window size or connecting to a chat room.

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine);
  useEffect(() => {
    const update = () => setIsOnline(navigator.onLine);
    window.addEventListener("online", update);
    window.addEventListener("offline", update);
    return () => {
      window.removeEventListener("online", update);
      window.removeEventListener("offline", update);
    };
  }, []);
  return isOnline;
}
```

Custom Hooks share **logic, not state**. Each component that calls `useOnlineStatus` gets its **own independent state**. Callers only see the same data if the Hook explicitly connects them to something shared, such as context or an external store.

## Rules of Hooks

React does not identify Hooks by name. It matches each Hook's stored state to the **order of Hook calls** during render: the first `useState` gets the first slot, the second gets the second, and so on. That is why Hooks must be called at the **top level** of a component, never inside conditions, loops, or nested functions. If a Hook call is skipped in one render, every later Hook shifts position and receives the **wrong state**.

Hooks can only be called from **React function components** and from **custom Hooks**. Calling them from ordinary functions, class components, or event handlers breaks the rules.

## useMemo and useCallback

`useMemo` **caches the result of a calculation** between renders and recomputes it only when one of its **dependencies** changes.

```jsx
const visibleTodos = useMemo(() => filterTodos(todos, tab), [todos, tab]);
```

It is a **performance optimization**, not a guarantee. React may discard the cache, so your code must still work correctly if the calculation runs again.

`useCallback` does the same for a **function reference**: it returns the same function between renders until its dependencies change. This matters when **function identity** is significant, for example when the function is passed to a memoized child or listed as a dependency of another Hook.

Memoization is not free. For a **cheap calculation**, or when dependencies **change on almost every render**, `useMemo` adds dependency comparisons, memory use, and extra code without saving meaningful work.

The **React Compiler** can add this kind of memoization automatically at build time, which reduces how often you need to write `useMemo` and `useCallback` by hand. Understanding manual memoization still explains what the compiler does and when it helps.

## React.memo

`React.memo` wraps a component so React can **skip rendering it** when its props are **shallowly equal** to the previous props. It does not freeze the component: a change in context it reads, or in its own state, still causes it to render.

Shallow comparison checks references, not contents. A **new object** or array literal created during every render, such as `style={{ color: "red" }}` or `options={[1, 2]}`, has a new reference each time, so the memoized child always sees a changed prop. The same applies to inline functions, which is where `useCallback` helps.

```jsx
const Chart = memo(function Chart({ options }) {
  /* expensive rendering */
});

// Defeats memo: a new object on every render
<Chart options={{ zoom: 2 }} />;
```

## Rendering is not the same as updating the DOM

It helps to separate two kinds of savings. A component may **render** and produce the same output as before; React then compares and makes **no DOM changes**, but it still paid for calling the component and diffing its output. **Memoization** goes one step earlier and, under the right conditions, **skips the render itself**.

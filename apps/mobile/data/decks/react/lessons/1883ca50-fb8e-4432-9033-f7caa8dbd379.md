# Render and commit

"Rendering" is one of the most used words in React, and one of the most misunderstood. Many developers assume that when a component renders, the screen changes. It does not, necessarily. React separates computing the UI from applying it, and that separation is what allows React to retry, pause, or discard work safely. It also creates the most important rule for writing components: keep rendering pure.

## What rendering means

**Rendering** means React calls your components to compute the next element tree. When `Counter` renders, React runs the `Counter` function, and the function returns elements describing what the UI should look like. Then React recursively renders any child components those elements contain.

Rendering by itself changes nothing on screen. React only compares the result with what is already there and afterward **commits** the necessary host updates, such as DOM changes.

Every screen update goes through three steps:

1. **Trigger**: something tells React a render is needed.
2. **Render**: React calls components to compute the new tree.
3. **Commit**: React applies the differences to the host environment.

Then the browser paints the result, and the user sees it.

## What causes a component to render again

The first render happens when the app starts. After that, a component can render again for three reasons:

- **Its own state updates.** Calling a state setter queues a render of that component.
- **Its parent renders and includes it.** When a parent renders, React renders the children in the tree it returns too, by default, even if their props did not change.
- **A consumed context value changes.** Context, covered in a later lesson, passes a value to deeply nested components; when it changes, components reading it render.

The second reason often surprises people. A state change at the top of a large tree renders everything beneath it. That is usually fine, because rendering is fast and React skips DOM updates for output that did not change. Later lessons show how to avoid unnecessary renders when they become measurably expensive.

## The render phase

During the **render phase**, React calls components and computes the next UI. Nothing is visible yet; React is only building a description.

Because nothing is committed, React is free to treat render work as disposable. It may **run render code more than once** for the same update, and it may **abandon the result** entirely. Concurrent features, which later lessons cover, can interrupt a slow render when a more urgent update arrives, throw the partial work away, and start again. Development checks also call components twice on purpose.

This is why render code must be **pure**.

## The commit phase

During the **commit phase**, React applies the chosen changes to the host environment. It inserts, updates, and removes DOM nodes so the screen matches the new tree. It updates **refs** so they point at the right DOM nodes. And it runs **layout effects** (the `useLayoutEffect` Hook) synchronously before the browser paints. Regular effects from `useEffect` run afterward, usually after the paint.

Unlike render, commit is not abandoned halfway. Once React starts committing, it finishes, so the user never sees a partially applied update.

If a render produces exactly the same output as before, the commit has nothing to change, and React leaves the DOM alone.

## Pure components

A **pure** component, given the same props, state, and context, returns the same UI description and does not change external state during render. Think of it like a math formula: `y = 2x` always gives the same `y` for the same `x`, and calculating it does not change anything else in the world.

```jsx
function PriceTag({ amount, currency }) {
  const formatted = new Intl.NumberFormat("en-US", { style: "currency", currency }).format(amount);
  return <span className="price">{formatted}</span>;
}
```

`PriceTag` is pure. It reads its inputs, computes a string, and returns elements. Calling it ten times with the same props gives ten identical descriptions and has no other consequences. Creating and changing local variables inside the function is fine; they did not exist before this call.

## Why side effects are unsafe during render

A **side effect** is anything that changes the world outside the function: writing to a variable declared outside the component, mutating a prop, sending an analytics event, starting a network request, or changing the DOM directly.

Side effects are unsafe during render because React may render more than once or discard a render. A side effect performed during render can therefore **happen without a corresponding committed UI**, or **happen multiple times**. Consider this impure component:

```jsx
let viewCount = 0;

function Article({ article }) {
  viewCount++; // side effect during render
  sendAnalytics("article_view", article.id); // side effect during render
  return (
    <article>
      <h1>{article.title}</h1>
      <p>Viewed {viewCount} times this session</p>
    </article>
  );
}
```

If React renders `Article` twice for one update, the counter jumps by two and two analytics events are sent. If React starts rendering it for a transition and then abandons that work, an event is sent for a screen the user never saw. The displayed count may also differ between two components that should agree.

Side effects still have to happen somewhere. The right places are **event handlers**, which run in response to a specific user action and never during render, and **Effects**, which run after commit. Both get their own lessons later in this deck.

## Common mistakes

- **Equating render with a DOM update.** A render can produce identical output, in which case the DOM does not change at all.
- **Counting on renders.** Code that assumes a component renders exactly once per update breaks under development checks and concurrent rendering.
- **Mutating inputs.** Changing a prop or a state object during render is a side effect, even though it looks local.

## Key points

- Rendering means React calls components to compute the next element tree; React commits the necessary host updates afterward.
- A component renders again when its own state updates, when its parent renders and includes it, or when a consumed context changes.
- In the render phase React computes the next UI; render code must be pure because React may run it more than once or abandon the result.
- In the commit phase React applies changes to the host environment, updates refs, and runs layout effects.
- A pure component returns the same UI description for the same props, state, and context and does not change external state during render.
- Side effects during render can happen without a committed UI or happen multiple times.

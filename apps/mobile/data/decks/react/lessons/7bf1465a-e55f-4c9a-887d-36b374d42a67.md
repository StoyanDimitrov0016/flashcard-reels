# Structuring state

Knowing how state works is only half the job. The other half is deciding where each piece of state should live, how components reach it, and what shape it should take. Good choices here prevent more bugs and slowdowns than any optimization applied later.

## Keep state close

**State colocation** means keeping state **as close as practical** to the components that actually read and update it. A search box's draft text belongs in the search box, not in the app root. Colocated state is easier to understand, and when it changes, only the small subtree that owns it renders again, instead of large parts of the app.

Move state **upward** only when there is a reason:

- **Several components** need a **coordinated value**, such as a filter that both a sidebar and a results list use.
- A **parent must control** the lifecycle and consistency of that state, for example to reset it or to save it together with other data.

Start local, and lift when sharing becomes necessary.

## External store state

Some state is **owned outside React**: a state management library's store, a browser API such as online status or media queries, or a subscription to data from another system. Components **subscribe** to this **external store** and render again when it notifies them of changes.

`useSyncExternalStore` is React's standard way to connect to such a store. You provide a `subscribe` function and a `getSnapshot` function, and React reads **consistent snapshots**, even in rendering modes where updates can be **concurrent**.

```jsx
function useOnlineStatus() {
  return useSyncExternalStore(
    (callback) => {
      window.addEventListener("online", callback);
      window.addEventListener("offline", callback);
      return () => {
        window.removeEventListener("online", callback);
        window.removeEventListener("offline", callback);
      };
    },
    () => navigator.onLine
  );
}
```

## Tearing

Why not just read the store directly during render? With concurrent rendering, React can pause a render partway through to handle something urgent. If a **mutable external store** changes during that pause, components rendered before the change and components rendered after it **observe different versions** of the same data.

The visible result is **tearing**: different parts of one screen show different versions of shared state, such as a header saying three items while the list shows four. `useSyncExternalStore` prevents this by coordinating **subscription and snapshot** reads so that one render sees one consistent value.

## Context, composition, and prop drilling

**Prop drilling** is passing data through intermediate components that **do not use it** themselves, only so a deeper descendant can receive it.

Prop drilling is not automatically a problem. When the path is **short** and **ownership stays clear**, passing props is often the simplest, most explicit option. Context is not automatically better for every shared value, because it hides where data comes from and can cause broad rerenders.

Often the better alternative is **composition**. Instead of passing data down so a deep child can build some UI, the parent builds that UI itself and passes the **finished elements** down as `children` or another prop:

```jsx
function Page({ user }) {
  return (
    <Layout sidebar={<Avatar user={user} />}>
      <Feed user={user} />
    </Layout>
  );
}
```

`Layout` never needs to know about `user`. Composition passes concrete UI or behavior **only where it is needed**, avoiding the **hidden dependencies** and extra rerenders that a large shared context value can create.

## Model states, not flags

Consider a request tracked with separate booleans: `isIdle`, `isLoading`, `isSuccess`, `isError`. Four independent booleans allow sixteen combinations, but only four of them make sense. Nothing stops a bug from producing an **impossible state**, such as `isIdle` and `isLoading` both being `true`.

A **single status value** encodes that the states are **mutually exclusive**:

```jsx
const [status, setStatus] = useState("idle");
// "idle" | "loading" | "success" | "error"
```

Taken further, this is the **state machine** approach. You model the UI as a set of **explicit states** and the **events or transitions** allowed between them: from "idle" a submit moves to "loading", from "loading" a response moves to "success" or "error". Transitions that are not listed simply cannot happen, so impossible combinations are ruled out by design. A reducer is a natural place to write such transitions.

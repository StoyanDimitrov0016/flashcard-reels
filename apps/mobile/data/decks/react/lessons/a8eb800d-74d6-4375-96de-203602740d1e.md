# Mutating data with Actions

Reading data is only half of an app. The other half is changing it: saving a profile, posting a comment, liking a photo. Every such mutation brings the same chores. Show that something is happening, disable the button so it is not clicked twice, display an error if it fails, and, ideally, make the change feel instant even though the server takes a moment. React 19 builds these chores into the framework under one idea: Actions.

## Actions

In modern React terminology, an **Action** is an **asynchronous, transition-oriented operation** that can **perform a mutation** and coordinate **pending**, **error**, **optimistic**, and **form-related** UI flows. Concretely, an Action is a function run inside a transition, which in React 19 may be async:

```jsx
const [isPending, startTransition] = useTransition();

function handleSave() {
  startTransition(async () => {
    const error = await updateDisplayName(name);
    if (error) {
      setError(error);
      return;
    }
    setSaved(true);
  });
}
```

While the async function runs, `isPending` is `true`. Because it is a transition, the UI stays responsive, and React treats everything inside as one operation: it tracks it as pending until it finishes, and errors thrown inside it reach the nearest error boundary.

Forms have built-in support. Passing a function to a `<form>`'s `action` prop (or a button's `formAction`) makes React run it as an Action when the form is submitted, with the form's `FormData` as its argument. React also resets uncontrolled form fields after a successful submission.

This is where the rule from the Effects lessons lands: mutations start from user events or Actions, not from a component mounting.

## useActionState

Most mutations produce a result you want to show, such as an error message or the saved record. **`useActionState`** manages the **state produced by an Action** and exposes whether that **Action is pending**, which is useful for **form and mutation workflows**.

```jsx
import { useActionState } from "react";

function ChangeNameForm({ currentName }) {
  const [error, submitAction, isPending] = useActionState(async (previousError, formData) => {
    const result = await updateDisplayName(formData.get("name"));
    return result.ok ? null : result.message;
  }, null);

  return (
    <form action={submitAction}>
      <input name="name" defaultValue={currentName} />
      <SubmitButton />
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

`useActionState` takes an action function and an initial state, and returns three things: the current state (here, `error`), a wrapped action to pass to the form, and `isPending`. When the user submits, React calls the function with the previous state and the form data. Whatever it returns becomes the new state. If the server rejects the name, the function returns the message and the alert appears; on success it returns `null` and the alert disappears. In earlier React canaries this Hook was called `useFormState`.

## useFormStatus

The form above renders a `SubmitButton`. Rather than passing `isPending` down as a prop, the button can ask the form directly. **`useFormStatus`**, from `react-dom`, provides status about the **parent form submission**, such as whether that form is currently **`pending`**, to components **within the form's subtree**:

```jsx
import { useFormStatus } from "react-dom";

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Saving..." : "Save"}</button>;
}
```

It must be called from a component rendered inside the `<form>`; it does not report on a form rendered in the same component or on other forms. That makes it ideal for reusable submit buttons and spinners in a design system, which work in any form without extra props. Besides `pending`, it exposes the submitted `data`, `method`, and `action`.

## Optimistic UI

Even a fast server takes a noticeable moment. **Optimistic UI** shows the **expected result of an operation before the server confirms it**, then **reconciles** with the outcome: on success the UI already looks right, and on failure it **rolls back or corrects** the value. Tapping a heart turns it red instantly; the request happens behind the scenes.

## The trade-off of optimistic UI

Optimistic UI **reduces perceived latency**, but it requires explicit handling for **rejection**, **conflicts**, **duplicate submissions**, and **authoritative server results**. If the server refuses the change, the UI must undo it and usually tell the user. If someone else changed the same data, your guess may be wrong. If the user taps five times quickly, you must not send five increments. And the server's final answer, such as a real ID or a like count that includes other users' likes, must replace your guess. Use optimistic UI for actions that nearly always succeed and are easy to reverse; avoid it for things like payments.

## useOptimistic

**`useOptimistic`** helps **render a temporary optimistic version of state** while an **asynchronous Action is pending**, before the **authoritative result** is known.

```jsx
import { useOptimistic, startTransition } from "react";

function LikeButton({ post, onLike }) {
  const [optimisticLikes, addOptimisticLike] = useOptimistic(
    post.likes,
    (currentLikes, delta) => currentLikes + delta
  );

  function handleClick() {
    startTransition(async () => {
      addOptimisticLike(1);
      await onLike(post.id); // saves the like; the parent then refreshes post.likes
    });
  }

  return <button onClick={handleClick}>Like ({optimisticLikes})</button>;
}
```

`useOptimistic` takes the real state (`post.likes`) and an update function. Outside an Action, `optimisticLikes` simply equals `post.likes`. When the user clicks, `addOptimisticLike(1)` is called inside the Action, and the button immediately shows one more like. When the Action finishes, React drops the optimistic value and shows the real `post.likes` again: the confirmed count if the server accepted it, or the original count if it failed, which rolls the UI back automatically. Optimistic updates must be made inside an Action or transition; React warns otherwise.

## Common mistakes

- **Tracking `isSubmitting` by hand.** `useActionState`, `useTransition`, and `useFormStatus` already track pending state.
- **Calling `useFormStatus` in the component that renders the form.** It only reports on a parent form.
- **Treating the optimistic value as truth.** Always reconcile with the server's authoritative result.

## Key points

- An Action is an asynchronous, transition-oriented operation that performs a mutation and coordinates pending, error, optimistic, and form-related UI.
- `useActionState` manages the state produced by an Action and exposes whether it is pending, suiting form and mutation workflows.
- `useFormStatus` gives components inside a form the status of the parent form's submission, such as whether it is pending.
- Optimistic UI shows the expected result before the server confirms it, then reconciles on success or rolls back or corrects on failure.
- Optimistic UI reduces perceived latency but requires handling rejection, conflicts, duplicate submissions, and authoritative server results.
- `useOptimistic` renders a temporary optimistic version of state while an async Action is pending.

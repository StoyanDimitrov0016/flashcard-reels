# Refs

State is how React remembers values that affect what is on screen. But some values have nothing to do with rendering: the ID of a running timer, the DOM node of an input you want to focus, the previous scroll position. Storing them in state would cause pointless renders, and storing them in a local variable would lose them on every render. Refs are React's escape hatch for exactly these values.

## What a ref is

A **ref** is a **stable object** whose **`.current`** field can hold **mutable data across renders** without causing a render when it changes. You create one with the `useRef` Hook:

```jsx
import { useRef } from "react";

const clickCount = useRef(0);
// later, in an event handler:
clickCount.current = clickCount.current + 1;
```

`useRef(0)` returns an object shaped like `{ current: 0 }`. You can read and write `current` freely. Unlike state, writing to it does not tell React anything; no render is queued.

## The same object every render

**`useRef` returns the same ref object for the lifetime of that component instance.** On the first render React creates the object; on every later render it hands back that exact object. That is why a value written into `current` during one event is still there during the next render. Two instances of the same component each get their own ref, just as they get their own state.

## When to use a ref instead of state

Use a ref for values **needed by imperative code but not for rendering**, such as **DOM nodes**, **timer handles**, or other mutable bookkeeping like the previous value of something or whether a request is already in flight.

A stopwatch shows the division clearly:

```jsx
function Stopwatch() {
  const [startTime, setStartTime] = useState(null);
  const [now, setNow] = useState(null);
  const intervalRef = useRef(null);

  function handleStart() {
    setStartTime(Date.now());
    setNow(Date.now());
    clearInterval(intervalRef.current);
    intervalRef.current = setInterval(() => setNow(Date.now()), 10);
  }

  function handleStop() {
    clearInterval(intervalRef.current);
  }

  const seconds = startTime != null && now != null ? (now - startTime) / 1000 : 0;

  return (
    <>
      <h1>{seconds.toFixed(2)} s</h1>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </>
  );
}
```

`startTime` and `now` are used to compute the displayed time, so they are state: changing them must update the screen. The interval ID is never displayed; only the Stop handler needs it, so it lives in a ref. Clicking Start begins a 10 ms interval that updates `now`, and each update renders the new time. Clicking Stop reads `intervalRef.current` and clears it.

## Why UI-visible data should not live only in a ref

The flip side: **changing a ref does not request a render**, so the screen will **not automatically update** to reflect the new value. If you move a click counter into a ref and display `{countRef.current}`, the number will look frozen. It is changing in memory, but React has no reason to render again, and the text only catches up when something else happens to cause a render.

A related rule: do not read or write `ref.current` during rendering (except for one-time lazy initialization). Rendering must be pure, and a ref is a mutable value React does not track. Read and write refs in event handlers and Effects.

## Refs to DOM nodes

The most common ref is one that points at a DOM node. Pass a ref object as the `ref` attribute of a host element, and React sets `ref.current` to that DOM node during commit (and back to `null` when it is removed):

```jsx
function SearchBar() {
  const inputRef = useRef(null);
  return (
    <>
      <input ref={inputRef} placeholder="Search" />
      <button onClick={() => inputRef.current.focus()}>Focus search</button>
    </>
  );
}
```

Focusing, scrolling into view, measuring size, and integrating a non-React widget all need the real DOM node, which is exactly what this gives you.

## Passing a ref to your own component

What if the input lives inside your own `TextField` component and the parent wants to focus it? The parent needs a way to hand a ref through `TextField` to the inner `<input>`.

Historically, **`forwardRef`** was the answer. It lets a component expose a child DOM node or imperative handle through a ref passed by its parent, because plain function components could not receive `ref` as a normal prop:

```jsx
// Before React 19
const TextField = forwardRef(function TextField(props, ref) {
  return <input ref={ref} {...props} />;
});
```

In React 19, function components receive **`ref` as a prop** directly, so the wrapper is no longer needed, and `forwardRef` is expected to be deprecated:

```jsx
// React 19
function TextField({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}
```

You will still meet `forwardRef` throughout existing code and libraries, and it continues to work.

## useImperativeHandle

Handing the parent the raw DOM node gives it full access: it can change styles, remove children, or rely on the exact element structure. **`useImperativeHandle`** customizes the value exposed through a ref, letting a component reveal a **small imperative API** instead of its raw DOM node.

```jsx
function VideoPlayer({ ref, src }) {
  const videoRef = useRef(null);

  useImperativeHandle(ref, () => ({
    play() {
      videoRef.current.play();
    },
    pause() {
      videoRef.current.pause();
    },
  }));

  return <video ref={videoRef} src={src} />;
}

function Lesson() {
  const playerRef = useRef(null);
  return (
    <>
      <VideoPlayer ref={playerRef} src="/intro.mp4" />
      <button onClick={() => playerRef.current.play()}>Play</button>
    </>
  );
}
```

`playerRef.current` in `Lesson` is not the `<video>` element; it is the object with `play` and `pause`. The parent can control playback but cannot touch anything else.

## Why imperative handles should be narrow

**Narrow** handles expose fewer operations, which keeps parent components from **depending on internal DOM structure** and preserves **component encapsulation**. If `VideoPlayer` later wraps the video in a custom-controls container or switches to a different player library, `Lesson` keeps working because it only ever used `play` and `pause`. Prefer props for anything that can be expressed declaratively, such as `isPlaying`; save imperative handles for actions like focusing, scrolling, or playing media.

## Common mistakes

- **Displaying a ref's value.** The screen will not update when it changes; use state.
- **Reading refs during render.** It makes rendering depend on untracked mutable data.
- **Exposing the whole DOM node by default.** Parents start depending on internals; expose a narrow handle instead.

## Key points

- A ref is a stable object whose `.current` field holds mutable data across renders without causing a render when it changes.
- `useRef` returns the same ref object for the lifetime of the component instance.
- Use a ref for values imperative code needs but rendering does not: DOM nodes, timer handles, mutable bookkeeping.
- UI-visible data should not live only in a ref, because changing a ref does not request a render.
- `forwardRef` historically let a component expose a child DOM node or imperative handle to its parent; React 19 lets function components take `ref` as a prop.
- `useImperativeHandle` customizes what a ref exposes, revealing a small imperative API instead of the raw DOM node.
- Narrow imperative handles keep parents independent of internal DOM structure and preserve encapsulation.

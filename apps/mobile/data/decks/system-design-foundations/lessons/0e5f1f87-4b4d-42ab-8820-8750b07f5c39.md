# Queues and asynchronous work

Not every piece of work has to finish while the user waits. Sending an email, resizing an image, or updating a search index can happen a moment later. A **queue** makes that possible.

## Decoupling with a queue

A queue stores work until consumers are ready to process it. Producers and consumers no longer need to run at the same speed or even at the same time. Bursts of traffic fill the queue, and consumers drain it at a steady pace.

The trade-off is that results arrive later, and the system must now handle **retries, duplicates, ordering, and visibility**, all problems a direct call would not have.

## Delivery guarantees

Messaging systems describe how often a message may be delivered:

- **At-most-once**: delivered zero or one time. There are no duplicates, but work can be lost.
- **At-least-once**: retried until delivery seems to succeed. Nothing is intentionally lost, but consumers can see duplicates.
- **Exactly-once** is the goal everyone wants, but it is hard to guarantee. After a failure, it can be unclear whether the work was done before the acknowledgment was lost.

In practice, systems use at-least-once delivery and make the _effect_ happen exactly once.

## Idempotency

An operation is **idempotent** when repeating it produces the same final result as doing it once. Setting a value is idempotent; adding to a balance is not.

APIs often accept an **idempotency key**, a stable identifier chosen by the client. The server stores the outcome under that key, and a retry returns the original result instead of charging a card twice:

```http
POST /payments
Idempotency-Key: 5f3c2a9e-order-1842
```

## When messages keep failing

A **dead-letter queue** holds messages that fail again and again. They stop blocking normal traffic and can be inspected, fixed, and replayed later.

## When consumers fall behind

An unbounded queue only hides overload until memory runs out. Healthy systems push back:

1. **Backpressure** makes producers slow down, wait, or get rejected when consumers cannot keep up.
2. **Load shedding** deliberately drops low-priority or excess work so the system can keep serving what matters most.

# Scaling up and out

When load grows, you have two basic moves: make one machine bigger, or add more machines. Most real systems use both, at different times.

## Vertical scaling

**Vertical scaling**, or scaling up, gives one machine more CPU, memory, or storage. It is attractive because nothing about the software has to change.

Its limits are just as clear:

- Hardware has a ceiling, and the largest machines are expensive.
- One big machine is one big **failure domain**. If it goes down, everything on it goes down.

## Horizontal scaling

**Horizontal scaling**, or scaling out, adds more machines or service instances and spreads the work across them. It can grow capacity much further and adds redundancy, but it brings new problems: requests must be distributed, and data must be shared or partitioned.

## Stateless services

Horizontal scaling is easiest when the application is **stateless**. Any instance can handle any request because durable state lives elsewhere, in a database, cache, or object store. Instances can then be added, removed, or replaced freely.

If an instance keeps user sessions in memory, losing that instance loses the sessions, and every request from that user must return to the same machine.

## Load balancers

A **load balancer** sits in front of the instances and distributes requests among them. It also runs **health checks**, so instances that cannot safely serve traffic are taken out of rotation.

Common strategies:

1. **Round robin** sends each new request to the next backend in turn. It is simple, but it ignores how expensive each request is.
2. **Least connections** prefers the backend with the fewest active connections. It copes better with long or uneven requests.
3. **Sticky sessions** keep sending a client to the same backend, often using a cookie. They make in-memory sessions work, but they weaken balancing and failover.

## Autoscaling

**Autoscaling** changes the number or size of instances in response to demand or a schedule. The hard part is choosing the signal. Scaling on CPU alone fails for services that run out of memory, connections, queue capacity, or downstream quota long before the CPU is busy.

# Caching

Many requests ask for the same data again and again. A **cache** keeps a temporary copy of expensive or frequently used results, so later reads skip the slow work of recomputing or refetching them.

## Measuring a cache

The key number is the **hit rate**: the fraction of reads served from the cache instead of the source. A higher hit rate means more backend work is avoided. A cache with a low hit rate adds memory and complexity without much benefit.

## Where the cache sits in the write path

Three common patterns decide who updates the cache:

- **Cache-aside.** The application checks the cache first. On a miss, it reads the source and stores the result. Writes go to the source, and the cached entry is invalidated or updated.
- **Write-through.** Writes pass through the cache, which updates the backing store before confirming. Cache and source stay in step, at the cost of slower writes.
- **Write-back.** Writes are confirmed once the cache has them and reach the backing store later. Writes are fast, but data can be lost if the cache fails before it flushes.

## Invalidation

**Cache invalidation** removes or expires cached data that may no longer match the source of truth. It is famously hard:

- Several copies can outlive an update.
- Invalidation messages can be delayed or lost.
- One change can affect many cached results.

That is why most caches also use a **time to live (TTL)**, so stale data eventually expires even when invalidation fails.

## Stampedes and jitter

A **cache stampede** happens when many requests miss the same hot key at once and all hit the backend together. Common defenses:

1. Let one request rebuild the value while others wait, which is called request coalescing.
2. Serve the slightly stale value while refreshing it in the background.
3. Add random **jitter** to TTLs, so many keys do not expire at the same moment.

## Caching at the edge

A **content delivery network (CDN)** serves cached content from locations close to users. It shortens network distance and takes load off your origin servers, which works especially well for images, scripts, and other static files.

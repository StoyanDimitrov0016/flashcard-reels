# Scale and performance metrics

Every system design question is really a question about a specific workload: how many users, how much data, how fast must a request return, how many writes per second, and what happens as all of that grows. Before picking a database, a queue, or a caching strategy, you need a vocabulary for describing load and speed precisely. This lesson builds that vocabulary, and the habit of reaching for it first.

## Start from the workload, not the technology

A recurring failure in system design is picking a technology first — "we'll use a message queue" or "we'll shard the database" — before knowing whether the workload needs it. The right architecture depends on concrete facts: the ratio of reads to writes, how large the data is and how fast it grows, what latency users will tolerate, what consistency the business actually requires, and which failures the system must survive.

Without those constraints, technology choices are mostly guesses. A system with a 1000:1 read/write ratio wants aggressive caching and read replicas; a write-heavy system wants a design that scales writes, where caching helps much less. A dashboard that can be five seconds stale needs a very different design from a payment ledger that cannot be. Gathering these numbers, even roughly, is the first step of any real design, not an afterthought once the interesting parts are decided.

## Scalability

**Scalability** is a system's ability to handle more load by adding resources, without an unacceptable loss of latency, throughput, or reliability. A scalable system does not have to be fast at every size; it has to keep working acceptably as load grows, ideally by adding resources rather than by a redesign.

There are two ways to add resources.

**Vertical scaling** gives one machine more CPU, memory, or storage. It is simple: no coordination, no partitioning, the same code runs unmodified. But it eventually hits hardware limits, upgrading a running machine to a bigger one usually means downtime, and one large machine is a large failure domain — losing it can mean losing everything it hosted.

**Horizontal scaling** adds more machines or service instances and distributes work across them. It has effectively no upper limit imposed by any single machine's hardware, and spreading work over many instances also spreads failure risk. The cost is coordination: work must be split across instances (partitioning), and those instances must be found and load-balanced (later lessons cover both). Most systems designed to handle real growth lean on horizontal scaling, often after some vertical scaling buys time.

## Throughput

**Throughput** is the amount of work a system completes per unit time — requests per second, messages per second, rows written per second. It answers "how much can this handle," and it is usually what capacity planning targets.

Throughput and resource usage are not always linear. A single server might handle 1,000 requests per second comfortably, but pushing toward 2,000 often costs more than double the resources, because contention (for locks, connections, cache space) grows with concurrency. This is one reason horizontal scaling has diminishing returns beyond a point, and why the next lessons spend real time on the mechanisms — caching, queues, partitioning — that keep throughput scaling with added resources.

## Latency

**Latency** is the elapsed time for one operation to complete, measured from the caller's perspective. Where throughput asks "how much," latency asks "how long for this one." The two interact: pushing throughput higher, by running a system closer to saturation, typically drives latency up, because requests start queuing behind each other.

## Why percentiles beat averages

Reporting only average latency hides exactly the users who are having the worst experience. Suppose 9,900 requests out of 10,000 complete in 50ms and 100 requests take 5 seconds because they hit a slow disk or a lock. The average is about 100ms — reasonable-looking — while 1% of users wait a hundred times longer than everyone else.

**Percentile latencies** report the value below which a given percentage of requests fall. The **p50** (median) is the typical request. The **p99** is the boundary for the slowest 1%, and **p999** for the slowest 0.1%. Percentiles show how slow requests are for the tail of users; an average can hide a small but important group of extremely slow requests, which is exactly the case above.

Tail percentiles matter operationally too: a page that makes 20 backend calls has close to an 18% chance that at least one of them hits its own p99 case, so what looks like a rare tail latency for one call becomes a common experience for a composed page (a theme picked up again in the lesson on fan-out).

## Common mistakes

- Treating "scalable" as a synonym for "fast." A system can be scalable and still slow at every size, or fast at one size and unable to scale at all. Scalability is about how behavior changes as resources and load grow, not about a single measurement.
- Reporting only averages for latency dashboards and SLOs. Two systems with the same average latency can have very different p99s, and it is the p99 that determines how many users have a bad experience.
- Reaching for a specific technology (a queue, a shard, a cache) before establishing the read/write ratio, data size, latency target, and consistency needs that would justify it.

## Key points

- Start a system design from workload and requirements — read/write ratio, data size, latency, consistency, growth, failure tolerance — before choosing technology.
- Scalability is the ability to handle more load by adding resources without unacceptable loss of latency, throughput, or reliability.
- Vertical scaling adds capacity to one machine; it is simple but hits hardware limits and creates a large failure domain.
- Horizontal scaling adds more machines and distributes work; it scales further but needs partitioning and coordination.
- Throughput is work completed per unit time; latency is the elapsed time of one operation from the caller's perspective.
- Percentile latencies (p50, p99, p999) reveal the tail of slow requests that an average latency can hide.

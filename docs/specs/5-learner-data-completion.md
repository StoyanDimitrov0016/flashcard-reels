# 5 - Learner data completion before the release

Status: ready for implementation. Persistence work only; the owner builds the UI separately.

## Problem and value

The next release starts the owner's real study data. Several agreed parts of the target data model
are still missing, and each one is cheaper now than after real data exists:

- deck learner data is deleted from several places, each listing its own tables;
- a deck's theme selection is deleted with the deck, while its learning data is kept;
- preferences live in Expo's key-value store, outside the database, backups, and checks;
- only bundled decks need to be remembered as dismissed, but every removed deck is;
- the app looks up audio files although the package already says which cards have audio;
- a recurrence is scheduled from an uncommitted rating, so changing Again to Good inside the
  editable window still brings the card back;
- several columns with a fixed set of values have no database `CHECK`;
- the backup holds learning progress only, not the learner's preferences and deck themes.

## Rules for the whole task

1. **One part at a time, in order.** Create the part's branch, finish the part, run its checks,
   and make one commit with the message given. Do not push and do not merge.
2. **Only the stated behavior changes.** Everything else the learner can do or see stays the same.
3. **Database changes.** The first part that changes `schema.ts` renames `DATABASE_NAME` to
   `flashcard-reels-v7.db` and adds it to `DATABASE_FILES` in
   `src/infrastructure/app-recovery.ts` and its test. Every part that changes `schema.ts`
   regenerates the single `0000` baseline as `docs/development.md` describes. No compatibility
   code for earlier development databases.
4. **Tests protect behavior.** Each part adds or updates tests for the behavior it changes,
   through the real SQLite graph where persistence is involved
   (`tests/support/sqlite-study-scenario.ts`). Do not weaken or delete a test to pass a part.
5. **Stop and report** when the code does not match this spec, instead of guessing.
6. Follow `AGENTS.md` and `docs/codebase-preferences.md`. Every new table has its own `id`
   generated by the injected `IdGenerator`; a reference to another table's row is
   `<resource>_id`, `UNIQUE` when one-to-one. Commands run from `apps/mobile` unless stated.
7. **Every part ends with:** `npm run check` and `npm test` pass; parts that change the schema
   also pass `npm run db:check`.

## Part 1: one owner for deck learner data

Deck learner data is deleted or archived in several transactions, each with its own table list:
`sqlite-deck-removal.transaction.ts`, `sqlite-learning-progress-reset-transaction.ts`,
`sqlite-saved-progress-deletion.transaction.ts`, and `sqlite-progress-backup-restore.transaction.ts`.

- Create one module in the `decks` or `flashcard-progress` infrastructure layer, whichever owns
  `deck_progress` today, that knows every learner-data table of a deck: today
  `flashcard_review_events`, `flashcard_progress`, `flashcard_memory_states`, and `deck_progress`.
  It offers the operations the four transactions need, for example "delete a deck's learner data"
  and "delete all learner data", running inside the caller's transaction.
- The four transactions use it instead of listing tables themselves. Card reset keeps deleting
  only that card's rows.
- No behavior change. Existing archive, reset, Start fresh, delete archive, and restore tests
  pass unchanged.
- Later parts add their tables to this module only.

Commit: `refactor(mobile): give deck learner data one owner`.

## Part 2: dismiss only bundled decks

`sqlite-deck-removal.transaction.ts` writes every removed deck to `dismissed_bundled_decks`, but
only `bundled-deck-installer.ts` reads it.

- Write a row only when the removed deck is a bundled deck. Use the bundled deck registry the
  installer already uses to know which decks are bundled.
- Installing a deck still clears its row.
- Tests: removing the bundled demo deck keeps it from coming back at the next startup; removing
  an imported deck writes no row.

Commit: `fix(mobile): remember only dismissed bundled decks`.

## Part 3: deck theme selections are learner data

- `deck_theme_selections.deck_id` loses its foreign key to `decks`, keeps `UNIQUE`.
- Removing a deck keeps its theme selection. Remove the explicit delete from the removal
  transaction.
- The learner-data owner (Part 1) includes theme selections: Start fresh and deleting an archive
  delete them; deck reset, card reset, and resetting all learning progress keep them, because
  they are not learning progress.
- Reading a stored theme the app does not define returns the default theme instead of throwing.
- Tests: remove and reinstall a deck, and its theme returns; Start fresh removes it; an unknown
  stored theme reads as the default.

Commit: `feat(mobile): keep deck theme selections as learner data`.

## Part 4: preferences in SQLite

Preferences are stored as JSON in Expo's key-value store
(`expo-sqlite-preferences.repository.ts`, key `flashcard-reels.preferences.v2`).

- Add a one-row table `learner_preferences`: `id` (primary key), `color_mode` (`light`, `dark`,
  `device`), `study_island_position` (`left`, `bottom`, `right`), `rating_direction` (`forward`,
  `reverse`), `audio_enabled`, `audio_side` (`primary`, `opposite`), `reading_enabled`,
  `reading_side` (`primary`, `opposite`), `haptics_enabled`, and `updated_at`. Booleans are
  integer booleans with `CHECK (column IN (0, 1))`. Every other fixed-value column has a
  `CHECK` listing its values.
- A missing row reads as `defaultAppPreferences`; saving writes or updates the one row.
- Replace the key-value repository with a SQLite repository behind the same
  `PreferencesRepository` interface. Remove every use of `expo-sqlite/kv-store`, and remove
  `ExpoSQLiteStorage` from the app data reset list.
- Preferences now load after the database opens. If any screen reads preferences before the
  database is ready, stop and report instead of adding a second store.
- Resetting learning progress does not touch preferences. A full app data reset removes them with
  the database.

Commit: `feat(mobile): store learner preferences in SQLite`.

## Part 5: `has_audio`

- Add `flashcards.has_audio` (integer boolean, required, `CHECK (has_audio IN (0, 1))`), written by the deck installer from the
  package card's `audio` flag.
- A card offers audio only when `has_audio` is true. Keep resolving the file path as today for
  cards that have audio; stop deciding by file lookup alone.
- Tests: a card with `audio: false` offers no audio; a card with `audio: true` resolves its file.

Commit: `feat(mobile): store which flashcards have audio`.

## Part 6: `CHECK` constraints

Add a `CHECK` for every column with a fixed set of values that lacks one:

- **Text columns with listed values:** `flashcard_memory_states.state`,
  `flashcard_review_events.rating`, `deck_progress.status`, and `study_sessions.scope` (its
  existing check ties scope to `deck_id` but should also limit the values).
- **Integer booleans:** every integer boolean column gets `CHECK (column IN (0, 1))`. Today
  that is `flashcards.active`; `has_audio` (Part 5) and the `learner_preferences` booleans
  (Part 4) already have theirs. Search `schema.ts` for `mode: "boolean"` to find every one.

Name each check after its table and column, as the existing checks are named.

Test: inserting a disallowed value into each of these columns fails, including `2` into
`flashcards.active`.

Commit: `feat(mobile): check fixed values in the database`.

## Part 7: recurrences at commit

Today `rateAttempt` in `study.service.impl.ts` schedules a recurrence from an uncommitted rating.

- Schedule the recurrence when the attempt commits, from its committed rating: Again and Hard
  schedule one as today; Good and Easy schedule none. Rating changes inside the editable window
  create or remove nothing.
- The target reel is computed as today from the source reel, and is never at or before the
  session's furthest reel at commit time.
- Tests: Again committed schedules a recurrence; Again changed to Good inside the window, then
  committed, schedules none; a recurrence target is always after the furthest reel.

Commit: `fix(mobile): schedule recurrences from committed ratings`.

## Part 8: learner data backup

The backup holds all learner data, not only learning progress.

- Rename the document format from `flashcard-reels-progress` to `flashcard-reels-learner-data`.
  It stays `version: 1` and changes directly; earlier development backups are rejected.
- Add `learnerPreferences` (one object, the Part 4 fields in camelCase) and
  `deckThemeSelections` (rows of `deckId` and `theme`). Rows carry no table IDs; restore
  generates them.
- Export reads them in the same transaction as the progress tables. Restore replaces them with
  the rest, through the learner-data owner and the preferences repository's table.
- Validation: every deck theme selection's `deckId` is unique; preferences values match the
  table's allowed values. Keep every existing rule.
- Update the backup fixture in `.maestro/fixtures` and the integration fixtures.
- Tests: a backup round trip restores preferences and deck themes; a document without
  `learnerPreferences` is rejected with progress unchanged.

Commit: `feat(mobile): back up preferences and deck themes with learning progress`.

## Part 9: publish check for section links

`deck-package-publication.ts` compares each card's `lessonSectionId` with the published card, but
no test covers it.

- Add integration tests to `deck-package-publication.integration.test.ts`: a card whose
  `lessonSectionId` changes is reported as changed; an unchanged card is not.
- No production change unless a test shows the comparison is wrong; then stop and report.

Commit: `test(mobile): cover section link changes in the publish check`.
